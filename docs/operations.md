# 運用ガイド（利用者向け）

現在形の設計書（[design/](design/)）が「どう作るか」を定めるのに対し、本書は**導入・運用する人向け**の手順・注意をまとめる。まだ認証（管理 UI / 閲覧 UI）の運用に絞った初版であり、他の運用トピック（本番昇格の手順、逆引き参照ゾーンの整備、TLS 受信の証明書運用など）は各機能の実装に合わせて追記していく。

> **申し送りの受け皿**: 本書は複数の ADR が「利用者向けドキュメント（operations.md 系）へ申し送る」と定めた事項の受け皿である。認証に関する申し送りは [ADR-0010](adr/0010-admin-ui-authentication.md) 委任事項 11・[ADR-0013](adr/0013-admin-winauth-session.md) 委任事項 8。

## 1. 認証は既定でオフ（信頼ネットワーク前提 + opt-in 強化）

Yagura は既定で**認証なし**（[ADR-0004](adr/0004-security-model.md)・[ADR-0001](adr/0001-project-founding.md) の「信頼ネットワーク前提」）で動く。管理 UI（既定ポート 8515）は loopback 束縛のみ、閲覧 UI（既定ポート 8514）は LAN 公開。**機微なログを扱う環境で「LAN 内の誰でも読める」を締めたい場合にのみ**、認証を opt-in で有効化する。有効化しない限り本書の内容は関係しない。

## 2. 閲覧 UI 認証（8514）を有効化する

閲覧 UI 認証は **Windows 統合認証 + AD グループ**を主経路とする（[ADR-0010](adr/0010-admin-ui-authentication.md) 決定 7）。設定ファイル `yagura.json`（データルート直下。既定 `%ProgramData%\Yagura`）に次を追記して**サービスを再起動**する（設定の反映はサービス再起動——[configuration.md](design/configuration.md) §3）。

```json
{
  "Viewer": {
    "Authentication": {
      "Windows": {
        "Enabled": "true",
        "ViewerGroups": [ "CONTOSO\\LogViewers" ],
        "AdminGroups": [ "CONTOSO\\LogAdmins" ]
      }
    }
  }
}
```

- **グループの指定は名前（`DOMAIN\グループ名`）でも SID（`S-1-...`）でもよい**。名前は起動時に SID へ解決してキャッシュする。存在しない名前・タイプミス・DC 到達不能で解決できないグループは**起動を止めず警告してスキップ**する（そのグループの所属者は認可されないだけ——安全側）。イベントログに `sec9-group-unresolved` の警告が出たらグループ名を見直す。
  - **名前指定は起動時に DC へ問い合わせる**（`S-1-...` の SID 指定は問い合わせを発しない）。DC が一時的に到達不能なときにサービスを再起動すると、名前解決が最大 5 秒で打ち切られてそのグループはスキップされる（**syslog 受信の開始をブロックしないため**——受信は止めない）。この間に認可対象のグループが欠けると閲覧できない利用者が出るので、**DC 障害に強くしたい場合はグループを SID で指定する**とよい（SID なら DC 非依存で即解決できる）。
- **`AdminGroups` を指定すると平文で管理等価 Cookie が流れる点に注意**（機微環境向け）。閲覧リスナは既定で平文 HTTP のため、`AdminGroups` 所属者が発行される「管理」役割の Cookie は Secure 属性なしで LAN を流れ、host スコープゆえ管理リスナ（8515/8516）へも届く。機微環境では管理役割の付与は管理リスナ側（loopback またはリモート HTTPS）で行い、閲覧リスナには `ViewerGroups`（閲覧のみ）だけを指定する運用を検討する。起動時にイベントログへ `viewer-admingroups-plaintext` 注意が出る。
- **役割**: `ViewerGroups` の所属者は「閲覧」（ログの閲覧・検索・CSV エクスポート・自身の状態表示）。`AdminGroups` の所属者は「管理」で、**管理は閲覧を含む**（管理者は閲覧 UI も読める）。ネストグループ（グループの入れ子）は OS が展開したトークンで自動的に効くため、追加設定は要らない。
- **8514（閲覧リスナ）には管理機能の導線を出さない**。`AdminGroups` の利用者が 8514 にログインしても、設定変更などの管理画面は表示されない（管理操作は管理リスナ 8515 で行う）。
- **アプリ独自 ID/パスワードでも閲覧ログインできる**（`Admin:Authentication:App:Enabled = true` のとき、閲覧ログイン画面にも ID/パスワード欄が出る）。アプリ独自アカウントは常に「管理」役割のため、閲覧 UI へも到達できる。
- **自己ロックアウト注意**: `Viewer:...:Windows:Enabled = true` なのに `ViewerGroups`・`AdminGroups` をどちらも指定しない（または全て解決失敗）と、**Windows 経由で閲覧できる人がいなくなる**。起動時にイベントログへ `viewer-auth-no-groups` 警告が出る。閲覧が止まっても syslog 受信は止まらない——管理者は 8515（管理リスナ）や設定ファイルの手編集で復旧できる。

Kerberos のみを許可し NTLM を拒否したい場合は `Viewer:Authentication:Windows:KerberosOnly = "true"`（管理側の `Admin:...:KerberosOnly` とは独立——ポートごとに選べる）。

**有効化したら 1 人ログインできることを必ず確認する**。グループ名のタイプミスや所属設定漏れは、既定ではイベントログ（`sec9-group-unresolved` / `viewer-auth-no-groups`）にしか出ない。有効化・再起動後に、閲覧を許可したいユーザーで実際に 8514 へブラウザアクセスしてサインインできるか確かめる（誰もサインインできない状態に気づかず放置しないため）。

## 3. 管理 UI 認証と AD グループ（SEC-9）

管理 UI 認証（[ADR-0010](adr/0010-admin-ui-authentication.md) Phase 1）の「管理者」は既定で `BUILTIN\Administrators`（ローカル Administrators）のみ。**AD グループを管理者にマップしたい場合**は、既定判定に**加えて** `Admin:Authentication:Windows:AdminGroups` を指定する（ローカル Administrators 判定は残る）。

```json
{ "Admin": { "Authentication": { "Windows": { "Enabled": "true", "AdminGroups": [ "CONTOSO\\LogAdmins" ] } } } }
```

- ドメインコントローラー上では、ネットワークログオンのトークンに `BUILTIN\Administrators`（S-1-5-32-544）が載らないことがある。この場合、ローカル Administrators だけに頼ると DC 上の管理者がログインできない——**ドメイングループを `AdminGroups` に指定すれば解決する**（ドメイングループの SID はネットワークトークンに載る）。

## 4. セッションが切れたときの挙動

認証成立後は方式に依らない**単一のセッション Cookie**（[ADR-0013](adr/0013-admin-winauth-session.md)）で認証状態を持つ。**Cookie の寿命は認証方式で非対称**である:

| 方式 | 絶対寿命 | sliding（操作で延長） | 理由 |
|---|---|---|---|
| Windows 統合認証 | **1 時間（仮値）** | なし | Windows 権限（グループ所属）の剥奪は再ログインまで反映できないため、寿命を短くして陳腐化を有界化する |
| アプリ独自 ID/パスワード | 8 時間 | あり | 将来のログインは無効化で即座に絞れるため、既発行セッションは従来どおり |

- **切れたら再ログイン画面へ誘導される**。掲示用の大型モニタで閲覧ダッシュボードを開きっぱなしにする運用（NOC の壁掛けモニタ等）では、Windows 由来セッションが 1 時間で切れて再ログインを求める点に注意する。
  - **24 時間無人で映し続ける掲示・キオスクには、そもそも閲覧認証を課さないネットワーク区分での運用を第一に推奨する**。認証を有効化した閲覧リスナは、方式に依らずいずれセッションが切れる（Windows 1 時間、アプリ独自も無操作なら絶対寿命 8 時間で切れる。sliding は操作前提のため無人では延びない）。無人掲示に「切れない認証セッション」は用意しない設計であり、認証と 24 時間無人掲示は本質的に両立しにくい。掲示用の区分は閲覧認証オフ（既定）で公開し、機微な検索・エクスポートを行う端末側だけ認証オンの閲覧リスナ（別インスタンス/別区分）を使う、といった分離が現実的である。
- **Windows 権限を剥奪しても、反映は最大 Cookie 寿命（Windows は最大 1 時間）だけ遅れる**。即時に締めたい場合は下記の緊急全失効を使う。

## 5. 緊急全失効（退職者・漏洩疑い時）

発行済みの**全**認証セッション（管理・閲覧の両方）を即時無効化できる（[ADR-0013](adr/0013-admin-winauth-session.md) 決定 2。監査イベント ID 2013）。管理 UI から実行する（セッション世代番号をバンプする——DC に依存せずローカルで効く）。

- **all-or-nothing**: 特定の 1 人だけを狙う失効はできない。正規利用者を含む全員が次の操作で無効化され、再ログインが必要になる。退職者対応・資格情報漏洩疑いなど「全部落として入れ直す」場面のための機構である。
- **ログイン経路は殺さない**: 全失効後も、アプリ認証・Windows 再ログイン・設定ファイル手編集は生きている（ロックアウトしない）。

## 6. ブレークグラス（非常口）の推奨

- **リモート管理を Windows 統合認証で運用する場合も、アプリ独自 ID/パスワードの管理者アカウントを最低 1 つ持つことを強く推奨する**（[ADR-0010](adr/0010-admin-ui-authentication.md) 決定 3）。AD/DC 障害時に RDP 経路も同じ AD に依存していると、Windows 認証単独では AD 障害 1 点で管理面全体を失う。
- **loopback 認証 opt-in（`Admin:Authentication:RequireForLoopback = true`）を有効化した環境の最終復旧**は「物理到達（RDP/コンソール）→ 設定ファイル手編集で opt-in を解除 → サービス再起動」。ただし現状、**設定反映にはサービス再起動が必要で、その間 syslog 受信が止まる**（受信断）。この代償を承知の上で opt-in を有効化する。
- **手編集の実行可能者はローカル Administrators に限られる**（設定ファイルの書き込み ACL）。AD グループ経由で「管理」役割のみを持つ（ローカル Administrators 非所属の）利用者は、この手編集復旧を自分では行えない——別途ローカル Administrator への依頼が要る。
- **DC 障害中の相互作用**: DC 障害中は既存セッションは寿命まで生存するが、寿命が切れた後の Windows 再ログインはグループ解決ができず失敗する。実質のレジリエンス窓が Cookie 寿命に縮む——ブレークグラス（アプリ管理者アカウント／手編集）で救う。

## 7. NTLM 縮退・非ドメイン機

- Windows 統合認証は Kerberos を優先し、成立しない場合（ホスト名の SPN 未登録・IP アドレスでのアクセス等）は自動的に **NTLM へ縮退**する。非ドメイン参加機（ワークグループ）でもローカル Windows アカウントに対する NTLM 認証がそのまま使える——ドメイン必須ではない。
- NTLM 縮退時は、ブラウザに**資格情報の入力ダイアログ**が出る（Kerberos SSO のような透過ログインにはならない）。NTLM の既知の弱点（リレー攻撃・pass-the-hash・相互認証の欠如）を受容できない環境では、`KerberosOnly = "true"` で NTLM を拒否する（Kerberos SSO が成立する SPN 構成が前提）。

## 8. 監査（誰がアクセスしたか）

認証を経由した操作は、監査記録（`audit.jsonl` + Windows イベントログ、ソース `Yagura`）の「誰が」欄に方式（`windows`/`app`）と利用者名が残る（[security.md](design/security.md) §4）。認証まわりの主なイベント ID:

| ID | レベル | 意味 |
|---|---|---|
| 2008 | 情報 | 管理 UI へサインイン成功 |
| 2014 | 情報 | 閲覧 UI へサインイン成功（`role=viewer`/`role=admin`） |
| 2013 | 情報 | 認証セッションの緊急全失効 |
| 3003 | 警告 | Windows 統合認証のハンドシェイク失敗 |
| 3008 | 警告 | 認証成功後に管理者権限がなく拒否 |
| 3009 | 警告 | 閲覧で認証成功後に閲覧/管理グループ非所属で拒否 |

「ソース Yagura の警告以上を通知」で最低限の監視が組める（拒否・セキュリティ事象は警告レベル）。

## 9. 閲覧 UI の HTTPS（8514）を有効化する（CF-D2）

閲覧 UI（既定 `http://<サーバ名>:8514/`）を HTTPS にする opt-in（[ADR-0022](adr/0022-viewer-https.md)）。有効化すると**同じポートのまま** `https://` に切り替わり、平文の面は残らない。**ファイアウォール規則には一切触らなくてよい**（ポートが変わらないため。「HTTPS にしたら FW も何かやるはず」と思って余計な穴を開けないこと）。

証明書は利用者の持ち込みが基本で、Yagura は生成しない（[configuration.md](design/configuration.md) §6）。環境別の入手指針:

| 環境 | 推奨経路 |
|---|---|
| **AD はあるが AD CS なし**（最多想定） | **自己署名 + グループポリシーでルート配布**（本節の主経路） |
| AD CS 導入済み | AD CS のテンプレートで発行するのが正道（本節の手順 1〜2 は不要。手順 3 以降は同じ）。**閲覧 HTTPS のためだけに AD CS を新設するのは勧めない**（誤設定時の影響が大きく、割に合わない） |
| 公開 DNS ドメイン + 公的 CA（Let's Encrypt 等） | **現時点では推奨しない**。90 日等の短い有効期間は、更新のたびに「管理画面で再選択 + サービス再起動」が必要な現在の方式（拇印固定参照）と相性が悪い。また公的 CA の証明書には短いサーバ名（`yagura01` など）を入れられないため、短名 URL では警告が出る |
| 非 AD（ワークグループ） | ルート証明書の配布が**端末 1 台ずつの手作業**になり、コストが跳ね上がる。無理に HTTPS 化せず、既定の平文 + 信頼ネットワーク前提の運用を維持するのも正直な選択である |

### 9.1 主経路: 自己署名 + GPO ルート配布（所要: 半日を見込む）

**30 分では終わらない。** 特に手順 2 の GPO 反映は既定で最長 90 分 + α かかり、電源オフの端末には届かない——「手順どおりやったのに一部の端末でまだ警告が出る」期間が**あるのが正常**である。設定を崩して原因を探し始めないこと。

**手順 1 — 証明書の作成**（Yagura サーバ上・管理者 PowerShell）。SAN にはサーバの **FQDN と短い名前（NetBIOS 名）の両方**を入れる（閲覧者がどちらの名前でアクセスしても警告なしにするため）:

```powershell
New-SelfSignedCertificate -DnsName "yagura01.example.local", "yagura01" `
  -CertStoreLocation "Cert:\LocalMachine\My" `
  -KeyAlgorithm RSA -KeyLength 2048 `
  -NotAfter (Get-Date).AddYears(5) `
  -TextExtension @("2.5.29.37={text}1.3.6.1.5.5.7.3.1") `
  -FriendlyName "Yagura viewer HTTPS"
```

このコマンドを**アレンジしないこと**。`-TextExtension` は用途をサーバー認証（serverAuth）に限定する指定で、これを外す・広げると、万一秘密鍵が漏えいした場合の悪用範囲が「閲覧 UI の偽装」を超えて広がる。有効期間 5 年は「更新の手間を減らす」ための選定である（期限の 30 日前から Yagura が警告する——§9.4）。

**手順 2 — ルートとしての配布**（GPO）: 作成した証明書を公開鍵のみ（.cer。秘密鍵は含めない）でエクスポートし、グループポリシーの「コンピューターの構成 > ポリシー > Windows の設定 > セキュリティの設定 > 公開キーのポリシー > **信頼されたルート証明機関**」へ取り込み、閲覧端末が属する OU へリンクする。**配布とセットで、撤去の予定も残すこと**（§9.3）。

**手順 3 — 秘密鍵の読み取り権限**: 管理者が作成した証明書の秘密鍵は、サービスアカウント（`NT SERVICE\Yagura`）からは読めないことがある。Yagura は起動時に自動付与を試みる（成功すると監査 2028 が残る）が、**成功に依存せず確認する**: `certlm.msc` → 個人 > 証明書 → 対象を右クリック →「すべてのタスク」→「秘密キーの管理」→ `NT SERVICE\Yagura` を追加し「読み取り」を許可（アカウント名は「場所」をローカルコンピュータにして手入力する）。

**手順 4 — 選択と有効化**: 管理画面（`http://localhost:8515/admin`）→「閲覧 UI の HTTPS 設定」→ 一覧から証明書を選択（**選択可** バッジが付いていること——付いていなければ手順 3 を再確認して「一覧を更新」）→ SAN 検査が緑であることを確認 → 有効化して適用 → **サービス再起動**で反映（再起動中は syslog 受信も止まる——管理 HTTPS・TLS 受信の証明書変更があればまとめて保存してから 1 回で再起動する）。

**再起動の前に周知する。** 反映の瞬間から `http://` の旧 URL（ブックマーク・ショートカット・掲示用端末）は開けなくなる。周知文の例:

> ○月○日 ○時ごろから、ログ閲覧の URL が `https://yagura01.example.local:8514/` に変わります。
> 現在の `http://` のブックマークは開けなくなりますので、お手数ですが更新をお願いします。
> 画面に証明書の警告が出る場合は情報システム担当までご連絡ください（設定配布が未反映の可能性があります）。

スタートメニュー・デスクトップの「Yagura」ショートカット（インストーラ作成分）は `http://` のまま残るため、手動で新 URL に更新する（自動では書き換わらない）。

### 9.2 検証

1. ルート配布済みの端末から `https://<FQDN>:8514/` と `https://<短名>:8514/` を開き、**鍵アイコンが警告なし**で表示されること（GPO 未反映の端末では警告が出る——`gpupdate /force` + 再起動で前倒しできる）
2. `http://` でアクセスすると開けないこと（平文の面が残っていないことの確認）
3. **IP アドレス（`https://192.168.x.x:8514/`）では警告が出るのが正常**。閲覧者には名前の URL を周知する

### 9.3 撤去・棚卸し（配布の対）

- **証明書を更新・廃止したら、旧証明書を GPO から外す**。この経路の証明書には失効の仕組み（CRL/OCSP）がなく、**GPO からの削除が事実上唯一の失効手段**である
- Yagura を廃止する際も、配布したルート証明書を GPO から削除する。「配布したルートの一覧と配布先 OU」を情シスの台帳に残しておくと、数年後の棚卸しで迷わない

### 9.4 更新（期限が近づいたら）

期限の 30 日前から、イベントログ（1036）とメール通知（設定済みの場合）で警告が出る。**更新は「配布し切ってから差し替える」順で行う**:

1. 手順 1 で新しい証明書を作成し、手順 2 で**新旧両方が信頼された状態**にする（GPO 反映のリードタイムを見込む）
2. 反映が行き渡ったら、管理画面で新しい証明書を再選択し、サービスを再起動する
3. 旧証明書を GPO と証明書ストアから撤去する（§9.3）

メール通知が無効の環境では、この事前警告は**イベントログにしか届かない**。期限切れになると LAN からの閲覧が止まる（受信は継続する）ため、メール通知（§運用ガイド該当節）の設定を強く推奨する。

### 9.5 証明書事故のとき（期限切れ・削除・秘密鍵の権限喪失）

- 閲覧は止まるが、**平文には落ちない**（意図的な設計——黙って暗号化が外れることを許さない）。syslog 受信・保存・管理画面は影響を受けない
- 復旧は**サーバ上**で行う: RDP でサーバへ入り、管理画面（`http://localhost:8515/admin`）→「閲覧 UI の HTTPS 設定」から証明書を差し替える（または HTTPS を無効化する）→ サービス再起動。管理画面のトップに停止理由が常時表示される
- リモート管理（8516）を使っている環境でも、証明書事故時の復旧はサーバ上の操作が前提である

### 9.6 外形監視をしている場合

有効化の前後で、監視の「正常」の定義が変わる:

| 状態 | 8514 の見え方 |
|---|---|
| 平文運用（従来） | TCP 接続可・HTTP 応答あり |
| HTTPS 有効・正常 | TCP 接続可・**TLS ハンドシェイク成立**・HTTPS 応答あり |
| 証明書事故（稼働中の期限切れ等） | **TCP 接続可だが TLS ハンドシェイクが失敗**——TCP ポート監視だけでは「正常」と誤判定する |
| 起動時から証明書が使えない（縮小継続） | ポート自体が閉（接続拒否） |

ポート監視は `https://` での応答確認（TLS ハンドシェイクを含む）へ更新すること。

関連イベント ID: 1035（起動時に証明書が使えず閲覧リスナを開かない）・1036（期限接近）・1037（稼働中の使用不能）・1038（閲覧認証の管理グループあり × 平文 × LAN の注意喚起）・監査 2028（秘密鍵権限の自動付与）・2029（設定変更）。

## 10. データベースに接続できないとき（縮退運転）

保存先（SQL Server）に接続できない間も、**Yagura は起動し、syslog の受信を続ける**（[ADR-0023](adr/0023-upgrade-availability.md) 決定 1）。何が止まり、何が動いているかを分けて把握すること。

| | 状態 |
|---|---|
| syslog の受信 | **継続**。DB へ書けない分はディスクのスプールへ退避される |
| 閲覧 | 見えるのは**障害が起きる前に DB へ書けた分まで**。障害中に受信した分はスプールにあり、閲覧には現れない。検索を実行すると「保存先に接続できていない」旨の警告が出る（**「該当なし」とは区別される**） |
| 状態画面（`/status`） | **開ける。** カウンタと一時保管（スプール）の状態は保存先に依存しないため表示される。蓄積件数・保存先の使用量・履歴だけが「取得できません」になる |
| ID/パスワードでのサインイン | **一時的に不可**（管理者アカウントの台帳が読めないため） |
| Windows 統合認証でのサインイン | 影響なし |

**障害中に最初に見る場所は状態画面である**——退避が起きているか（`yagura.ingestion.spool.evacuated`）、損失系カウンタが動いていないか（`spool.discarded` / `persistence.failed` 等）をここで確認する。

**復旧に操作は要らない。** DB が復旧すると自動的に元へ戻り、スプールの内容も順次 DB へ流し込まれる（イベントログに 1040 が記録される）。

### 10.1 「再起動できるようになった」は「直った」ではない

**無損失でいられる時間の上限はスプールの容量**である。DB 障害が長引いてスプールが一杯になると、そこから先のログは失われる。復旧作業では**残りどれくらいスプールが保つか**を見ながら動くこと（管理画面の状態表示・ダッシュボードでスプール使用率を確認できる）。

この上限は DB 障害についての話であり、アップグレード中の受信断（サービス停止から再起動までの間）には当てはまらない——リスナが閉じている間の UDP はそもそも受け取れず、スプールでは救えない。

### 10.2 管理画面に入れなくなる構成

`Admin:Authentication:RequireForLoopback` が有効で、かつ**アプリ独自認証（ID/パスワード）しか有効にしていない**構成では、DB が復旧するまで管理画面へ入る手段が実質なくなる。この構成の復旧経路は**設定ファイルの手編集**である（[ADR-0010](adr/0010-admin-ui-authentication.md) 決定 1 が「認証手段が全滅した場合の最終復旧経路」として設計している）。

> **緩めるのは `RequireForLoopback` 側**。`yagura.json` の `Admin:Authentication:RequireForLoopback` を `false` にしてサービスを再起動する。
>
> **アプリ独自認証を無効化する側を編集してはいけない。** `RequireForLoopback` が有効なまま認証方式がゼロになり、**fail-closed で起動そのものが拒否される**（イベント ID 1011）。DB 障害と同じ「受信が止まる」状態を別経路で作ってしまう。

復旧後は緩めた設定を元に戻すこと。回復通知（1040）にもその案内が入っている。

**保存先の到達不能を理由に、Yagura が認証を自動的に緩めることはない**（意図的な設計）。それを認めると「攻撃者が DB を落とせば認証が外れる」という、誘発可能な認証バイパスになるためである。

### 10.3 関連イベント ID

1039（保存先のスキーマ初期化に失敗・縮退運転中。メール通知の対象）・1040（復旧して自動回復）・監査 3015（保存先到達不能によるログイン拒否）。

## 11. アップグレードに失敗した / 製品が消えた・起動しないとき

MSI のアップグレードが `1920`（サービスを開始できませんでした）や `1603`（インストール中に致命的なエラー）で失敗した場合、および再インストールしても `Access to the path ... is denied` で起動しない場合の復旧手順。

> **0.6.0 以降では、アップグレードの失敗で製品が消えることはない**（[ADR-0023](adr/0023-upgrade-availability.md) 決定 2）。旧製品の削除がインストールのトランザクション内に入ったため、失敗時は全体がロールバックされて**旧版がそのまま残り、動き続ける**。本節はそれ以前の版で被害に遭った場合、および何らかの理由で状態が壊れた場合の手当てである。

### 11.1 まず確認する

1. 「プログラムと機能」に Yagura が残っているか
2. サービス `Yagura` が存在し、動いているか（`Get-Service Yagura`）
3. Windows イベントログ（アプリケーション）に Yagura のエラーが出ていないか

サービスが動いていれば**受信は継続している**。慌てて再インストールする前に、まずここを見ること。

### 11.2 製品が 1 つも残っていない場合

`%ProgramData%\Yagura` 配下の設定・データベース・スプールは**アンインストールでは消えない**。新しい MSI をそのままインストールすれば、既存のデータを引き継いで復帰する。

### 11.3 再インストールしても `Access to the path ... is denied` で起動しない場合

アップグレードが途中で失敗した際に、データルート配下のファイルのアクセス権が壊れている可能性がある（[Issue #467](https://github.com/Yanai-Taketo/Yagura/issues/467) 現象 B）。0.6.0 以降ではインストーラがこれを自動で戻す・是正するが、それ以前の版で壊れた状態はそのまま残る。

管理者権限の PowerShell で、次を**上から順にそのまま**実行する:

```powershell
$Root = "$env:ProgramData\Yagura"
$Fwd  = Join-Path $Root 'forwarder'
$Svc  = 'NT SERVICE\Yagura'   # gMSA 運用中なら 'DOMAIN\gmsa名$' に置き換える

icacls "$Root" /reset /T /C
icacls "$Root" /inheritancelevel:r /grant "*S-1-5-18:(OI)(CI)(F)" "*S-1-5-32-544:(OI)(CI)(F)" "${Svc}:(OI)(CI)(M)"
icacls "$Fwd"  /inheritancelevel:r /grant "*S-1-5-18:(OI)(CI)(F)" "*S-1-5-32-544:(OI)(CI)(F)" "${Svc}:(OI)(CI)(R)"
```

そのうえで MSI を再インストールする。

> **`icacls /reset` は「そのフォルダに個別に付けたアクセス権をすべて捨てる」操作である。** 上のブロックが 3 行で 1 セットなのはこのためで、**2 行目・3 行目まで実行しないと権限が正しく戻らない**。
>
> とりわけ 3 行目を飛ばすと、フォワーダ配布フォルダ（`forwarder`）がデータルートの権限をそのまま引き継ぎ、**サービスアカウントに書き込み権限が付いたままになる**。ここは「管理者だけが書ける」設計であり（[ADR-0008](adr/0008-forwarder-kit-generation.md) 設計条件 9）、`/reset` はその区別を壊す。
>
> 監査目的で独自の ACE を追加している場合、それも `/reset` で消える。実行前に `icacls "$env:ProgramData\Yagura" /save acl-backup.txt /T` で控えておくとよい。

### 11.4 それでも起動しない場合

DB に接続できないことが原因かもしれない。その場合は §10 を参照すること——0.6.0 以降は DB に接続できなくても起動して受信を続けるため、「起動しない」なら別の原因である。イベントログの Yagura のエラーを確認し、[Issues](https://github.com/Yanai-Taketo/Yagura/issues) へ報告してほしい。

## 12. 対応環境を維持する（時間が経ってから効く話）

導入時点の要件は [README のシステム要件](../README.md#システム要件)が正。本節は**運用を続けるうちに効いてくる**side を扱う（対応環境の定義と根拠は [ADR-0024](adr/0024-supported-environments.md)）。

### 12.1 閉域環境でのブラウザ更新

Yagura はインターネットに出さない設置を推奨している（§1・README「セキュリティの前提」）。一方で管理画面は Blazor 製で、**対応ブラウザは「最新版」**である（Microsoft・Mozilla・Apple・Google のいずれも最新版のみをサポート対象とするため）。この 2 つは同時に成り立たせる必要がある。

- **サーバ機のブラウザが必要になるのは初回セットアップと設定変更のときだけ**である。日々のログ閲覧は手元の端末から行える（8514）。つまり**更新が必要なのはサーバ機のブラウザ 1 つで、頻度も低い**
- 閉域のサーバ機では、ブラウザのオフラインインストーラ（Edge は「Microsoft Edge for Business」のオフライン版、Chrome は MSI 版など）を持ち込んで更新する。組織で WSUS / 構成管理を運用しているならその配布対象に含める
- **管理リモート HTTPS（8516）を opt-in で有効にしている場合は、手元の端末のブラウザで管理できる**ため、サーバ機のブラウザ更新の必要性はさらに下がる（有効化そのものは設定ファイルの手編集でも行える。§3）

**ブラウザが古いまま放置されるとどうなるか**は、ブラウザと Blazor の組み合わせに依存し、Yagura 側では制御できない。管理画面が開かない・表示が崩れる・操作が効かないといった形で現れうる。**管理画面の不調に遭遇したら、まずサーバ機のブラウザの版を確認すること**。

### 12.2 対応下限の環境は「二重に劣後」する

Windows Server 2019 と SQL Server 2019 は、Yagura の**対応区分**ではあるが Microsoft の**メインストリームサポートは終了済み**である（それぞれ 2024-01-09 / 2025-02-28。以降はセキュリティ更新のみで、機能不具合の修正は出ない）。

さらに Yagura 側でも、これらの環境に固有の不具合は**推奨環境（Server 2022 / 2025・SQL Server 2022 以降）の品質維持を優先して**修正の優先度を判断する。

つまり**この構成は OS・DB ベンダとアプリベンダの双方で劣後する**。動かないという意味ではないが、**更新計画を立てる際はこの二重性を前提に置くこと**。

### 12.3 Yagura のサポートは対応 OS より先に切れる

| | 期限 |
|---|---|
| **Yagura v1.0 系列** | **2028-11-14** |
| Windows Server 2019 | 2029-01-09 |
| Windows Server 2022 | 2031-10-14 |
| SQL Server 2019 | 2030-01-08 |

v1.0 系列は同梱する .NET 10（LTS）のサポート終了日を上限とする。**「OS が生きている限り Yagura も使える」とは読まないこと**——先に切れるのは Yagura の側である。

修正を受け取る条件（最新リリースへの追随が前提であること等）は [SECURITY.md](../SECURITY.md) を参照。次のメジャーバージョンへの移行時期は、上表の Yagura 側の期限から逆算して計画する。

### 12.4 対応外の OS で動かしている場合

**v1.0 以降の MSI は対応外の OS では導入できない**（インストーラが OS ビルドを判定して停止する）。これは新規インストールだけでなく**アップグレードにも適用される**——対応外 OS 上の既存インストールは、そのまま動き続けるが**新しい版を受け取れなくなる**。

SECURITY.md のとおり修正は最新リリースにのみ提供され、過去の版へのバックポートは行わない。したがって**対応外 OS に留まることは、脆弱性修正を受け取る経路が無くなることを意味する**。

対応 OS への移行が難しい事情がある場合は、[Discussions](https://github.com/Yanai-Taketo/Yagura/discussions) で相談してほしい。

### 12.5 TLS 受信（6514）を有効化したら、ファイアウォール規則を自分で足す

MSI が作成する受信許可規則は **UDP 514 / TCP 514 / TCP 8514 の 3 本だけ**である。TLS 受信は opt-in で導入後に有効化するため、**MSI は 6514 の規則を作れない**。

規則が無いまま TLS 受信を有効化すると、起動時とその後の周期監視で次の警告が出る（loopback からの検証は通るため、**リモートの送信元だけが届かない**という気づきにくい状態になる）。

```
[firewall-rule-mismatch] リスナの実ポートと Yagura 名前空間のファイアウォール規則に不一致があります:
  syslog TLS 受信（TCP 6514）に対応する有効な受信許可規則がありません
```

管理者権限の PowerShell で、MSI が作る規則と同じ条件（Domain + Private・受信許可・実行ファイル限定）を満たす規則を追加する。

```powershell
New-NetFirewallRule -DisplayName 'Yagura Syslog (TLS 6514)' `
  -Direction Inbound -Action Allow -Protocol TCP -LocalPort 6514 `
  -Profile Domain,Private `
  -Program 'C:\Program Files\Yagura\Yagura.Host.exe'
```

インストール先を既定から変えた場合は `-Program` のパスを合わせる。規則を追加すると次回の突合で警告は消える。**ポート番号を `Ingestion:Tls:Port` で変更した場合も同じ警告が出る**（古いポートの規則が「どのリスナにも対応していない」として併せて列挙される）。

### 12.6 Windows Server 2019 の送信元から TLS 受信へ送るとき

Yagura の TLS 受信は **TLS 1.2 を下限**とする（1.0 / 1.1 は受け付けない）。一方 **Windows Server 2019 の既定のクライアント設定は、.NET Framework 系のツールで TLS 1.0 までしか提示しない**ことがある。

実機で確認した例（2026-08-02。Server 2019 10.0.17763.3650、`SchUseStrongCrypto` / `SystemDefaultTlsVersions` とも未設定）: PowerShell 5.1 の `SslStream` で既定のまま接続すると、共通アルゴリズムが無く必ず失敗する。

```
A call to SSPI failed, see inner exception.
---> The function requested is not supported   (SEC_E_UNSUPPORTED_FUNCTION 0x80090302)
```

サーバ側のイベントログには次が記録される（**失敗は必ず観測できる**——ログが出ないまま接続が消えることはない）。

```
TLS 接続 <送信元>:<ポート> のハンドシェイクに失敗しました。
---> クライアントとサーバーは共通のアルゴリズムを処理していないので、通信できません。
```

対処は送信側の設定である。

- **送信側が .NET Framework 系のツール**（PowerShell 5.1・自作スクリプト等）: レジストリの `SchUseStrongCrypto` / `SystemDefaultTlsVersions` を有効にするか、コード側で `[System.Security.Authentication.SslProtocols]::Tls12` を明示する
- **送信側が syslog 転送エージェント**: そのエージェントの TLS バージョン設定を 1.2 以上にする
- **サーバ側を 1.0 まで下げることはしない**。Yagura は導入先の OS バージョンが混在しても TLS 1.0 / 1.1 が意図せず露出しないよう、プロトコルの下限を明示固定している（[ADR-0010](adr/0010-admin-ui-authentication.md) Phase 2 決定 4）

## 13. 昇格後に旧データベースファイルを処分する

SQLite から SQL Server へ「本番昇格」すると、管理画面のウィザードで**旧・組み込みデータベースの処分（退避 / 削除）を選ぶ**。ただし**現在の版では、この選択は記録されるだけで、ファイルの移動・削除は自動では行われない**。切り替え後も旧ファイルは元の場所に残る。

処分は切り替えの完了後に手動で行う。

### 13.1 なぜ手動なのか

旧ファイルは**サービスが停止するまで開かれたまま**であり、切り替えの反映自体がサービス再起動を伴う。したがって処分は「再起動をまたいだ後始末」になる。この後始末を自動化する仕組みは、無瞬断での切替手順とあわせて設計する項目として残っている（[#502](https://github.com/Yanai-Taketo/Yagura/issues/502)）。

**放置しても受信・閲覧に影響はない**が、次の 2 点のため、方針を決めて処分することを勧める。

- 旧ファイルには**切り替え前のログがそのまま入っている**。保持期間の自動削除は新しい保存先にしか効かないため、**旧ファイルの中身は消えない**
- ディスク容量を占め続ける

### 13.2 手順

切り替えが完了し、新しい保存先へログが保存されていることを確認してから行う。

```powershell
# 1. サービスを停止する（ファイルの掴みを解放するため）
Stop-Service Yagura

# 2. 旧ファイルを確認する（既定のデータルート配下。ファイル名の既定は yagura.db）
$Root = "$env:ProgramData\Yagura"
Get-ChildItem $Root -Filter 'yagura.db*'   # -wal / -shm が併存する場合がある

# 3a. 退避する場合（-wal / -shm も一緒に移す）
$Dest = 'D:\Backup\Yagura'
New-Item -ItemType Directory -Path $Dest -Force | Out-Null
Move-Item "$Root\yagura.db*" $Dest

# 3b. 削除する場合
Remove-Item "$Root\yagura.db*"

# 4. サービスを起動する
Start-Service Yagura
```

**`-wal` / `-shm` を置き去りにしないこと。** SQLite は本体ファイルの脇に書き込みログ（`yagura.db-wal`）と共有メモリ索引（`yagura.db-shm`）を作る場合があり、**本体だけを移すと退避先のファイルから最新の書き込みを読めなくなることがある**。`yagura.db*` のようにまとめて扱う。

データルートを既定から変えている場合、または SQLite のファイル名を変えている場合は、`yagura.json` の該当設定を確認してパスを読み替える。

### 13.3 退避したファイルを後で読みたい場合

退避先の `yagura.db` は**そのままの SQLite ファイル**である。Yagura に読み込ませる機能は現時点では無いため、SQLite の閲覧ツール（`sqlite3` コマンド等）で直接開く。
