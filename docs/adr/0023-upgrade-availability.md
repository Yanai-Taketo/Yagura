# ADR-0023: アップグレード時の可用性 — DB 到達不能での起動継続とインストーラのロールバック安全性

- 状態: proposed
- 日付: 2026-07-26
- 決定者: YANAI Taketo
- 関連: [ADR-0001](0001-project-founding.md)（品質の原則「ログを失わない」）/ [ADR-0002](0002-architecture-principles.md)（決定 2 のスプール退避）/ [ADR-0006](0006-v1-release-criteria.md)（基準 2 の重大不具合「起動不能」・基準 4 のアップグレード実証）/ [ADR-0010](0010-admin-ui-authentication.md)（決定 1 の loopback 最終復旧経路・受信断のコスト）/ [ADR-0011](0011-app-auth-failure-backoff.md)（決定 2〜4 の「締め出さない」設計）/ [ADR-0015](0015-gmsa-service-account.md)（決定 2・4・7 のインストーラ CA と lab ④）/ [Issue #466](https://github.com/Yanai-Taketo/Yagura/issues/466)・[Issue #467](https://github.com/Yanai-Taketo/Yagura/issues/467)（本 ADR の起案元。実機 lab で検出）/ Issue #283（lab 実施）/ Issue #291（環境要因での縮小継続への反転の先例）/ [architecture.md](../design/architecture.md) §1.2・[configuration.md](../design/configuration.md) §1・[security.md](../design/security.md) §4.3

## 文脈と課題

2026-07-26 の実機 lab（Issue #283。実インストール・保存先 SQL Server・既存データあり）で、
**「受信が止まったまま自力復旧できない」経路が 2 つ**見つかった。両者は独立の不具合ではなく、
**片方がもう片方の引き金を引く関係**にある。

### 観測 1: 保存先 SQL Server が到達不能だとサービスが起動できない（Issue #466）

`Storage:Provider=sqlserver` + アプリ独自認証が有効な構成で SQL Server が停止していると、
起動シーケンスの管理者アカウントストア初期化が未処理例外を投げ、プロセスが即クラッシュする
（`APPCRASH e0434352`）。受信パイプライン側は同じ DB 障害でスプールへ正しく縮退するのに、
**管理アカウントストアの初期化だけが縮退せず起動そのものを落とす**。

帰結は 2 つある。**①DB 障害中はサービスを再起動できない**（OS 再起動・SCM の回復動作・手動を
問わず、DB が復旧するまで受信を再開できない）。**②MSI のインストール・アップグレードが
失敗する**（SCM の起動待ち 30 秒を超え、エラー 1920 → 1603）。

### 観測 2: アップグレードの起動段が失敗すると製品が 1 つも残らない（Issue #467）

`MajorUpgrade` は既定（`Schedule="afterInstallValidate"`）で**先に旧製品を削除する**ため、
新製品側の `InstallServices`（サービス登録）や `InstallFinalize`（サービス開始）が失敗すると、
ロールバック後に **Yagura が 1 つも残らない**。サービスも消え、syslog 受信が停止する。

さらに重い形として、**ACL 付替 CA を通過してから起動段で失敗すると再インストールも不能になる**
（現象 B。2 回再現）。フォルダの ACL はロールバックで復元されるが**既存の子ファイルは復元されず**、
新アカウントの ACE を `(I)`（継承）のまま保持して仮想 SA の ACE を失う。この状態では既定
アカウントで再インストールしても `yagura.json` を読めず（`UnauthorizedAccessException`）また
1920 → 1603 となり、**MSI の通常経路では復旧できない**。復旧には管理者による手動 ACL 修復
（`icacls … /reset /T` + 再インストール）を要した。

### 2 つは連結している

観測 1 が起動段の失敗を作り、観測 2 がその失敗を「製品消失」へ増幅する。すなわち
**「DB 障害中にアップグレードを試みると Yagura が消え、受信が止まり、入れ直しても起動しない」**
という連鎖が現実に起こりうる。本 ADR が 1 本で両者を扱うのはこの連結のためである。

### 既存の設計原則との関係（本 ADR の論拠）

本プロジェクトは一貫して「**受信を止めないこと**」を他に優先してきた。関連する既存決定:

- **ADR-0001 の品質の原則**: 「ログを失わないこと。失った場合に必ず観測できること」
- **architecture.md §1.2 の起動順序**: スプール → **受信開始** → DB provider 初期化 → Web UI。
  「DB や UI の初期化失敗・遅延が受信開始を遅らせない」ことを明文で約束している。スプール領域を
  開けない場合ですら「起動失敗（= 受信断の固定化）よりも、可視化された縮退の方が『ログを
  失わない』原則への害が小さい」として縮退運転を選ぶ
- **configuration.md §1**: 接続文字列の**未設定・復号失敗**は「SQLite へ縮小 + 強い警告」で
  **起動を止めない**（「設計判断: 受信を止めないことを優先」）
- **Issue #291（2026-07-16 オーナー裁定）**: 「起動失敗」は静的検証で判定できる値の不正に限り、
  **値は正しいが環境要因で bind できない場合は全リスナが開けない場合を含めて縮小継続とする**
  （#141「原子的起動」を環境要因について反転した先例）
- **`Program.cs` の既存判断**（自己ロックアウトの起動時警告）: 「ハード起動失敗にはしない——
  それだと syslog 受信自体が止まってしまい、より悪い結果になる」

**既存の起動時 fail-closed（1011/1012/1032・1024）はいずれも DB 到達不能を正当化しない**。
前者 3 つは「誤設定 1 つで防御が外れた状態で公開される」ことを防ぐもので**方向が逆**であり、
1024（設定ファイルを読めない）は「キー単位の縮退に分解できず**何が既定へ落ちたかを提示できない**
から可視化された縮退の系に載せられない」ことを根拠とする。DB 到達不能は防御を緩める方向でもなく、
接続先と失敗種別を提示できる**可視化可能な縮退**である。

なお `Program.cs` の該当箇所は、アカウントストアの初期化を受信開始より前に置く理由として
「`ILogStore` と同じ順序」と記していたが、**`ILogStore` は §1.2 手順 3 = 受信開始の後**である。
この理由づけ自体が齟齬しており、観測 1 はその齟齬が実害として現れたものである。

## 検討した選択肢

### 選択肢 A: 現状維持（DB 到達不能は起動失敗のまま・MajorUpgrade も既定のまま）

- 利点: 実装変更ゼロ。「DB が使えないなら起動しない」は一見わかりやすい
- 欠点: architecture.md §1.2 の約束（DB 初期化失敗が受信開始を遅らせない）が**再起動を挟むと
  破れる**。スプール退避の設計目的そのものが条件付きになる。ADR-0006 基準 2 の重大不具合定義
  「③起動不能」に該当し、**v1.0 公開の全域条件をブロックする**
- 却下

### 選択肢 B: DB 到達不能時も起動を継続する（採用）

観測 1 に対し、管理アカウントストアの初期化失敗で**起動を中止しない**。縮退の程度で 3 案を比較した:

- **B-1: SQLite へフォールバックする**: 接続文字列の未設定・復号失敗と同じ扱い。却下——
  未設定・復号失敗は「**そもそも本番 DB を使う構成が成立していない**」のに対し、到達不能は
  「**本番 DB を使う構成が成立していて一時的に届かないだけ**」である。ここで SQLite へ落とすと、
  復旧後に**分裂したアカウント台帳**（SQLite 側で作ったアカウントと SQL Server 側の台帳）が
  残る。認証の真実源を一時障害で二重化するのは、監査の「誰が」の一意性（ADR-0010 決定 6）を
  壊す代価が大きすぎる
- **B-2: アプリ独自認証を一時的に利用不能とし、それ以外は継続する（採用）**: 受信・閲覧・
  Windows 統合認証は生き続ける。アプリ独自認証だけが「保存先が復旧するまで使えない」状態に
  なり、復旧後は遅延初期化で自動的に回復する（スプールの drain と同じ「復旧したら自動で戻る」
  体験に揃う）
- **B-3: 管理 UI 全体を閉じる**: 却下——過剰である。Windows 統合認証が構成されていればそちらは
  健全に機能するし、閲覧 UI（ログの取り出し）を DB 障害の巻き添えで閉じる理由はない
  （ADR-0006 基準 2 の「⑤ログを取り出せない持続的な閲覧不能」に自ら該当してしまう）

### 選択肢 C: インストーラのロールバック安全性を上げる（採用。B と独立に効く）

観測 2 に対し 3 案を比較した:

- **C-1: `RemoveExistingProducts` を後段へ移す（採用）**: `Schedule="afterInstallFinalize"` に
  すると、新製品の導入が成立してから旧製品を消すため、**起動段の失敗で製品が消えることを
  構造的に防げる**。副作用（同一ファイルの共存・サービス名衝突・ディスク一時使用量）の検証を
  受け入れ条件に含める
- **C-2: ACL 付替 CA に rollback CA を対にする（採用）**: 現行は「ロールバック CA は設けない
  （付与済み ACE はデータルートに残るが**実害はなく**、次のインストールで冪等に再適用される）」
  と判断していた。**観測 2 の現象 B はこの判断が誤りだったことの実証**である——子ファイルに
  孤児継承 ACE が残り、次のインストールが冪等に回復しない。付与前の ACE を復元する rollback CA
  を対にする
- **C-3: ガイドに復旧手順を書くだけ**: 却下（単独では）——「製品が消えて入れ直しても起動しない」
  という失敗様式を、手順書だけで受け入れることはできない。ただし **C-1・C-2 を入れてもなお
  失敗しうる**（電源断等）ため、復旧手順の明記は**併用**する

## 決定

選択肢 B（B-2）と C（C-1 + C-2 + 併用の C-3）を採用する。

### 1. 保存先が到達不能でも起動する（観測 1）

- **管理者アカウントストアの初期化失敗は起動を止めない**。失敗は能動通知（1000 番台。採番は
  委任 1）として記録し、**アプリ独自認証を「保存先の復旧待ち」として一時的に利用不能**にする。
  受信・閲覧・Windows 統合認証は影響を受けない
- **復旧は自動**とする: 遅延初期化により、保存先が復旧した後の最初の利用時（またはモニタの
  周期評価）に初期化を再試行し、成功したらアプリ独自認証を回復する。**運用者の操作を要しない**
  （スプールの drain と同じ体験に揃える）
- **利用不能の間、アプリ独自認証のログインは「一時的に利用できない」ことが分かる形で拒否する**
  ——資格情報の誤りと区別できない汎用エラー（ADR-0011 決定 3 の列挙耐性）に紛れさせない。
  ここは列挙耐性の対象外である（アカウントの存否ではなく**サーバ側の状態**を伝えるため）
- **fail-closed 不変条件との関係**: 本決定は防御を緩めない。1011/1012/1032 が守るのは
  「無認証・無防備な公開」であり、本決定が作るのは「認証手段が 1 つ減った状態」である。
  ADR-0011 が「唯一の管理者を締め出さない」ことを一貫して優先してきた流儀（決定 2〜4）とも
  向きが同じ——**認証が使えないことを理由に受信を止めるのは、締め出しの最も重い形**である
- **起動経路に SCM の待ちを超えるブロッキングを置かない**: 保存先への接続試行のタイムアウトは、
  SCM の起動待ち（30 秒）より十分短い上限を**製品側で明示指定**する（既定 15 秒の接続タイムアウトが
  複数の初期化で直列に積み上がると 30 秒を超える——観測 1 の実測）。確定値は委任 1
- **`ILogStore` 側の初期化失敗も同じ原則で扱う**（観測 1 は管理アカウントストアで顕在化したが、
  ログストアの初期化例外も `IHostedService.StartAsync` の失敗としてプロセスを落とす）。
  こちらは既にスプール退避の受け皿があるため、**初期化失敗は「保存先未接続の縮退」として
  受信を継続**する

### 2. アップグレードで製品を消さない（観測 2 現象 A）

- **`MajorUpgrade` の `Schedule` を後段へ移す**（`afterInstallFinalize` を第一候補とする）。
  新製品の導入が成立してから旧製品を削除することで、起動段の失敗が製品消失に至る経路を
  構造的に断つ
- **副作用の検証を受け入れ条件に含める**（委任 2）: 同一ファイルの共存・サービス名の衝突・
  一時的なディスク使用量の増加・ロールバック時の挙動を実機で確認する。`REINSTALLMODE` には
  引き続き手を入れない（ADR-0015 起案時の自己拘束を維持する）

### 3. ACL 付替のロールバックを対にする（観測 2 現象 B）

- **gMSA 構成の ACL 付替 deferred CA に rollback CA を対にする**。付与前の状態
  （少なくとも「付与した ACE の撤去」）を復元し、**子ファイルに孤児継承 ACE が残らない**ことを
  保証する
- **「ロールバック CA は設けない（実害はなく、次のインストールで冪等に再適用される）」という
  従来の判断を撤回する**（ADR-0015 決定 2 の実装注記。本 ADR で明示的に置き換える）——
  現象 B は「実害があり、次のインストールでも回復しない」ことを 2 回の再現で示した

### 4. 復旧手順の明記（C-3 の併用）

- 上記を入れてもなお失敗しうる場合（電源断・ディスク障害等）に備え、**「アップグレードに失敗して
  製品が起動しない/消えた場合の復旧手順」**を operations 系ドキュメントに明記する。lab で実測した
  復旧コマンド（`icacls … /reset /T /C` + 再インストール。forwarder の独立 SDDL は `/reset` で
  失われるため再適用が要ることを含む）を根拠つきで載せる

### 5. 受け入れ基準

- **CI 回帰**: ①保存先が到達不能な構成でプロセスが起動しきり受信を開始すること（実プロセス E2E。
  1011/1012 と同型）、②復旧後にアプリ独自認証が自動回復すること、③初期化のブロッキングが
  規定のタイムアウト上限で打ち切られること
- **lab 実機検証**（conventions.md「実環境依存の機能は lab 検証を受け入れ条件に含める」）:
  ④DB 停止中の `Restart-Service` で受信が再開すること、⑤DB 停止中の MSI アップグレードが
  成立すること（または失敗しても**製品が残る**こと）、⑥アカウント切替の失敗で子ファイルの
  孤児継承 ACE が残らないこと（現象 B の否定）、⑦失敗後に MSI の通常経路で復旧できること
- **本 ADR の実装完了までは、v1.0 公開判定を行わない**（ADR-0006 基準 2 の重大不具合定義
  「③起動不能」に該当する既知不具合が未解決のため）

### 6. ADR-0006 基準 4 の穴の指摘（本 ADR では変更しない）

ADR-0006 基準 4 は「蓄積データと設定が実際に保全されること」を要求するが、**製品自体の存続を
要求していない**。観測 2 は「データと設定は保全されたが製品が消えた」形であり、基準 4 を
文字どおり満たしながら最悪の失敗が起こりうる。**基準の変更は ADR-0006 の supersession を要する**
ため本 ADR では行わず、**指摘として記録する**（委任 4）。

## 帰結

- 良くなること:
  - **DB 障害中でも再起動できる**。architecture.md §1.2 の約束（DB 初期化失敗が受信開始を
    遅らせない）が、再起動を挟んでも成立するようになる
  - **アップグレードの失敗で製品が消えない**。ログ集約サーバとして最も避けたい失敗様式
    （「アップグレードを試みたら製品が消えて、入れ直しても起動しない」）が構造的に消える
  - ADR-0006 基準 2 の重大不具合「③起動不能」が解消し、v1.0 公開判定の障害が 1 つ減る
- 悪くなること（受け入れるトレードオフ）:
  - **「起動しているのにアプリ独自認証が使えない」状態が新設される**。運用者から見た状態が
    1 つ増え、能動通知と画面表示で可視化する責務が生じる（沈黙させれば「なぜログインできない
    のか分からない」に退化する）
  - **`RemoveExistingProducts` の後段化は MSI の挙動を根本的に変える**。同一ファイルの共存・
    サービス名衝突という新しい失敗様式を招く可能性があり、検証コストは小さくない
  - rollback CA の追加によりインストーラの分岐が増える（供給網上最も注視される成果物である以上、
    分岐の増加それ自体が費用である——ADR-0020 決定 2 で「インストーラに条件分岐を増やすだけ」を
    却下理由としたのと同じ天秤）
- 受け入れるリスク:
  - **遅延初期化の回復判定が誤ると「復旧したのに使えないまま」になる**。回復の観測可能性
    （通知・画面表示）を受け入れ基準に含めることで緩和する
  - gMSA 構成の DC 依存（サービス起動前に SCM がアカウントを解決できない場合）は**本 ADR の
    射程外**である。configuration.md が既に「この依存は構造的に解消できない——『受信を止めない』
    原則の適用範囲が SCM の外側で狭まる」と受容しており、本 ADR が扱うのは **SCM の内側**
    （プロセスが起動した後）の可用性である

## 先送りにする場合の再評価トリガ

本 ADR が却下（選択肢 A 維持）となった場合、以下のいずれかで再評価する:

- 実利用環境で「DB 障害中に再起動して受信が再開しなかった」実例が報告された場合
- アップグレード失敗による製品消失が実利用環境で発生した場合
- ADR-0006 の v1.0 公開判定で、基準 2 の重大不具合定義「③起動不能」の解釈が本件を含むと
  裁定された場合（現状の起案者の理解では含む）
