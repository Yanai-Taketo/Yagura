## 文脈と課題

2026-07-26 の実機 lab（Issue #283。実インストール・保存先 SQL Server・既存データあり）で、
**「受信が止まったまま自力復旧できない」経路が 2 つ**見つかった。両者は独立の不具合ではなく、
**片方がもう片方の引き金を引く関係**にある。

### 観測 1: 保存先 SQL Server が到達不能だとサービスが起動できない（Issue #466）

`Storage:Provider=sqlserver` + アプリ独自認証が有効な構成で SQL Server が停止していると、
起動シーケンスの管理者アカウントストア初期化が未処理例外を投げ、プロセスが即クラッシュする
（`APPCRASH e0434352`）。受信パイプライン側は同じ DB 障害でスプールへ正しく縮退するのに、
**管理アカウントストアの初期化だけが縮退せず起動そのものを落とす**。

帰結は 2 つある。**①DB 障害中はサービスを再起動できない**（OS 再起動・SCM の回復動作・手動を
問わず、DB が復旧するまで受信を再開できない）。**②MSI のインストール・アップグレードが
失敗する**（SCM の起動待ち 30 秒を超え、エラー 1920 → 1603）。

### 観測 2: アップグレードの起動段が失敗すると製品が 1 つも残らない（Issue #467）

`MajorUpgrade` は既定（`Schedule="afterInstallValidate"`）で**先に旧製品を削除する**ため、
新製品側の `InstallServices`（サービス登録）や `InstallFinalize`（サービス開始）が失敗すると、
ロールバック後に **Yagura が 1 つも残らない**。サービスも消え、syslog 受信が停止する。

さらに重い形として、**ACL 付替 CA を通過してから起動段で失敗すると再インストールも不能になる**
（現象 B。2 回再現）。フォルダの ACL はロールバックで復元されるが**既存の子ファイルは復元されず**、
新アカウントの ACE を `(I)`（継承）のまま保持して仮想 SA の ACE を失う。この状態では既定
アカウントで再インストールしても `yagura.json` を読めず（`UnauthorizedAccessException`）また
1920 → 1603 となり、**MSI の通常経路では復旧できない**。復旧には管理者による手動 ACL 修復
（`icacls … /reset /T` + 再インストール）を要した。

### 2 つは連結している

観測 1 が起動段の失敗を作り、観測 2 がその失敗を「製品消失」へ増幅する。すなわち
**「DB 障害中にアップグレードを試みると Yagura が消え、受信が止まり、入れ直しても起動しない」**
という連鎖が現実に起こりうる。本 ADR が 1 本で両者を扱うのはこの連結のためである。

### 既存の設計原則との関係（本 ADR の論拠）

本プロジェクトは一貫して「**受信を止めないこと**」を他に優先してきた。関連する既存決定:

- **ADR-0001 の品質の原則**: 「ログを失わないこと。失った場合に必ず観測できること」
- **architecture.md §1.2 の起動順序**: スプール → **受信開始** → DB provider 初期化 → Web UI。
  「DB や UI の初期化失敗・遅延が受信開始を遅らせない」ことを明文で約束している。スプール領域を
  開けない場合ですら「起動失敗（= 受信断の固定化）よりも、可視化された縮退の方が『ログを
  失わない』原則への害が小さい」として縮退運転を選ぶ
- **configuration.md §1**: 接続文字列の**未設定・復号失敗**は「SQLite へ縮小 + 強い警告」で
  **起動を止めない**（「設計判断: 受信を止めないことを優先」）
- **Issue #291（2026-07-16 オーナー裁定）**: 「起動失敗」は静的検証で判定できる値の不正に限り、
  **値は正しいが環境要因で bind できない場合は全リスナが開けない場合を含めて縮小継続とする**
  （#141「原子的起動」を環境要因について反転した先例）
- **`Program.cs` の既存判断**（自己ロックアウトの起動時警告）: 「ハード起動失敗にはしない——
  それだと syslog 受信自体が止まってしまい、より悪い結果になる」

**既存の起動時 fail-closed（1011/1012/1032・1024）はいずれも DB 到達不能を正当化しない**。
前者 3 つは「誤設定 1 つで防御が外れた状態で公開される」ことを防ぐもので**方向が逆**であり、
1024（設定ファイルを読めない）は「キー単位の縮退に分解できず**何が既定へ落ちたかを提示できない**
から可視化された縮退の系に載せられない」ことを根拠とする。DB 到達不能は防御を緩める方向でもなく、
接続先と失敗種別を提示できる**可視化可能な縮退**である。

なお `Program.cs` の該当箇所は、アカウントストアの初期化を受信開始より前に置く理由として
「`ILogStore` と同じ順序」と記していたが、**`ILogStore` は §1.2 手順 3 = 受信開始の後**である。
この理由づけ自体が齟齬しており、観測 1 はその齟齬が実害として現れたものである。

## 検討した選択肢

### 選択肢 A: 現状維持（DB 到達不能は起動失敗のまま・MajorUpgrade も既定のまま）

- 利点: 実装変更ゼロ。「DB が使えないなら起動しない」は一見わかりやすい
- 欠点: architecture.md §1.2 の約束（DB 初期化失敗が受信開始を遅らせない）が**再起動を挟むと
  破れる**。スプール退避の設計目的そのものが条件付きになる。ADR-0006 基準 2 の重大不具合定義
  「③起動不能」に該当し、**v1.0 公開の全域条件をブロックする**
- 却下

### 選択肢 B: DB 到達不能時も起動を継続する（採用）

観測 1 に対し、管理アカウントストアの初期化失敗で**起動を中止しない**。縮退の程度で 4 案を比較した:

- **B-1: 書き込み可能な SQLite へフォールバックする**: 却下——未設定・復号失敗は「そもそも
  本番 DB を使う構成が成立していない」のに対し、到達不能は「本番 DB を使う構成が成立していて
  一時的に届かないだけ」である。**書き込み可能な** SQLite へ落とすと、復旧後に分裂した
  アカウント台帳が残り、認証の真実源が一時障害で二重化する
- **B-1': 読み取り専用の資格情報キャッシュ、または新規作成を禁じた SQLite で認証だけ継続する**
  （ペルソナレビュー クリスの指摘 5 による追加）: 真実源は二重化しないため B-1 の却下理由は
  当たらない。**別の理由で却下する**——認証だけを継続するには**資格情報のコピーを保持し続ける**
  必要があり、(i) パスワード変更・アカウント削除の反映が DB 復旧まで遅れる（失効したはずの
  資格情報で入れる窓ができる。ADR-0013 決定 2 が世代番号で緊急全失効を作った意図に反する）、
  (ii) ハッシュの複製がもう 1 箇所増える。**可用性のために失効の即時性を犠牲にする交換は、
  本プロジェクトの優先順位では成立しない**
- **B-2: アプリ独自認証を一時的に利用不能とし、それ以外は継続する（採用）**: 受信は継続し、
  プロセスは生き、Windows 統合認証が構成されていればそちらは機能する。復旧後は自動回復する
- **B-3: 管理 UI 全体を閉じる**: 却下。ただし**「閲覧は健全」と言い切るのは誇張である**
  （クリスの指摘 4）——保存先が SQL Server で落ちている間、閲覧できるのは障害前に DB へ書けた
  分までであり、障害中の受信分はスプールに退避されていて閲覧対象に現れない。B-3 を却下する
  理由は「閲覧が完全に健全だから」ではなく「**管理 UI を閉じても DB 障害は何も改善しないのに、
  復旧作業の窓口まで失う**」ことである

**B-2 が受け入れるトレードオフ（クリスの指摘 4 による明示）**: Windows 統合認証が未構成の
構成——ゼロ設定ファーストランの主戦場——では、B-2 は**DB 復旧までリモートからの管理 UI 到達を
失う**ことを意味する。「認証手段が 1 つ減るだけ」という表現はこの構成では正しくない。
残る到達手段はサーバ上の loopback であり、それも閉じている構成（決定 1 の不変条件）では
設定ファイル手編集が復旧経路になる。**それでも B-2 を採るのは、管理 UI に入れないことと受信が
止まることでは後者の害が大きいためである**（ADR-0001 の品質の原則）。

### 選択肢 C: インストーラのロールバック安全性を上げる（採用）

観測 2 に対し 4 案を比較した。**本節の判断は公式ドキュメントの引用に基づく**
（ペルソナレビュー クリスの指摘 1——起案時は一般論だけで `afterInstallFinalize` を第一候補に
していた。引用の水準が決定間で非対称だという指摘は正しく、**確認の結果、第一候補が入れ替わった**）。

[RemoveExistingProducts Action（Microsoft Learn。確認日 2026-07-26）](https://learn.microsoft.com/en-us/windows/win32/msi/removeexistingproducts-action)
の "Sequence Restrictions" より:

- `InstallExecute` と `InstallFinalize` の間（= WiX の `afterInstallExecute`）:
  > "In this case the updated files are installed first and then the old files are removed.
  > **However, if the removal of the old application fails, then the installer rolls back both
  > the removal of the old application and the install of the new application.**"
- `InstallFinalize` の後（= `afterInstallFinalize`）:
  > "This is the most efficient placement for the action. … **If the removal of the old
  > application fails, then the installer only rolls back the uninstallation of the old
  > application.**"

- **C-1: `afterInstallFinalize`**: **却下（起案時の第一候補から降格）**——旧製品の削除失敗が
  **トランザクション外**であり、失敗すると新旧が両方残る新しい失敗様式を作る。より弱い保護のために
  より重い失敗様式を招く
- **C-1': `afterInstallExecute`（採用）**: Issue #467 が併記していた候補（起案時に検討記録なく
  落としていた——クリスの指摘 2）。**削除がトランザクション内に留まる**ため、観測 2 の起点である
  `StartServices` の失敗では**全体がロールバックされ旧製品が残る**。削除自体が失敗しても
  新旧両方がロールバックされる。目的（製品を消さない）を満たしつつ、C-1 の新失敗様式を作らない。
  **順序の根拠**（round 2 クリスの指摘 2——起案時は無引用の断定だった）:
  [Suggested InstallExecuteSequence（Microsoft Learn。確認日 2026-07-26）](https://learn.microsoft.com/en-us/windows/win32/msi/suggested-installexecutesequence)
  の標準シーケンス番号は `StopServices` = 1900 / `InstallFiles` = 4000 /
  `InstallServices` = 5800 / `StartServices` = 5900 / `InstallFinalize` = 6600 であり、
  遅い `RemoveExistingProducts`（`InstallExecute`〜`InstallFinalize` 間）は
  **`StartServices` より後**に位置する
- **C-2: ACL 付替 CA に rollback CA を対にする（採用）**: 現行は「ロールバック CA は設けない
  （付与済み ACE は…**実害はなく**、次のインストールで冪等に再適用される）」と判断していた
  （`installer/Package.wxs` の `GrantServiceAccountDataRootAcl` 周辺コメント）。**観測 2 の
  現象 B はこの判断が誤りだったことの実証**である
- **C-3: ガイドに復旧手順を書くだけ**: 却下（単独では）。ただし C-1'・C-2 を入れてもなお
  失敗しうる（電源断等）ため、復旧手順の明記は**併用**する

**遅いスケジュールに共通して残る前提（採否条件。委任 2 で先に確認する）**: `afterInstallExecute`・
`afterInstallFinalize` のいずれも
> "requires strict adherence to the component rules because it relies on component reference
> counts to be accurate"

（[How To: Implement a Major Upgrade / MajorUpgrade element](https://docs.firegiant.com/wix/schema/wxs/majorupgrade/)）
であり、**コンポーネント GUID の版間安定性に完全に依存する**。本製品は
`<Files Include="$(PublishDir)\**">` による自動採番を使っており、GUID が版間で安定しなければ
**旧製品の削除が新製品のファイル・サービスを巻き添えにする**（クリスの指摘 1(a)(b)）。
この確認が取れない場合、C-1' は採らず **C-2 + C-3 のみで着地する**（決定 2 の採否条件）。

## 決定

選択肢 B（B-2）と C（C-1' + C-2 + 併用の C-3）を採用する。**着地順序は決定 1・決定 3 が先、
決定 2 は採否条件の確認後**とする（クリスの指摘 6——確実に効く変更を、前提が覆りうる変更の
検証待ちで人質に取らない。決定 1 と決定 3 はそれぞれ単独で完了しうる）。

### 1. 保存先が到達不能でも起動する（観測 1）

- **管理者アカウントストア・ログストアの初期化失敗は起動を止めない**。失敗は能動通知として
  記録し、**アプリ独自認証を「保存先の復旧待ち」として一時的に利用不能**にする。受信・
  Windows 統合認証は影響を受けない（閲覧については選択肢 B-3 の注記のとおり、障害前に DB へ
  書けた分までが見える）
- **不変条件: 保存先の到達不能を理由に、認証の要否・適用範囲を緩めない**（田中の指摘 1）。
  具体的には **`Admin:Authentication:RequireForLoopback` の自動解除・loopback 限定への自動縮退を
  行わない**——これを認めると「**攻撃者が保存先を落とせば認証が外れる**」という誘発可能な認証
  バイパスになる。Issue #466 修正案 3 の「loopback 限定へ縮退」はこの理由で却下する。
  **`RequireForLoopback` 有効 + アプリ独自認証のみの構成では、DB 復旧まで管理面は閉じたまま**に
  なる（認証手段が実質ゼロになる）。この構成の復旧経路は ADR-0010 決定 1 の設定ファイル手編集で
  あり、それは元々「認証手段が全滅した場合の最終復旧経路」として設計されている
- **回復は周期監視を契機とする**（田中の指摘 3・クリスの指摘 3）。**「利用時（ログイン要求）」を
  契機にした再試行は行わない**——未認証の要求で任意に保存先への接続試行を誘発でき、接続・
  スレッドの占有と保存先への増幅になる。加えて初期化は接続確認ではなく **DDL + スキーマ移行**
  （v1→v3 の `ApplyMigrationsAsync`）であり、要求スレッド上で走らせてよい処理ではない
- **回復処理の不変条件（決定の一部。委任へ落とさない——クリスの指摘 3）**: ①**単一実行**
  （同時に複数の初期化が走らない）、②**失敗の負のキャッシュ**（失敗直後に再試行を繰り返さない。
  再試行間隔の下限を設ける）、③**接続タイムアウトの明示上限**
- **起動経路のブロッキングの天井を決定として固定する**（リサの質問 2）: **起動シーケンス中の
  保存先接続試行は、合計で 10 秒を超えない**（SCM の起動待ち 30 秒に対する余裕。個別値の配分と
  直列/並行の実装は委任 1-2）。**本上限は起動経路にのみ適用**し、稼働中の書き込みタイムアウト
  （M-13）には及ばない（鈴木の指摘 4）——AG フェイルオーバー・名前付きインスタンス解決で
  正常系が数十秒かかる経路を、起動用の天井で切らないため
- **スキーマ移行そのものを起動経路から外す**（round 2 鈴木の指摘 2）: 接続に天井を置いても、
  **DDL + スキーマ移行が起動経路に残れば SCM の 30 秒は依然破れる**（移行は接続とは独立に
  長引きうる。`CommandTimeout = 0` を明示している箇所もある）。初期化は**起動シーケンスの外**
  （周期監視の初回評価と同じ経路）で完了させ、**起動は初期化の完了を待たない**
- **縮退中のログイン応答は「一時的に利用できない」ことが分かる形で返す**。これを ADR-0011
  決定 3 の列挙耐性の対象外とする**成立条件を本文で固定する**（田中の指摘 2）:
  **アカウント照会より前に、実在・非実在を問わず一律に同じ応答を返す**こと。
  「実在アカウントには unavailable、非実在名には汎用エラー」は per-name オラクルの再開であり
  禁止する。**失敗回数 n を進めない**（資格情報の検証に到達していないため。攻撃でバケットを
  涸らして正規管理者を巻き込む経路も塞ぐ）。ただし**無コストの状態オラクルにはしない**
  （round 2 田中の指摘 2——縮退応答を三層防御のすべてより前に置くと、保存先の停止と復旧の瞬間を
  未認証・無制限に外部から観測でき、DB を落とす攻撃の成功確認や帰属水準が下がる窓の狙い撃ちに
  使える）: **リモート発の縮退応答は IP レート制限のカウント対象とする**（グローバルバケットと
  n は据え置く）。loopback は ADR-0011 決定 4 のとおり三層すべての対象外のままとし、復旧
  オペレータを妨げない。**応答に保存先名・例外文字列・再試行時刻を含めない**
- **監査**（田中の指摘 4）: security.md §4.2 のとおり**監査記録はローカルファイル + イベント
  ログであり、保存先の障害では失われない**（読者が「DB 障害中は監査も消える」と誤読しないよう
  明記する）。そのうえで **①縮退の開始 ②縮退中のログイン拒否 ③回復** の 3 事象をそれぞれ
  独立に採番する（既存 3004「ログイン失敗」への相乗りは、資格情報検証を経ていない事象を混ぜる
  ことになり §4.3 の意味凍結に反する）。**縮退の開始と回復を対の事象にする**ことで
  「アプリ独自認証が使えなかった窓」を事後に確定できる
- **fail-closed 不変条件との関係**: 本決定は防御を緩めない。1011/1012/1032 が守るのは
  「無認証・無防備な公開」であり、本決定は認証を**緩めずに**受信を守る

### 2. アップグレードで製品を消さない（観測 2 現象 A。採否条件つき）

- **`MajorUpgrade` の `Schedule` を `afterInstallExecute` にする**（削除がトランザクション内に
  留まる。公式ドキュメントの引用は選択肢 C 参照）
- **採否条件（先に確認する。不成立なら本決定は不採用とする——後述の手続き）**:
  ①コンポーネント GUID の版間安定性が保たれること（`HostPublishFiles` の自動採番）、
  ②**`RemoveExistingProducts` が起動する旧製品のアンインストールが、直前に起動した新サービスを
  止める・削除しないこと**（`ServiceControl` は同名 `Yagura` を `Stop="both" Remove="uninstall"`
  で対象とするため、これを防ぐのはコンポーネント参照カウントのみ）
- **共存窓に関する起案時の記述を訂正する**（round 2 で鈴木・クリスが揃って指摘。**起案時の
  「旧サービスが稼働したまま新製品が入る」は実装と整合しない誤りだった**）: `Package.wxs` の
  `ServiceControl` は `Stop="both"` であり、標準シーケンスの `StopServices`（1900）は
  `InstallFiles`（4000）より前に走る。**新製品のインストール開始時点で旧サービスは既に停止して
  いる**ため、UDP 514 の bind 競合も 2 プロセスによるデータルート・監査ファイル・スプールへの
  二重アクセスも起きない。**実在するリスクは②に集約される**——遅いスケジュールでは
  「新サービスを起動した後に旧製品のアンインストールが走る」ため、参照カウントが崩れていれば
  それが新サービスを止め・消す
- **受信断の窓は残る**: `StopServices`（1900）から `StartServices`（5900）までがアップグレード中の
  受信断であり、これは既定スケジュールでも同じである（本決定が新設するものではない）。
  ただし実測は受け入れ基準⑪で行う
- **採否条件が不成立だった場合の手続き**（round 2 クリスの指摘 3——本文が「採用」のまま実態と
  乖離しないため）: **決定 2 を撤回し、その事実と理由を本 ADR の改訂履歴に記録する**。
  その場合の着地は決定 1 + 決定 3 + 決定 4 である。判定は委任 2 の実装 PR で行い、
  結果（採用・撤回のいずれでも）を改訂履歴に残す
- `REINSTALLMODE` には引き続き手を入れない（ADR-0015 起案時の自己拘束を維持する）

### 3. ACL 付替のロールバックを対にする（観測 2 現象 B）

- **gMSA 構成の ACL 付替 deferred CA に rollback CA を対にする**。付与前の ACE を復元し、
  **子ファイルに孤児継承 ACE が残らない**ことを保証する
- **不変条件**（田中の指摘 5）: ①**rollback CA はいかなる主体の権限も増やさない**、
  ②**`/reset` 相当の一括再設定を行わない**（決定 4 のとおり `/reset` は forwarder の独立 SDDL を
  破壊する）、③復元に使う付与前 ACE は **CustomActionData またはロールバックスクリプト内に
  限定して保持する**（`Users` が書ける一時パス等に置くと、LocalSystem が攻撃者制御の SDDL を
  復元する踏み台になる）
- **rollback CA 自体は失敗してもロールバックされない**ため、**撤去を先・復元を後**の順序とする
  （round 2 田中の指摘 3——途中で中断しても権限が増えない向きに倒す）
- **前方修復**（鈴木の指摘 5）: 既に孤児継承 ACE が残っている環境は rollback CA では救われない。
  **インストール時に ACL の整合を検査し、期待と異なる場合は是正する**。ただし**是正対象は
  本製品が付与した ACE の系に限る**（round 2 田中の指摘 3——「期待と異なれば是正」を広く取ると
  第三者が付与した ACE の削除、すなわち実質 `/reset` に化ける）
- **本決定の位置づけ（リサの指摘 1・2 による訂正）**: 撤回する「ロールバック CA は設けない
  （実害はない）」は **ADR-0015 決定 2 の本文ではなく `installer/Package.wxs` の実装コメント**に
  ある。経緯としてより重要なのは、**ADR-0015 決定 2 が「フォールバックした場合の…失敗時
  ロールバック要件…を本 ADR の改訂履歴に記録する」と約束していたのに、改訂履歴 1 にその記録が
  無い**ことである——約束された amendment が欠落したまま、実装コメントが事実上の決定として
  機能していた。**本決定は ADR-0015 決定 2 の部分 supersession として扱う**（docs/adr/README.md
  の ADR-0015 行と決定 2 冒頭に本 ADR への参照注記を加える。README の「疑わしければ supersession
  側に倒す」に従う）。あわせて **security.md §5.2 の「付与失敗は `Return="check"` で fail-closed に
  ロールバックする」は現象 B の観測と矛盾する**（ロールバックされるのは MSI が管理するフォルダの
  静的 SDDL のみで、CA が付けた ACE と子ファイルは戻らない）——委任 3 で誤りとして訂正する

### 4. 復旧手順の明記（C-3 の併用）

- **「アップグレードに失敗して製品が起動しない/消えた場合の復旧手順」**を文書化する。掲載先は
  **リリースノートとオンラインの運用ドキュメントの両方**とし（佐藤の指摘 3——製品が消えた状態では
  インストール先の手順書も消えている）、`1920` / `1603` / `Access to the path … is denied` の
  **エラー文字列を本文に含める**（検索で辿り着けるように）
- 復旧コマンドは **`icacls … /reset /T /C` と forwarder の独立 SDDL 再適用を 1 つのコピー可能な
  ブロック**にまとめ、`/reset` が何を消すのかの警告を添える（佐藤の指摘 4——順番を間違えられる
  形の手順は危険である）
- **認証手段が全滅した構成の復旧手順では「緩めるのは `RequireForLoopback` 側」であることと
  その順序を明記する**（round 2 田中の指摘 1）: 焦った運用者が代わりに「アプリ独自認証を無効化
  する」側を編集すると、`RequireForLoopback` が有効なまま認証方式ゼロになり **1011 の
  fail-closed で起動拒否**となって観測 1 と同じ症状を別経路で再現する。あわせて**回復通知
  （決定 1 の 3 事象の③）には、緩めた設定を元に戻す導線を含める**——恒久的に無効化したまま
  忘れる誘因を、戻し忘れの可視化で断つ

### 5. 受け入れ基準

- **CI 回帰**: ①保存先が到達不能な構成でプロセスが起動しきり受信を開始すること（実プロセス
  E2E）、②復旧後にアプリ独自認証が自動回復すること（**回復までの上限時間つき**）、
  ③起動経路の接続試行が合計 10 秒の天井で打ち切られること（決定 1 で値を固定済みのため
  起案時点でテスト可能）、④**縮退中のログイン応答が実在・非実在で区別できないこと**
  （田中の指摘 2。実装コメントではなく回帰テストで固定する）、
  ⑤**アップグレードの起動段失敗で製品が残ること**——DB を止めずに**サービス起動を意図的に
  失敗させる細工**で `installer-e2e` に落とす（リサの質問 3。AD も SQL も不要なため fork からの
  PR でも自己確認できる）。合格条件は「一覧にエントリが残る」ではなく
  **旧版のサービスが起動したままで受信が継続していること**（佐藤の質問 2）
- **lab 実機検証**: ⑥DB 停止中の `Restart-Service` で受信が再開すること、⑦DB 停止中の MSI
  アップグレードが成立すること（または失敗しても製品が残ること）、⑧アカウント切替の失敗で
  **付与前と ACE 集合が一致すること**（田中の指摘 5——「孤児 ACE が残らない」より強い条件）、
  ⑨失敗後に MSI の通常経路で復旧できること、⑩アップグレード完了後に**全リスナが実際に
  bind されており、かつ bind しているのが新版プロセスであること**（鈴木の指摘 2 と round 2 の
  訂正）、⑪アップグレード中の**受信断時間の実測**——**既知 EPS の連続送信下**で計測し、
  暫定でよいので上限値を置いて超過を不合格とする（round 2 鈴木の指摘 3。無負荷での計測では
  保守窓のサイズ決めに使えない）。実測値はリリースノートに載せる、
  ⑫失敗後に「アプリと機能」に Yagura が 2 つ残らないこと（佐藤の指摘 2。残る場合は正しい対処が
  文書化されていること）
- **lab 項目（⑥〜⑫）の消化はオーナー側（受領側）の責務とし、外部コントリビュータの実装 PR の
  受理条件としない**（ADR-0020 決定 5 の準用。リサの指摘 4）
- **ADR-0006 基準 2 の重大不具合定義「③起動不能」への該当可否はオーナーの裁定を仰ぐ**
  （クリスの指摘 7・リサの指摘 6）。**該当するなら公開ゲートは ADR-0006 側で自動的に成立する**
  ため、本 ADR は独自の公開ゲートを設けない（起案時は「本 ADR の実装完了までは v1.0 公開判定を
  行わない」と書いていたが、§6 で「基準の変更は supersession を要する」と自制した規律と
  矛盾していた）

### 6. ADR-0006 基準 4 の穴の指摘（本 ADR では変更しない）

ADR-0006 基準 4 は「蓄積データと設定が実際に保全されること」を要求するが、**製品自体の存続を
要求していない**。観測 2 は「データと設定は保全されたが製品が消えた」形であり、基準 4 を
文字どおり満たしながら最悪の失敗が起こりうる。基準の変更は ADR-0006 の supersession を要するため
本 ADR では行わないが、**放置しないための再評価トリガを定める**（リサの指摘 5）:
**ADR-0006 基準 4 の実地実証（v0.x → v1.0 更新検証）に着手する時点、または本 ADR 決定 2・3 の
実装完了時点のいずれか早い方**で、基準 4 への「製品の存続」追加を ADR-0006 の supersession として
起案するか否かを判断する。

## 帰結

- 良くなること:
  - **DB 障害中でも再起動できる**。architecture.md §1.2 の約束（DB 初期化失敗が受信開始を
    遅らせない）が、再起動を挟んでも成立するようになる
  - **アップグレードの失敗で製品が消えない**。ログ集約サーバとして最も避けたい失敗様式
    （「アップグレードを試みたら製品が消えて、入れ直しても起動しない」）が構造的に消える
- 悪くなること（受け入れるトレードオフ）:
  - **受信断は防ぐが、ログの損失は防がない**（鈴木の指摘 1）。DB 復旧までの無損失の上限は
    **スプール容量**（architecture.md M-12。既定値は未確定）であり、超過すれば §3.2.3 の
    新規破棄でログは落ちる。「再起動できるようになった」ことを「直った」と誤認させないため、
    復旧手順には**残余スプール時間を見て動く**観点を含める（委任 5）。
    **この上限は DB 障害軸の話であり、アップグレード中の受信断（`StopServices`〜`StartServices`）
    には及ばない**——スプールは受信の下流にあるため、リスナが閉じている間の UDP は
    そもそも受け取れず救えない（round 2 鈴木の指摘 3）
  - **Windows 統合認証が未構成の構成では、DB 復旧までリモートからの管理 UI 到達を失う**
    （選択肢 B の注記。ゼロ設定ファーストランの主戦場がこれに当たる）。`RequireForLoopback`
    有効 + アプリ独自認証のみなら管理面は完全に閉じ、復旧は設定ファイル手編集になる
  - **DB 障害中は監査の帰属水準が下がる**（田中の指摘 4）: 監査記録自体は失われない（§4.2）が、
    アプリ独自認証が使えない間に既定の無認証 loopback で行われた管理操作は、ADR-0010 決定 6 の
    「誰が」欄が接続元アドレスへ退化する
  - **`MajorUpgrade` のスケジュール変更は MSI の挙動を根本的に変える**。遅いスケジュールは
    コンポーネント参照カウントの正確さに依存するため、**コンポーネント GUID の版間安定性が
    新しい不変条件になる**（採否条件で先に確認する）
  - **供給網統治の費用は分岐の増加ではない**（田中の指摘 7）: 遅いスケジュールでは
    **過去に出荷済みの版のアンインストール処理が、新製品の導入後に実行される**。アップグレードの
    安全性が現在のツリーだけでは論証できなくなり、全出荷版の除去処理が上流依存になる。
    受け入れ基準⑤〜⑦には**アップグレード元バージョンのマトリクス**を含める
  - **決定 2 と決定 3 は独立ではない**（田中の指摘 6。round 2 で内容を訂正）: 起案時に書いた
    「2 プロセスの共存窓」は誤りだった（`Stop="both"` により旧サービスは早期に停止する——決定 2
    参照）。実在する結合は、**新サービスを起動した後に旧製品のアンインストールが走る**という
    順序であり、ACL 付替の rollback CA がその時点で動くと**起動済みの新サービス**のアクセスを
    壊しうる。委任 2 の検証項目に含める
  - **着地順序を決めた代償**（round 2 クリスの指摘 4）: 決定 3 を先に着地させた後で決定 2 が
    採用されると、rollback CA を新しい順序（新サービス起動後にアンインストールが走る）の前提で
    **再検証する戻りが発生する**。それでも先行着地を選ぶのは、決定 2 の採否条件の確認が
    長引いた場合に確実に効く 2 つが止まる害の方が大きいためである
- 受け入れるリスク:
  - **遅延初期化の回復判定が失敗し続けると「復旧したのに使えないまま」になる**。縮退の
    **継続通知**と**回復通知**を対で採番し、§4.6 のゲージへ載せることで観測可能にする
    （鈴木の指摘 3）
  - gMSA 構成の DC 依存（サービス起動前に SCM がアカウントを解決できない場合）は**本 ADR の
    射程外**である。configuration.md が既に「この依存は構造的に解消できない——『受信を止めない』
    原則の適用範囲が SCM の外側で狭まる」と受容しており、本 ADR が扱うのは **SCM の内側**
    （プロセスが起動した後）の可用性である

## 先送りにする場合の再評価トリガ

本 ADR が却下（選択肢 A 維持）となった場合、以下のいずれかで再評価する:

- 実利用環境で「DB 障害中に再起動して受信が再開しなかった」実例が報告された場合
- アップグレード失敗による製品消失が実利用環境で発生した場合
- ADR-0006 の v1.0 公開判定で、基準 2 の重大不具合定義「③起動不能」に本件が該当すると
  裁定された場合

（決定 6 の ADR-0006 基準 4 に関する先送りの再評価トリガは、決定 6 の本文に記載した）

## 改訂履歴

### 1. 決定 2 の採否条件の判定 — **採用**（2026-07-26。委任 2 の実装 PR にて）

**分類**: 決定 2 が定めた手続き（「判定は委任 2 の実装 PR で行い、結果〔採用・撤回のいずれでも〕を
改訂履歴に残す」）の履行。決定本文は変更しない。

決定 2 は「まず採否条件（①〜②）を確認する。**不成立なら本決定は不採用とする**」と定めていた。
判定の結果、**両条件とも成立したため決定 2 を採用し、`Schedule="afterInstallExecute"` を実装した**。

**条件①（コンポーネント GUID の版間安定性）— 成立**。`HostPublishFiles` は
`<Files Include="$(PublishDir)\**">` の自動採番であり、版が変わると GUID が変わるなら
遅いスケジュールの参照カウントは崩れる。ビルドして `Component` テーブルを突き合わせた実測:

| 比較条件 | 結果 |
|---|---|
| 0.5.0 → 0.6.0（版のみ変更） | **419 コンポーネントが完全一致**（Component キー・ComponentId・Directory すべて） |
| 上記に加えファイル 1 件の追加 + 既存ファイルの内容変更 | **増分は新規 1 行のみ。既存 419 行の GUID は不変** |

自動採番はパス由来であり、版・ファイル内容・ファイル集合の変化に影響されない。実アップグレードは
版と中身の両方が変わるため、**2 段目（内容変更・ファイル追加）まで確認して初めて条件①が
満たされたと言える**。

**条件②（旧製品のアンインストールが新サービスを止めない・消さない）— 成立**。
`afterInstallExecute` により `RemoveExistingProducts` は `InstallExecute`（6500）と
`InstallFinalize`（6600）の間 = **`StartServices`（5900）より後**に入る。すなわち新サービスを
起動した後に旧製品のアンインストールが走り、これを防ぐのはコンポーネント参照カウントのみである。
**この条件は MSI テーブルの照合では確かめられない**ため、`installer-e2e` に実アップグレードの
シナリオを追加し、GitHub ホストランナー上の実測で判定した（run 30202340161）:

- 旧版（0.0.1）をインストール → Running を確認
- 新版（0.5.0）へメジャーアップグレード → 成功
- **`upgrade-service-survives`: サービス `Yagura` が Running のまま残存**（条件②の核心）
- `upgrade-single-product-entry`: 製品エントリは 1 件のみ・**ProductCode は変化**
  （= 実際にメジャーアップグレードが起きたことの確認。同一版の再インストールでは検証にならない）
- `upgrade-ingestion-still-works`: アップグレード後に UDP 受信 → 閲覧照合が成立

**継続検知**: 上記シナリオは `installer-e2e` の常設ステップとして残る（受け入れ基準⑤の
正常系側）。アップグレード元 MSI が見つからない場合は workflow が明示的に失敗する——黙って
スキップして緑になる経路を残さない。

**本判定が確定させた新しい不変条件**: 遅いスケジュールを採る以上、**コンポーネント GUID の
版間安定性は今後の変更で守るべき制約**になった（決定 2 の帰結「コンポーネント GUID の版間
安定性が新しい不変条件になる」の実効化）。ハーベスト方式の変更・明示 GUID の導入は、
この条件を再確認してから行う。

**未了**: 受け入れ基準⑤の**起動段を意図的に失敗させる細工**による「製品が残ること」の検証は
本判定には含まれない（正常系のアップグレードを先に固めた）。異常系は別途 `installer-e2e` へ
追加する。
