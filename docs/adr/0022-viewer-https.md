## 文脈と課題

閲覧 UI（TCP 8514）の HTTPS は、ADR-0004 決定 3 が予告した opt-in セキュリティ強化 3 点（TLS 受信・Web UI の HTTPS・AD 連携認証）のうち**最後の未提供項目**であり、v1.0 公開基準 1（ADR-0006）を閉じるために必須である。

証明書の取り扱いは configuration.md §6 で**確定済み**（Windows 証明書ストア参照方式のみ・選択時に秘密鍵の読み取り権限のみ付与・自己署名の生成支援はしない・期限切れ/失効時は HTTPS を停止し HTTP へ落とさない・復旧動線は loopback 管理面が担う）。本 ADR はその上に残っていた実装設計——**リスナ/ポート設計・設定キー・失敗時挙動・閲覧認証との関係・導入支援**——を確定する。主要な方向は Discussion #449 でオーナー裁定済み（2026-07-26）: ①8514 同一ポート切替、②最重要懸念は「対象利用者が証明書を用意できるか」、③閲覧認証有効時の HTTPS 必須化はしない（「手軽に導入できるツール」の立ち位置を確立する）、④HSTS 等の付帯機能は初版に含めない。

### スコープ（非目標）

- 証明書の取得・生成（ACME・自己署名生成等）は扱わない（configuration.md §6 で確定済み。参考手順は CF-D2 の文書レール）
- HSTS・HTTP/2 最適化・OCSP stapling 等の付帯機能は扱わない（オーナー裁定 ④）
- 管理リスナの HTTPS は扱わない（ADR-0010/0012 の領分。設定キーの独立は §6 確定——暗黙の連動はしない）
- クライアント証明書（相互 TLS）は扱わない（既存の意図的先送りのまま）

## 検討した選択肢

### A. リスナ/ポート設計

- **(a) 8514 を HTTPS へ切り替える（採用。オーナー裁定）**: opt-in 有効化で閲覧リスナ（`Viewer:HttpPort`。既定 8514）が平文 HTTP から HTTPS に変わる。ポートは増えず、インストーラが作る受信許可規則（ポート単位）も社内の案内資料もそのまま生きる。平文面が残らないため「暗号化したつもりが平文でも読める」状態を構造的に排除できる
- (b) HTTPS を別ポートに追加し平文 8514 を選択制で残す: 移行は緩やかだが、平文の残置を許すと opt-in の意味が薄れる。管理リスナが別ポート（8516）に分離したのは「loopback 平文 + リモート HTTPS の同一ポート共存が OS の bind 制約上不可能」（configuration.md §4.2）という制約ゆえであり、閲覧リスナには loopback 平文を残す要件がなく、この根拠が当てはまらない。**却下**
- (c) 平文要求を検知して 308 リダイレクトを返す経路の併設: 技術的には成立し得る（TLS ClientHello は先頭バイトで平文 HTTP と判別でき、平文検知 → リダイレクト変換を行う実装は他製品に実在する）。しかし**リダイレクト方式では、クライアントは応答を受け取る前に要求全体（パス・検索クエリ・Cookie）を平文で送信し終えている**——防げるのは平文の応答だけであり、「平文送信の排除」という opt-in の目的を達成しない。加えて Kestrel に組み込みの平文検知手段はなく、接続ミドルウェアの自作・維持を要する。**却下**（帰結: 旧 `http://` ブックマークは平文応答なしの断絶になる——緩和は決定 6。当初案が却下理由とした「同一ポートで平文応答と TLS は共存できない」という不可能性の断定は、ペルソナレビュー——クリス——の指摘で撤回し、上記の protocol 上の根拠に差し替えた）

### B. 証明書が使えないときの挙動（Enabled=true で拇印未設定・ストア解決不能・期限切れ/失効）

- (a) 起動失敗（管理リモートバインドの fail-closed 1012 と同型）: 閲覧 HTTPS の設定不備で**サービス全体が起動せず、syslog 受信まで止まる**。受信の停止はその瞬間のログの喪失そのものであり取り返しがつかない（security.md §6 が確定した「HTTPS = 停止 / TLS 受信 = 継続」の非対称の根拠と同じ判断軸）。管理リモートバインドの起動失敗が許されるのは、拒否しても loopback 管理面が無傷で本体機能（受信・保存・閲覧）に影響しないからであり、閲覧リスナには当てはまらない。**却下**
- (b) 平文 HTTP へフォールバック: configuration.md §6 が明示的に禁止済み（opt-in した環境の閲覧が証明書事故で黙って平文に戻ることを許さない）。**却下**
- **(c) 閲覧リスナのみ閉じて縮小継続（採用）**: 受信・解析・保存・スプール・管理リスナはすべて通常どおり動き、閲覧リスナ（8514）だけを開かない。可視化と復旧動線は決定 2 で確定する

### C. 閲覧認証との関係

- (a) 閲覧認証（`Viewer:Authentication:Windows:Enabled`）有効時に HTTPS を必須化（管理 UI のリモート公開時 HTTPS 必須と同型）: 認証 Cookie の平文送信を構造的に排除できるが、既存の「認証だけ有効」環境が v1.0 更新で閲覧不能になり（後方互換性の凍結——ADR-0006 基準 4——と衝突）、「認証だけ試したい」利用者の導入コストが跳ねる。**却下（オーナー裁定 ③）**——管理面の必須化は**書き込み権限**の防御であり fail-closed に足るが、閲覧面で連動強制すると「手軽に導入できるツール」の立ち位置を損なう。既定を軽く、強化を明示的に、の流儀を閲覧側では貫く
- **(b) 独立 opt-in + 併用推奨（採用）**: HTTPS と閲覧認証は互いに独立に有効化できる。`Viewer:Authentication:Windows:AdminGroups` を使う構成での管理等価 Cookie 平文送信リスクは、SECURITY.md の注意喚起 + CF-D2 の併用推奨 + 起動時警告（決定 5——連動強制ではなく可視化）で扱う

### D. 証明書更新への追従

- **(a) 拇印固定参照（採用）**: `Admin:Https:CertificateThumbprint`・`Ingestion:Tls:CertificateThumbprint` と同型。更新（拇印変化）のたびに UI での再選択が要る。ADR-0019 決定 4 が「選択の明示性を優先」として意図的に確定した扱いに揃える
- (b) サブジェクト等による更新後証明書への自動追従: 短寿命証明書（Let's Encrypt 等の 90 日級）との相性は良いが、意図しない証明書への無断切替の面を作る。**初版では却下**（再評価トリガへ——ADR-0019 の同項と統合的に扱う）

## 決定

### 1. 設定キーは 2 つだけ追加する — `Viewer:Https:Enabled`・`Viewer:Https:CertificateThumbprint`

- ポートキーは追加しない（選択肢 A (a)）。`Viewer:Https:Enabled = true` のとき、既存の閲覧リスナ（`Viewer:HttpPort`。既定 8514）が HTTPS で listen する。**`Viewer:HttpPort` のキー名は additive-only 規約（conventions.md）により改名しない**——「HTTPS 有効時はこのポートが HTTPS になる」旨を configuration.md §8 の同キー行に注記する（環境変数 `YAGURA_HTTP_PORT` の上書きも HTTPS 有効時は同ポートを支配する——名前と実態の乖離は §8 注記で先回りして塞ぐ。委任 2）
- §8 宣言（実装 PR で表へ登録する内容の骨子）: 反映方式はいずれも**再起動**（Kestrel の bind エントリは `WebApplicationBuilder` 構築時に固定——`Admin:Https:*` と同じ）。不正時挙動:
  - `CertificateThumbprint` は形式不正を未設定として扱う（正規化規則は `Admin:Https:CertificateThumbprint` と同型）。`Enabled=true` で拇印が未設定・解決不能なら決定 2 の縮小継続
  - `Enabled` が真偽値として不正な場合、**`CertificateThumbprint` が設定済み（= 利用者が HTTPS を意図した証跡がある）なら無効（平文）へ倒さず、決定 2 の縮小継続と同経路で閲覧リスナを開かない + 警告**。拇印も未設定なら無効へ + 警告（HTTPS が構成された形跡がなく、閲覧全停止は釣り合わない）。「緩い側へ倒せば暗号化の意図が黙って外れる」を無音にしない判断は `Notification:Email:Smtp:Security` の確定済み前例に従う（`Admin:Https:Enabled` の「不正値は無効へ」と異なるのは意図的——管理側は RemoteBinding との fail-closed 組み合わせ検証（1012）が最終防衛線として控えるため無効化が平文露出に直結しないが、閲覧側にその防衛線はない。ペルソナレビュー——田中・クリス——の指摘による訂正）
- **保存時は受信断のレールに乗る**（ADR-0012 決定 6・ADR-0019 決定 4 の流用）: 保存だけでは反映されない・反映は次回サービス再起動時・その間全受信が停止することを保存時に予告し（概算表示は ADR-0012 改訂 1 の撤回に追従——定性表示）、未反映変更は既存の再起動待ちキー機構（1020・/admin 常設カード）へ計上する。**管理 HTTPS・TLS 受信・閲覧 HTTPS の証明書変更を 1 回の再起動でまとめて反映できる**（証明書の年次更新の計画断を 1 回に集約できる——ペルソナレビュー——鈴木——の指摘で明文化）
- 最低 TLS バージョンは管理リモート HTTPS と同じ明示固定（TLS 1.2 以上・1.3 優先——security.md §2.4 と同型）とする

### 2. 失敗時挙動 — 「失敗時に受信を巻き添えにしない・平文へは決して落ちない・閲覧面は可視化つきで落ちてよい」

- `Viewer:Https:Enabled = true` で証明書が使えない場合（拇印未設定・形式不正・ストアで解決不能・期限切れ/失効・秘密鍵アクセス不能）、**起動時は閲覧リスナを開かない（縮小継続）**。起動失敗にはしない（選択肢 B の却下理由——受信を巻き添えにしない）。平文 HTTP では開かない（§6 確定の遵守）。なおこの三原則は失敗時挙動の宣言であり、**計画変更（有効化・証明書差し替え）の反映は再起動 = 計画受信断を伴う**（決定 1 のレールで予告・集約する）
- **稼働中の失効・期限切れは、管理 HTTPS の前例（`ServerCertificateSelector` が期限切れで null を返し新規ハンドシェイクを拒否する——security.md §2.5・§6）への整合を既定とする**。検出周期・接続確立済みの閲覧者（Blazor circuit）の扱い・外形監視から観測される状態（起動時縮小 = ポート閉 / 稼働中 = TCP accept + TLS ハンドシェイク失敗、の 2 態の明示）は委任 6 で確定する。乖離させる場合はその根拠を委任 6 で示す（起案時の「次回 bind 時から開かない」という記述は、再利用元の実挙動・§6 の「停止」との矛盾をペルソナレビュー——鈴木・リサ・クリス——に指摘され撤回した）
- 縮小継続の可視化は 3 層とする: **①起動時警告イベント + 稼働中は 1018 同型の周期監視（抑制窓つき）で継続的に記録**（ID は実装 PR で採番——委任 1。イベントレベルの吟味〔機能停止 = エラー側か〕を含む）、**②能動通知（メール通知の対象。原因が証明書であることと復旧手段〔サーバ上の管理画面〕を明記）**、**③管理画面（8515）の常設バナー**（「閲覧リスナ（8514）は証明書の問題で停止中。原因と復旧導線」——メール通知未設定の環境では RDP して管理画面を開いた瞬間に分かることが現実的な発見経路になるため。ペルソナレビュー——佐藤——の指摘）
- **復旧動線**: 閲覧系ルートは管理リスナ（8515・loopback）に同居しているため、8514 が閉じていてもサーバ上では閲覧・証明書差し替え・HTTPS 無効化のすべてが実行できる（configuration.md §6 の「復旧の動線は HTTPS 停止に巻き込まれない」の実装形）。ただしこの動線は**管理面の認証構成に従う**——`Admin:Authentication:RequireForLoopback = true` の構成では loopback でも認証が要り、Windows 統合認証のみ + DC 到達不能の状況では既存挙動（ADR-0010/0013）どおり認証が成立しない。本 ADR はこの既存の性質を変えない。また、管理リモート HTTPS（8516）を opt-in 済みで別証明書が健在な環境では、8516 経由のリモート閲覧が事実上の迂回路になり得る（管理 HTTPS 面は閲覧系ルートに到達できる——security.md §1）が、**設計上の保証には数えない**（リモート管理 opt-in 環境でも期限切れ時の復旧はサーバ上の操作が前提——CF-D2 に明記済みの帰結を維持する）

### 3. 証明書選択 UI は ADR-0012 設計の 3 回目の再利用（+ 本 ADR 固有の拡張 1 点）

- 列挙契約（serverAuth EKU + 秘密鍵あり・最小フィールド・read-only）・選択 UI・保存前 fail-closed 検証・「UI 事前検証と起動時検証の乖離ゼロ」・秘密鍵の読取検証 + 誘導（付与は試みない——lab 実測 2026-07-11 の縮退確定を流用）・テスト戦略を **ADR-0012/0019 から流用**する。列挙・検証の実装は既存 2 画面と共有し、三重実装しない（共有単位 = `CertificateProvider.Load`——#359 で中立名へ整理済み）。**本 ADR が加える拡張は決定 4 の SAN 助言検査のみ**であり、SAN 読み出しの契約配置（共有契約 `CertificateCandidate` への additive フィールド追加か、選択後の拇印による個別読み出しか）は委任 8 で確定する——いずれの場合も既存 2 画面（管理 HTTPS・TLS 受信）の表示・挙動は変えない
- **起動時の best-effort 秘密鍵権限付与（監査 2010 の機構）は閲覧 HTTPS 証明書も対象に含める**（管理 HTTPS・TLS 受信と同列。閲覧版の監査 ID 採番は委任 1——configuration.md §6 の「付与は監査記録の対象とする」との整合）
- **期限切れ証明書の保存は拒否側**とする（管理 HTTPS と同じ。TLS 受信の「警告付きで通す」とは異なる）——判断軸は ADR-0019 決定 2 が確定した非対称そのもの: 期限切れで**停止する**面（管理 HTTPS・閲覧 HTTPS）は保存を拒否し、**継続する**面（TLS 受信）は警告で通す
- 画面は閲覧 HTTPS 専用とし（管理 HTTPS・TLS 受信と同様に分離）、3 画面に相互リンクと用途の書き分け（「閲覧画面〔LAN のブラウザ → Yagura〕用」）を置く

### 4. 保存前検証の「警告して通す」側に SAN ホスト名整合の助言検査を追加する（本 ADR の新規拡張）

- ADR-0019 決定 2 が確立した「拒否する項目 / 警告して通す項目」の二分宣言に載せる: **拒否**側は ADR-0012 流用のまま（拇印未設定・証明書不在・秘密鍵不可・EKU 不適合 + 本 ADR の期限切れ〔決定 3〕）、**警告して通す**側に「SAN にサーバ自身の FQDN・NetBIOS 短名が含まれない」を追加する（保存は通す——利用者が閲覧に使う名前をサーバは断定できないため、助言に留める）
- 目的: 「証明書を入れたのにブラウザ警告が出続ける」典型事故（短名 `http://<サーバ名>:8514/` でのアクセス × FQDN のみの SAN）を**保存前に**潰す（Discussion #449 論点 2。オーナーの最重要懸念「証明書入手の壁」への製品側の直接の手当て——製品は証明書を「作る」支援はしないが「正しく選ぶ」支援はする）
- 警告文言には「この証明書ではどの URL でのアクセスが警告なしになるか」を SAN の実値から具体的に示す。**検査対象はホスト名のみであり、IP アドレスでのアクセスは検査対象外**（IP で開くと警告が出る）——この限界を本文・警告文言・CF-D2 の三方に明記し、IP SAN を検査対象に含めるかは委任 4 で判断する（ペルソナレビュー——佐藤——の指摘）
- 検査の実効性の限界と分岐は委任 4 で確定する: ①「SAN に短名があれば警告なしになる」という主張のブラウザ実機検証（GPO 配布ルート + 単一ラベル dNSName での Chrome/Edge、および Windows 証明書ストアを既定で見ない Firefox の扱い）を警告文言確定のゲートとする、②公的 CA 発行証明書は Baseline Requirements により internal name（単一ラベル名）を SAN に含められないため、**短名警告の抑制または文言分岐**を設ける（正しい証明書を選んだ利用者への全数警告は助言疲れで検査を無価値化する）、③ワイルドカード SAN の整合判定（ペルソナレビュー——クリス——の指摘）
- 警告の表示は保存時一度きりにせず、設定画面で保存後も現在の検査結果を確認できるようにする（委任 3）

### 5. 閲覧認証との関係 — 連動強制なし（独立 opt-in + 併用推奨 + 可視化）

- `Viewer:Https:*` と `Viewer:Authentication:Windows:*`・`Viewer:PublicAccess` は互いに独立。組み合わせによる起動失敗・強制無効化は入れない（選択肢 C。`PublicAccess = LocalhostOnly` × HTTPS 有効も単純に直交として扱う——意味は薄いが拒否しない）
- 管理 UI（リモート公開時 HTTPS 必須 = fail-closed）との非対称は**意図的**である: 管理面は書き込み権限の防御であり必須化に足るが、閲覧面の連動強制は「手軽に導入できるツール」の立ち位置（オーナー裁定 ③）を損ない、既存の「認証だけ有効」環境の互換も壊す
- **連動強制はしないが、無音にもしない**: `Viewer:Authentication:Windows:AdminGroups` が非空・`Viewer:Https:Enabled` が無効・`Viewer:PublicAccess` が `Lan` の組み合わせ（= 管理等価 Cookie が平文で LAN を流れ得る構成）は、**起動時警告イベント 1 件**（起動も機能も止めない。文言に HTTPS 併用の推奨と本 ADR の設定キーを含める）で可視化する。`ViewerGroups` のみの構成は警告対象外（焦点は管理等価 Cookie。警告のノイズ化を避ける——ペルソナレビュー——田中——の指摘による追加。これは可視化であり、オーナー裁定 ③ が却下した連動強制ではない）
- SECURITY.md・CF-D2 には「閲覧認証（特に `AdminGroups`）を使う構成では HTTPS の併用を推奨する」を明記する（現行の注意喚起を、解決手段の提示つきに更新する）

### 6. 旧 URL 断絶の緩和 — 事前告知と有効化時案内を受け入れ基準に含める

- 8514 切替の帰結として、有効化後は `http://<サーバ名>:8514/` への平文アクセスが平文応答なしの断絶になる（選択肢 A (c) の却下による受け入れ。ブラウザに表示される実際のエラー表示・自動 `https://` 再試行の有無は委任 3 の文言確定時に実機確認する）
- **有効化の保存時の案内**に次を含める: (a) 反映は次回サービス再起動時であること（保存直後に `https://` を試して開けないのは正常）、(b) 新しい閲覧 URL（環境変数上書き後の実効ポートで組み立てた `https://...`）のコピー可能な提示、(c) 既存のブックマーク・スタートメニュー/デスクトップショートカット・完了画面リンク・掲示板/キオスク端末の URL が古くなることの警告、(d) メール通知が無効の場合「期限切れの事前警告はイベントログにしか届かない」ことの指摘とメール通知設定への導線（決定 7 が「命綱」と位置づける以上、命綱の細さをここで可視化する——ペルソナレビュー——佐藤——の指摘）
- **保存から再起動までの間、まだ平文で稼働している閲覧 UI 自身に告知バナーを表示する**（「この URL はまもなく `https://...` に変わります。ブックマークの更新を」——再起動待ちキー機構〔#286〕の状態参照で成立し、新機構は不要。断絶コストを負担する閲覧者本人に届く唯一の window を使う——ペルソナレビュー——クリス——の指摘）
- インストーラが作成するショートカット・完了画面の URL は平文 `http://` 固定であり、インストール後の opt-in をインストーラは知り得ない（configuration.md §4.3 の管理リモート FW 規則と同じ構造）。ショートカットの自動更新は行わず、案内 + CF-D2 の手順（ショートカットの手動更新・社内周知テンプレート）で扱う

### 7. 期限接近の事前警告 — 既存機構の第 3 用途

- 証明書期限接近の能動通知（`CertificateExpiryWarningWindow`——管理リモート HTTPS・TLS 受信の共有閾値。#359 で中立化済み。仮値 30 日）に**閲覧 HTTPS 証明書を第 3 の用途として追加**する（`ICertificateStatusProbe` の閲覧版。イベント ID は実装 PR で採番——1014/1017 の閲覧版）。閾値は既存の共有値を使い、用途別の値は導入しない（#359 の判断——用途別の値を採用すべき設計上の根拠が無い——を踏襲）
- 閲覧 HTTPS は期限切れで**停止する**面のため、事前警告が実質的な命綱になる。メール通知（opt-in）の対象に含め、**通知文言には更新手順（CF-D2 の該当箇所）への参照を含める**（長寿命自己署名の運用では次に触るのが数年後の「手順を忘れた自分」になるため——ペルソナレビュー——佐藤——の指摘）

### 8. 利用者向け文書（CF-D2）の重心 — 「自己署名 + GPO ルート配布」

対象利用者（AD はあるが AD CS 未導入のひとり情シス——本製品のターゲットで最多と想定）が、追加投資ゼロ・既存スキル圏内でブラウザ警告なしに到達できる経路はこれだけである（Discussion #449 論点 2）。CF-D2（operations.md への申し送り）の構成方針を次のとおり確定する:

- **主経路の手順一式**: ①`New-SelfSignedCertificate` で **SAN に FQDN と NetBIOS 短名の両方**を入れ、**EKU を serverAuth に限定し CA フラグを持たせない形で生成コマンドを固定**（逸脱アレンジをしない旨の注意書き——鍵が漏えいした場合の影響範囲を「閲覧 UI の偽装」に限定する）、有効期間は長め（例 5 年——拇印固定参照〔選択肢 D〕の更新頻度を下げる）→ ②GPO「信頼されたルート証明機関」で全端末へ配布 → ③**certlm.msc での秘密鍵読み取り権限付与（`NT SERVICE\Yagura` を追加）と、UI の読取検証が緑になることの確認**（管理者が生成した鍵はサービスアカウントから読めないため、主経路の全員がこのステップを必ず通る——ペルソナレビュー——佐藤——の指摘で明文化。決定 3 の起動時 best-effort 付与が成功する環境では省略できる旨も記す）→ ④検証手順。**ルート配布とセットでのみ案内する**（「ブラウザ警告を無視して進む」手順は書かない——生成支援を提供しない理由〔§6〕を文書側でも守る）
- **撤去とセットでのみ案内する**（配布の対に撤去を置く）: 配布したルートの撤去手順（GPO からの削除 = 本経路における事実上の唯一の失効手段であることの明記）と、証明書の更新・Yagura 廃止時に旧証明書を GPO から外す棚卸しを、導入手順と同一文書に一体で載せる（ペルソナレビュー——田中——の指摘）
- **運用の期待値**: 所要時間の目安（GPO 反映待ち〔既定 90 分 + α・電源オフ端末は残る〕を含め、30 分ではなく半日仕事であること）・「GPO 伝播中は警告が残る端末があるのが正常」・**ファイアウォール規則には一切触らなくてよい**（ポート不変のため——「HTTPS にしたら FW も何かやるはず」という思い込みでの穴あけを予防）・更新 runbook（新ルートを配布し切ってから差し替える順序・30 日前通知から GPO 伝播 + 再選択 + 再起動までのリードタイム試算・生成手順と更新手順の一体記載〔数年後の失伝対策〕）
- AD CS 既設環境: テンプレートで発行する正道を短く案内する。**閲覧 HTTPS のためだけの AD CS 新設は勧めない**（誤設定時の攻撃面が大きく、ひとり情シスに勧める投資ではない）
- **短寿命証明書（Let's Encrypt 等の 90 日級）は初版では推奨しない**と明記する（拇印固定参照との相性——更新のたびに管理画面での再選択が要る。再評価トリガ参照）
- 非 AD（ワークグループ）環境: ルート配布が端末ごとの手作業になりコストが跳ねることを正直に書き、無理に HTTPS へ誘導しない（既定の平文 + 信頼ネットワーク前提の現行案内を維持——ADR-0004 の姿勢）

### 9. 「管理リモート HTTPS と同じ証明書を使う」ショートカットを置く

- 閲覧 HTTPS の証明書選択画面に、`Admin:Https:CertificateThumbprint` に設定済みの拇印を**明示操作でコピーする**ボタンを置く（設定済みの場合のみ表示）。設定キーの独立（暗黙の連動をしない——§6 確定）は崩さない——コピーは保存前の入力操作であり、以後の連動はない旨を画面に明記する
- **コピーされた拇印も通常の選択と同一の保存前検証 + SAN 助言検査を通る**（コピーが検査のバイパス経路にならない。管理用証明書の SAN に閲覧用の名前がないケースはむしろ起きやすく、そこで決定 4 の警告が出るのは意図どおり）
- 同一証明書の流用は §6 が認める形態であり、導入の手数を 1 段減らす（オーナー裁定の「手軽さ」への小さな寄与）

### 10. 監査

- `Viewer:Https:Enabled`・`Viewer:Https:CertificateThumbprint` の変更を独立イベント ID で記録する（2000 番台 additive。採番は実装 PR——SEC-5 のレール。2012〔管理 HTTPS〕・TLS 受信版と同型: 変更キーと新値〔拇印は公開識別子〕+ 操作者）
- 決定 3 の起動時 best-effort 秘密鍵権限付与の閲覧版（2010 同型）も監査対象に含める（委任 1）

### 11. 残存リスクの明記（ADR-0012 決定 8・ADR-0019 決定 6 の流用）

- 既定無認証 loopback で列挙 API・設定保存 API が到達可能である構造は本 ADR でも変わらない。**書き込み面は増える**: 既定無認証 loopback に到達できる任意のローカル実行主体（ADR-0010 が脅威モデルに明記）は、閲覧 HTTPS の無効化・拇印差し替えを保存でき、次回再起動で LAN 全体の閲覧経路（決定 5 により認証 Cookie を含み得る）が平文化する。事故モードは「見えるが平文であることには気づかない」（ブラウザは平文 HTTP に警告を出さない）点で無音に近い
- 緩和は既存構造に収まる: 反映は再起動時であり独立監査 ID（決定 10）が残り、loopback 認証 opt-in（`Admin:Authentication:RequireForLoopback`）で守れる。この収まりを SECURITY.md にも記載する（委任 7）

## 受け入れ基準

- opt-in 有効化後、8514 は HTTPS でのみ応答し、平文 HTTP の応答面が存在しない
- 証明書事故（期限切れ・解決不能・秘密鍵不可）で**受信・解析・保存・スプール・管理リスナが一切影響を受けない**——**起動時経路・稼働中検出経路の双方**を回帰テストで固定し、周期監視 probe・証明書解決の例外がプロセスを停止させないことを含める（Issue #345〔証明書鍵パス解決の未処理例外でプロセス停止〕の再発防止——ペルソナレビュー——鈴木——の指摘）
- 縮小継続時に警告イベント（起動時 + 稼働中の周期記録）+ 能動通知が出て、管理画面（8515）に常設バナーが表示され、管理リスナ経由でサーバ上の閲覧・復旧操作ができる
- 期限切れ証明書は保存前に拒否される（管理 HTTPS と同一。TLS 受信との挙動差分の説明が画面に表示される）
- SAN 助言検査が「警告して通す」側で機能する（サーバの FQDN/短名が SAN に無い証明書の保存時に、警告と「警告なしでアクセスできる URL」の提示が出る。保存は通る。保存後も検査結果を画面で確認できる）
- 閲覧認証（`Viewer:Authentication:Windows:*`）・公開範囲（`Viewer:PublicAccess`）と独立に有効化・無効化でき、いずれの組み合わせでも起動失敗しない。`AdminGroups` 非空 × HTTPS 無効 × `Lan` の構成では起動時警告イベントが 1 件出る
- 保存時に受信断の予告が表示され、未反映変更が再起動待ちカードに現れる。管理 HTTPS・TLS 受信・閲覧 HTTPS の変更が 1 回の再起動でまとめて反映できる
- 有効化の保存時に新しい閲覧 URL（実効ポート）と旧 URL 断絶の警告が表示され、再起動までの間、閲覧 UI に事前告知バナーが表示される
- 変更の監査記録（新 ID・対象 2 キー・新値・操作者）と、秘密鍵権限付与（best-effort）の監査記録が残る
- 期限接近が共有閾値（`CertificateExpiryWarningWindow`。仮値 30 日）に達した時点から能動通知（メール opt-in 併用時はメールも）が発火し、通知文言に更新手順への参照が含まれる
- 残存リスク（決定 11）が SECURITY.md に記載される

## 帰結

- 良くなること: v1.0 公開基準 1 が閉じる。閲覧経路（ログ本文・検索クエリ・認証 Cookie）の平文送信を opt-in で排除できる。証明書 UI・検証・秘密鍵誘導・期限監視の実装をすべて再利用するため、新規の設計リスクは小さい
- 悪くなること・受け入れるリスク:
  - **有効化・証明書差し替えの反映は再起動 = 計画受信断を伴う**（拇印固定参照のため証明書更新のたびに発生。長寿命自己署名の推奨と 3 面バッチ反映〔決定 1〕で頻度と回数を抑える）
  - 有効化後、旧 `http://` ブックマーク・ショートカットが平文応答なしで断絶する（決定 6 の事前告知バナー + 保存時案内で緩和。自動更新はしない）
  - 証明書事故時は LAN からの閲覧が止まる（受信は続く。8515 のサーバ上閲覧・3 層の可視化で緩和）。掲示板的な常時表示運用では、稼働中挙動（委任 6）の確定内容次第で「接続中の画面は生き続け、再接続の瞬間に消える」形になり得る——顕在化タイミングが非決定的であることは受け入れる（事前警告側〔決定 7〕を命綱とする）
  - 拇印固定参照のため、証明書更新のたびに管理画面での再選択 + 再起動が要る（短寿命証明書は再評価トリガへ）
  - 閲覧認証と HTTPS を連動強制しないため、「認証だけ有効・平文」の構成は引き続き作れる（意図的な受け入れ——決定 5。起動時警告 + 文書レールで可視化・推奨する）
  - TLS 終端の計算コスト: Blazor Interactive Server は接続確立後 WebSocket 常時接続であり、TLS ハンドシェイクは接続時のみ・以後は対称暗号のストリーム処理に留まる構造のため、想定規模（十数閲覧者）では受信パイプラインとの CPU 競合は無視できる**見込み**（実測はしていない——「閲覧が重いのは HTTPS のせいか」の切り分け根拠としてこの構造理解を残す）

## 先送りにする場合の再評価トリガ

- **サブジェクト等による更新後証明書への自動追従（選択肢 D (b)）**: 次のいずれか早い方で再評価する——(a) 短寿命証明書（期限接近警告が年 2 回以上発火する水準——概ね 180 日未満）が閲覧 HTTPS に設定される事象の検出（ADR-0019 の同項トリガと統合）、(b) 公的 CA の有効期間短縮（CA/Browser Forum の段階的短縮）で 100 日級が標準化した時点（2027 年目安）、**(c) 拇印変更監査イベント（決定 10 の新 ID）が示す再選択の実績、または再選択 + 再起動の運用負担に関する利用者 Issue**——(a) は決定 8 が短寿命証明書を非推奨とするため推奨に従う利用者からは発火しない。推奨経路と独立に発火するトリガとして (c) を置く（ペルソナレビュー——クリス——の指摘）
- **閲覧認証有効時の HTTPS 必須化（選択肢 C (a) の再検討）**: 後方互換を破る変更のため MAJOR バージョンでのみ検討する。トリガ: 平文 Cookie 起因の実被害・脆弱性報告が届いた場合、または閲覧認証利用環境の実態（試用報告・Issue・決定 5 の起動時警告への反応）で HTTPS 併用率が十分高く強制のコストが実質消えたと判断できる場合
- **HSTS 等の付帯機能**: 利用者からの具体的要望（Issue）を待つ受動トリガでよい（LAN 内利用が前提であり、公開 Web 向けの強化を先回りで積まない）
