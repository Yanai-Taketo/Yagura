# ADR-0022: 閲覧 UI の HTTPS 化（opt-in。8514 同一ポート切替。ADR-0006 基準 1 の最終残件）

- 状態: proposed
- 日付: 2026-07-26
- 決定者: YANAI Taketo
- 関連: [ADR-0004](0004-security-model.md) 決定 3（opt-in 強化 3 点の予告）/ [ADR-0006](0006-v1-release-criteria.md) 基準 1 / [ADR-0010](0010-admin-ui-authentication.md)（決定 4 = loopback 管理面は HTTPS 対象外・Phase 4 = 閲覧 UI 認証）/ [ADR-0012](0012-admin-https-cert-ui.md)・[ADR-0019](0019-ingestion-tls-cert-ui.md)（証明書選択 UI——本 ADR は 3 回目の再利用）/ [configuration.md](../design/configuration.md) §6（閲覧 HTTPS 証明書の確定済み設計）・§4.2・§8 / [security.md](../design/security.md) / Discussion #449（オーナー裁定 2026-07-26）

## 文脈と課題

閲覧 UI（TCP 8514）の HTTPS は、ADR-0004 決定 3 が予告した opt-in セキュリティ強化 3 点（TLS 受信・Web UI の HTTPS・AD 連携認証）のうち**最後の未提供項目**であり、v1.0 公開基準 1（ADR-0006）を閉じるために必須である。

証明書の取り扱いは configuration.md §6 で**確定済み**（Windows 証明書ストア参照方式のみ・選択時に秘密鍵の読み取り権限のみ付与・自己署名の生成支援はしない・期限切れ/失効時は HTTPS を停止し HTTP へ落とさない・復旧動線は loopback 管理面が担う）。本 ADR はその上に残っていた実装設計——**リスナ/ポート設計・設定キー・失敗時挙動・閲覧認証との関係・導入支援**——を確定する。主要な方向は Discussion #449 でオーナー裁定済み（2026-07-26）: ①8514 同一ポート切替、②最重要懸念は「対象利用者が証明書を用意できるか」、③閲覧認証有効時の HTTPS 必須化はしない（「手軽に導入できるツール」の立ち位置を確立する）、④HSTS 等の付帯機能は初版に含めない。

### スコープ（非目標）

- 証明書の取得・生成（ACME・自己署名生成等）は扱わない（configuration.md §6 で確定済み。参考手順は CF-D2 の文書レール）
- HSTS・HTTP/2 最適化・OCSP stapling 等の付帯機能は扱わない（オーナー裁定 ④）
- 管理リスナの HTTPS は扱わない（ADR-0010/0012 の領分。設定キーの独立は §6 確定——暗黙の連動はしない）
- クライアント証明書（相互 TLS）は扱わない（既存の意図的先送りのまま）

## 検討した選択肢

### A. リスナ/ポート設計

- **(a) 8514 を HTTPS へ切り替える（採用。オーナー裁定）**: opt-in 有効化で閲覧リスナ（`Viewer:HttpPort`。既定 8514）が平文 HTTP から HTTPS に変わる。ポートは増えず、インストーラが作る受信許可規則（ポート単位）も社内の案内資料もそのまま生きる。平文面が残らないため「暗号化したつもりが平文でも読める」状態を構造的に排除できる
- (b) HTTPS を別ポートに追加し平文 8514 を選択制で残す: 移行は緩やかだが、平文の残置を許すと opt-in の意味が薄れる。管理リスナが別ポート（8516）に分離したのは「loopback 平文 + リモート HTTPS の同一ポート共存が OS の bind 制約上不可能」（configuration.md §4.2）という制約ゆえであり、閲覧リスナには loopback 平文を残す要件がなく、この根拠が当てはまらない。**却下**
- (c) 平文で 308 リダイレクトを返す軽量リスナの併設: UX は良いが平文リスナの維持そのものであり (a) の原則と矛盾する。同一ポートで平文応答と TLS は共存できないため 8514 単一ポートとも両立しない。**却下**（帰結: 旧 `http://` ブックマークは不親切なブラウザエラーで断絶する——緩和は決定 6）

### B. 証明書が使えないときの挙動（Enabled=true で拇印未設定・ストア解決不能・期限切れ/失効）

- (a) 起動失敗（管理リモートバインドの fail-closed 1012 と同型）: 閲覧 HTTPS の設定不備で**サービス全体が起動せず、syslog 受信まで止まる**。受信の停止はその瞬間のログの喪失そのものであり取り返しがつかない（security.md §6 が確定した「HTTPS = 停止 / TLS 受信 = 継続」の非対称の根拠と同じ判断軸）。管理リモートバインドの起動失敗が許されるのは、拒否しても loopback 管理面が無傷で本体機能（受信・保存・閲覧）に影響しないからであり、閲覧リスナには当てはまらない。**却下**
- (b) 平文 HTTP へフォールバック: configuration.md §6 が明示的に禁止済み（opt-in した環境の閲覧が証明書事故で黙って平文に戻ることを許さない）。**却下**
- **(c) 閲覧リスナのみ閉じて縮小継続（採用）**: 受信・解析・保存・スプール・管理リスナはすべて通常どおり動き、閲覧リスナ（8514）だけを開かない。起動時警告イベント + 能動通知（メール対象）で可視化する。**サーバ上の閲覧は失われない**——閲覧系ルートは管理リスナ（8515・loopback）からも到達できる（configuration.md §4.2 M6-1）ため、復旧操作（証明書の差し替え・HTTPS の無効化）も閲覧確認も RDP + loopback で完結する

### C. 閲覧認証との関係

- (a) 閲覧認証（`Viewer:Authentication:Windows:Enabled`）有効時に HTTPS を必須化（管理 UI のリモート公開時 HTTPS 必須と同型）: 認証 Cookie の平文送信を構造的に排除できるが、既存の「認証だけ有効」環境が v1.0 更新で閲覧不能になり（後方互換性の凍結——ADR-0006 基準 4——と衝突）、「認証だけ試したい」利用者の導入コストが跳ねる。**却下（オーナー裁定 ③）**——管理面の必須化は**書き込み権限**の防御であり fail-closed に足るが、閲覧面で連動強制すると「手軽に導入できるツール」の立ち位置を損なう。既定を軽く、強化を明示的に、の流儀を閲覧側では貫く
- **(b) 独立 opt-in + 併用推奨（採用）**: HTTPS と閲覧認証は互いに独立に有効化できる。`Viewer:Authentication:Windows:AdminGroups` を使う構成での管理等価 Cookie 平文送信リスクは、SECURITY.md の注意喚起 + CF-D2 の併用推奨で扱う（現行の扱いを維持し、HTTPS という解決手段が増える）

### D. 証明書更新への追従

- **(a) 拇印固定参照（採用）**: `Admin:Https:CertificateThumbprint`・`Ingestion:Tls:CertificateThumbprint` と同型。更新（拇印変化）のたびに UI での再選択が要る。ADR-0019 決定 4 が「選択の明示性を優先」として意図的に確定した扱いに揃える
- (b) サブジェクト等による更新後証明書への自動追従: 短寿命証明書（Let's Encrypt 等の 90 日級）との相性は良いが、意図しない証明書への無断切替の面を作る。**初版では却下**（再評価トリガへ——ADR-0019 の同項と統合的に扱う）

## 決定

### 1. 設定キーは 2 つだけ追加する — `Viewer:Https:Enabled`・`Viewer:Https:CertificateThumbprint`

- ポートキーは追加しない（選択肢 A (a)）。`Viewer:Https:Enabled = true` のとき、既存の閲覧リスナ（`Viewer:HttpPort`。既定 8514）が HTTPS で listen する。**`Viewer:HttpPort` のキー名は additive-only 規約（conventions.md）により改名しない**——「HTTPS 有効時はこのポートが HTTPS になる」旨を configuration.md §8 の同キー行に注記する
- §8 宣言（実装 PR で表へ登録する内容の骨子）: 反映方式はいずれも**再起動**（Kestrel の bind エントリは `WebApplicationBuilder` 構築時に固定——`Admin:Https:*` と同じ）。不正時挙動: `Enabled` は真偽値として不正なら**無効へ + 警告**（`Admin:Https:Enabled` と同型）。`CertificateThumbprint` は形式不正を未設定として扱い（正規化規則も `Admin:Https:CertificateThumbprint` と同型）、`Enabled=true` で拇印が未設定・解決不能なら決定 2 の縮小継続
- 環境変数上書きは追加しない（既存方針の踏襲——上書き対象はポート系に限定されており、本 ADR はポートを追加しない）
- 最低 TLS バージョンは管理リモート HTTPS と同じ明示固定（TLS 1.2 以上・1.3 優先——security.md §2.4 と同型）とする

### 2. 失敗時挙動 — 「受信は決して止めない・平文へは決して落ちない・閲覧面は可視化つきで落ちてよい」

- `Viewer:Https:Enabled = true` で証明書が使えない場合（拇印未設定・形式不正・ストアで解決不能・期限切れ/失効・秘密鍵アクセス不能）、**閲覧リスナを開かない（稼働中に使えなくなった場合は次回 bind 時から開かない）**。起動失敗にはしない（選択肢 B の却下理由——受信を巻き添えにしない）。平文 HTTP では開かない（§6 確定の遵守）
- 縮小継続は**起動時警告イベント（ID は実装 PR で採番——1013/1016 の閲覧版）+ 能動通知（メール通知の対象）**で可視化する。「閲覧できない」は利用者が最初に気づく形の障害だが、通知には**原因（証明書）と復旧手段（サーバ上の管理画面）を明記**する
- **復旧動線**: 閲覧系ルートは管理リスナ（8515・loopback）に同居しているため、8514 が閉じていてもサーバ上では閲覧・証明書差し替え・HTTPS 無効化のすべてが実行できる（configuration.md §6 の「復旧の動線は HTTPS 停止に巻き込まれない」の実装形）。リモート管理 opt-in 環境でも期限切れ時の復旧はサーバ上の操作（RDP + loopback）が前提になる——CF-D2 に明記済みの帰結を閲覧 HTTPS にもそのまま適用する

### 3. 証明書選択 UI は ADR-0012 設計の 3 回目の再利用

- 列挙契約（serverAuth EKU + 秘密鍵あり・最小フィールド・read-only）・選択 UI・保存前 fail-closed 検証・「UI 事前検証と起動時検証の乖離ゼロ」・秘密鍵の読取検証 + 誘導（付与は試みない——lab 実測 2026-07-11 の縮退確定を流用）・テスト戦略を **ADR-0012/0019 からそのまま流用**し、対象キーと縮小継続の警告経路だけ差し替える。列挙・検証の実装は既存 2 画面と共有し、三重実装しない（共有単位 = `CertificateProvider.Load`——#359 で中立名へ整理済み）
- **期限切れ証明書の保存は拒否側**とする（管理 HTTPS と同じ。TLS 受信の「警告付きで通す」とは異なる）——判断軸は ADR-0019 決定 2 が確定した非対称そのもの: 期限切れで**停止する**面（管理 HTTPS・閲覧 HTTPS）は保存を拒否し、**継続する**面（TLS 受信）は警告で通す
- 画面は閲覧 HTTPS 専用とし（管理 HTTPS・TLS 受信と同様に分離）、3 画面に相互リンクと用途の書き分け（「閲覧画面〔LAN のブラウザ → Yagura〕用」）を置く

### 4. 選択時検査に「SAN ホスト名整合の助言検査」を追加する（本 ADR の新規拡張）

- ADR-0012 の検証項目（EKU・秘密鍵・期限）に加え、**選択された証明書の SAN にサーバ自身の FQDN・NetBIOS 短名が含まれるかを検査し、含まれない名前を警告表示する**（保存は通す——利用者が閲覧に使う名前をサーバは断定できないため、助言に留める）
- 目的: 「証明書を入れたのにブラウザ警告が出続ける」典型事故（短名 `http://<サーバ名>:8514/` でのアクセス × FQDN のみの SAN）を**選択時点で**潰す（Discussion #449 論点 2。オーナーの最重要懸念「証明書入手の壁」への製品側の直接の手当て——製品は証明書を「作る」支援はしないが「正しく選ぶ」支援はする）
- 警告文言には「この証明書ではどの URL でのアクセスが警告なしになるか」を SAN の実値から具体的に示す

### 5. 閲覧認証との関係 — 連動強制なし（独立 opt-in + 併用推奨）

- `Viewer:Https:*` と `Viewer:Authentication:Windows:*` は互いに独立。組み合わせによる起動失敗・強制無効化は入れない（選択肢 C）
- 管理 UI（リモート公開時 HTTPS 必須 = fail-closed）との非対称は**意図的**である: 管理面は書き込み権限の防御であり必須化に足るが、閲覧面の連動強制は「手軽に導入できるツール」の立ち位置（オーナー裁定 ③）を損ない、既存の「認証だけ有効」環境の互換も壊す
- SECURITY.md・CF-D2 には「閲覧認証（特に `AdminGroups`）を使う構成では HTTPS の併用を推奨する」を明記する（現行の注意喚起を、解決手段の提示つきに更新する）

### 6. 旧 URL 断絶の緩和 — 有効化時の案内を受け入れ基準に含める

- 8514 切替の帰結として、有効化後は `http://<サーバ名>:8514/` への平文アクセスが不親切なブラウザエラーになる（選択肢 A (c) の却下による受け入れ）。緩和として、**有効化の保存時に新しい閲覧 URL（`https://...`）を画面へ明示し、既存のブックマーク・スタートメニュー/デスクトップショートカット・完了画面リンクが古くなることを警告する**
- インストーラが作成するショートカット・完了画面の URL は平文 `http://` 固定であり、インストール後の opt-in をインストーラは知り得ない（configuration.md §4.3 の管理リモート FW 規則と同じ構造）。ショートカットの自動更新は行わず、案内 + CF-D2 の手順（ショートカットの手動更新）で扱う

### 7. 期限接近の事前警告 — 既存機構の第 3 用途

- 証明書期限接近の能動通知（`CertificateExpiryWarningWindow` = 共有 30 日。#359 で両用途共有として中立化済み）に**閲覧 HTTPS 証明書を第 3 の用途として追加**する（`ICertificateStatusProbe` の閲覧版。イベント ID は実装 PR で採番——1014/1017 の閲覧版）。閾値は既存の共有値を使い、用途別の値は導入しない（#359 の判断——用途別の値を採用すべき設計上の根拠が無い——を踏襲）
- 閲覧 HTTPS は期限切れで**停止する**面のため、事前警告が実質的な命綱になる。メール通知（opt-in）の対象に含める

### 8. 利用者向け文書（CF-D2）の重心 — 「自己署名 + GPO ルート配布」

対象利用者（AD はあるが AD CS 未導入のひとり情シス——本製品のターゲットで最多と想定）が、追加投資ゼロ・既存スキル圏内でブラウザ警告なしに到達できる経路はこれだけである（Discussion #449 論点 2）。CF-D2（operations.md への申し送り）の構成方針を次のとおり確定する:

- **主経路 = 自己署名 + GPO ルート配布**: `New-SelfSignedCertificate` で **SAN に FQDN と NetBIOS 短名の両方**を入れ、有効期間を長め（例 5 年——拇印固定参照〔選択肢 D〕の更新頻度を下げる）に取り、GPO「信頼されたルート証明機関」で全端末へ配布する。貼って動く PowerShell・GPO 手順・検証手順を一式で載せる。**ルート配布とセットでのみ案内する**（「ブラウザ警告を無視して進む」手順は書かない——生成支援を提供しない理由〔§6〕を文書側でも守る）
- AD CS 既設環境: テンプレートで発行する正道を短く案内する。**閲覧 HTTPS のためだけの AD CS 新設は勧めない**（誤設定時の攻撃面が大きく、ひとり情シスに勧める投資ではない）
- **短寿命証明書（Let's Encrypt 等の 90 日級）は初版では推奨しない**と明記する（拇印固定参照との相性——更新のたびに管理画面での再選択が要る。再評価トリガ参照）
- 非 AD（ワークグループ）環境: ルート配布が端末ごとの手作業になりコストが跳ねることを正直に書き、無理に HTTPS へ誘導しない（既定の平文 + 信頼ネットワーク前提の現行案内を維持——ADR-0004 の姿勢）

### 9. 「管理リモート HTTPS と同じ証明書を使う」ショートカットを置く

- 閲覧 HTTPS の証明書選択画面に、`Admin:Https:CertificateThumbprint` に設定済みの拇印を**明示操作でコピーする**ボタンを置く（設定済みの場合のみ表示）。設定キーの独立（暗黙の連動をしない——§6 確定）は崩さない——コピーは保存前の入力操作であり、以後の連動はない旨を画面に明記する
- 同一証明書の流用は §6 が認める形態であり、導入の手数を 1 段減らす（オーナー裁定の「手軽さ」への小さな寄与）

### 10. 監査

- `Viewer:Https:Enabled`・`Viewer:Https:CertificateThumbprint` の変更を独立イベント ID で記録する（2000 番台 additive。採番は実装 PR——SEC-5 のレール。2012〔管理 HTTPS〕・TLS 受信版と同型: 変更キーと新値〔拇印は公開識別子〕+ 操作者）

## 受け入れ基準

- opt-in 有効化後、8514 は HTTPS でのみ応答し、平文 HTTP の応答面が存在しない
- 証明書事故（期限切れ・解決不能・秘密鍵不可）で**受信・解析・保存・スプール・管理リスナが一切影響を受けない**（回帰テストで固定）
- 縮小継続時に警告イベント + 能動通知が出て、管理リスナ（8515）経由でサーバ上の閲覧・復旧操作ができる
- 期限切れ証明書は保存前に拒否される（管理 HTTPS と同一。TLS 受信との挙動差分の説明が画面に表示される）
- SAN 助言検査が機能する（サーバの FQDN/短名が SAN に無い証明書の選択時に、警告と「警告なしでアクセスできる URL」の提示が出る。保存は通る）
- 閲覧認証（`Viewer:Authentication:Windows:*`）と独立に有効化・無効化でき、いずれの組み合わせでも起動失敗しない
- 有効化の保存時に新しい閲覧 URL と旧 URL 断絶の警告が表示される
- 変更の監査記録（新 ID・対象 2 キー・新値・操作者）が残る
- 期限接近 30 日前から能動通知（メール opt-in 併用時はメールも）が発火する

## 帰結

- 良くなること: v1.0 公開基準 1 が閉じる。閲覧経路（ログ本文・検索クエリ・認証 Cookie）の平文送信を opt-in で排除できる。証明書 UI・検証・秘密鍵誘導・期限監視の実装をすべて再利用するため、新規の設計リスクは小さい
- 悪くなること・受け入れるリスク:
  - 有効化後、旧 `http://` ブックマーク・ショートカットが不親切なエラーで断絶する（決定 6 の案内で緩和。自動更新はしない）
  - 証明書事故時は LAN からの閲覧が止まる（受信は続く。8515 のサーバ上閲覧と能動通知で緩和）。掲示板的な常時表示運用では「表示が消える」形で現れる
  - 拇印固定参照のため、証明書更新のたびに管理画面での再選択 + 再起動が要る（自己署名長寿命の推奨で頻度を下げる。短寿命証明書は再評価トリガへ)
  - 閲覧認証と HTTPS を連動強制しないため、「認証だけ有効・平文」の構成は引き続き作れる（意図的な受け入れ——決定 5。文書レールで併用を推奨)

## 先送りにする場合の再評価トリガ

- **サブジェクト等による更新後証明書への自動追従（選択肢 D (b)）**: ADR-0019 の同項トリガと統合して扱う——(a) 短寿命証明書（期限接近警告が年 2 回以上発火する水準——概ね 180 日未満）が閲覧 HTTPS に設定される事象の検出、(b) 公的 CA の有効期間短縮（CA/Browser Forum の段階的短縮）で 100 日級が標準化した時点（2027 年目安）、のいずれか早い方
- **閲覧認証有効時の HTTPS 必須化（選択肢 C (a) の再検討）**: 後方互換を破る変更のため MAJOR バージョンでのみ検討する。トリガ: 平文 Cookie 起因の実被害・脆弱性報告が届いた場合、または閲覧認証利用環境の実態（試用報告・Issue）で HTTPS 併用率が十分高く強制のコストが実質消えたと判断できる場合
- **HSTS 等の付帯機能**: 利用者からの具体的要望（Issue）を待つ受動トリガでよい（LAN 内利用が前提であり、公開 Web 向けの強化を先回りで積まない）
