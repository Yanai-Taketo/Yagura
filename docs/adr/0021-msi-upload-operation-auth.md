# ADR-0021: フォワーダ MSI アップロードの前提条件の変更 — RequireForLoopback 必須からアップロード操作単位の実認証必須へ

- 状態: proposed
- 日付: 2026-07-26
- 決定者: YANAI Taketo
- 関連: [ADR-0020](0020-forwarder-msi-upload.md)（決定 1 の有効化条件 (ii) = 本 ADR の部分 supersession 対象）/ [ADR-0010](0010-admin-ui-authentication.md)（決定 1 の loopback 認証 opt-in と復旧経路の代償）/ [ADR-0013](0013-admin-winauth-session.md)（Cookie/circuit ログインフロー——操作単位認可の実装基盤）/ [ADR-0011](0011-app-auth-failure-backoff.md)（失敗試行対策の loopback 除外）/ [ADR-0001](0001-project-founding.md)（「Windows 管理者が GUI で完結」の思想）/ [Issue #440](https://github.com/Yanai-Taketo/Yagura/issues/440)（起案元。lab 受け入れ初回実施の体験記録）/ Issue #283（ADR-0020 の再起案元。loopback 到達主体の実機棚卸し）/ [security.md](../design/security.md) §5.1.1 / [configuration.md](../design/configuration.md) §8

## 文脈と課題

### lab 受け入れ初回実施で観測された利用障壁（2026-07-26。Issue #440）

ADR-0020 決定 5 の lab 受け入れ検証を初回実施した際、フォワーダ MSI アップロード機能への
到達までに次の手順連鎖が必要だった:

1. 管理 UI 認証の有効化（GUI）
2. `Admin:Authentication:RequireForLoopback = true`（GUI。ただしロックアウトリスク警告つき）
3. ロックアウト対策の非常口アプリアカウント作成（パスワード 12 文字以上）
4. `Admin:ForwarderKit:MsiUpload:Enabled` の**設定ファイル手編集**（GUI なし）+ サービス再起動
5. `icacls` による ACE 付与（ターミナル）

GUI・設定ファイル・ターミナルの 3 操作面をまたぎ、「Windows 管理者が既に持つスキルだけで
導入・運用できる」というプロジェクト思想（ADR-0001）から乖離している。オーナーからも
「簡単に使えるを目標とした Yagura において複雑になりすぎている」
「ローカル 8515 ではアップロードを使えてもよいのでは（リモートは現行どおり）」という
問題提起があった（Issue #440）。

### 現行設計が (ii) RequireForLoopback を要求している理由の再確認

ADR-0020 決定 1 の条件 (ii) は「管理リスナに無認証の到達経路が存在しない」ことを構成で
保証するために置かれた。その動機は、無認証 loopback の暗黙プリンシパルでも既存の
管理ポリシー（`RequireAuthorization(AdminPolicy)`）が通ってしまうことにある——
無認証 loopback 構成では「認可済み = loopback から来た」でしかなく、
アップロード操作の主体を特定できない（ADR-0020 却下理由 2 の構造）。

つまり (ii) が守っているのは**アップロード操作の身元保証**であって、管理リスナ全体の
認証状態そのものではない。リスナ全体を守る手段（RequireForLoopback）で操作単位の要件を
満たしているため、本来不要な代償——ADR-0010 決定 1 の復旧経路の代償（認証手段全滅時の
復旧 = 設定ファイル手編集 + サービス再起動 = **syslog 受信断**）——まで輸入している。
ADR-0020 帰結はこの輸入を「知らずに交換させない」形で受容したが、lab 初回実施は
「知っていても重い」ことを示した。

### 脅威分析 — 「loopback なら無条件で許可」にできない理由

オーナー問題提起の直截な解釈（無認証 loopback ならアップロード可）は採れない。
ADR-0020 の実機棚卸し（Issue #283）が確定させたとおり:

- loopback 8515 に到達できる主体は、コンソールの管理者だけでなく**サーバ上の全ローカル
  プロセス・非管理者ユーザーを含む**（実測でサービスプロセス 93 個が到達可能。
  メンバーサーバでは既定で `BUILTIN\Users` = Domain Users 全員が対話ログオン権を持つ）
- `forwarder` フォルダの ACL は SYSTEM / Administrators / サービスアカウントのみ。
  非管理者ローカルユーザーは**直接には**書き込めない（security.md §5.1）
- 無認証 loopback でアップロードが使えると、書込 ACE を持つ**サービスプロセスが代行書き込み**
  するため、「非管理者ローカルプロセス → 全端末配布 MSI の差し替え」という**権限昇格経路**が
  開く。配布先では企業配布基盤経由で SYSTEM 権限インストールされ得る

よって「**無認証経路から MSI 書き込み口へ到達できない**」という ADR-0020 決定 1 の
fail-closed 不変条件そのものは維持しなければならない。変えるべきは不変条件ではなく、
その担保の単位——リスナ全体か、アップロード操作か——である。

## 検討した選択肢

### 選択肢 A: 現状維持（RequireForLoopback 必須のまま）

- 利点: 実装変更ゼロ。「管理リスナの全経路が認証済み」というより強い保証が既に成立している
- 欠点: 本機能のためだけに loopback 認証 opt-in とその復旧代償（受信断リスク・非常口
  アカウント運用）を輸入し続ける。操作面が GUI・設定ファイル・ターミナルの 3 面に分散した
  まま。lab 初回実施が示した利用障壁がそのまま残り、ADR-0020 決定 6 の効果測定
  （利用実態レビュー）が「使われない」側へ傾く要因を設計自身が作っている
- 却下（ただし本 ADR が却下された場合の受け皿として現行設計は成立し続ける）

### 選択肢 B: 無認証 loopback でのアップロード許可（リモートのみ認証必須）

- オーナー問題提起の直截な解釈。利点は導入手数の最小化
- 却下: 上記の脅威分析のとおり、無認証 loopback の到達主体は「このホストでコードを実行
  できる者」全体であり、サービスの書込 ACE を踏み台にした権限昇格経路（非管理者ローカル
  プロセス → 全端末配布 MSI 差し替え）が開く。ADR-0020 決定 1 の不変条件の放棄であり、
  却下理由 2（操作者の身元保証の構造的不成立）の再来でもある。検討の俎上に載せない

### 選択肢 C: アップロード操作単位の実認証必須（採用）

守る対象を「リスナ全体」から「アップロード操作」へ絞る:

- アップロード系操作専用の認可ポリシーを新設し、「暗黙の loopback プリンシパルを拒否し、
  実際にサインインした管理者のみ許可」とする
- `RequireForLoopback = true` を前提条件から撤廃する（認証手段が最低 1 つ構成済みである
  ことは引き続き要求する）
- loopback の閲覧・通常管理は従来どおり無認証のまま（ゼロ設定思想を維持）。アップロードを
  使うときだけその場でサインインする（Windows 統合認証なら実質ワンクリック——ADR-0013 の
  ログインフローに乗る）
- 利点: 不変条件（無認証経路から書き込み口へ到達不能）を**操作単位の認可で維持**しつつ、
  ロックアウトリスクの輸入と操作面の分散を解消する。監査の「誰が」欄も引き続き必ず実名が入る
- 欠点: 専用ポリシーという新しい実装・テスト面が増える。「同じ画面の中で認証状態が操作に
  よって異なる」という UI 状態が生まれる（帰結参照）

## 決定

選択肢 C を採用する。ADR-0020 決定 1 の有効化条件 (ii) を部分 supersede する。
それ以外の ADR-0020 の決定（決定 2 の ACL 開放統制・決定 3 の操作仕様・決定 4 の監査・
決定 5 の受け入れ基準・決定 6 の効果測定・決定 7 の supersession 範囲）は**すべて不変**である。

### 1. アップロード操作専用の認可ポリシー

- **対象操作**: stage（アップロード本文の受理）・commit・discard・delete、および
  アップロード用 antiforgery トークンの配布。すなわち配置フォルダへの書き込み・削除に
  つながる全操作と、その入口
- **判定**: 「実際にサインインした管理者」のみ許可する——Windows 統合認証
  （Negotiate/Kerberos）またはアプリ独自認証で認証済みのプリンシパルが管理役割
  （既定 `BUILTIN\Administrators` SID 判定・AD 管理グループ・アプリ独自アカウント——既存の
  管理認可判定そのまま）を保持していること。**無認証 loopback の暗黙プリンシパルは、
  管理ポリシーが通る構成であっても本ポリシーでは拒否する**
- **実装面**: HTTP エンドポイント（stage）は専用ポリシーの `RequireAuthorization` で守る。
  Blazor circuit 側の操作（commit / discard / delete）は circuit の認証状態
  （ADR-0013 の Cookie/circuit ログインフローで汲み直された認証済みプリンシパル）で
  同じ判定を行う。判定ロジックは HTTP 側・circuit 側で単一実装を共有する
  （検出/アップロードの版読み取りを単一ソースにしたのと同じ流儀）
- **閲覧・通常管理への影響なし**: 本ポリシーはアップロード系操作にのみ適用する。
  loopback の無認証閲覧・通常管理操作（`RequireForLoopback = false` 構成）は従来どおり

### 2. 有効化条件の改訂（ADR-0020 決定 1 の条件 (ii) の撤廃）

アップロード機能（配置経路 (b)）の有効化条件を次の 2 条件へ改める:

- **(i) 管理 UI 認証が有効**: Windows 統合認証・アプリ独自認証の少なくとも一方が有効
  （不変。サインインの手段が存在しなければ操作単位認可は誰も通過できないため、
  引き続き前提条件である）
- **(iii) アップロード機能自体の明示 opt-in**: `Admin:ForwarderKit:MsiUpload:Enabled`
  （不変。既定 `false`）

**(ii) `Admin:Authentication:RequireForLoopback = true` は前提条件から撤廃する**。
`RequireForLoopback` 自体の機能・意味（ADR-0010 決定 1）は一切変更しない——管理リスナ
全体を認証必須にしたい環境は引き続き有効化でき、その構成でも本機能は当然に動作する。

付随する改訂:

- **fail-closed（起動時。イベント ID 1032）**: 拒否条件を「(iii) 有効 + (i) 不成立」へ
  変更する。エラーメッセージの復旧誘導（本キーを `false` に戻す）は不変
- **fail-closed（UI）**: 逆方向の対称防御も (i)(iii) の 2 条件へ追随する（(iii) 有効の
  稼働構成で (i) を無効化する設定変更は書き込み前に UI レベルで拒否——不変条件の維持）
- **エンドポイントの構造的非存在**（条件不成立時は登録自体を省略。無効構成では 404）は
  判定条件が (i)(iii) に変わるのみで機構は不変
- **UI 表出**: 生成画面の条件案内から (ii) 関連——RequireForLoopback の有効化案内・
  ロックアウト代償の提示・ブレークグラス強推奨——を**本機能の文脈からは**除去する
  （ADR-0010 決定 1 の代償の記述自体は認証設定画面の管轄として残る）。代わりに、
  (i)(iii) 成立 + 未サインインの状態では「アップロード操作にはサインインが必要」の案内と
  サインイン動線を表示する（条件不成立時に沈黙にしない流儀は不変）

### 3. 不変条件の維持宣言と ADR-0011 整合

- **「無認証経路から MSI 書き込み口へ到達できない」は維持される**: 担保が
  「リスナ全体の認証必須（構成レベル）」から「アップロード操作の実認証必須（操作レベル）」へ
  移るだけで、無認証の主体が書き込み口に到達できない事実は変わらない。ADR-0020 の
  却下理由 2（操作者特定の構造的不成立）への回答——監査 2026/2027 の「誰が」欄に必ず
  認証済み利用者名が入る——も維持される（本ポリシーを通過した操作は定義上すべて認証済み）
- **ADR-0011 決定 4（loopback は IP レート制限・グローバルトークンバケットの対象外）は
  不変**: (ii) 撤廃により「loopback からアプリ独自認証への低速試行が③バックオフのみに
  律速される」露出の議論（ADR-0020 決定 1）は前提ごと変化するが、受容の構造は同じ——
  ローカル実行主体による試行は監査（3004/3006）・1019 昇格で観測される。なお本 ADR は
  ADR-0020 と異なり RequireForLoopback の有効化を促さないため、この露出が新たに生じる
  環境はむしろ減る
- **ADR-0020 決定 2（ACL 開放は OS 管理者の明示 `icacls` 操作のみ）は不変**: 書き込みの
  物理的成立には引き続き ACE 付与が必要であり、「使うときだけ開く」運用・二系統の ACL 検出
  （1033/1034）・開放状態の常時表示はそのまま適用される。操作面の分散は 3 面 → 2 面
  （GUI + ターミナル）に減るが、ACE 付与のターミナル操作は本 ADR の対象外として維持する
  （書き込み口の物理的開閉を OS レベルの身元保証に残す構造は B-2 採用の核心であり、
  ここを UI 化すると ADR-0020 選択肢 B-2 の却下理由が再来する）

### 4. 設定動線の改善（(iii) の GUI トグル化）の委任

lab 初回実施の手順 4（設定ファイル手編集 + 再起動）も操作面分散の一因である。
`Admin:ForwarderKit:MsiUpload:Enabled` の管理画面トグル化（1032 の fail-closed 検証は
UI 書き込み前判定として維持）を本改訂の実装と同時に検討する（委任 2）。
ADR-0020 委任 1 の「(i)〜(iii) の有効化が管理画面から完結する設定動線」の残課題を、
条件が 2 つに減った本改訂の下で消化する位置づけである。

## 帰結

- 良くなること:
  - **ロックアウトリスクの輸入が消える**: 本機能のために `RequireForLoopback` を有効化する
    必要がなくなり、ADR-0010 決定 1 の復旧代償（受信断）・非常口アカウント運用を
    本機能の利用者が背負わなくなる
  - **操作面の分散が減る**: RequireForLoopback 関連の手順（lab 初回実施の手順 2・3）が
    消滅する。委任 2（GUI トグル化）が成立すれば、残るターミナル操作は ACE 付与のみになる
  - **監査の「誰が」欄は常に実名のまま**（不変条件の維持）。かつ ADR-0020 構成より
    サインインの時点が操作に近づくため、「その操作のために認証した」ことが証跡上明確になる
  - リモート経路（8516。認証 + HTTPS 必須）は変更なし
- 悪くなること（受け入れるトレードオフ）:
  - **専用認可ポリシーという新しい実装・テスト面が増える**: 「暗黙 loopback プリンシパルの
    拒否」が HTTP 側・circuit 側の両方で正しく効くことの回帰テスト（決定 5 相当の受け入れ
    基準——委任 1）が必須になる。判定の単一実装共有はその緩和である
  - **同一画面内の認証状態の非対称**: 無認証 loopback で生成画面を開けるが、アップロード節
    だけはサインインを要する。「なぜこの操作だけ」の説明責務が UI に生じる（決定 2 の
    案内文言で対処。委任 1）
  - ADR-0020 が持っていた「管理リスナ全体が認証済み」という**より強い保証は、本機能の
    前提としては**失われる（RequireForLoopback を自ら有効化する環境では引き続き成立する）。
    本機能が必要とするのは操作単位の保証であることを本 ADR の脅威分析で確認済みであり、
    リスナ全体の認証はそれ自体の判断として ADR-0010 の管轄に戻る
- 受け入れるリスク:
  - プロセス侵害シナリオ（ADR-0020 帰結）の残余リスクは本改訂で増減しない——認証・監査を
    プロセス自身が握る限界も、SACL・外部コピーが実効的な独立証跡である事実も不変
  - Windows 統合認証が構成できない・アプリ独自認証のパスワード運用を避けたい環境にとって、
    (i) が引き続き参入条件になる。これは意図的である——全端末に配布される MSI の差し替え口
    に身元保証なしの経路を作らない（選択肢 B の却下理由）

## ADR-0020 決定 6（効果測定）との関係

本改訂は利用障壁を下げる変更であり、ADR-0020 決定 6 の利用実態レビュー（v1.0 公開後
6 ヶ月以内目安）は**本改訂の実装がリリースに載った後の実態**で評価するのが公平である
（Issue #440 の整理のとおり）。撤回基準・期限の枠組み自体は変更しない。

## 先送りにする場合の再評価トリガ

本 ADR が却下（選択肢 A 維持）となった場合、以下のいずれかで再評価する:

- ADR-0020 決定 6 の利用実態レビューで「前提条件の重さ」が不使用の主因として観測された場合
- RequireForLoopback 有効化に起因するロックアウト・受信断の実例が報告された場合
- 閲覧 UI 認証を含む認証運用が既定化する方向の再評価（ADR-0004 の既存トリガ）が成立した場合
