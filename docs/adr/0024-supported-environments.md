## 文脈と課題

v1.0 は利用者に対する「本番利用を推奨できる」という宣言である（ADR-0006）。しかし現時点の Yagura は、**動作環境を利用者に一切表明していない**。README にあるのは ADR-0009 が定めた対応アーキテクチャ表（x64 = 対応 / ARM64 = 試験的）だけで、**OS のバージョン・SQL Server のバージョン・ブラウザ・ハードウェアの要件はどの文書にも存在しない**。

ADR-0009 委任事項 7 は「README のシステム要件表をアーキ別に更新する」と書いたが、実際にはシステム要件表そのものが存在せず、アーキ表だけが作られた。更新すべき土台が無かったためである。

これは ADR-0006 基準 3（利用者向け文書の完備——作者と独立した人間が文書だけを頼りに導入から運用まで到達できること）の穴である。導入判断の最初の一歩、「うちの Windows Server で動くのか」に答える文書が無い。

さらに問題は表明の欠落だけではない。**v0.x の間に実機で踏んだ環境は狭い**。「表明していない」だけでなく「検証していない」状態であり、v1.0 で何を約束するかを決めるには、まず外部の前提（.NET・Windows・SQL Server・ブラウザのサポート状況）を確定させる必要がある。

### CI の現況（本 ADR の決定 5 の前提）

`.github/workflows/ci.yml` の実ファイルを確認した結果は次のとおり（確認日 2026-07-26）。

- **SQL Server 適合テストは全 PR の CI で実走している**。GitHub ランナーの image に SQL Server インスタンスは同梱されないが、`ci.yml` の `Ensure SQL Server LocalDB is available` ステップが公式 `SqlLocalDB.msi` をその場でサイレント導入し、適合テストは `(localdb)\MSSQLLocalDB` を既定接続先として実行される。CI ではスキップせず fail する設計（偽装 green の防止）
- **ただしその実行基盤は LocalDB であり、実インスタンス（Express / Standard / Enterprise）に対する CI 実行は無い**。決定 2 は LocalDB を運用形態としては対応外とするため、**SQL Server provider の常設・blocking な自動検証が「対応外の実行形態」の上にのみ立っている**という捻れが残る。この捻れは決定 2 で明示的に扱う
- 回帰ベンチの blocking 判定は**突合成立（`requireReconciled`）のみ**である（M-5 v2。architecture.md §5.2）。スループット・保存件数の比判定はランナー個体差が支配的で blocking にできないことが実測で確定済み。**性能退行の blocking 検知は基準環境での絶対値判定（M-6）の管轄**
- 基準値ファイル `tools/Yagura.Bench/baselines/ci-baseline.json` は **1 本**で、ランナー OS 別の区分を持たない。その出自は 2026-07-06 の `windows-latest`（当時 = Server 2022）実測であり、**現行の実行環境（Server 2025）とずれている**

### 検証で判明した製品側の未確認事項・欠陥

外部前提の確認と併せてコードを監査し、本 ADR の決定に影響する事項を 3 点特定した。

- **TLS 1.3 の固定指定**: Yagura は TLS を使う 3 か所すべてで `SslProtocols.Tls12 | SslProtocols.Tls13` を固定している（syslog TLS 受信 = `src/Yagura.Ingestion/Tls/TlsSyslogListener.cs:245`、管理 HTTPS・閲覧 HTTPS = `src/Yagura.Host/Program.cs:359`）。**TLS 1.3 非対応の OS でこの指定が TLS 1.2 へ縮退するのか、例外になるのかは未検証**である
- **接続ハンドラの無音脱落（欠陥。[Issue #482](https://github.com/Yanai-Taketo/Yagura/issues/482)）**: 上記の検証中に発見。`TlsSyslogListener.HandleConnectionAsync` の catch フィルタは `AuthenticationException or IOException or OperationCanceledException` に限定され（`TlsSyslogListener.cs:268`）、包括 catch を持たない。接続タスクを起動する `ContinueWith`（同 183〜189 行）も `t.Exception` を観測しない。**フィルタ外の例外型が出ると、カウンタにも警告ログにも残らずに接続が落ちる**——プロセスは生存し TCP accept も継続するため外形監視は緑のまま。ADR-0001 の品質原則「失った場合に必ず観測できる」に反し、**ADR-0006 基準 2 の重大不具合定義①に該当する**（未解決のまま v1.0 は公開できない）。TLS 1.3 非対応 OS はこの経路を踏み得る一例にすぎず、**欠陥そのものは TLS 1.3 と独立**である
- **MSI に OS バージョンの起動条件が無い**（`installer/Package.wxs`）。対応外の OS にもインストールできてしまう

## 検討した選択肢

### 対応 OS の下限をどこに置くか

**識別因子の整理を先に置く。** Server 2016 と Server 2019 を比較すると、**TLS 1.3 非対応（外部検証 (3)）も Edge 非同梱（同 (5)）も両者に等しく当てはまる**。したがってこの 2 点は 2016 と 2019 を分ける根拠として使えない。**両者を実際に識別するのはライフサイクルの残存期間のみ**である（2027-01-12 と 2029-01-09）。この事実を踏まえて選択肢を評価する。

- **(A) .NET 10 が対応する全 OS（Server 2012 以降）を対応と表明する**: 却下。理由は 2 点——①**Server 2012 / 2012 R2 は VC++ 再頒布可能パッケージの別途導入が前提**であり（外部検証 (1)）、ADR-0001 の**ゼロ設定ファーストラン**が成立しない。②Server 2016 の残存ライフサイクルが約 6 か月しかなく、下記のコスト比較が成立しない。**なお「検証していない環境を対応と呼べない」という理由は本選択肢の却下には使えない**——採用案 (B) も Server 2019 を検証せずに対応と呼ぼうとしており、同じ矛盾を抱えるためである（この点は決定 1 のゲートで処理する）
- **(B) 対応 = Server 2019 以上 / 推奨 = Server 2022 以上の 2 段（採用）**: Server 2019 の残存ライフサイクルは 2029-01-09 までで、**v1.0 系列のサポート期限（決定 7 の 2028-11-14）を完全に覆う**。一方 Server 2016 の残存は約 6 か月であり、v1.0 の公開時期が未定である以上、重なる可能性はあるが**重なっても最大で数か月**である。その数か月のために単発検証・不具合対応・文書の説明責任を恒常的に負うことは、**ADR-0009 が x86 について適用した「需要の裏付けが無い対応範囲の恒常保守コストを負わない」という判断と同型**である。これは事実命題ではなくコスト比較として本 ADR の根拠に置く
- **(C) 対応 = Server 2022 以上に統一する**: 却下。検証コストは最も小さく TLS 1.3 も揃うが、**延長サポートが 2029 年まで残る Server 2019 環境を切ることになり、ADR-0001 が定めた対象利用者（中小企業の Windows 管理者）と衝突する**。ただし**この却下は、委任事項 1 の実機検証で Server 2019 に TLS 1.3 以外の重大な差が出た場合には撤回する**（再評価トリガ）
- **(D) 下限を設けず「動作報告を募る」形にする**: 却下。v1.0 は「本番利用を推奨できる」宣言であり、推奨の範囲を利用者に決めさせるのは宣言の放棄にあたる

**対応範囲の増減を判断する規則**（ADR-0009 との基準の一貫性を検証可能にするため明文化する）:

- **新規の拡大**（未表明の環境を対応に加える）には、**需要の一次情報**（利用者からの要望・Issue へのリアクション等）を要する。ADR-0009 が x86 に適用し、本 ADR が Server Core に適用する基準
- **既公表範囲の縮小**（ADR-0009 の「Windows Server 全般」から削る）には、**ライフサイクル・機能・検証コストのいずれかの根拠**を要する。需要の一次情報は要求しない——縮小の可否を「切られる側の声が上がるか」に委ねると、声を上げる手段を持たない利用者の環境が黙って残り続けるため
- **既公表範囲の維持**（Server 2019）には追加の根拠を要しない。既に表明済みの範囲を維持することは新規の約束ではない

この規則により、x86（不拡大・一次情報なし）・Server Core（縮小・検証コスト）・Server 2016 以前（縮小・ライフサイクル）・Server 2019（維持）の 4 件がすべて同じ物差しで説明できる。

### ブラウザ要件を明記するか

- **(a) 「最新版の Edge / Chrome / Firefox / Safari」を要件として明記する（採用）**
- **(b) 書かない（現状維持）**: 却下。**既定構成では管理 UI が loopback 固定**であり（ADR-0004・configuration.md §4）、初回セットアップ・本番昇格・保持期間変更はサーバ機上のブラウザから行う。Blazor は IE 非対応（外部検証 (4)）であり、かつ **Server 2019 / 2016 には Edge が同梱されない**（同 (5)）ため、**追加ブラウザを入れていない素の状態では管理 UI に到達できない**。Server 2022 以降は Edge が同梱されるためこの問題は起きない。書かなければ「インストールは成功したのに設定画面が開けない」に着地し、ADR-0001 の導入体験の原則に反する

### ハードウェア要件をどう決めるか

- **(a) 実測に基づく算出式 + 検証済み構成の実測値で表現し、CPU・メモリの下限確定は M-6 に委ねる（採用）**
- **(b) 一般的な目安（例「2 コア / 4 GB 以上」）を書く**: 却下。architecture.md §5.2 が定めた「公称値は基準環境での絶対値で判定する」原則と衝突する。**根拠のない数値を要件表に書くと、それが後から公称値の既成事実になる**（ADR-0006 運用の「量的な床も自己拘束の内側に置く」に反する）。**この却下理由は採用案にも適用する**——採用案が提示する算出式・目安値についても、確定値と暫定値を区別し、前提を明示することを決定 4 で義務づける

### 検証基盤をどう組むか

- **(a) 推奨環境は CI に加え、対応下限は単発検証する（採用）**: `windows-2022` ランナーは公開リポジトリで無料・無制限（[GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)。ADR-0009 の「CI のアーキ別実行基盤」選択肢 (a) が確認した前提と同じ。確認日 2026-07-26）。一方 `windows-2019` ランナーは**退役済み**でランナー一覧に存在しない（同、確認日 2026-07-26）ため、Server 2019 は CI では踏めない。オーナー lab には Proxmox の x64 機があり、Windows Server 2019 の評価版（180 日・ISO/VHD で配布継続中。確認日 2026-07-26）を載せれば**追加費用ゼロで単発検証できる**
- **(b) Server 2019 を含む多 OS の恒常 lab を組む**: 却下（現時点）。常時保持は保守コストが個人運営規模に見合わない
- **(c) クラウド VM（Azure / AWS）で単発検証する**: 却下（第一選択としては）。ライセンス込みで評価版の期限・アクティベーション制約が無い利点はあるが、(a) が費用ゼロで同じ目的を達する。**Proxmox 機が使えない状況になった場合の代替として残す**

## 決定

**選択肢 (B) + (a) + (a) + (a)** を採用する。

### 決定 1: OS のサポート行列を「推奨 / 対応 / 試験的 / 対応外」の 4 区分で定義する

| 区分 | 対象 | 約束する水準 | 検証水準 |
|---|---|---|---|
| **推奨（Recommended）** | Windows Server 2022 / 2025（x64） | 全機能。ADR-0004 決定 3 の opt-in 強化 3 点（TLS 受信・閲覧 HTTPS・AD 連携認証）を含む。**性能公称値（M-6）を表明するのはこの区分に対してのみ** | Server 2025 = CI（`windows-latest`）+ 実機 lab E2E。**Server 2022 = CI のみ**（下記の非対称を参照） |
| **対応（Supported）**<br>**※暫定・検証待ち** | Windows Server 2019（x64） | 中核機能（受信・保存・閲覧・管理・スプール・昇格）。**opt-in 強化 3 点の可否と、TLS が 1.2 止まりになるかは委任事項 1 の検証結果で確定する（現時点で未確定）**。性能公称値は対象外 | 単発の実機検証（決定 5）。CI 回帰の対象外 |
| **試験的（Experimental）** | Windows 11 on Arm 等のクライアント（ARM64） | ADR-0009 決定 2 の ARM64 行をそのまま継承（修正 SLA を約束しない） | リリースごとの `windows-11-arm` スモーク（ADR-0009 Phase 1） |
| **対応（Supported）** | Windows 11（現行版）・Windows 10 LTSC / Enterprise の .NET 10 対応版（x64） | 中核機能。試用・小規模用途を想定 | 開発機・lab メンバー機での実機使用 |
| **対応外** | Windows Server 2016 以前、Server Core / Nano Server、**Windows 10 Home / Pro**、32-bit | — | — |

**Server 2016 以前を対応外とする根拠**: **識別因子はライフサイクルの 1 点のみである**（残存約 6 か月。選択肢 (B) のコスト比較を参照）。TLS 1.3 非対応・Edge 非同梱は Server 2019 にも等しく当てはまるため 2016 特有の根拠にはならない——**この 2 点を根拠として数えない**。Server 2012 / 2012 R2 についてはこれに加えて VC++ 再頒布可能パッケージの前提（外部検証 (1)）がある。

**Windows 10 Home / Pro を対応外とする根拠**: ①**.NET 10 の対象外**である（外部検証 (1)。Windows 10 の対応は LTSC・Enterprise に限られる）。②**2025-10-14 に提供終了済み**（同 (6)）。Server 2016 に適用したライフサイクル基準を、クライアント側にも同じ物差しで適用した結果である。なお lab のメンバー機実績（「Windows 10 Pro」）はこの区分に当たるため、**対応表明の裏付けとしては使わない**。

**Server Core / Nano Server を対応外とする根拠**: **未検証だからである**。当初案は「管理 UI がブラウザを前提とする製品構造と原理的に噛み合わない」としていたが、これは誤りであり撤回する——**ADR-0004 決定 2 は Server Core を明示的に想定し、「既定構成の管理手段は設定ファイルの手編集となる。GUI での管理は認証 opt-in 後のリモート管理で行う」と定めている**。configuration.md §3（CF-5）はさらに `sc control Yagura 128` による再読み込みを「**Server Core・管理画面に入れない状況でも手編集を受信断なしで反映できる**」ことを理由に採用している。すなわち製品側に経路は設計されている。本 ADR が対応外とするのは、その経路を一度も実機で検証していないためであり、「動作しない」という主張ではない。**Server Core での需要が一次情報として確認された場合は再評価する**（再評価トリガ）。

**ADR-0009 決定 2 の x64 行の部分 supersession**: 本 ADR は ADR-0009 のアーキテクチャ軸の判断（x64 = 対応 / ARM64 = 試験的）を反転させないが、**同決定 2 の x64 行が無条件文として書いた対象範囲を条件文へ書き換える**。docs/adr/README.md の判定の目安（「疑わしい場合は最小の単位で反転の有無を検証する」）を最小単位「x64 × 特定 OS」に適用すると、Server 2016 / 2012 系・Windows 10 Home/Pro はいずれも「対応 → 対応外」の反転にあたるため、**同ルールの「疑わしければ supersession 側に倒す」に従い部分 supersession として扱う**。ADR-0009 の status は accepted のまま維持し、①一覧表の状態欄と②決定 2 の該当行に注記を加える（委任事項 9）。

**「対応」と「推奨」の差の意味**（ADR-0009 決定 2 の「サポート水準の定義」と同じ作法で明文化する）:

- **設計原則は全区分共通**: ADR-0001 の品質原則（ログを失わない・失った場合に必ず観測できる）は Server 2019 でも設計上の原則として適用される。区分によって「観測できない喪失を許容する」ことはしない
- **意図的な機能差は設けない（方針の言明）**: Yagura の実装都合で区分ごとに機能を削ることはしない。**ただし「実際に観測される差は TLS 1.3 のみである」という実測命題は、検証前の現時点では主張しない**——差の全体は委任事項 1 の検証で確定する（決定 2 末尾の「差が無いことを前提に置かない」と同じ姿勢）
- **性能特性の同等性は主張しない**: Server 2019 での持続流量・OS 受信バッファ挙動（M-2 の 1 MiB 既定を含む）の実測は無い。**性能公称値（M-6）は推奨区分に対してのみ表明する**
- **検証の裏付けが非対称**: 推奨環境は CI で継続検証する。対応環境は決定 5 の契機に該当したときの単発検証にとどまる。**この検証水準は、ラベルが下位である ARM64（リリースごとのスモーク + スプール 1 サイクル）より弱い**。この逆転を放置しないため、委任事項 1 に ARM64 と同水準の負荷項目を課し（⑤⑥）、**それを通過するまで Server 2019 の区分は「暫定」とする**
- **不具合対応**: Server 2019 固有の不具合報告は受け付け、再現・修正を試みるが、修正の優先度は推奨環境の品質維持を優先して判断する
- **対応下限の二重劣後**: 対応下限（Server 2019 / SQL Server 2019）はいずれも Microsoft の**メインストリームサポートが終了済み**（2024-01-09 / 2025-02-28）であり、ベンダから提供されるのはセキュリティ更新のみである。Yagura 側でも修正優先度が劣後するため、**この区分は OS・DB ベンダとアプリベンダの双方で劣後する**。この合成をシステム要件表にも記す（委任事項 3）

### 決定 2: SQL Server は「2019 以上を対応・2022 以上を推奨」とし、未検証バージョンには表明ゲートを掛ける

| 区分 | 対象 | 根拠 | 表明ゲート |
|---|---|---|---|
| **推奨** | SQL Server 2022（Express・Standard・Enterprise） | 延長サポート 2033-01-11。Express は M7-2 で実測済み | Express のみ実測済み。他エディションは未検証（下記） |
| **推奨** | SQL Server 2025 | 延長サポート 2036-01-06 | **実測ゼロ。委任事項 2 のゲートを通すまで README で表明しない** |
| **対応** | SQL Server 2019（同上） | 延長サポート 2030-01-08。v1.0 のサポート期間を覆う | **実測ゼロ。委任事項 2 のゲートを通すまで README で表明しない** |
| **対応外** | SQL Server 2017 以前 | 2017 は 2027-10-12 に終了予定で v1.0 のサポート期間に収まらない。**2016 は 2026-07-14 に終了済み** | — |

- **エディションは問わない**が、**Express の適用限界は database.md §5.3 のとおり利用者向けに明示する**（DB 最大 10 GB・バッファプール 1,410 MB・4 コア）。ゼロ設定ファーストランの既定は SQLite であり、Express は「無償で本番昇格したい場合の選択肢」として位置づける
- **エディション差は未検証**である。Standard / Enterprise は Express の制限を持たないため機能面の劣化は想定しないが、実測はしていない
- **LocalDB は運用形態としては対応外**とする。常駐サービスの保存先として設計された製品ではなく（ユーザーセッションに紐づく起動モデル）、Yagura が仮想サービスアカウント / gMSA で動く前提と噛み合わない。**ただし開発・CI の検証環境としては現に使用している**——「CI の現況」のとおり SQL Server 適合テストは LocalDB 上で全 PR 実走しており、**SQL Server provider の常設・blocking な自動検証はこの対応外の実行形態の上にのみ成立している**。ADR-0006 基準 1 の証拠として適合テスト記録を提出する際は、**この事実を明示する**（黙って提出しない）。実インスタンスに対する CI 実行の要否は委任事項 5 で判断する
- **組み込み DB（SQLite）は全区分で同一**とする。ネイティブ資産はアーキ別に self-contained publish へ含まれる（ADR-0009 決定 3・Phase 0 で検証済み）ため、**DB 製品の別途導入も OS 側の前提も持たない**。OS バージョンによる挙動差の有無は委任事項 1 の単発検証で確認する（差が無いことを前提に置かない）

### 決定 3: ブラウザ要件を明記し、管理 UI の到達性の前提として位置づける

- **要件**: 最新版の Microsoft Edge / Google Chrome / Mozilla Firefox / Apple Safari のいずれか（Blazor の対応ブラウザに従う。外部検証 (4)）。**Internet Explorer は対応しない**
- **要件が掛かる場所を明示する**: 閲覧 UI（8514）は**任意の端末のブラウザ**から開ける。日常のログ閲覧にサーバ機のブラウザは要らない。一方 **管理 UI（8515）は既定構成で loopback 固定のため、サーバ機自身に対応ブラウザが必要**である（管理リモート HTTPS を opt-in で有効にすれば〔ADR-0010〕リモート端末のブラウザでよい。その有効化は管理 UI からでも**設定ファイルの手編集からでも**行えるため〔ADR-0002 決定 5〕、サーバ機のブラウザは厳密には必須ではないが、**既定構成の導線ではサーバ機のブラウザを通る**）
- **推奨環境（Server 2022 / 2025）では Edge が同梱されるため追加作業は要らない**。対応環境（Server 2019）では**対応ブラウザの導入が導入手順の前提条件になる**
- **閉域環境での成立性**: README のセキュリティ前提はインターネットに露出しない設置を推奨しており、「最新版のブラウザを維持せよ」という要件と衝突しうる。**この解き方（オフラインインストーラの入手手順・更新の維持責任の所在・要件を満たさない場合の症状）は利用者向け文書で明示する**（委任事項 3）。要件だけを書いて成立手段を書かない状態にはしない

### 決定 4: ハードウェア要件は「provider 別の算出式 + 条件付きの実測値」で表現し、CPU・メモリの下限確定は M-6 に委ねる

- **ディスクの算出式は provider 別に分け、DB 側とボリューム側を分離する**:

  **DB 側（Express の 10 GB 上限と比較できる値）**
  - SQLite: `DB サイズ ≒ (平均メッセージ長 + 95 B) × 秒間流量 × 保持期間の秒数`
  - SQL Server: **未確定**。上記の単価はレコード単価の SQLite ファイルサイズ実測（M7-2）に基づくが、**SQL Server は全文字列列が `nvarchar`（UCS-2/UTF-16）で `_UTF8` 系照合順序を付与しない方針**のため（database.md §5.4）、ASCII 本文は 1 文字 2 バイトで格納される。**SQLite の単価は転用できない**。委任事項 2 の実機検証に容量計測を追加して確定するまで、SQL Server 版の式は公表しない

  **ボリューム側**
  - `必要な空き ≒ DB サイズ + スプール使用量上限【暫定・M-12】 + 空き容量の下限 1 GiB【暫定・M-16】`

  **確定値と暫定値を区別して表記する**（【暫定】の注記を要件表でも維持する）。選択肢 (b) を却下した理由（根拠のない数値の既成事実化）は自案にも適用する。**「安全率」は定義できないため式から外し、本式の見積もりが下限であること（索引・トランザクションログ・システムイベント・削除遅延分を含まない）を明記する**
- **既定構成の目安を載せる場合は前提を必ず併記する**: 保持 30 日・**平均メッセージ長 約 200 B**・10 msg/s で **約 7.8 GB**（DB-1 が Express 10 GB 上限への収まりを判定するために算出した値であり、**スプール・空き容量下限を含まない裸値**）。**この値は M-16 の Express 容量接近警告の閾値（10 GB × 0.8 = 8 GB）のすぐ下にある**——既定運用を Express で続けると定常状態で容量接近警告が出うることを、利用者向け文書で必ず伝える（委任事項 3）
- **CPU・メモリの下限は本 ADR では確定しない**。architecture.md §9 **M-6** が管轄する。本 ADR は M-6 に「**基準環境の定義は決定 1 の推奨区分に含まれる構成から選ぶ**」という制約を追加する（委任事項 8）。推奨区分は 2 バージョンあるため、**選ばれなかった側のバージョンについて公称値をどう扱うかも M-6 で決める**
- **参考実測値には条件を必ず並記する**: 「8 論理コア / 7 GiB・SQL Server 2022 Express 同居・単一マシン・1 回の実測」における Express ≈ 4,500〜5,000 msg/s・SQLite ≈ 15,000 msg/s（M7-2）。**これは性能上限を測るための構成であって推奨構成ではない**ことを、要件表では誤読されない文言で書く（委任事項 3）

### 決定 5: 検証水準は「推奨環境は CI・対応下限は単発」の 2 段とする

- **推奨環境**: `.github/workflows/` のジョブに **`windows-2022` を加える**。公開リポジトリの標準ランナーは無料・無制限のため追加費用は発生しない。**ただし CI で得られるものを過大に見積もらない**——回帰ベンチの blocking 判定は突合成立のみであり（M-5 v2）、`windows-2022` の追加で得られるのは「**Server 2022 でも突合が成立する**」ことである。**性能退行の検知は M-6 の管轄**であって CI の追加では得られない
- **委任先が判断できるよう、次の制約を先に置く**（委任事項 4）:
  - **OS バージョン差が現れるのは `installer-e2e` 相当のジョブ**（Windows サービス登録・ACL/監査・MSI の起動条件・証明書ストア）である。`ci.yml`（ビルド + 単体テスト + 短縮ベンチ）への追加では OS 差の被覆はほとんど増えない
  - `installer-e2e.yml` は `pull_request` の paths フィルタ付きであり、ここへの追加は決定 1 の表が言う「CI」の常時性を満たさない。**「常設」の語が指す実体を委任事項 4 で確定する**
  - `build-and-test` を matrix 化すると job 名が変わり、**ブランチ保護の必須ステータスチェック設定の更新（リポジトリ設定。外部 PR では完結しない）が同時に必要**になる
  - **基準値ファイルを OS 別に分けるか単一のまま使うかを判断する**。M-5 v2 が踏んだ分布混合による誤較正の再発を防ぐため。あわせて既存 baseline の出自（Server 2022）と現行実行環境（Server 2025）のずれの是正要否も判断する
  - `installer-e2e.yml` の「ci.yml には触れない（並行 PR との衝突回避）」という既存方針との関係を整理する
- **推奨区分内の検証の非対称を明示する**: AD 連携認証・gMSA・MSI のアップグレード挙動は **CI では原理的に検証できない**（conventions.md）。これらの実機裏付けは **Server 2025 の lab のみ**であり、**Server 2022 では AD 系が一度も踏まれていない**。Server 2022 での lab 実施要否は委任事項 10 で判断する
- **対応下限（Server 2019）**: **オーナー lab の Proxmox（x64）上に Windows Server 2019 評価版の VM を立てて単発検証する**。`windows-2019` ランナーは退役済みで CI では踏めない
- **単発検証を再実施する契機**: ①v1.0 リリース判定時、②対応下限の表明を変えるとき、③**Server 2019 の挙動に影響し得る変更**が入ったリリース。③は「インストーラに変更が入ったリリース」では毎回該当して運用不能になるため、**対象を具体的なパスで機械的に定める**（確定は委任事項 4。確定内容は改訂 2 を参照）。それ以外では再実施しない
- **受け入れるトレードオフ**: 上記③に該当しないセキュリティ修正（パーサ・認証・UI・監査経路など）は、**対応環境で一度も検証されずに出荷され得る**。その場合の対応環境での動作は「設計上共通であること」に依拠する

### 決定 6: MSI の起動条件で対応下限（OS ビルド番号）を機械的に強制する

- `installer/Package.wxs` に **OS ビルド番号による LaunchCondition を追加する**。**Windows Server 2019 と Windows 10 1809 はいずれもビルド 17763** であり、単一の条件式で表現できる
- **本条件の射程を正直に限定する**: この条件が新たに止めるのは実質「**Server 2016 以前**」だけである。**Server Core / Nano Server はビルド番号で判別できない**ため素通しする——決定 3 が特定した「入るのに管理 UI に到達できない」に最も確実に着地するのは Server Core であり、**本条件はその最悪ケースを捕まえない**。Server Core の判別手段の有無と、判別できる場合の拒否要否は委任事項 6 で調査する
- **`LaunchCondition` を採る理由**: `installer/Package.wxs` は利用者入力の検証について「`LaunchCondition` は UI シーケンスの先頭（利用者入力の前）にも評価されるため使えない」として type 19 エラー CA を採用済みである（同ファイル 217-219 行）。OS バージョンはシーケンス開始時点で確定し利用者入力に依存しないため、本件では `LaunchCondition` が適合する
- **アップグレード経路にも掛かる**: `LaunchConditions` は `InstallExecuteSequence` の先頭付近で評価されるため、**メジャーアップグレードも拒否される**。既定シーケンス上 `RemoveExistingProducts`（ADR-0023 決定 2 により `afterInstallExecute`）より手前で走るため、拒否されても ADR-0023 が扱った「製品が 1 つも残らない」には至らず**既存インストールは無傷で残る**。ただしその利用者は**新版を受け取れない**——決定 7・SECURITY.md の「最新リリースのみ・バックポートなし」と合成すると、**対応外 OS の既存利用者には脆弱性修正の受領経路が無くなる**。この帰結を利用者向け文書に明記する（委任事項 3・7）
- **誤判定のリスク**: Windows Installer は Windows 10 以降の互換性マニフェストを持たないため、`VersionNT` / `WindowsBuild` が実ビルド番号を返さない可能性がある。該当すると条件式は**全対応環境で false となり、新規インストールとアップグレードの両方が全環境で拒否される**。アップグレードでも評価されるため、これを含んだリリースは**全既存環境を更新不能にし、以後の修正の配布経路を断つ**。**検証は 4 区分 × 2 経路（新規 / アップグレード）で行い、推奨・対応区分で正常に通ることの確認を、対応外での拒否確認と同格の必須項目とする**（委任事項 6）
- **メッセージは「なぜ入れられないか」と「どうすればよいか」を含める**。対応する OS の下限・システム要件表への導線に加え、**対応外 OS の利用者が取れる選択肢**（移行の案内、既存 v0.x の扱い、相談先）を含める

### 決定 7: サポート表明の期限を .NET 10 のライフサイクルに接続する

- Yagura は .NET 10（LTS・サポート終了 **2028-11-14**）に self-contained で依存する。**v1.0 系列のサポート表明はこの日付を超えない**
- **.NET のメジャー更新は v1.0 系列の中では行わない**。**当初案はこれを「ADR-0006 基準 4（後方互換性の凍結）と同じ扱い」と書いたが、援用の誤りであり撤回する**——基準 4 の凍結対象は「設定スキーマ・DB スキーマ・保存データ形式」であり、ランタイムのメジャーバージョンを含まない。据え置きの根拠は独立に置く: **self-contained 配布ではランタイム更新が全成果物の再ビルド・再署名・再検証を伴い、v1.0 系列内での挙動同一性の担保コストが大きい**ため。この判断の代替案（v1.x で次期 LTS へ載せ替える / self-contained をやめる / セキュリティ修正のみ延長する）は本 ADR では比較していない——**比較していないことを明記する**
- **self-contained 配布の帰結（配布責任の移転）**: .NET ランタイムは MSI に同梱されるため、**ランタイムの脆弱性修正は Windows Update では利用者に届かない**。Yagura が再ビルド・再署名・再配布して初めて届く。**この責任範囲と対応方針（追随の有無・契機）を SECURITY.md に明記する**（委任事項 7）。方針が「自動監視は行わない」であっても、明記しないまま放置するよりよい
- **期限の逆転を利用者に見える場所へ書く**: v1.0 系列の期限（2028-11-14）は、**対応環境の OS・DB のいずれよりも先に来る**（Server 2019 = 2029-01-09、SQL Server 2019 = 2030-01-08、Server 2022 = 2031-10-14）。「OS が生きている限り Yagura も使える」と読まれるのが自然な導線であるため、**SECURITY.md だけでなくシステム要件表にも併記する**（委任事項 3・7）
- **既存ポリシーとの合成結果も明記する**: SECURITY.md の現行方針は「修正は最新リリースと `main` に提供・バックポートしない」である。決定 7 の期限と合成すると、**利用者が修正を受け取る条件は「最新版に追随し続けること」のみ**になる。この合成結果を SECURITY.md に書く（委任事項 7）

## 帰結

- **良くなること**:
  - 導入判断の最初の問い（「うちの環境で動くのか」）に文書で答えられるようになり、ADR-0006 基準 3 の穴が塞がる
  - Server 2022 が CI で踏まれるようになり、「推奨に挙げる環境がどのジョブでも踏まれていない」状態が解消される（ただし得られるのは突合成立の継続確認であり、性能回帰の検知ではない）
  - **Server 2016 以前への新規インストールをインストーラが止める**（Server Core は止まらない——決定 6 の射程参照）
  - サポート表明の期限と、その根拠・合成結果（バックポートなし・ランタイム同梱）が外部のライフサイクルに接続され、利用者が実効的な保証範囲を判断できるようになる
  - 起案の過程で **[Issue #482](https://github.com/Yanai-Taketo/Yagura/issues/482)（TLS 接続ハンドラの無音脱落）を発見**した。ADR-0006 基準 2 の重大不具合定義①に該当する欠陥であり、v1.0 の前に解消が必要
- **悪くなること（受け入れるトレードオフ）**:
  - **説明責任が増える**。「Server 2019 は対応だが検証は単発」「Server Core は未検証ゆえ対応外」「Windows 10 は LTSC/Enterprise のみ」といった非直感的な制約を一貫して書き続ける必要がある
  - CI の実行時間とジョブ数が増える。ブランチ保護の設定変更も伴う
  - **公表済みのサポート範囲を縮小する**。ADR-0009 の「Windows Server 全般」から Server 2016 以前・Server Core・Windows 10 Home/Pro を撤回する。現時点で該当環境の利用報告は無いが、**いないことの確認もできていない**
  - 決定 5 の契機③に該当しないセキュリティ修正は、対応環境で未検証のまま出荷され得る
- **リスク**:
  - **Server 2019 の単発検証で中核機能に不成立が出る可能性がある**。特に TLS 1.3 固定指定が Issue #482 の無音経路に落ちる場合、送信元が痕跡なく全滅しうる。**本 ADR が accepted でも、この検証を通過するまで Server 2019 の区分は「暫定」であり、README へ転記しない**
  - **決定 1 の Server 2019 行が外れた場合の波及が大きい**——選択肢 (C) へ倒れれば決定 3・5・6 と委任事項 1/3/6 が連鎖して書き直しになる
  - 決定 4 が CPU・メモリの下限と SQL Server のディスク算出式を確定しないため、**v1.0 のシステム要件表は「サイジングに使える数字が乏しい」状態で公開される**。大量ログ環境の導入検討者は判断材料を得られない。**ADR-0006 基準 1 は性能公称値の充足を求めており、M-6 は v1.0 のクリティカルパスである**——本 ADR はこれを「先送りできる宿題」として扱わない
  - **SQL Server 2019・2025・Express 以外のエディションは実測ゼロ**であり、ライフサイクル上の妥当性だけを根拠に区分している。ドライバ側の下限が公式に確認できなかったこと（検証の限界）と合わせ、この表明は推論に立つ
  - 決定 6 の条件式が誤判定した場合、**全環境で更新不能になる**（決定 6 の誤判定リスク）

## 先送りにする場合の再評価トリガ

- **Server 2019 の単発検証で TLS 1.3 以外の重大な差、または中核機能の不成立が出た場合**: 選択肢 (C)（対応 = Server 2022 以上）への転換を supersession で検討する
- **委任事項 1 の負荷項目（⑤⑥）が通らない場合**: Server 2019 の区分を「試験的」へ落とすことを検討する（ARM64 との検証水準の整合）
- **SQL Server 2019 の性能が 2022 Express と同オーダーに収まらない場合**: 決定 2 の対応区分を見直す
- **Windows Server 2022 のメインストリームサポートが終了した場合（2026-10-13。約 3 か月後）**: 推奨区分の表現を点検する（延長サポートは 2031-10-14 まで残るため区分自体の変更は要さない見込み）
- **Windows Server 2019 の延長サポート終了（2029-01-09）が近づいた場合**: 対応区分から外す。v1.0 系列のサポート期限（2028-11-14）より後であり、実質的には次のメジャーバージョンの論点になる
- **Server Core での需要が一次情報として確認された場合**: ADR-0004 決定 2 が定めた手編集 + リモート管理の経路を実機検証し、対応区分への追加を検討する
- **GitHub が `windows-2022` ランナーを退役させた場合**: Server 2022 を単発検証側へ移す

### 改訂 2（2026-08-01）: 委任事項 4 の実施結果を記録。決定は不変

**CI への Server 2022 追加**（決定 5）と、決定 5 が委任先へ送った制約 5 点の判断結果。

- **ランナーラベルは明示ピンにする（`windows-latest` を推奨環境の被覆に使わない）**: `windows-latest` は GitHub の都合で指す OS が動くため、**推奨区分として何を踏んでいるかが暗黙になる**。実際これは既に一度起きている——以前 `windows-latest` が Server 2022 だった頃の基準値が残ったまま実体が 2025 へ移り、「推奨に挙げた Server 2022 がどのジョブでも踏まれていない」状態が生まれた（文脈節）。明示ピン（`windows-2025` / `windows-2022`）なら**推奨区分を変えるときに CI も必ず直すことになり、ずれが沈黙しない**。**将来 OS への追従は別の目的として分離**し、`build-and-test-latest`（`windows-latest`）をカナリアとして置く——非必須チェックであり、落ちても「Yagura が対応を表明していない OS の話」としてリリースを止めない。`continue-on-error` は使わない（緑に見えると兆候が埋もれるため）。現在 `windows-latest` は Server 2025 を指すのでカナリアは実体が重複するが、**本ジョブの価値は GitHub がラベルを移した日から生じる**。重複コストを許容できないと判断した場合はカナリアだけを削ればよい（推奨環境の被覆は明示ピンの 2 ジョブが持つ）。`installer-e2e.yml` にはカナリアを置かない——1 実行 30 分規模のため重複コストが見合わない
- **対象ジョブと「常設」の定義**: `ci.yml`（全 PR + main への push で走る＝常設）に **`build-and-test-server2022` を追加**し、`installer-e2e.yml`（paths フィルタ付き＝常設ではない）を **matrix 化**して両 OS を踏む。決定 5 が指摘したとおり **OS バージョン差が現れるのは installer-e2e の検証面**（Windows サービス登録・ACL・MSI の起動条件）であり、ci.yml 側は「Server 2022 でもビルド・単体テストが通る」の常設確認にとどまる
- **ブランチ保護の必須ステータスチェック**: **実作業のジョブ名で OS を明示し（`build-and-test-2025` / `build-and-test-2022` / `build-and-test-latest`）、必須チェック名は集約ジョブ `build-and-test` で安定させる**構成にした。matrix 化は採らない——job 名に matrix 値が付いて（`build-and-test (windows-2022)`）必須チェック名が動くため。逆に必須チェック側のジョブ名へ OS を書かないと、**名前が「どの OS を守っているか」を語らない**（明示ピンを選んだ判断と一貫しない）。集約ジョブを挟むことで両立し、**ゲートの構成は `needs` に明示され、変更は workflow ファイルだけで完結する**（リポジトリ設定の変更を伴わず、外部貢献者の PR で推奨区分の増減に追随できる）。**ゲート対象は推奨区分の 2 つに限り、カナリアは含めない**——対応を表明していない OS の失敗でリリースを止めないため。なお本構成により **Server 2022 の失敗はマージを止める**（決定 1 が推奨区分へ「全機能」を約束している以上、片方だけ非 blocking にする理由がない）。旧案（`build-and-test` を Server 2025 の実作業ジョブのまま据え置き、2022 を非必須で足す）は、必須チェック名が OS を語らない点と、推奨区分の片方だけがゲートに入らない点で劣ると判断した。
- **（旧記述）** `build-and-test` を **matrix 化しない**判断とした。matrix 化すると job 名が `build-and-test (windows-latest)` へ変わり、conventions.md が定める必須チェック（`build-and-test`）が外れてリポジトリ設定の変更を伴う。**別ジョブなら既存の必須チェック名を保ったまま信号を足せ、外部貢献者の PR だけで完結する**。`installer-e2e.yml` は必須チェックではないため matrix 化してよい——2 つのファイルで手法が異なるのはこの差による。**なお `build-and-test-server2022` 自体を必須チェックにするかはリポジトリ設定の判断であり、本 PR の範囲外**（設定しない限り、失敗は可視だがマージを止めない）
- **baseline の扱い**: **回帰ベンチは Server 2022 側では走らせない**。基準値ファイル `ci-baseline.json` は 1 本でランナー OS 別の区分を持たず、そこへ 2 つの OS の分布を混ぜると **M-5 v2 が診断した分布混合による誤較正を再現する**。ベンチの blocking 判定は突合成立のみであり、これは M-5 v2 の全 7 標本で成立した OS 非依存の機能保証（architecture.md §5.2）。したがって OS 軸を増やす価値はビルド・単体テスト側にあり、ベンチ側には無い。**既存 baseline の出自ずれ**（Server 2022 で採取・現行の `windows-latest` は Server 2025）は本 ADR の管轄外の別件として残す——ベンチの比判定が既に非 blocking であるため実害は情報記録の解釈に限られ、是正するなら基準値更新手続き（conventions.md）に載せる必要がある
- **`installer-e2e.yml` の「ci.yml には触れない」既存方針との整合**: 同方針は**インストーラ側の作業が ci.yml を巻き込まないようにする**趣旨（並行 PR の衝突回避）であり、本件のように **OS 対応範囲という横断的な軸**を両ファイルへ独立に足す変更はこれに抵触しない。両ファイルの変更は互いに依存せず、片方だけでも成立する
- **再実施契機③のパス定義（確定）**: 次のいずれかに変更が入ったリリースで、Server 2019 の単発検証（委任事項 1）を再実施する。それ以外では再実施しない。
  - `src/Yagura.Ingestion/Tls/**`（TLS 受信リスナ一式）
  - `src/Yagura.Ingestion/Tcp/TcpConnectionAcceptLoop.cs`（両リスナ共通の Accept ループ）
  - `src/Yagura.Host/Program.cs` の Kestrel HTTPS 構成（`UseHttps` / `SslProtocols` / `ServerCertificateSelector`）
  - `installer/Package.wxs` の起動条件（決定 6 の LaunchCondition）
  - `src/Yagura.Host/Administration/Https/**`（証明書ストア参照）

  選定基準は「**Server 2019 と推奨環境で OS 側の実装が異なる面に触れるか**」——具体的には Schannel（TLS プロトコル・暗号スイート）、証明書ストア、Windows Installer の版判定である。ビルド設定・DB provider・UI・パーサの変更はこの基準に当たらない（OS 差を持たない）。
