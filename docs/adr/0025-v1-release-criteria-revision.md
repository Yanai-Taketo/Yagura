### 12 か月トリガより前に改定する理由（オーナーの判断）

ADR-0006 の再評価トリガは「v0.x 公開から 12 か月を経ても試用環境が現れない場合、呼びかけ方法と基準の現実性を再評価する」である。v0.1.0 の公開は 2026-07-05 なので、トリガの時点は 2027-07-05 になる。本 ADR はその約 4.4 か月の時点で基準そのものを改定する。**トリガが発火したからではない。オーナーの判断（2026-11-16）による前倒しである**。

判断の中身は次のとおり。

- 基準 2・3 の充足は外部協力者の出現に依存し、作者の作業では期限を持てない。募集を始めてから約 4 か月、申し出は 0 件である。12 か月まで待てば状況が変わると考える根拠を、作者は持っていない。12 か月の時点で再評価しても、取れる選択肢は本 ADR と同じである。
- 一方、作者の lab は前節のとおり、外部の試用者がまず行わない種類の検証を積み、約 30 件の欠陥を見つけ、その大半を直してきた。
- そこで、v1.0 の公開を外部要因に預けたまま待つより、**作者 lab の記録で判定して今公開し、代替で失ったものを利用者へ開示する**方を選ぶ。

この判断は「基準を満たせないので基準を動かす」ものである。ADR-0006 の文脈が警戒した「基準を後から決めると、達成しやすい形に基準の方が動く」に、そのまま当たる。本 ADR はこれを否定しない。

### README の宣言との緊張

README は「基準は先に固定してあり、達成しやすい形に動かしません」と宣言している（「v0.5 の位置づけ」）。本 ADR はこの宣言に反する。宣言を黙って消すのではなく、反したことを同じ場所で利用者に書く（決定 4）。

## 本 ADR の位置づけ — 自己拘束が弱まることについて

ADR-0006 は「決定者と supersession の承認者が同一人物である以上、この拘束は手続きと公開記録による自己拘束である」と自覚的に記していた。**本 ADR は、その自己拘束を基準の達成前に緩める最初の実例である。**

- 本 ADR を承認するのは、基準を緩めることで利益を得る作者本人である。ペルソナレビューは起案側が起動する AI であり、構造的な独立性を持たない（persona-review.md の運用ノート）。**本 ADR の正当性を担保する独立した承認者はいない**。
- したがって本 ADR が拠り所にできるのは次の 4 点だけである。
  1. 改定の事実と理由を公開の場に残すこと
  2. 代替で失ったものを利用者へ開示する義務を課すこと（決定 4）
  3. 作者が後から代替の中身を薄められないよう、最小の実施項目を本 ADR に固定すること（基準 2'・基準 3'）
  4. v1.0 の後も外部からの確認を受け付け続けること（決定 5）
- ADR-0006 は検討した選択肢で「(c) 作者環境のみ: 『独立した環境で動く』ことの検証にならない。却下」としていた。本 ADR はこの却下した選択肢を、開示義務と追加の証拠を付けて採る。**却下の理由（独立した環境での動作は検証されない）は本 ADR でも正しく、解消されない**。

## amendment か supersession かの自己吟味

[docs/adr/README.md](README.md) は「既定を反転させるなら supersession」「疑わしければ supersession 側に倒す」「最小の単位で反転の有無を検証する」と定める。基準ごとに最小の単位で見る。

| 基準 | 最小の単位での変化 | 性質 |
|---|---|---|
| 1 | 性能公称値の基準環境の枠を固定する。ADR-0006 は基準環境の定義を全体設計書に委ねていたため、本 ADR 単独で見れば amendment 相当。ただし architecture.md §5.2 の「絶対値の合否は CI では行わない」という立場を反転させる | 波及先での反転 |
| 2 | 「作者環境だけの記録を判定に使うか」: No → Yes。ADR-0006 が却下した選択肢 (c) の採用 | **既定の反転** |
| 3 | 「AI を判定材料に使うか」: No（明文で不可）→ Yes。「利害の独立した人間の確認」: 必須 → 不要 | **既定の反転** |
| 4 | 証拠形式の変更（清算 PR のリンク一覧 → 導入ゼロの宣言）と、要求の追加（製品の存続。ADR-0023 決定 6 が ADR-0006 の supersession として判断するよう委ねていた） | 証拠形式の変更・要求の追加 |
| 5 | 変更なし | — |
| 運用・再評価トリガ | 12 か月トリガを、v1.0 後の受け皿と新しいトリガへ置き換える | 置き換え |

5 基準のうち 2 つで既定が反転し、2 つで証拠形式または要求が変わる。部分 supersession にすると、v1.0 の判定のたびに ADR-0006 と本 ADR を突き合わせ、どの文言が生きているかを読み分ける必要が生じる。**判定を 1 文書で引けるよう、全体 supersession とする**。ADR-0006 の状態は superseded とし、本文は書き換えない。どの基準をどう緩めたかを後から比較できるよう、履歴として残す。

## 検討した選択肢

### 基準 2・3 の扱い

- **(a) ADR-0006 を維持し、外部協力者を待つ（v1.0 の延期）**: 「v1.0 = 独立した環境で検証済み」という意味を守れる唯一の案で、README の宣言も守れる。欠点は、充足の時期を作者が決められないこと（ADR-0006 が帰結で予見した長期化）。**却下（オーナーの判断、2026-11-16）**。この案を捨てる代償は帰結に書く
- (b) 基準 2・3 を v1.0 の判定から外し、v1.0 後の継続目標へ転換する（代替の証拠は求めない）: 判定が軽くなり、すぐ公開できる。しかし現にある作者 lab の記録すら判定に使わないことになり、ADR-0006 の「判定は沈黙ではなく観測記録で行う」原則も消える。却下
- (c) 基準 2・3 を廃止する: (b) と同じ欠点に加え、外部からの確認の受け皿まで失う。却下
- (d) 基準 2 だけを作者 lab で代替し、基準 3 は外部の人間を探し続ける: 文書の確認は 30 日の運用より協力者の負担が小さく、見つかる見込みは基準 2 より高い。しかし現時点で候補はおらず、v1.0 の時期が外部要因に依存する点は (a) と変わらない。却下（v1.0 後の受け皿として残す。決定 5）
- (e) 依頼による第三者確認（知人や有償の業者に、文書の通読と手順の実施を頼む）: 基準 3 の「利害の独立した人間」を最も短い期間で満たし得る。課題は費用と、依頼先の「利害の独立」をどう示すかである。**オーナーがこの案を検討したかは、本起案の時点で確認できていない**（オーナーへの確認事項）。本起案では採用案に含めない
- (f) v1.0 の名を使わず、限定した表明で出す（例: v0.9 系のまま「本番利用可・独立検証なし」と表明する）: 「v1.0」の意味を守ったまま利用を促せる。しかし互換凍結（基準 4）と署名（基準 5）を備えた版を v0.x と呼び続けると、版番号の意味（Semantic Versioning の 1.0.0 は公開 API の安定の宣言）と実態がずれる。名前を変えて実質を同じにするのは、本 ADR が採る開示より不透明である。却下
- **(g) 作者 lab の検証記録と、ペルソナ通読 + 作者による手順実施で代替し、失ったものを開示する（採用）**: 作者が制御できる期限で v1.0 を判定できる。代替の中身を本 ADR に固定し、RC での lab・連続稼働の最小記録・利用者への開示義務を課して、ADR-0006 から失うものを可能な範囲で小さくする

### 性能公称値（M-6）の基準環境

- オーナー lab の VM: 実機に近いが、1 台・1 構成であり、第三者が同じ条件を再現できない。却下
- 専用の物理機: 再現性はあるが費用がかかり、第三者は同じ機器を持たない。却下
- **GitHub ホストランナーの標準 Windows（採用）**: workflow は公開されており、誰でも同じ条件で再実行できる。ADR-0006 基準 1 が求めた証拠「CI のベンチジョブの合格記録」とも形がそのまま一致する。弱点は個体差が大きいことである（M-5 v2 で保存率 22.4% の個体を観測した。CI の記録上、CPU の世代も個体ごとに異なる）。これは単発の値ではなく、多数の個体の分布の下側で公称値を置くことで扱う（基準 1）

### 連続稼働の最小記録

- 課さない: 公開が最も早い。ただし、時間で効く欠陥（リーク・累積・夜間の保持期間削除・証明書の期限）を検出する機会が lab に一度も無いまま公開することになる
- 7 日: 週単位の事象まで覆えるが、公開をその分遅らせる
- **72 時間（採用案。オーナーへの確認事項）**: 夜間に走る保持期間削除（database.md §3）を 2 回以上またぎ、未達のまま残っているフォワーダの 24 時間計測を内包できる最短の長さである。30 日の代わりにはまったくならないことを、開示に書く

## 決定

### 決定 1: ADR-0006 を全体 supersede する

- 本 ADR の accepted をもって ADR-0006 を superseded とする。v1.0 の公開判定は本 ADR だけを根拠に行う
- ADR-0006 の本文は書き換えない
- ADR-0006 から文言を変えずに引き継ぐもの: 重大不具合の定義と全域条件（決定 2）、基準 5、運用のうち決定 6 に挙げるもの、および判定の作法（**判定はリリース準備時に行い、各基準の充足根拠〔リンク・記録〕を公開の場〔Issue / Discussion / リリースノート〕に残す**。作者の自己申告に閉じる判定〔チェックリストに ✓ を付けるだけ〕を排し、リンク可能な記録で充足を示す）
- 判定の記録は、v1.0 の公開判定 Issue を 1 つ立て、基準ごとに証拠へのリンクを並べる

### 決定 2: 重大不具合の定義と全域条件を、独立した決定にする

ADR-0006 では基準 2 の一部だった。基準 2 を置き換えても失われないよう、本決定に移す。

- **定義**（ADR-0006 基準 2 から文言を変えずに移す）: ①観測不能なログ喪失（発生箇所別カウンタに計上されない喪失）、②設計上の想定（上限・流量制御の既定等）を逸脱した喪失、③起動不能、④データ破損（タイムスタンプ・送信元の誤記録を含む）、⑤ログを取り出せない持続的な閲覧不能。**カウンタに正しく計上された仕様内のドロップは重大不具合としない**
- **全域条件**: 環境を問わず、リリース判定時点で**未解決の重大不具合（上記定義）が存在しない**こと。ADR-0006 の文言から変えたのは、2 環境への参照（「上記 2 環境の内外を問わず」と、括弧内の例示「2 環境が無事でも、第 3 の環境で既知のデータ破損が未解決なら公開できない」）を外した点だけである
- **定義①の射程**（既存の決定の解釈を引き継ぐ。新しい判断ではない）:
  - OS のソケットバッファより前の喪失は、アプリが直接計上できない当初からの明示的な限界であり、定義①の約束の範囲外である（[ADR-0016](0016-os-drop-gauge-mechanism.md) 帰結）
  - クラッシュの瞬間にメモリ上にあったログは件数を計上できない。この局面では、発生の事実と時間範囲を受信断区間として記録することをもって定義①への回答とする（architecture.md §4.4）
- ADR-0006 にあった「期間中に重大不具合が発生したら 30 日を再起算する」規定は、基準 2 とともに消える
- **判定記録**: リリース判定時（v1.0.0 RC の時点）に、open の Issue をすべて定義①〜⑤に照らして分類し、該当しない理由を書く。境界にある事例（例: #518。OS のファイアウォールで落ちる分はカウンタに載らないが、起動時の警告で観測でき、文書化もされている）は、判定の理由を特に詳しく残す
- 定義⑤の「持続的」に数値の目安は置かない。該当の疑いがある事象は、判定記録で個別に理由を書く

### 決定 3: v1.0 公開基準

v1.0 は次の 5 基準を**すべて**満たしたときに公開できる。

#### 基準 1: 機能（ADR-0006 基準 1 を継承し、性能公称値と流量制御の閾値の決め方を固定する）

- ADR-0001 の**導入体験の原則**（インストール → 最初のログ閲覧、追加サーバ製品・手編集なし）が動作している。**証拠**: この動線を検証する E2E テストの CI 実行記録
- ADR-0001 の**品質の原則**の実装群（ADR-0002 決定 2 の発生箇所別ドロップ計測と、決定 4 のベンチの CI 合否判定）が動作している。合否は回帰検知にとどめず、**全体設計書で実測により確定した性能公称値を満たすこと**を含む
- **性能公称値の基準環境と算出の枠**（M-6 で決める事項のうち、本 ADR が固定するもの）:
  - **基準環境は GitHub ホストランナーの `windows-2022` と `windows-2025`** とする。どちらも ADR-0024 決定 1 の推奨区分（Windows Server 2022 / 2025）にあたる。**両方で測り、小さい方を推奨区分の公称値とする**。これで ADR-0024 決定 4 が残した「選ばれなかった側の版の扱い」を、同値の仮定を置かずに解消する
  - 単発の値で公称値を置かない。**多数のランナー個体（1 ジョブ = 1 標本）で測り、分布の下側の値から余裕を差し引いて置く**。標本数、下側の取り方、余裕率、合格の定義は architecture.md §5.2（M-6）で確定する
  - **算出方法は、公称値を決める標本を取る前に確定する**。探索のための予備測定は方法の設計に使ってよいが、公称値の算出には使わない。データを見てから方法を選ぶ余地を残さないためである
  - 合格の定義には、計上済みの破棄と OS バッファ破棄（導出値）がともに 0 であることに加えて、**スプール退避が 0 であること**を含める。持続的な退避は、いずれ破棄に至る状態だからである（architecture.md §3.2.2）
  - 能力の測定は、流量制御の影響を受けない条件で行う。ベンチは本物の `Yagura.Host` を起動するため、既定の流量制御（単一送信元あたり持続 10,000 件/秒の仮値）がそのまま効き、それを超えるレートの測定は流量制御に抑えられる（`BenchHostProcess` と `Program.cs` の結線を読んで確認した）
  - 公称値として表明するのは、組み込み DB（SQLite）の既定構成での UDP / TCP の持続受信とする。**SQL Server の書き込み上限は公称値として表明しない**。ランナー上で継続的に立てられるのは LocalDB だけで、LocalDB は運用形態として対応外だからである（ADR-0024 決定 2）。条件を並記した参考実測値として載せる（オーナーへの確認事項）
  - 公称値には基準環境の構成（論理コア数・メモリ・観測した CPU の内訳・ディスク）を並記し、**利用者の機器での性能を保証する値ではない**ことを書く
  - 生データ（ジョブごとの JSON と環境情報）はリポジトリに収録する。CI の実行記録と artifact は 90 日で消えるためである
  - SQL Server provider の検証記録は、継続の層（LocalDB での適合テスト。全 PR・blocking）と単発の層（実インスタンスの lab）を分けて書く（ADR-0024 改訂 11 を継承）
  - **証拠**: 公称値を確定した PR（算出方法・生データ・集計結果）と、リリース時に基準環境で判定した run の記録
- ADR-0002 で v0.1 必須とした範囲（組み込み DB・SQL Server provider・スプール・バックプレッシャ・箇所別計測）と、**流量制御が完動**している。加えて、**流量制御の既定閾値（M-4）を仮値のまま v1.0 を出さない**。基準環境で、①通常運用で発火しないこと、②暴走した送信元から他の送信元を守れること、の両面を実測で確かめる。両立しない場合は、どちらを優先したかを理由とともに architecture.md §3.3 に記録する。**証拠**: 受け入れテストの CI 記録と、閾値を確定した PR の実測記録
- ADR-0004 決定 3 の **opt-in 強化 3 点（TLS 受信・Web UI の HTTPS・AD 連携認証。AD 環境向けの gMSA を含む）がすべて提供済み**である。**証拠**: 各機能の受け入れテスト記録 + 実環境での動作確認記録（最低 1 環境。作者環境で可）

#### 基準 2': 作者 lab の検証記録（ADR-0006 基準 2 の置き換え）

- **証拠の本体は lab 台帳とする**:
  - installer/lab/ に 1 ファイルで新設する（ファイル名は実施 PR で決める）。lab の 1 回を 1 行とする
  - 列は、回・日付・環境（OS ビルド・SQL Server の版・構成）・検証した版とコミット SHA・**実施者（人間の作者 / AI エージェント）**・使った手順書・結果・見つかった欠陥の Issue・記録の URL とする
  - 対象は、2026-07-05 以降の回のうち、Issue・PR・手順書・ベンチ結果のいずれかに記録が残っているもの。記録がチャットにしか無い回は証拠に数えない（台帳に載せる場合は「記録なし」と書く）
  - **無効だった検証を明示する**。#514 で無効と分かったアップグレード確認は、その項目を無効と記す
  - 台帳を作るときに、既存の記録の整合を正す（第 2 回・第 3 回の番号の食い違い、手順書の冒頭注記と実施記録表の古さ、第 3 回の SQL Server 2025 の部分実測、未マージの PR を指すリンク切れ）
  - 台帳と報告書に資格情報（パスワード等）を書かない。既存の記録も点検する
- **v1.0.0 RC で lab を 1 回、必ず行う**:
  - 対象は、v1.0.0 として公開するのと同じコミットからリリース workflow で作った MSI（署名付き）とする
  - 環境は、推奨区分の Windows Server 1 台（lab で一度も踏んでいない Server 2022 を推奨）と、対応下限の Server 2019 とする。下記 (iii) の拒否の確認には Server 2016 を使う
  - 内容は次の 4 点とする。(i) 新規インストール → 受信 → 閲覧。(ii) **公開済み v0.5.0 の MSI からの更新**を、AD・gMSA と SQL Server の実インスタンスを含む構成で行う（CI では踏めない範囲。基準 4）。(iii) 第 5 回として依頼済みの内容（#511 の修正の確認、昇格の 1 サイクルでの #510・#512 の観測、Server 2016 での拒否ダイアログの目視）。(iv) 全域条件の判定に必要な観測
  - RC の後で製品コードに変更が入った場合は、変更が及ぶ項目を再実施する。対象の判定は ADR-0024 改訂 2 が定めた対象パスに準じて機械的に行ってよい
- **連続稼働の最小記録として、RC で 72 時間以上連続稼働させる**:
  - 開始時と終了時に、発生箇所別カウンタの値を含む報告を残す。ADR-0006 基準 2 の「判定は沈黙ではなく観測記録で行う」の形式を継承する
  - 送信元は、lab クライアントの Fluent Bit と、テスト送信で模した複数の送信元とする。フォワーダの 24 時間計測を内包させる
  - 計画外の停止があった場合は原因を記録する。重大不具合に当たれば、修正後に 72 時間をやり直す
- 全域条件の判定記録（決定 2）を残す
- **実施者**: 基準 2' の lab は AI エージェントが実施してよい。ただし台帳に実施者を偽りなく書く
- **正直な限界**: 基準 2' の証拠の大半は、基準 1 が既に認めている「実環境での動作確認記録（作者環境で可）」と同じ母集団である。**基準 2' が独自に加えるのは、台帳化（網羅性と実施者の明示）、RC での lab、72 時間の連続稼働記録、全域条件の判定記録の 4 点に限られる**。基準 2 が担っていた独立性の検証は、どれも代わりに担わない
- **証拠**: lab 台帳へのリンク、RC lab の報告（判定 Issue）、72 時間の開始・終了報告、全域条件の判定記録

#### 基準 3': 利用者向け文書の完備 — ペルソナ通読 + 作者による手順実施（ADR-0006 基準 3 の置き換え）

- **前提条件として、対象文書がそろっていること**。誰が確認するかより先に、確認の対象が存在しなければならない:
  - 導入: README（インストール・システム要件・既定ポート・セキュリティの前提）、SECURITY.md
  - 運用: operations.md の既存の節と、新設する次の手順——バックアップ・復旧（DPAPI で暗号化した値の再入力を含む）、通常のアップグレード（v0.5.0 から v1.0 へ。0.3.3 以前は先にアンインストールが要ることを含む）、蓄積ログ移行機能の使い方、サーバの移設・交換、アンインストールとデータの扱い
  - ADR-0004 委任の利用者向けチェックリスト類: 信頼ネットワーク成立チェックリスト、リバースプロキシ前置の要件（v1.0 でも前置をサポートしないことの明示。決定 7）、DPAPI のサーバ束縛とバックアップ手順、localhost 監査で個人を特定できない限界
  - ガイド: gMSA によるサービス実行、Windows イベントログの転送
- **「手動 DB 移行手順（ADR-0002 決定 3 (iii)）」は、蓄積ログ移行機能（database.md DB-5）の使い方と、SQL Server から別の SQL Server へのサーバ交換手順に置き換える**。ADR-0002 決定 3 (iii) は、手動手順を移行機能の提供「までの間」の措置としていた。移行機能は提供済みである
- **(i) ペルソナによる通読**: 5 ペルソナが、対象文書のコミット SHA を固定して通読する。分担は佐藤 = 導入、鈴木 = 運用と障害時、田中 = セキュリティの前提、リサ = 文書の品質と一貫性、クリス = 主張の根拠とする。各ペルソナは「文書だけでは先へ進めない箇所」と「製品の挙動と食い違う箇所」を節番号つきで挙げる。結果は判定 Issue にペルソナごと 1 コメントで残し、モデル名・実施日・文書の SHA を書く（persona-review.md の作法）
- **(ii) 作者による手順の実施**: 作者本人が、(i) と同じ文書 SHA（または (i) の指摘を直した後の SHA）だけを頼りに、新しく用意した推奨区分の Windows Server で、少なくとも次の項目を実施する。AD を要する項目は既存の AD lab を使ってよい

  | # | 実施項目 | 対象文書 |
  |---|---|---|
  | 1 | 対話インストールを既定のまま行い、別ホストから UDP 514 へ送信し、8514 で閲覧し、スタートメニューから管理画面へ入る | README「インストール」「システム要件」「既定ポート」 |
  | 2 | 記述と実機（ファイアウォール規則のプロファイル、6514 の規則が自動では追加されないこと）を突き合わせる | README「セキュリティの前提」、SECURITY.md |
  | 3 | TLS 受信を有効化し、文書どおりに規則を足し、別ホストから TLS で送る | operations.md §12.5 |
  | 4 | SQL Server Express への本番昇格、再起動、件数の確認、蓄積ログの移行、旧 DB の処分（#502 の実装後の手順） | README・operations.md の昇格と処分の節 |
  | 5 | バックアップと復旧（SQLite、SQL Server、設定、DPAPI で暗号化した値の再入力） | 新設 |
  | 6 | v0.5.0 から v1.0 への通常のアップグレード | 新設 |
  | 7 | 別ホストへの移設（復元） | 新設 |
  | 8 | SQL Server を止めて縮退運転を観察し、復旧する | operations.md §10・§11.1 |
  | 9 | 閲覧認証・管理認証・緊急全失効・ブレークグラス | operations.md §2・§3・§5・§6 |
  | 10 | 閲覧 HTTPS と GPO によるルート証明書の配布。Chrome と Edge で確認する | operations.md §9.1・§9.2 |
  | 11 | 導入時の gMSA 指定と、稼働中の切替 | gMSA ガイド §3・§5 |
  | 12 | 転送の導入手順と、管理画面での配布キット生成 | Windows イベントログ転送ガイド |
  | 13 | 信頼ネットワーク成立チェックリストを実際の lab 環境に当てはめる | 新設 |

- **記録**: 項目ごとの結果、文書のコミット SHA、**手順どおりに進まなかった箇所（必須欄）**を判定 Issue に残す。進まなかった箇所は文書（または製品）を直し、直した部分を再実施する。確認の後で該当文書に実質的な変更が入った場合、変更部分は再確認の対象とする（ADR-0006 基準 3 の規定を継承）
- **実施者の定義**: (ii) を操作するのは**作者本人（人間）に限る**。lab 機上の AI エージェントに代行させた実施は (ii) の証拠に数えない（基準 2' の台帳には載せてよい）。(i) が AI である以上、(ii) まで AI にすると、人が文書を読んで操作できるかを誰も確かめないことになるためである
- **証拠**: 判定 Issue 上の、ペルソナごとの通読結果と、作者による項目別の実施記録（いずれも文書のコミット SHA つき）

#### 基準 4: 後方互換性の凍結（ADR-0006 基準 4 を継承し、証拠形式と要求を改める）

- 設定スキーマ・DB スキーマ・保存データ形式について、**v1.0 以降は後方互換を破る変更を MAJOR バージョンでのみ行う**運用を開始できる状態にある。凍結対象の一覧は database.md §7 に置く（変更なし）
- **deprecation の清算**: v0.x で導入した deprecation が 0 件であることを宣言し、その根拠を判定 Issue に残す。根拠は、v0.1.0〜v0.5.0 の全リリースと v1.0 の設定キーを比べて削除されたキーが 0 件であること、`[Obsolete]` の付いた要素が 0 件であることとする。清算の対象が無いため、清算 PR のリンク一覧は求めない。あわせて、v1.x で適用する deprecation 規約を conventions.md で確定させる
- **更新の実証**: 直前の v0.x は v0.5.0 である（v0.6.0 は出さない。決定 7）。**公開済みの v0.5.0 の MSI（リリース資産そのもの。.sha256 で照合する）から v1.0 RC の MSI への更新を CI で実証することを、ADR-0006 基準 4 の「実地に実証」にあたるものと認める**。同じソースツリーから版番号だけを下げて作った MSI は使わない。#479・#514 で、版だけ上がって中身が旧版のままのファイルが残る失敗が起き、その方式ではこれを捉えられないと分かっているためである
  - 検証項目: 蓄積ログ（件数と内容）、設定（DPAPI で暗号化した値を含む）、管理者アカウント、監査記録、発生箇所別カウンタの連続性、未消化のスプールセグメント（database.md §7 の凍結対象）が保全されること
  - **製品の存続**（ADR-0023 決定 6 への回答として要求に加える）: 更新後に新版のサービスが稼働し、全リスナを新版のプロセスが bind し、受信と閲覧が成立し、「アプリと機能」の製品エントリが 1 件であること。更新が失敗した場合に旧版が残り、受信が再開することも、同じ v0.5.0 を起点に確かめる
  - CI で踏めない範囲（AD・gMSA の構成、SQL Server の実インスタンス）は、基準 2' の RC lab で踏む
  - **正直な限界**: CI の更新元は作ったばかりのデータであり、数か月運用した v0.5.0 環境の状態は再現しない。また、v0.5.0 を OS ビルド 17763 未満（Server 2016 以前など）で動かしている利用者は、MSI の対応 OS 下限（ADR-0024 決定 6）のため v1.0 へ更新できない（既存のインストールは無傷で残る）。これをリリースノートに書く
- **証拠**: 凍結対象一覧へのリンク、deprecation が 0 件であることの根拠、更新の実証の run と artifact

#### 基準 5: リリースの完全性 — コード署名を含む（ADR-0006 基準 5 を文言を変えずに継承）

- リリース資産（インストーラ）に **Authenticode コード署名（タイムスタンプ付き）**が付与されている（SmartScreen 警告への対処 + 証明書期限後も署名が有効であり続けるため。証明書の入手・管理はリリース準備の課題として別途扱う）
- リリース資産に checksum（.sha256）が添付され、リリース手順が再現可能な形で文書化されている
- **SECURITY.md が実態と一致している**: リリース提供の開始を反映し、**v1.0 以降の修正提供対象（サポート対象バージョン。最低限「最新リリース + main」の明記）が確定**している
- **証拠**: リリースノートから署名の検証手順（signtool verify 等）と .sha256 が辿れること、SECURITY.md の該当節へのリンク
- 判定の前提（現況から必要なもの）: ADR-0014 が accepted であること、SECURITY.md のサポート対象表が v1.0 を反映していること、リリース手順が 1 か所にまとまっていること

### 決定 4: 代替したことと失ったものを、利用者に開示する

ADR-0006 は、署名なしで公開する場合について「代替手段の差し替えではなく『本番推奨』の意味の縮小であり、利用者への明示義務を伴う」と定めていた（同 ADR の再評価トリガ）。本 ADR の代替も「本番推奨」の意味の縮小であり、同じ型の明示義務を課す。

- **掲載先**: README の状態表示の節と、v1.0.0 のリリースノートの両方。v1.0.0 より後のリリースノートからは README の該当節へリンクする
- **必須の内容**:
  1. v1.0 の判定は、独立した環境での運用実績と、作者と独立した人間による文書の実地確認を**得ないまま**行ったこと
  2. 代わりに何に基づいたか（作者 lab の検証記録〔台帳へのリンク〕、AI ペルソナによる文書の通読、作者による手順の実施）
  3. 確かめていないこと: 連続稼働の最長記録（実績の値で書く）、実機器のトラフィックと多数の送信元からの受信、SQL Server の Express 以外のエディション、作者の環境以外での動作
  4. 性能公称値は GitHub ホストランナーでの実測であり、利用者の機器での性能を保証しないこと
  5. 運用報告と文書の不備の報告の受付先（決定 5）
  6. 本 ADR へのリンク
- README の「基準は先に固定してあり、達成しやすい形に動かしません」は、**黙って消さない**。基準を達成前に改定したこと（本 ADR）を、同じ場所に書く
- 文言の例（拘束はしない）:「v1.0 は、独立した環境での運用実績と、第三者による文書の確認を得ていません。公開の判定は作者の検証環境での記録に基づきます（詳細: ADR-0025）。」
- 開示は、決定 5 の記帳で失ったものが埋まるまで維持する。埋まった項目だけを書き換える

### 決定 5: v1.0 の後の扱い

- **受け皿を続ける**: 運用報告と文書確認報告の Issue テンプレートを用意し、README で呼びかけを続ける。運用報告の様式は、ADR-0006 基準 2 の観測記録の形式（開始時・終了時の発生箇所別カウンタ。重大事象の発生時は随時）を継承する。PR #448 の「試用協力の募集の節を削除する」方針は改める
- **記帳**: 独立した環境からの 30 日以上の運用報告と、作者と独立した人間による文書確認の報告は、本 ADR の改訂履歴に記帳する。ADR-0006 の基準 2（2 環境 × 30 日）・基準 3 の水準に達したら、その事実を記帳し、決定 4 の開示を更新する
- **重大不具合が報告されたとき**: v1.0 系列で重大不具合（決定 2）が報告された場合、最優先で修正版を出し、README の既知の問題に載せる。あわせて、その不具合が本 ADR の代替で失った検証（独立した環境・長期の連続稼働・実機器のトラフィック）でしか見つからない種類のものかを判断し、改訂履歴に記帳する

### 決定 6: ADR-0006 の運用から引き継ぐもの

- 基準は**満たすまで下げない**。基準の変更（緩和を含む）は本 ADR の supersession によってのみ行い、必ず公開の場（PR + ペルソナレビュー）を通す
- **自己拘束の自覚**: 決定者と supersession の承認者が同一人物である以上、この拘束は手続きと公開記録による自己拘束である。本 ADR はその自己拘束を基準の達成前に緩めた実例であることを、ここにも記す。**本 ADR の基準を緩める supersession を起案する場合は、当該リリースの延期を対等な選択肢として併記・比較し、緩和で失うものを決定 4 と同じ形で利用者に開示する**（ADR-0006 が署名なしの公開について課した歯止めを、基準の緩和全般に広げる）
- **量的な床も自己拘束の内側に置く**: 性能公称値（基準 1）の確定後の引き下げは本 ADR の変更と同等に扱い、supersession に準ずる手続き（PR + ペルソナレビュー + 変更理由の公開）を要する。ADR-0006 にあった実運用の下限流量（基準 2）は、全体設計書で確定されないまま、基準 2 とともに廃止する
- **署名を外す変更の歯止め**: ADR-0006 の再評価トリガにあった歯止め条件（①無償・低コストの代替の検討記録、②延期との対等な比較、③署名なしの事実と検証手順の明示）は本 ADR に引き継ぐ
- v0.x の間の運用（MINOR で機能を追加し、後方互換を破る変更も許容する。conventions.md の deprecation 階段は守る）は v1.0 の公開で終わる。以後は基準 4 の運用（後方互換を破る変更は MAJOR でのみ行う）に移る

### 決定 7: v1.0 の公開判定に付随する判断の記録

オーナーが 2026-11-16 に既定判断とした事項を、判定の前提として記録する。いずれも他の ADR・設計書の決定を適用するものであり、本 ADR はそれらの決定を変えない。

- **閲覧 HTTPS のブラウザ実機検証（#455）**: 2026-07-26 の実機記録をもって M1・M2 を通過とし、M3・M6・M7 は v1.0 の後の Issue へ移す。ただし 07-26 の記録はクライアントの種別（Chrome / Edge）を明記していないため、基準 3' の実施項目 10 で Chrome と Edge による確認を兼ねる
- **SQL Server 2025**: v1.0 では対応を表明しない（未検証）。ADR-0024 決定 2 の表明ゲートを閉じたまま公開する。2026-08-08 の lab で接続・照合順序・スキーマ作成を部分的に実測した事実（#514・#515）は、ADR-0024 の改訂として記録する
- **リバースプロキシの前置**: v1.0 でもサポートしない。ADR-0004 委任の利用者向け文書でそれを明示する
- **ADR-0014**: accepted にする（基準 5 の前提）
- **v0.6.0 は出さない**。v0.5.0 から v1.0.0 へ直接更新する（基準 4 の実証の起点）
- **#502（昇格後の旧 DB の自動処分）**: v1.0 で実装する。設計は database.md で行い、別途ペルソナレビューを通す。設計の入力として、蓄積ログ移行の機会を消さないよう、移行の完了または「移行しない」の明示の選択を待ってから処分することを前提に置く（現行の operations.md §13 の手動手順は移行機能に触れていない）

## 帰結

- **良くなること**:
  - v1.0 の時期を外部要因に預けず、作者が制御できる作業で判定できる
  - lab の記録が台帳として整理され、実施者・版・環境・無効だった検証が明示される。これまで記録は Issue・PR・手順書に散らばり、番号の食い違いもあった
  - 基準 4 が強くなる。公開済み v0.5.0 の MSI からの更新を実証し、「製品の存続」を要求に加えて ADR-0023 決定 6 の宿題を閉じる
  - 性能公称値が、誰でも再実行できる環境で、方法を先に固定した手続きによって決まる
  - 基準 3' の前提として、欠けていた運用文書（バックアップ・アップグレード・移設）が書かれる
- **悪くなること（代替で失うもの）**:
  1. **独立性**: 「作者の環境でしか動かない」可能性を排除する手段が無くなる。ADR-0006 が却下した選択肢 (c) を採ることになる。lab の実施者も、作者本人と、コードを書いた AI と同系統の AI である
  2. **時間で効く欠陥を検出する機会**: 30 日に対して 72 時間である。リーク、累積、保持期間の長期の挙動、DB の成長と Express の容量接近警告、証明書の期限経過、Windows Update による再起動は踏まない
  3. **実機器のトラフィックの多様性と、多数の送信元からの継続受信**: ベンダごとの書式の揺れや自然なバーストを受けない。途絶検知と流量制御が実際のトラフィックで試されない
  4. **期間をまたいだ観測記録**: 72 時間の 1 回だけになる
  5. **SQL Server の Express 以外のエディションと、実運用の規模**
  6. **文書確認の独立性と「人間であること」**: 通読は AI が、手順の実施は文書を書かせた側の作者が行う。書いた本人の暗黙知による見落としは避けられない。文書を書いた AI と通読する AI が同系統であることも、同じ問題を抱える
  7. **自己拘束の信用**: README で「動かさない」と宣言した基準を、12 か月のトリガより前に動かした。今後このプロジェクトが「先に固定した」と書く基準の重みは下がる
  8. **v1.0 の版そのものでの実地確認の厚み**: RC での lab は 1 回である
- **受け入れるリスク**:
  - v1.0 の最初の独立した利用者が、lab で踏まなかった環境差の欠陥を踏む。対処は決定 5（最優先の修正と、既知の問題への掲載）とする
  - 公称値が、ランナーの構成変更（イメージの更新・CPU 世代の入れ替え）で割れる。余裕率と、割れた場合の手続き（決定 6）で扱う
  - 基準 3' を通っても、実在の管理者が文書だけでは到達できない箇所が残る。決定 5 の文書確認報告で拾う
  - 開示を読まずに「v1.0 = 独立した検証済み」と受け取る利用者がいる。開示を README の状態表示の節に置くことで最小化する

## 先送りにする場合の再評価トリガ

本 ADR は「外部からの確認」を v1.0 の後へ先送りする。次のいずれかで再評価する。

- **独立した環境から重大不具合（決定 2）が報告された場合**: 決定 5 の処置に加えて、それが代替で失った検証でしか見つからない種類かを判断し、記帳する。**v1.0 の公開から 6 か月以内にその種類の報告が 1 件でもあれば、v1.x の「本番推奨」の表明の扱いを再検討する**（結論が「変えない」でも、理由を改訂履歴に残す）。表明を変える場合は本 ADR の supersession による
- **独立した環境から 30 日以上の運用報告が届いた場合、または作者と独立した人間から文書確認の報告が届いた場合**: 記帳し、決定 4 の開示を更新する
- **2027-07-05（v0.1.0 の公開から 12 か月。ADR-0006 の再評価トリガの期日）の時点で外部の運用報告が 0 件の場合**: 呼びかけの方法を再評価する。ADR-0006 の期日を失わないよう、ここに残す
- **性能公称値の余裕が architecture.md §5.2 の閾値を割った場合**: 決定 6 の手続きに従う
