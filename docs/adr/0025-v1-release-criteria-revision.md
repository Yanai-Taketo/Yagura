### 12 か月トリガより前に改定する理由（オーナーの判断）

ADR-0006 の再評価トリガは「v0.x 公開から 12 か月を経ても試用環境が現れない場合、呼びかけ方法と基準の現実性を再評価する」である。v0.1.0 の公開は 2026-07-05 なので、トリガの時点は 2027-07-05 になる。本 ADR はその約 4.4 か月の時点で基準そのものを改定する。**トリガが発火したからではない。オーナーの判断（2026-11-16）による前倒しである**。

判断の中身は次のとおり。

- 基準 2・3 のうち、独立した 2 環境と利害の独立した人間を求める部分は、外部協力者の出現に依存し、作者の作業では期限を持てない。募集を始めてから約 4 か月、申し出は 0 件である。12 か月まで待てば状況が変わると考える根拠を、作者は持っていない。12 か月の時点で再評価しても、この部分について取れる選択肢は変わらないと作者は見込んでいる。ただし、これは検証された主張ではない。
- 一方、基準 2 のうち**作者自身の環境での 30 日の観測**は、外部協力者に依存しない（文脈の表の「0 環境」には作者の環境も含まれる）。本 ADR はこれも求めない。その理由は外部への依存ではなく、追加の lab を課さないというオーナーの選好である（「連続稼働の最小記録」）。
- 一方、作者の lab は前節のとおり、外部の試用者がまず行わない種類の検証を積み、約 30 件の欠陥を見つけ、その大半を直してきた。
- そこで、v1.0 の公開を外部要因に預けたまま待つより、**作者 lab の記録で判定して今公開し、代替で失ったものを利用者へ開示する**方を選ぶ。

この判断は「基準を満たせないので基準を動かす」ものである。ADR-0006 の文脈が警戒した「基準を後から決めると、達成しやすい形に基準の方が動く」に、そのまま当たる。本 ADR はこれを否定しない。

### README の宣言との緊張

README は「基準は先に固定してあり、達成しやすい形に動かしません」と宣言している（「v0.5 の位置づけ」）。本 ADR はこの宣言に反する。宣言を黙って消すのではなく、反したことを同じ場所で利用者に書く（決定 4）。

## 本 ADR の位置づけ — 自己拘束が弱まることについて

ADR-0006 は「決定者と supersession の承認者が同一人物である以上、この拘束は手続きと公開記録による自己拘束である」と自覚的に記していた。**本 ADR は、その自己拘束を基準の達成前に緩める最初の実例である。**

- 本 ADR を承認するのは、基準を緩めることで利益を得る作者本人である。ペルソナレビューは起案側が起動する AI であり、構造的な独立性を持たない（persona-review.md の運用ノート）。**本 ADR の正当性を担保する独立した承認者はいない**。
- したがって本 ADR が拠り所にできるのは次の 4 点だけである。
  1. 改定の事実と理由を公開の場に残すこと
  2. 代替で失ったものを利用者へ開示する義務を課すこと（決定 4）
  3. 作者が後から代替の中身を薄められないよう、代替に使う証拠の範囲と形式を本 ADR に固定すること（基準 2' の lab 台帳の要件、基準 3' のペルソナ通読の作法と、手順に沿った lab の回の対応づけ）
  4. v1.0 の後も外部からの確認を受け付け続けること（決定 5）
- 本 ADR は追加の lab を課さない（オーナーの判断、2026-11-16）。したがって 3 で固定するのは新しい検証ではなく、**既存の記録をどの範囲で、どう示して判定に使うか**である。代替の中身は薄い。その薄さは決定 4 の開示で利用者に示し、ここに固定した範囲をさらに狭める変更は決定 6 の手続きを要する
- ADR-0006 は検討した選択肢で「(c) 作者環境のみ: 『独立した環境で動く』ことの検証にならない。却下」としていた。本 ADR はこの却下した選択肢を、開示義務と、既存の記録を台帳として固定することを条件に採る。**却下の理由（独立した環境での動作は検証されない）は本 ADR でも正しく、解消されない**。
- **決定の順序**: 本 ADR の主な決定（追加の lab を課さないこと、Windows 実機での確認が要る Issue を CI の通過で閉じることなど）は、オーナーが 2026-11-16 にペルソナレビューの前に下した。初版（b464452）にあった 72 時間の連続稼働、v1.0.0 候補での lab、(ii) の実施者を作者本人（人間）に限る要件は、同日のレビュー前の改訂（8a6c979）で外した。#510・#512 は本 PR のレビュー中に修正 PR のマージで閉じた。つまり公開の場（PR + ペルソナレビュー）は、決定を形づくる場ではなく、**下した決定とその理由を記録し、批判を受ける場**として使われた。後から読む人がこの順序を取り違えないよう、ここに記す

## amendment か supersession かの自己吟味

[docs/adr/README.md](README.md) は「既定を反転させるなら supersession」「疑わしければ supersession 側に倒す」「最小の単位で反転の有無を検証する」と定める。基準ごとに最小の単位で見る。

| 基準 | 最小の単位での変化 | 性質 |
|---|---|---|
| 1 | 性能公称値の基準環境の枠を固定する。ADR-0006 は基準環境の定義を全体設計書に委ねていたため、本 ADR 単独で見れば amendment 相当。ただし architecture.md §5.2 の「絶対値の合否は CI では行わない」という立場を反転させる | 波及先での反転 |
| 2 | 「作者環境だけの記録を判定に使うか」: No → Yes。ADR-0006 が却下した選択肢 (c) の採用 | **既定の反転** |
| 3 | 「AI を判定材料に使うか」: No（明文で不可）→ Yes。「利害の独立した人間の確認」: 必須 → 不要 | **既定の反転** |
| 4 | 証拠形式の変更（清算 PR のリンク一覧 → 導入ゼロの宣言）と、要求の追加（製品の存続。ADR-0023 決定 6 が ADR-0006 の supersession として判断するよう委ねていた） | 証拠形式の変更・要求の追加 |
| 5 | 変更なし | — |
| 運用・再評価トリガ | 12 か月トリガを、v1.0 後の受け皿と新しいトリガへ置き換える | 置き換え |

5 基準のうち 2 つで既定が反転し、2 つで証拠形式または要求が変わる。部分 supersession にすると、v1.0 の判定のたびに ADR-0006 と本 ADR を突き合わせ、どの文言が生きているかを読み分ける必要が生じる。**判定を 1 文書で引けるよう、全体 supersession とする**。ADR-0006 の状態は superseded とし、本文は書き換えない。どの基準をどう緩めたかを後から比較できるよう、履歴として残す。

## 検討した選択肢

### 基準 2・3 の扱い

- **(a) ADR-0006 を維持し、外部協力者を待つ（v1.0 の延期）**: 「v1.0 = 独立した環境で検証済み」という意味を守れる唯一の案で、README の宣言も守れる。欠点は、充足の時期を作者が決められないこと（ADR-0006 が帰結で予見した長期化）。**却下（オーナーの決定、2026-11-16）**。理由: 外部協力者に依存する部分について、充足の時期を作者が決められないこと。延期の費用と緩和に固有の利益は「延期（(a)）との比較」に、この案を捨てる代償は帰結に書く
- (b) 基準 2・3 を v1.0 の判定から外し、v1.0 後の継続目標へ転換する（代替の証拠は求めない）: 判定が軽くなり、すぐ公開できる。しかし現にある作者 lab の記録すら判定に使わないことになり、ADR-0006 の「判定は沈黙ではなく観測記録で行う」原則も消える。却下
- (c) 基準 2・3 を廃止する: (b) と同じ欠点に加え、外部からの確認の受け皿まで失う。却下
- (d) 基準 2 だけを作者 lab で代替し、基準 3 は外部の人間を探し続ける: 文書の確認は 30 日の運用より協力者の負担が小さく、見つかる見込みは基準 2 より高い。しかし現時点で候補はおらず、v1.0 の時期が外部要因に依存する点は (a) と変わらない。却下（v1.0 後の受け皿として残す。決定 5）
- (e) 依頼による第三者確認（知人や有償の業者に、文書の通読と手順の実施を頼む）: 基準 3 の「利害の独立した人間」を外部の協力者を待つより短い期間で満たし得る。課題は費用と、依頼先の「利害の独立」をどう示すかである。加えて、依頼先が見つかり実施を終える時期は相手に依存し、(a)(d) と同じく v1.0 の時期が外部要因に依存する。採用案に含めない
- (f) v1.0 の名を使わず、限定した表明で出す（例: v0.9 系のまま「本番利用可・独立検証なし」と表明する）: 「v1.0」の意味を守ったまま利用を促せる。名前そのものが状態を表すので、(g) の受け入れるリスクに挙げた「開示を読まずに『v1.0 = 独立した検証済み』と受け取る」誤読も生じない。しかし互換凍結（基準 4）と署名（基準 5）を備えた版を v0.x と呼び続けると、版番号の意味（Semantic Versioning の 1.0.0 は公開 API の安定の宣言）と実態がずれる。却下。初版はもう 1 つの理由に「名前を変えて実質を同じにするのは、開示より不透明」を挙げていたが、上記の誤読の点で (g) の方が不透明になり得るため、この理由は撤回する。(f) を採らない理由は版番号のずれだけである
- **(g) 作者 lab の検証記録と、ペルソナ通読 + 作者による手順実施で代替し、失ったものを開示する（採用）**: 作者が制御できる期限で v1.0 を判定できる。代替に使う証拠の範囲と形式（lab 台帳の要件、ペルソナ通読の作法、手順に沿った lab の回の対応づけ）と、利用者への開示義務を本 ADR に固定する。追加の lab は課さない（後述の「連続稼働の最小記録」「v1.0 の版での lab と、作者本人による手順の実施」）。ADR-0006 から失うものを小さくするのではなく、**失ったものを利用者が知り得る形にする**案である
- (h) 1.0.0 を基準 1・4・5（機能・互換凍結・署名）で出し、「本番推奨」の表明を 1.0.0 から切り離して、ADR-0006 の基準 2・3 のまま据え置く: 版番号は Semantic Versioning の読みどおりになり、時期は作者が決められ、自己拘束は緩まない。開示も 1 行で済む（例:「本番推奨の判定は、独立した確認を待っています」）。(g) との違いは、v1.0 で「本番推奨」を表明するかどうかだけである。**却下（オーナーの決定、2026-11-16: 基準 2・3 は据え置かず、代替で満たす）**。(h) を採らない実質の理由は、「本番推奨」の表明を外部協力者の出現に預けたままにすると、その表明について (a) と同じく時期を作者が決められないことである。その代わりに (g) は、「本番推奨」を意味を縮小したまま表明し、縮小を開示する義務（決定 4）と、条件つきの始め方を勧める義務（決定 4 の 7）を負う

### 延期（(a)）との比較

決定 6 は、基準を緩める supersession に、延期を対等な選択肢として比べることを求める。その最低限の中身（決定 6）を、本 ADR 自身に当てはめる。

- **延期の費用**: v1.0 の時期が外部協力者の出現に依存し、期限を持てない。失うのは、v1.0（互換の凍結と本番推奨の表明）の時期を決める作者の裁量である。v1.0 を待っている利用者は、確認できた範囲ではいない（試用の申し出は 0 件、Issue の作成者は全員オーナー）
- **緩和に固有の利益**（延期しても得られる利益を除いたもの）: 帰結の「良くなること」のうち、lab 台帳の整理、基準 4 の強化、方法を先に固定した公称値、欠けていた運用文書は、延期しても得られる。**本 ADR の本文が示せる固有の利益は、v1.0 の時期を作者が決められることだけである**。これは決定の言い換えに近く、作者以外の誰かの利益としては示せていない
- **公開日への影響の見積もり**: 公開までの期間を理由に却下した案（7 日・72 時間の連続稼働、v1.0.0 候補での lab、作者本人による手順の実施）について、公開日を何日遅らせるかは見積もっていない。却下の理由はオーナーの選好（公開までの期間を優先する）であり、遅れの日数との比較によるものではない

### 性能公称値（M-6）の基準環境

- オーナー lab の VM: 実機に近いが、1 台・1 構成であり、第三者が同じ条件を再現できない。却下
- 専用の物理機: 再現性はあるが費用がかかり、第三者は同じ機器を持たない。却下
- **GitHub ホストランナーの標準 Windows（採用）**: workflow は公開されており、誰でも同じ workflow を同じランナーラベルで再実行できる（ラベルが指すイメージは更新されていくため、同一条件の再現を保証するものではない）。ADR-0006 基準 1 が求めた証拠「CI のベンチジョブの合格記録」とも形がそのまま一致する。弱点は個体差が大きいことである（M-5 v2 で保存率 22.4% の個体を観測した。CI の記録上、CPU の世代も個体ごとに異なる）。これは単発の値ではなく、多数の個体の分布の下側で公称値を置くことで扱う（基準 1）

## 決定

### 決定 1: ADR-0006 を全体 supersede する

- 本 ADR の accepted をもって ADR-0006 を superseded とする。v1.0 の公開判定は本 ADR だけを根拠に行う
- ADR-0006 の本文は書き換えない
- ADR-0006 から文言を変えずに引き継ぐもの: 重大不具合の定義と全域条件（決定 2）、基準 5、運用のうち決定 6 に挙げるもの、および判定の作法（**判定はリリース準備時に行い、各基準の充足根拠〔リンク・記録〕を公開の場〔Issue / Discussion / リリースノート〕に残す**。作者の自己申告に閉じる判定〔チェックリストに ✓ を付けるだけ〕を排し、リンク可能な記録で充足を示す）
- 判定の記録は、v1.0 の公開判定 Issue を 1 つ立て、基準ごとに証拠へのリンクを並べる
- Issue とそのコメントは後から編集・削除できる。そこで、**公開時点の判定 Issue の内容をリポジトリ（docs 配下またはリリースノート）に写し、そのコミット SHA をリリースノートから辿れるようにする**。v1.0 の判定が、どの記録のどの状態に基づいたかを後から確定できるようにするためである

### 決定 2: 重大不具合の定義と全域条件を、独立した決定にする

ADR-0006 では基準 2 の一部だった。基準 2 を置き換えても失われないよう、本決定に移す。

- **定義**（ADR-0006 基準 2 から文言を変えずに移す）: ①観測不能なログ喪失（発生箇所別カウンタに計上されない喪失）、②設計上の想定（上限・流量制御の既定等）を逸脱した喪失、③起動不能、④データ破損（タイムスタンプ・送信元の誤記録を含む）、⑤ログを取り出せない持続的な閲覧不能。**カウンタに正しく計上された仕様内のドロップは重大不具合としない**
- **全域条件**: 環境を問わず、リリース判定時点で**未解決の重大不具合（上記定義）が存在しない**こと。ADR-0006 の文言から変えたのは、2 環境への参照（「上記 2 環境の内外を問わず」と、括弧内の例示「2 環境が無事でも、第 3 の環境で既知のデータ破損が未解決なら公開できない」）を外した点だけである
- **定義①の射程**（既存の決定の解釈を引き継ぐ。新しい判断ではない）:
  - OS のソケットバッファより前の喪失は、アプリが直接計上できない当初からの明示的な限界であり、定義①の約束の範囲外である（[ADR-0016](0016-os-drop-gauge-mechanism.md) 帰結）
  - クラッシュの瞬間にメモリ上にあったログは件数を計上できない。この局面では、発生の事実と時間範囲を受信断区間として記録することをもって定義①への回答とする（architecture.md §4.4）
- ADR-0006 にあった「期間中に重大不具合が発生したら 30 日を再起算する」規定は、基準 2 とともに消える
- **判定記録**: リリース判定時に、open の Issue と、実機未確認のラベルを付けて閉じた Issue（決定 7）をすべて定義①〜⑤に照らして分類し、該当しない理由を書く。境界にある事例（例: #518。OS のファイアウォールで落ちる分はカウンタに載らないが、起動時の警告で観測でき、文書化もされている）は、判定の理由を特に詳しく残す
- **観測の量**: 判定記録の冒頭に、判定の根拠になった観測の量を書く。lab の延べ稼働時間、最長の連続稼働時間、CI と lab で処理した延べ件数である（記録から分かる範囲で書き、分からない部分は「不明」と書く）。外部の利用者は 0 人で、lab の連続稼働も最長で数時間単位である。「未解決の重大不具合なし」は、見ていないから無いのではなく、この量を観測したうえでの「なし」として読めるようにする
- **出荷時点のセキュリティ確認の記録**: 重大不具合の定義①〜⑤はログの喪失・起動不能・データ破損・閲覧不能だけを対象にし、脆弱性やセキュリティ判断を誤らせる欠陥を含まない。そこで判定記録に次を残す（記録の義務であり、新しい検証は加えない）:
  - 未修正の非公開脆弱性報告（SECURITY.md の窓口・GitHub の Security Advisory の下書き）の件数と重大度。詳細は書かない
  - Dependabot と CodeQL の open のアラートの件数と重大度
  - v1.0.0 の MSI に実際に焼き込まれた .NET ランタイムの版と、判定日時点の .NET 10 の最新パッチの版（SECURITY.md は同梱ランタイムの見直しの契機に「各リリースの準備時（その時点の最新パッチへ追随します）」を挙げている）
  - 判定日に Fluent Bit の検証済み版を見直した記録
  - セキュリティ判断を誤らせる open の Issue（例: 閲覧 HTTPS の SAN 助言検査が古い結果を表示し続けた #480。2026-11-16 に修正済み）の有無と、残る場合の扱いと理由
- 定義⑤の「持続的」に数値の目安は置かない。該当の疑いがある事象は、判定記録で個別に理由を書く

### 決定 3: v1.0 公開基準

v1.0 は次の 5 基準を**すべて**満たしたときに公開できる。

#### 基準 1: 機能（ADR-0006 基準 1 を継承し、性能公称値と流量制御の閾値の決め方を固定する）

- ADR-0001 の**導入体験の原則**（インストール → 最初のログ閲覧、追加サーバ製品・手編集なし）が動作している。**証拠**: この動線を検証する E2E テストの CI 実行記録
- ADR-0001 の**品質の原則**の実装群（ADR-0002 決定 2 の発生箇所別ドロップ計測と、決定 4 のベンチの CI 合否判定）が動作している。合否は回帰検知にとどめず、**全体設計書で実測により確定した性能公称値を満たすこと**を含む
- **性能公称値の基準環境と算出の枠**（M-6 で決める事項のうち、本 ADR が固定するもの）:
  - **基準環境は GitHub ホストランナーの `windows-2022` と `windows-2025`** とする。どちらも ADR-0024 決定 1 の推奨区分（Windows Server 2022 / 2025）にあたる。**両方で測り、小さい方を推奨区分の公称値とする**。これで ADR-0024 決定 4 が残した「選ばれなかった側の版の扱い」を、同値の仮定を置かずに解消する
  - 単発の値で公称値を置かない。**多数のランナー個体（1 ジョブ = 1 標本）で測り、分布の下側の値から余裕を差し引いて置く**。手続きの骨格は次のとおりとする（オーナーの判断、2026-11-16）:
    - 標本数は**版あたり 29**（`windows-2022` と `windows-2025` のそれぞれで 29 ジョブ）
    - 下側の値は、29 標本の**最小値**とする。標本が独立とみなせる場合、29 標本の最小値が母集団の 10 パーセンタイル以下になる確率は約 95% である（1 − 0.9^29 ≈ 0.953）。28 標本では約 0.948 で 95% に届かない。29 はこの条件を満たす最小の標本数である
    - **余裕率は 20%** とする。最小値に 0.8 を掛ける
    - その結果を **500 件/秒の単位で切り捨てた値**を、その版の値とする。2 つの版の小さい方を推奨区分の公称値とする
    - 余裕率 20% と 500 件/秒の刻みはオーナーの決定であり、本 ADR に実測や導出による根拠は無い
    - **測定値による除外はしない**。最小値を取る以上、遅い個体も母集団の一部として扱う。ジョブが測定を完了できなかった場合（結果の JSON が無い）だけを欠測とし、同じ手続きで補充する。欠測の件数と理由は記録する
    - **標本の独立性に近づける**: 標本は 1 つの workflow run にまとめず、複数の日と時間帯に分散して取る。環境情報には、既存の項目（OS・CPU・論理コア数・メモリ・ディスク・.NET の版）に加えて、ランナーイメージの名前と版を記録する。MachineName は個体の識別に使えない（M-5 の 6 標本は同じ MachineName のまま CPU が 4 種類あった）。それでも独立性を確かめる手段は無く、「独立とみなせる場合」の前提は検証されないまま残る
  - **算出方法は、公称値を決める標本を取る前に確定する**。上記の骨格は本 ADR で固定する。次の細部も標本の取得前に M-6 で確定する。探索のための予備測定は方法の設計に使ってよいが、公称値の算出には使わない。データを見てから方法を選ぶ余地を残さないためである
    - 合格の定義（下記）の細部: レートの刻み、測定の継続時間、測定開始時の DB の大きさ、TCP の接続数
    - 標本を分散させる日と時間帯の決め方
    - **リリース時の判定方法**: 基準環境で判定する run の本数、公称値との余裕、再実行を認めるか。先行固定は較正の段階だけでなく判定の段階にも要る
    - **公称値が低く出た場合の扱い**: 0.8 × 最小値が 500 を下回って公称値が 0 になる場合と、公称値が一定の水準を下回る場合に、そのまま公開するか、方法を変えずに基準環境の選択を見直すか
  - 方法と集計スクリプトを固定したコミットが、公称値を決める最初の run より前の日時であることを、run の記録（コミット SHA と実行日時）から確かめられるようにする
  - **標本の取得前の見込み**: M-5 v2 の第 7 標本は、SQLite へ約 670 件/秒（保存 5,380 件 ÷ 送出約 8 秒。概算）しか書けなかった。同種の個体が 29 標本に 1 つでも混じれば N3 は 500 件/秒になる。N1・N2 も、合格の定義にスプール退避 0 を含むため同じ個体の書き込み速度に縛られる。**3 つとも 500 件/秒前後になる可能性は高い**。結果がこの見込みと違ったとき、また見込みどおりだったときに方法を変えたくなったときに、後から分かるよう記しておく
  - 合格の定義には、計上済みの破棄と OS バッファ破棄（導出値）がともに 0 であることに加えて、**スプール退避が 0 であること**を含める。持続的な退避は、いずれ破棄に至る状態だからである（architecture.md §3.2.2）。このため **N1・N2 が表すのは受信能力ではなく、受信から保存までの持続速度**であり、N3 を超えない
  - 能力の測定は、流量制御の影響を受けない条件（測定用の構成で既定の流量制御を外す、または閾値を測定レートより十分に上げる）で行い、**それ以外の設定は SQLite の既定構成とする**。ベンチは本物の `Yagura.Host` を起動するため、既定の流量制御（単一送信元あたり持続 10,000 件/秒の仮値）がそのまま効き、それを超えるレートの測定は流量制御に抑えられる（`BenchHostProcess` と `Program.cs` の結線を読んで確認した）
  - 公称値として表明するのは、組み込み DB（SQLite）の既定構成（流量制御を除く）での次の 3 つとする: **N1 UDP の持続受信**、**N2 TCP の持続受信**、**N3 SQLite の書き込み上限**。**SQL Server の書き込み上限は公称値として表明しない**。ランナー上で継続的に立てられるのは LocalDB だけで、LocalDB は運用形態として対応外だからである（ADR-0024 決定 2）。条件を並記した参考値として載せる
  - 公称値には基準環境の構成（論理コア数・メモリ・観測した CPU の内訳・ディスク・ランナーイメージの版）と送信の条件（同一機上のループバックからの送信、送信元アドレスは 1 つ、TCP の接続数）を並記し、**利用者の機器での性能を保証する値ではない**ことを書く。あわせて、**公称値と流量制御の既定閾値の関係**（単一の送信元が既定で受けられる速度と公称値の大小）を書く
  - 公称値を判定する workflow は、fork でシークレットなしに手動実行できるものとする。「誰でも同じ workflow を再実行できる」を基準環境の選定理由にしているためである
  - 同じジョブで、スプールの 1 件あたりのバイト数も記録する。既定のスプール上限（M-12）で DB 障害を何分吸収できるかの換算（流量ごと）を運用文書に載せるためである
  - 生データ（ジョブごとの JSON と環境情報）はリポジトリに収録する。CI の実行記録と artifact は 90 日で消えるためである
  - SQL Server provider の検証記録は、継続の層（LocalDB での適合テスト。全 PR・blocking）と単発の層（実インスタンスの lab）を分けて書く（ADR-0024 改訂 11 を継承）
  - **証拠**: 公称値を確定した PR（算出方法・生データ・集計結果）と、リリース時に基準環境で判定した run の記録
- ADR-0002 で v0.1 必須とした範囲（組み込み DB・SQL Server provider・スプール・バックプレッシャ・箇所別計測）と、**流量制御が完動**している。加えて、**流量制御の既定閾値（M-4）を仮値のまま v1.0 を出さない**。既定閾値は、基準環境で**通常運用で発火しないこと**を実測で確かめて確定する。暴走した送信元から他の送信元を守れることの実測（送信元を複数にした測定）は v1.0 の後の Issue とし、v1.0 の閾値は前者を優先して決める（オーナーの判断、2026-11-16）。前者を優先したことと、保護を実測していないことを architecture.md §3.3 に記録し、決定 4 で開示する。**証拠**: 受け入れテストの CI 記録と、閾値を確定した PR の実測記録
  - 流量制御が発火するかどうかを決めるのは送信元の速度であり、サーバの環境ではない。そこで M-4 の確定では、**「通常運用」とみなす 1 送信元あたりの最大速度**（中継・集約〔rsyslog 等〕から 1 つのアドレスでまとめて送る構成を含めるか）を明記する
  - 流量制御は送信元を IP アドレスで判別し（UDP では偽装できる）、追跡数の上限を超えた新規の送信元は追跡せずに通す設計である（architecture.md §3.3）。**意図的な洪水を防ぐ仕組みではない**。これを決定 4 で開示する
- v1.0 で新設する**旧 DB の処分（#502）は、ログを消す経路**である。PR #531 の設計が定める安全条件（処分の前提となる移行の完了または明示の選択、使用中のファイルの拒否、退避の検証に失敗したときに元を消さないこと等）を CI のテスト（LocalDB を用いた昇格から処分までの通しを含む）で検証する。実機では実施しないことを決定 4 で開示する。**証拠**: 当該テストの CI 記録
- **仮値のまま出す設計値の一覧**: M-4・M-6 のほかにも、障害時の挙動を決める設計値のうち v1.0 で仮値または未確定のまま出すものがある（architecture.md §9 の M-3 大規模 backlog の drain、M-9 停止から起動までの時間、M-12 スプールのディスク使用量上限、M-13 書き込みのタイムアウト、M-14 TCP 同時接続数の上限など）。これらは判定 Issue に一覧し、決定 4 で開示する。重大不具合の定義②（設計上の想定を逸脱した喪失）の判定では、その時点の仮値を想定として扱う
- ADR-0004 決定 3 の **opt-in 強化 3 点（TLS 受信・Web UI の HTTPS・AD 連携認証。AD 環境向けの gMSA を含む）がすべて提供済み**である。**証拠**: 各機能の受け入れテスト記録 + 実環境での動作確認記録（最低 1 環境。作者環境で可）

#### 基準 2': 作者 lab の検証記録（ADR-0006 基準 2 の置き換え）

- **証拠の本体は lab 台帳とする**:
  - installer/lab/ に 1 ファイルで新設する（ファイル名は実施 PR で決める）。lab の 1 回を 1 行とする
  - 列は、回・日付・環境（OS ビルド・SQL Server の版・構成）・検証した版とコミット SHA・**実施者（人間の作者 / AI エージェント / 不明）**・**実施者の判別根拠**・**沿った文書とその節（利用者向け文書と lab の手順書を分けて書く）**・結果・見つかった欠陥の Issue・記録の URL とする
  - 実施者の判別根拠は、記録中の該当箇所への permalink とする（リポジトリ内のファイルはコミット SHA つきの URL）。根拠を示せない区分は「不明」とする
  - 対象は、2026-07-05 以降の回のうち、Issue・PR・手順書・ベンチ結果のいずれかに記録が残っているもの。記録がチャットにしか無い回は証拠に数えない（台帳に載せる場合は「記録なし」と書く）
  - **無効だった検証を明示する**。#514 で無効と分かったアップグレード確認は、その項目を無効と記す
  - 台帳を作るときに、既存の記録の整合を正す（第 2 回・第 3 回の番号の食い違い、手順書の冒頭注記と実施記録表の古さ、第 3 回の SQL Server 2025 の部分実測、未マージの PR を指すリンク切れ）
  - 台帳と報告書に資格情報（パスワード等）を書かない。既存の記録も点検する。資格情報が見つかった場合は、値を失効（ローテーション）させ、編集履歴からも削除する（Issue・PR のコメントは、編集しても編集履歴に旧版が残る）
- **追加の lab は課さない**（オーナーの判断、2026-11-16）。v1.0.0 として公開する版での lab も、連続稼働の最小記録も求めない。証拠は上記の既存の記録に限る
- 全域条件の判定記録（決定 2）を残す
- **実施者**: 台帳に載せる回は、AI エージェントが実施したものでよい。ただし台帳に実施者を偽りなく書く。記録から実施者を判別できない回は「不明」と書き、人間の作者の実施とは数えない
- **不合格の条件**: 次のいずれかに当たれば、基準 2' を満たさない。どれも**記録と開示の完全性についての条件**であり、製品の動作の合否ではない
  - 台帳の回に、必須の列が欠けているものがある
  - 台帳の回で見つかった欠陥のうち、修正済みでも、実機未確認のラベル（決定 7）付きでも、決定 4 の開示の一覧に載ってもいないものがある
  - 無効と判定された検証（#514 によるアップグレード確認など）のうち、有効な検証に置き換わってもおらず、開示もされていないものがある
- **正直な限界**: 基準 2' の証拠の大半は、基準 1 が既に認めている「実環境での動作確認記録（作者環境で可）」と同じ母集団である。**基準 2' が独自に加えるのは、台帳化（既存の記録の網羅、実施者の明示、無効だった検証の明示、記録の整合）と全域条件の判定記録の 2 点に限られる**。新しい検証は加えない。基準 2 が担っていた独立性の検証と長期の連続稼働の観測は、どれも代わりに担わない。上記の不合格の条件も、記録が欠けていれば落ちるというだけで、台帳の中身（全回が AI の操作でも、全回で欠陥が見つかっていても）によっては落ちない。実質は「(b)〔基準 2 を判定から外す〕+ 記録の義務 + 開示の義務」に近い
- **示し方**: このため、判定 Issue・README・リリースノートでは、基準 2' を「検証に合格した」とは書かず、**「記録と開示を完了した」**と書く。5 つの基準に同じ ✓ を並べて、5 つの門を通ったように見せない（基準 3' (ii) も同じ）
- **証拠**: lab 台帳へのリンク、全域条件の判定記録

#### 基準 3': 利用者向け文書の完備 — ペルソナ通読 + 作者による手順実施〔既存の lab 記録〕（ADR-0006 基準 3 の置き換え）

- **前提条件として、対象文書がそろっていること**。誰が確認するかより先に、確認の対象が存在しなければならない:
  - 導入: README（インストール・システム要件・既定ポート・セキュリティの前提）、SECURITY.md、新設する「受信できないときの切り分け」（ファイアウォールのネットワークプロファイル〔受信許可規則は Domain + Private 限定で、未分類のネットワークは Public のことがある〕、514 を既に使っている他製品、送信元機器の宛先設定、システム状態画面で何を見るか）
  - 運用: operations.md の既存の節（トピック別のファイルへ分割する。決定 7）と、新設する次の手順:
    - バックアップ・復旧（DPAPI で暗号化した値の再入力を含む）
    - 通常のアップグレード（v0.5.0 から v1.0 へ。0.3.3 以前は先にアンインストールが要ることを含む）
    - **本番昇格**（SQL Server 側の準備と権限、ウィザードの流れ、**切替はサービスの再起動で反映され、反映前のログは旧 SQLite に入ること**、切替後の確認方法、旧 DB の処分〔#502〕）
    - 蓄積ログ移行機能の使い方
    - サーバの移設・交換
    - アンインストールとデータの扱い
    - **障害時の手順**（スプール上限の接近・到達の警告、スプールなしの縮退起動、速度不足でスプールが伸び続ける場合、流量制御の発火、TCP 接続数の上限到達、受信断区間の読み方。既定のスプール上限で DB 障害を何分吸収できるかの換算〔基準 1〕と、数百台を TCP で受ける場合の接続数上限の見直しを含む）
    - 導入後の 1 か月に見ておく指標（製品のカウンタに加えて、プロセスのメモリ量・ハンドル数を OS の計器で見る方法。製品自身はこれらを出していない）
  - **新設する手順には監査記録の扱いを含める**。監査記録は DB ではなくデータルート配下の日次ファイルと Windows イベントログにあり（security.md §4.2）、DB のバックアップや移行の対象にならないためである:
    - バックアップ・復旧: 監査記録を巻き戻さない手順（復旧時に現行の監査ファイルを退避して残す）と、復旧したことの記録
    - サーバの移設・交換: 監査ファイルの移送と、旧機のイベントログの保全
    - アンインストール: データ削除を選ぶと監査記録も消えることの明示と、事前の退避
    - SQL Server から別の SQL Server へのサーバ交換: database.md §6.2 が手動移行に課していた「実施の事実を残すステップ」を引き継ぐ。製品の監査記録に残らない操作は、そのことを明記する（security.md §4.1 の逆引きを整合させる）
  - ADR-0004 委任の利用者向け文書（同 ADR の委任事項の 5 項目すべて）: 信頼ネットワーク成立チェックリスト、リバースプロキシ前置の要件（v1.0 でも前置をサポートしないことの明示。決定 7）、DPAPI のサーバ束縛とバックアップ手順、localhost 監査で個人を特定できない限界、機微ログ環境での認証有効化の推奨
  - ガイド: gMSA によるサービス実行、Windows イベントログの転送
  - **全体設計書の申し送りの反映**: architecture.md §10・configuration.md §10・database.md §9・security.md §8 の「利用者向けドキュメントへの申し送り」の各項目が、すべて「✅ 反映 → 文書#節」になっていること。機械的に判定でき、後から範囲を狭められない。とくに security.md SEC-D4（v1.0 で凍結するイベント ID の全一覧〔database.md §7〕と、「ソース Yagura の警告以上」を起点にした監視設定）を含む
  - **入口から辿れること**: README の「ドキュメント」表から、上記の対象文書のすべてへ直接辿れること
- **「手動 DB 移行手順（ADR-0002 決定 3 (iii)）」は、蓄積ログ移行機能（database.md DB-5）の使い方と、SQL Server から別の SQL Server へのサーバ交換手順に置き換える**。ADR-0002 決定 3 (iii) は、手動手順を移行機能の提供「までの間」の措置としていた。移行機能は提供済みである
- **(i) ペルソナによる通読**: 5 ペルソナが、対象文書のコミット SHA を固定して通読する。分担は佐藤 = 導入、鈴木 = 運用と障害時、田中 = セキュリティの前提、リサ = 文書の品質と一貫性、クリス = 主張の根拠とする。各ペルソナは「文書だけでは先へ進めない箇所」と「製品の挙動と食い違う箇所」を節番号つきで挙げる。対象文書に無いトピック（例: 必要な手順そのものが文書に無い）も「先へ進めない箇所」として挙げ、(i) の指摘に含める。結果は判定 Issue にペルソナごと 1 コメントで残し、モデル名・実施日・文書の SHA を書く
  - 照合先として、文書と同じコミット SHA のコードとテストを固定する。AI のペルソナは製品を動かせないので、「製品の挙動と食い違う箇所」は、コードかテストで裏が取れたものと「未照合」のものに分けて書く
  - 鈴木の通読は、障害の筋書き（DB 停止、ディスク満杯、スプール上限到達、クラッシュ、流量制御の発火、TCP 接続数の上限、更新の失敗、証明書の期限切れ）を 1 つずつ文書だけでたどる形にする
  - この通読は、設計文書を対象にする persona-review.md の制度とは対象・記録先・形式・位置づけが異なる。作法は persona-review.md に節を設けて定める（反映チェックリスト）。食い違う場合は本 ADR が優先する
- **(ii) 作者による手順の実施 — 既存の lab 記録で代替する**: 基準 2' の lab 台帳に載る回のうち、**手順書（installer/lab/ ほか）または利用者向け文書に沿って実施した回の記録**をもって (ii) とする。新たな実施は課さない（オーナーの判断、2026-11-16）。ここでいう「作者による」は作者の lab での実施を指し、作者の指示で lab 機上の AI エージェントが操作した回を含む
  - **lab 台帳で、回ごとに、沿った文書とその節、実施者が人間の作者か AI エージェントかを明示する**。沿った文書の版（コミット SHA または日付）が記録から分かる場合はそれも書く
  - **数えるのは、利用者向け文書の節に沿って操作したことが記録から分かる回に限る**。lab の手順書（installer/lab/。試験者向け）は利用者向け文書とは別物であり、lab の手順書だけに沿った回は、対象文書の節に「同等の操作を行った回」として併記してよいが、「沿って実施した回」には数えない。lab の手順書に沿った回を利用者向け文書の節に対応づけると、利用者向け文書を誰も読んでいないのに「沿って実施した回あり」になるためである
  - 判定 Issue には、対象文書の節ごとに、沿って実施した回が台帳にあるかを示す。**沿って実施した回が 1 つも無い文書と節は列挙し、決定 4 の開示に含める**
  - **(ii) の不合格の条件**: 対象文書の節のうち、沿って実施した回の有無が判定 Issue に示されていない節がある場合、または沿って実施した回の無い節が開示の一覧に無い場合。基準 2' と同じく、記録と開示の完全性についての条件である
  - **新設する文書（バックアップ・復旧、通常のアップグレード、サーバの移設・交換など、上記の前提条件で新設するもの）は、v1.0 の時点で誰も手順を実施していない**。既存の lab の記録はすべて、それらの文書より前のものだからである。これを決定 4 の開示の必須内容とする
  - 既存の文書についても、lab の回が沿ったのは v1.0 で公開する版より古い版である。その後に変わった部分は、手順としては踏まれていない
- **記録**: (i) で挙がった箇所は、文書（または製品）を直す。直した部分は (i) の作法で再び通読する。確認の後で該当文書に実質的な変更が入った場合、変更部分は再確認の対象とする（ADR-0006 基準 3 の規定を継承）。この再確認は v1.0 の公開判定までの規定であり、v1.0 の後の文書の修正には求めない
- **実施者についての限界**: (i) は AI であり、(ii) に数える回の多くも AI エージェントが操作している。**人が文書を読んで操作できるかを確かめた記録は、台帳で人間の作者の実施と明示された回に限られる**。これを決定 4 で開示する
- **証拠**: 判定 Issue 上の、ペルソナごとの通読結果（文書のコミット SHA つき）と、lab 台帳のうち手順書・利用者向け文書に沿った回の一覧（沿った文書と節、実施者つき）、および沿って実施した回の無い文書と節の一覧

#### 基準 4: 後方互換性の凍結（ADR-0006 基準 4 を継承し、証拠形式と要求を改める）

- 設定スキーマ・DB スキーマ・保存データ形式について、**v1.0 以降は後方互換を破る変更を MAJOR バージョンでのみ行う**運用を開始できる状態にある。凍結対象の一覧は database.md §7 に置く（変更なし）
- **deprecation の清算**: v0.x で導入した deprecation が 0 件であることを宣言し、その根拠を判定 Issue に残す。根拠は、v0.1.0〜v0.5.0 の全リリースと v1.0 の設定キーを比べて削除されたキーが 0 件であること、`[Obsolete]` の付いた要素が 0 件であることとする。清算の対象が無いため、清算 PR のリンク一覧は求めない。あわせて、v1.x で適用する deprecation 規約を conventions.md で確定させる
- **更新の実証**: 直前の v0.x は v0.5.0 である（v0.6.0 は出さない。決定 7）。**公開済みの v0.5.0 の MSI（リリース資産そのもの。.sha256 で照合する）から、v1.0.0 として公開するコミットで作った MSI への更新を CI で実証することを、ADR-0006 基準 4 の「実地に実証」にあたるものと認める**。同じソースツリーから版番号だけを下げて作った MSI は使わない。#479・#514 で、版だけ上がって中身が旧版のままのファイルが残る失敗が起き、その方式ではこれを捉えられないと分かっているためである
  - 検証項目: 蓄積ログ（件数と内容）、設定（DPAPI で暗号化した値を含む）、管理者アカウント、監査記録、発生箇所別カウンタの連続性、未消化のスプールセグメント（database.md §7 の凍結対象）が保全されること
  - **製品の存続**（ADR-0023 決定 6 への回答として要求に加える）: 更新後に新版のサービスが稼働し、全リスナを新版のプロセスが bind し、受信と閲覧が成立し、「アプリと機能」の製品エントリが 1 件であること。更新が失敗した場合に旧版が残り、受信が再開することも、同じ v0.5.0 を起点に確かめる
  - **更新に伴う受信断の長さ**: v0.5.0 の停止から v1.0 が全リスナを bind するまでの秒数を測って記録し、その区間が受信断区間として残るかも確かめて記録する。合否には使わず、M-9（停止から起動までの時間）の最初の実測として扱う。UDP の装置を多数抱える利用者にとっては、保守作業の申請に書く数字である
  - **v1.0 の時点で更新の実地確認をしていない範囲**: AD・gMSA の構成と、SQL Server の実インスタンスを含む構成での v0.5.0 からの更新は、CI では踏めず、lab でも確かめない（追加の lab を課さないため。基準 2'）。これを決定 4 で開示する
  - **正直な限界**: CI の更新元は作ったばかりのデータであり、数か月運用した v0.5.0 環境の状態は再現しない。また、v0.5.0 を OS ビルド 17763 未満（Server 2016 以前など）で動かしている利用者は、MSI の対応 OS 下限（ADR-0024 決定 6）のため v1.0 へ更新できない（既存のインストールは無傷で残る）。v0.5.x のサポートは v1.0.0 の公開で終わり、猶予期間は置かない（決定 7）ので、該当する利用者は公開日に修正の経路を失う。該当する外部の利用者は、確認できた範囲では 0 件である。これらをリリースノートと SECURITY.md に書く
- **証拠**: 凍結対象一覧へのリンク、deprecation が 0 件であることの根拠、更新の実証の run と artifact

#### 基準 5: リリースの完全性 — コード署名を含む（ADR-0006 基準 5 を文言を変えずに継承）

- リリース資産（インストーラ）に **Authenticode コード署名（タイムスタンプ付き）**が付与されている（SmartScreen 警告への対処 + 証明書期限後も署名が有効であり続けるため。証明書の入手・管理はリリース準備の課題として別途扱う）
- リリース資産に checksum（.sha256）が添付され、リリース手順が再現可能な形で文書化されている
- **SECURITY.md が実態と一致している**: リリース提供の開始を反映し、**v1.0 以降の修正提供対象（サポート対象バージョン。最低限「最新リリース + main」の明記）が確定**している
- **証拠**: リリースノートから署名の検証手順（signtool verify 等）と .sha256 が辿れること、SECURITY.md の該当節へのリンク
- 判定の前提（現況から必要なもの）: ADR-0014 が accepted であること、SECURITY.md のサポート対象表が v1.0 を反映していること、リリース手順が 1 か所にまとまっていること

### 決定 4: 代替したことと失ったものを、利用者に開示する

ADR-0006 は、署名なしで公開する場合について「代替手段の差し替えではなく『本番推奨』の意味の縮小であり、利用者への明示義務を伴う」と定めていた（同 ADR の再評価トリガ）。本 ADR の代替も「本番推奨」の意味の縮小であり、同じ型の明示義務を課す。

- **掲載先**: README の状態表示の節と、v1.0.0 のリリースノートの両方。v1.0.0 より後のリリースノートからは README の該当節へリンクする
- **必須の内容**:
  1. v1.0 の判定は、独立した環境での運用実績と、作者と独立した人間による文書の実地確認を**得ないまま**行ったこと
  2. 代わりに何に基づいたか（作者 lab の検証記録〔台帳へのリンク〕、AI ペルソナによる文書の通読、既存の lab 記録のうち手順書・利用者向け文書に沿って実施した回）。**lab の多くは AI エージェントが操作した**こと
  3. 確かめていないこと:
     - 連続稼働: 最長記録は数時間単位である（実績の値で書く）。24 時間以上の連続稼働は、確認できた範囲で記録が無い
     - v1.0.0 として公開する版そのものでの lab。lab で踏んだのは v1.0 より前の版である
     - 人が画面ありのインストールを行い、別の機器から LAN 越しに送ったログが閲覧画面に出るまでを通しでなぞった記録は、v1.0 の版に無いこと（CI の E2E はサイレントインストールで、送信も同じ機械の中から行う）
     - 新設した文書（バックアップ・復旧、通常のアップグレード、本番昇格、移設、障害時の手順など）の手順は、誰も実施していないこと。あわせて、沿って実施した回の無い既存の文書と節（基準 3'）
     - 信頼ネットワーク成立チェックリストを含む ADR-0004 委任の文書は、人が使って確かめていないこと（既定構成〔平文受信・認証なしの閲覧〕が安全かどうかは、利用者がこのチェックリストで自分のネットワークを正しく判定できるかにかかっている）
     - AD・gMSA の構成と、SQL Server の実インスタンスを含む構成での v0.5.0 からの更新（基準 4）
     - 実機未確認のラベルを付けて閉じた Issue（#510・#511・#512 ほか）の修正を、実機で確かめていないこと（決定 7。ラベルの検索結果へリンクする）
     - 旧 DB の処分機能（#502）は v1.0 で新設したもので、実機では実施していないこと（基準 1）
     - 閲覧 HTTPS の実機記録（#455）がクライアントの種別（Chrome / Edge）を明記していないこと（決定 7）
     - 流量制御が、暴走した送信元から他の送信元を守れることの実測（基準 1）。あわせて、流量制御の既定閾値と公称値の関係、および**流量制御は送信元 IP の偽装を伴う意図的な洪水を防ぐ仕組みではない**こと
     - v1.0 で仮値または未確定のまま出す設計値の一覧（基準 1。スプール上限・書き込みタイムアウト・TCP 同時接続数の上限など）
     - 実機器のトラフィックと多数の送信元からの受信、SQL Server の Express 以外のエディション、作者の環境以外での動作
     - 第三者によるセキュリティ診断は受けていないこと（ADR-0006 にも無かった要件であり、代替で失ったものではない。導入の審査で最初に問われる点なので併記する）
  4. 性能公称値は GitHub ホストランナーでの実測であり、利用者の機器での性能を保証しないこと
  5. 運用報告と文書の不備の報告の受付先（決定 5）
  6. 本 ADR へのリンク
  7. **利用者に勧める始め方**（平易な言葉で）。v1.0 は「本番推奨」を意味を縮小したまま表明する版であり、縮小の分を利用者の始め方で補うよう勧める:
     - 最初の 30 日は、既存の受信先と並行受信（ミラー）で始める
     - 本番に移す前に、バックアップと復旧を自分の環境で 1 回試す
     - システム状態画面の取りこぼしのカウンタが 0 かを定期的に見る
- **README での書き方**: 必須の内容の 1〜7 を README にそのまま並べる必要はない。README の状態表示の節には**平易な要約（5 行程度）と 7 の始め方**を置き、3 の詳細な一覧はリリースノートまたは docs 配下の 1 ページに置いてリンクしてよい。長い注意書きは読まれず、読んだ人は導入を見送るためである。ただし要約から詳細へのリンクは必須とする
- README の「基準は先に固定してあり、達成しやすい形に動かしません」は、**黙って消さない**。基準を達成前に改定したこと（本 ADR）を、同じ場所に書く（本 PR で反映済み。開示の全文は v1.0.0 の公開時に載せる）
- 文言の例（拘束はしない）:「v1.0 は、独立した環境での運用実績と、第三者による文書の確認を得ていません。公開の判定は作者の検証環境での記録に基づきます（詳細: ADR-0025）。」
- 開示は、決定 5 の記帳で失ったものが埋まるまで維持する。埋まった項目だけを書き換える

### 決定 5: v1.0 の後の扱い

- **受け皿を続ける**: 運用報告と文書確認報告の Issue テンプレートを用意し、README で呼びかけを続ける。運用報告の様式は、ADR-0006 基準 2 の観測記録の形式（開始時・終了時の発生箇所別カウンタ。重大事象の発生時は随時）を継承し、v1.0 が手放した長期の観測を最初の利用者の報告で補えるよう、**プロセスのメモリ量とハンドル数、スプールの使用量、DB の大きさ、保持期間削除の所要時間**を加える。PR #448 の「試用協力の募集の節を削除する」方針は改め、募集の節は「実運用の報告を歓迎する」趣旨に書き換えて残す（決定 7）
- **記帳**: 独立した環境からの 30 日以上の運用報告と、作者と独立した人間による文書確認の報告は、本 ADR の改訂履歴に記帳する。ADR-0006 の基準 2（2 環境 × 30 日）・基準 3 の水準に達したら、その事実を記帳し、決定 4 の開示を更新する
- **判定の前に届いた報告**: v1.0 の判定の前に、作者と独立した人間から文書確認や運用の報告が届いた場合も同じく記帳し、基準 3' の証拠に加え、該当する開示の項目を書き換える。受け皿の Issue テンプレートができるまでは、GitHub の Issues / Discussions で受け付ける
- **重大不具合が報告されたとき**: v1.0 系列で重大不具合（決定 2）が報告された場合、最優先で修正版を出し、README の既知の問題に載せる。製品には新版を通知する機能が無いため、README で GitHub のリリース通知（リポジトリの Watch で Releases を選ぶ）の購読を案内する。あわせて、その不具合が本 ADR の代替で失った検証（独立した環境・長期の連続稼働・実機器のトラフィック）でしか見つからない種類のものかを判断し、改訂履歴に記帳する

### 決定 6: ADR-0006 の運用から引き継ぐもの

- 基準は**満たすまで下げない**。基準の変更（緩和を含む）は本 ADR の supersession によってのみ行い、必ず公開の場（PR + ペルソナレビュー）を通す
- **自己拘束の自覚**: 決定者と supersession の承認者が同一人物である以上、この拘束は手続きと公開記録による自己拘束である。本 ADR はその自己拘束を基準の達成前に緩めた実例であることを、ここにも記す。**本 ADR の基準を緩める supersession を起案する場合は、当該リリースの延期を対等な選択肢として併記・比較し、緩和で失うものを決定 4 と同じ形で利用者に開示する**（ADR-0006 が署名なしの公開について課した歯止めを、基準の緩和全般に広げる）
- **「対等な比較」の最低限の中身**: 延期を 1 行並べて「却下（オーナーの判断）」と書くだけでは、この歯止めを満たさない。少なくとも次を書く。本 ADR 自身にも適用した（検討した選択肢「延期（(a)）との比較」）
  - 延期の費用（誰が、何を、どれだけ失うか）
  - 緩和に固有の利益（延期しても得られる利益を除いたもの）。無ければ、無いと書く
  - 公開日への影響を理由に案を却下する場合は、見積もった遅れの日数を書く。見積もっていなければ、見積もっていないと書く
  - 理由を書くべき位置に決定の事実（「オーナーの判断」）だけを書かない。理由が選好であれば、選好であると書く
- **量的な床も自己拘束の内側に置く**: 性能公称値（基準 1）の確定後の引き下げは本 ADR の変更と同等に扱い、supersession に準ずる手続き（PR + ペルソナレビュー + 変更理由の公開）を要する。ADR-0006 にあった実運用の下限流量（基準 2）は、全体設計書で確定されないまま、基準 2 とともに廃止する
- **署名を外す変更の歯止め**: ADR-0006 の再評価トリガにあった歯止め条件（①無償・低コストの代替の検討記録、②延期との対等な比較、③署名なしの事実と検証手順の明示）は本 ADR に引き継ぐ
- v0.x の間の運用（MINOR で機能を追加し、後方互換を破る変更も許容する。conventions.md の deprecation 階段は守る）は v1.0 の公開で終わる。以後は基準 4 の運用（後方互換を破る変更は MAJOR でのみ行う）に移る

### 決定 7: v1.0 の公開判定に付随する判断の記録

オーナーが 2026-11-16 に既定判断とした事項を、判定の前提として記録する。他の ADR・設計書の決定に関わるものは、その決定を適用するものであり、本 ADR はそれらの決定を変えない。

本決定の事項は、決定 3 の基準そのものではない。変更に決定 6 の supersession は要らず、本 ADR の改訂（改訂履歴への記帳）で行う。ただし、変更が基準の要求を弱める場合（例: 基準 4 の更新実証の起点を、公開済みのリリース資産でないものにする）は、基準の緩和として決定 6 に従う。

- **閲覧 HTTPS のブラウザ実機検証（#455）**: 2026-07-26 の実機記録をもって M1・M2 を通過とし、M3・M6・M7 は v1.0 の後の Issue へ移す。07-26 の記録はクライアントの種別（Chrome / Edge）を明記していない。追加の確認は行わず、この点を決定 4 で開示する
- **Windows 実機での確認が要る Issue**（#510・#511・#512 ほか）: 修正 PR が CI を通った時点で閉じる。lab での追認は求めない。lab の第 5 回として依頼済みだった観測（#511 の修正の確認、昇格の 1 サイクルでの #510・#512 の観測、Server 2016 での拒否ダイアログの目視）は実施しない。実機で確かめていないことは決定 4 で開示する
  - 閉じるときに、**実機未確認を示すラベル（`hardware-unverified`）を付け、閉じた後も外さない**。閉じた Issue の一覧から、どれが実機で確かめられていないかを引けるようにするためである。「など」で開いたままにせず、開示の対象の集合をこのラベルで定める。決定 4 の開示はラベルの検索結果へリンクし、決定 2 の判定記録はラベルの付いた閉じた Issue も分類の対象にする。将来 lab を再開したときや外部の協力者が現れたときに、何を実機で確かめればよいかもこのラベルで引く
  - 経過: #510・#512 は 2026-11-16（本 PR のレビュー中）に修正 PR #537・#535 のマージで閉じた。#511 は修正 PR #519 が未マージで open である。#511 の前回の修正は lab 第 4 回で回帰を起こしており（PR #519）、その種の欠陥を CI が捉える保証は無い。PR #519 は判定の結果（警告するか・監査に記録するか）の単体テストに「失敗時は警告する」（見逃しの方向）を含むが、権限が本当に無い証明書を OS の上で扱う経路は CI では踏まない
- **SQL Server 2025**: v1.0 では対応を表明しない（未検証）。ADR-0024 決定 2 の表明ゲートを閉じたまま公開する。2026-08-08 の lab で接続・照合順序・スキーマ作成を部分的に実測した事実（#514・#515）は、ADR-0024 の改訂として記録する
- **リバースプロキシの前置**: v1.0 でもサポートしない。ADR-0004 委任の利用者向け文書でそれを明示する
- **ADR-0014**: accepted にする（基準 5 の前提）
- **v0.6.0 は出さない**。v0.5.0 から v1.0.0 へ直接更新する（基準 4 の実証の起点）
- **v0.5.x のサポート**: v1.0.0 の公開をもって終了する。SECURITY.md のサポート対象表に反映する（基準 5）
- **README の試用協力の募集節**: 削除せず、「実運用の報告を歓迎する」趣旨に書き換えて残す（決定 5）
- **operations.md**: トピック別のファイルへ分割する（基準 3' の対象文書の構成）。分割には次の条件を付ける。operations.md は、書き換えない ADR（ADR-0007・0010・0016・0022・0024 と本 ADR）、lab の手順書、製品の文言から参照されているためである:
  - docs/operations.md は目次として残し、旧節番号（§1〜§13）から新しいファイルへの対応表を置く
  - 製品の文言が operations.md を案内している箇所（`ActiveNotificationMonitor.cs` の閲覧 HTTPS 証明書の警告 3 か所。Windows イベントログに出る）は、分割と同じ PR で直す
  - 分割したファイルの置き場所と層（常に現在形・仕様の正は design/）は docs/README.md に定める。guides/ は「外部ツールとの組み合わせ手順」に限る層なので、そのままでは置けない
- **#502（昇格後の旧 DB の自動処分）**: v1.0 で実装する。設計は推奨設計とし、database.md で行って別途ペルソナレビューを通す（PR #531）。設計の入力として、蓄積ログ移行の機会を消さないよう、移行の完了または「移行しない」の明示の選択を待ってから処分することを前提に置く（現行の operations.md §13 の手動手順は移行機能に触れていない）

## 帰結

- **良くなること**:
  - v1.0 の時期を外部要因に預けず、作者が制御できる作業で判定できる。追加の lab を課さないため、残る作業（文書の新設、M-6・M-4 の確定、更新の実証ジョブ、台帳と判定記録）は lab の日程に依存しない
  - lab の記録が台帳として整理され、実施者・版・環境・沿った文書と節・無効だった検証が明示される。これまで記録は Issue・PR・手順書に散らばり、番号の食い違いもあった
  - 基準 4 が強くなる。公開済み v0.5.0 の MSI からの更新を実証し、「製品の存続」を要求に加えて ADR-0023 決定 6 の宿題を閉じる
  - 性能公称値が、誰でも再実行できる環境で、方法を先に固定した手続きによって決まる
  - 基準 3' の前提として、欠けていた運用文書（バックアップ・アップグレード・本番昇格・移設・障害時の手順）が書かれる
  - ただし、このうち延期しても得られないのは 1 つ目だけである（検討した選択肢「延期（(a)）との比較」）
- **悪くなること（代替で失うもの）**:
  1. **独立性**: 「作者の環境でしか動かない」可能性を排除する手段が無くなる。ADR-0006 が却下した選択肢 (c) を採ることになる。lab の実施者も、作者本人と、コードを書いた AI と同系統の AI であり、**lab の多くの回は AI エージェントが操作した**
  2. **時間で効く欠陥を検出する機会と、期間をまたいだ観測記録**: 30 日に対して、既存の記録での連続稼働の最長は数時間単位であり、24 時間以上の記録は確認できた範囲で無い。開始時と終了時のカウンタを比べる形の長期の観測記録も無い。リーク、累積、夜間の保持期間削除、DB の成長と Express の容量接近警告、証明書の期限経過、Windows Update による再起動は踏まない
  3. **実機器のトラフィックの多様性と、多数の送信元からの継続受信**: ベンダごとの書式の揺れや自然なバーストを受けない。途絶検知と流量制御が実際のトラフィックで試されない。流量制御が他の送信元を守れることも、v1.0 の時点では実測しない（基準 1）
  4. **v1.0 の版そのものでの実地確認**: v1.0.0 として公開する版では lab を行わない。lab で踏んだのは v1.0 より前の版であり、その後の変更（#510・#512 の修正、#511 の修正で生じた回帰の修正〔PR #519〕、#502 の実装、M-4 の確定値など）を実機で踏まないまま公開する。とくに #510・#511・#512 は Windows 実機での確認が要る修正だが、CI の通過だけで閉じる（決定 7）
  5. **更新の実地確認の範囲**: AD・gMSA の構成と SQL Server の実インスタンスを含む構成での v0.5.0 からの更新は、CI でも lab でも確かめない（基準 4）
  6. **SQL Server の Express 以外のエディションと、実運用の規模**
  7. **文書確認の独立性と「人間であること」**: 通読は AI が行い、手順の実施は既存の lab 記録で代え、その多くは AI エージェントが操作した。人が文書を読んで操作できるかを確かめた記録は、台帳で人間の作者の実施と明示された回に限られる。書いた側の暗黙知による見落としは避けられない。文書を書いた AI と通読する AI が同系統であることも、同じ問題を抱える
  8. **新設文書の手順の実施**: バックアップ・復旧、通常のアップグレード、移設などの新設文書は、v1.0 の時点で誰も手順を実施していない。既存の文書も、lab が沿ったのは v1.0 で公開する版より古い版である
  9. **自己拘束の信用**: README で「動かさない」と宣言した基準を、12 か月のトリガより前に動かした。今後このプロジェクトが「先に固定した」と書く基準の重みは下がる
- **受け入れるリスク**:
  - v1.0 の最初の独立した利用者が、lab で踏まなかった環境差の欠陥を踏む。対処は決定 5（最優先の修正と、既知の問題への掲載）とする
  - 公称値が、ランナーの構成変更（イメージの更新・CPU 世代の入れ替え）で割れる。余裕率と、割れた場合の手続き（決定 6）で扱う
  - 基準 3' を通っても、実在の管理者が文書だけでは到達できない箇所が残る。決定 5 の文書確認報告で拾う
  - 新設した文書（とくにバックアップ・復旧と移設）に、実施して初めて分かる誤りが残る。最初にそれを踏むのが、障害の最中の利用者になり得る。決定 4 で手順が未実施であることを開示し、決定 5 の文書確認報告で拾う
  - Windows 実機での確認を要した修正（#510・#511・#512 など）が、CI では捉えられない実機の条件では効いていない可能性が残る。決定 5（最優先の修正と、既知の問題への掲載）で扱う
  - 開示を読まずに「v1.0 = 独立した検証済み」と受け取る利用者がいる。開示を README の状態表示の節に置くことで最小化する

## 先送りにする場合の再評価トリガ

本 ADR は「外部からの確認」を v1.0 の後へ先送りする。次のいずれかで再評価する。

- **独立した環境から重大不具合（決定 2）が報告された場合**: 決定 5 の処置に加えて、それが代替で失った検証でしか見つからない種類かを判断し、記帳する。**v1.0 の公開から 6 か月以内にその種類の報告が 1 件でもあれば、v1.x の「本番推奨」の表明の扱いを再検討する**（結論が「変えない」でも、理由を改訂履歴に残す）。表明を変える場合は本 ADR の supersession による
- **独立した環境から 30 日以上の運用報告が届いた場合、または作者と独立した人間から文書確認の報告が届いた場合**: 記帳し、決定 4 の開示を更新する
- **2027-07-05（v0.1.0 の公開から 12 か月。ADR-0006 の再評価トリガの期日）の時点で外部の運用報告が 0 件の場合**: 呼びかけの方法を再評価する。あわせて、決定 4 の開示が 1 項目も埋まらないまま「本番推奨」を表明し続けることの扱いも再評価する（結論が「変えない」でも、理由を改訂履歴に残す）。上の 6 か月のトリガは報告が届くことを前提にしており、利用者が 0 人のままでは発火しないためである。ADR-0006 の期日を失わないよう、ここに残す
- **性能公称値の余裕が architecture.md §5.2 の閾値を割った場合**: 決定 6 の手続きに従う
