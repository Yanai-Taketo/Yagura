# 導入前の確認と設定ファイルの手編集

[運用ガイドの目次へ戻る](../operations.md)

Yagura を導入する前（または導入した直後）に確かめておくことと、設定ファイル `yagura.json` を手で編集するときの注意をまとめる。インストールの手順そのものは [README の「インストール」](../../README.md#インストール)が正である。

## 信頼ネットワークが成り立つかを確かめる

Yagura の既定構成は、次の 3 条件を満たすネットワークでの利用を前提にしている（[SECURITY.md の「設計上の前提」](../../SECURITY.md#設計上の前提--信頼ネットワーク)・[ADR-0004](../adr/0004-security-model.md) 決定 1）。

1. syslog の送信元・Yagura サーバ・閲覧者が**同一の管理主体**の管理下にある
2. 設置セグメントが**インターネットから直接到達できない**
3. そのセグメントへ**接続できる者を管理主体が把握・統制している**

前提が崩れたときに何が起きるかを先に押さえておく。既定構成では次のとおりである。

- **閲覧 UI（TCP 8514）に届く人は、誰でもログを閲覧・検索・CSV エクスポートできる**（認証なし）
- **受信ポート（UDP/TCP 514）に届く人は、誰でも偽のログを送り込める**。syslog には送信元を認証する仕組みがない。TLS 受信（6514）を有効にしても、行うのは通信の暗号化とサーバ証明書の提示だけで、送信元の認証はしない（相互 TLS は対象外）
- **設定の変更はできない**。書き込み系の管理操作は loopback 専用の管理リスナ（TCP 8515）でしか受け付けず、サーバ自身からしか実行できない

### チェックリスト

上から順に「はい / いいえ」で答える。「いいえ」が 1 つでもあれば、右の列の対処（記号は次の表）を検討する。例は網羅ではない。迷ったら「いいえ」として扱う。

| # | 確認すること | 「いいえ」のとき |
|---|---|---|
| 1 | Yagura サーバ・syslog の送信元・閲覧する人が、すべて自社（同じ管理主体）の管理下にある | 他社・他組織と共用するネットワーク（共用ビルの LAN、グループ会社や委託先と相乗りするネットワーク等）には既定構成のまま置かない。A〜E をすべて検討する |
| 2 | Yagura サーバにインターネットから直接届かない（グローバル IP アドレスを付けていない・ルータで 514 や 8514 を転送していない） | インターネットに露出させない。インターネットへの公開は想定していない |
| 3 | VPN で接続した在宅勤務端末が、Yagura サーバのあるセグメントに制限なく入れる構成になっていない | E、加えて A・C |
| 4 | 保守業者の持ち込み端末を、Yagura と同じセグメントに一時接続させる運用がない | E、加えて A・C |
| 5 | 来客用（ゲスト）無線 LAN が、社内 LAN と分離されている（ゲストの端末から Yagura サーバへ届かない） | E、加えて A・C |
| 6 | 会議室などの空いている LAN ポートに、誰でも端末をつなげる状態になっていない | E、加えて A・C |
| 7 | Yagura サーバにサインイン（コンソール・リモートデスクトップ）できる人を、管理者として把握している | D |

| 記号 | 対処 | 効くこと | 手順 |
|---|---|---|---|
| A | 閲覧 UI 認証を有効にする（Windows 統合認証 + AD グループ） | 閲覧・検索・CSV エクスポートを、許可したグループの人に限る | [閲覧 UI 認証（8514）を有効化する](authentication.md#閲覧-ui-認証8514を有効化する) |
| B | 閲覧 UI の公開範囲をサーバ自身だけに縮める | LAN から閲覧できなくなる（閲覧はサーバ上のブラウザだけになる） | [機微なログを扱う環境での推奨](#機微なログを扱う環境での推奨) |
| C | 閲覧 UI を HTTPS にする | 閲覧の通信（閲覧 UI 認証を有効にした場合のセッション Cookie を含む）を暗号化する | [閲覧 UI の HTTPS（8514）を有効化する](viewer-https.md) |
| D | 管理 UI の認証を、サーバ自身からの接続にも課す（`Admin:Authentication:RequireForLoopback`） | サーバにサインインできる管理者以外の人は、管理 UI の認証を通らなければ設定を変えられない（ローカル Administrators は設定ファイルの手編集で変えられる）。画面から行った操作の監査記録に利用者名が残る | 管理画面「管理 UI の認証」。注意点は[ブレークグラス（非常口）の推奨](authentication.md#ブレークグラス非常口の推奨)と[管理画面に入れなくなる構成](degraded-operation.md#管理画面に入れなくなる構成) |
| E | ネットワーク機器（スイッチ・ルータ・UTM など）で、VPN・ゲスト・持ち込み端末のセグメントから Yagura サーバへの通信を遮断する | 偽のログの送り込みを含め、届くこと自体を防ぐ（Yagura の設定では防げない） | 各機器の手順による |

syslog が信頼できない区間（拠点間の回線など）を通る場合は、TLS 受信（6514）で通信路を暗号化できる。受信許可規則は自分で足す（[ファイアウォール規則を自分で足す](firewall.md)）。上記のとおり、TLS 受信は偽のログの送り込みは防がない。

## リバースプロキシの前置はサポートしない

IIS（ARR）や nginx などのリバースプロキシを Yagura の前に置き、閲覧 UI・管理 UI をプロキシ経由で公開する構成は**サポートしない**（v1.0 も同じ）。管理 UI の認証を有効にしても同じである。

この扱いは、[ADR-0004](../adr/0004-security-model.md) 決定 2 の文言「リバースプロキシ前置構成は既定構成ではサポートせず、認証 opt-in の有効化を必須とする」（認証を有効にすれば前置できるとも読める）より狭い。[ADR-0010](../adr/0010-admin-ui-authentication.md) が検討した選択肢 (c) で残した「アプリ独自 ID/パスワード + プロキシ側 TLS 終端」の組み合わせも、サポートの対象に含めない。理由は次のとおり。

- **管理操作の保護が外れる**。既定構成で管理操作を守っているのは「サーバ自身（loopback）からの接続しか受け付けない」ことである。同じサーバ上のプロキシが管理リスナ（8515）へ転送すると、外からの要求がすべてサーバ自身からの接続として届き、プロキシに届く人なら誰でも設定を変えられる状態になる
- **監査記録の接続元がプロキシになる**。Yagura はプロキシが付けるヘッダ（`X-Forwarded-For` など）を解釈しないため、記録される接続元はすべてプロキシのアドレスになる
- **Windows 統合認証がプロキシ経由では成り立たない**。Microsoft のドキュメントは、プロキシが接続を 1 対 1 で維持しない限り、Negotiate 認証をプロキシ経由で使わないよう警告している（[ADR-0010](../adr/0010-admin-ui-authentication.md) のライブ検証記録）
- **プロキシの HTTPS は、リモート管理の前提条件の代わりにならない**。管理 UI をリモートに開く設定（`Admin:RemoteBinding:Enabled`）は、Yagura 自身が HTTPS で待ち受けること（`Admin:Https:Enabled` と証明書の拇印）と認証の有効化を条件にしており、満たさないと起動を拒否する（イベント ID 1012）。プロキシが HTTPS を終端しても、この条件は満たせない。プロキシから Yagura までの区間は平文のまま残る

プロキシで実現したかったことには、次の代わりの方法がある。

| やりたいこと | 代わりの方法 |
|---|---|
| 閲覧 UI を HTTPS にしたい | 閲覧 UI の HTTPS（同じポートのまま HTTPS に切り替わる）。[閲覧 UI の HTTPS（8514）を有効化する](viewer-https.md) |
| 閲覧できる人を絞りたい | 閲覧 UI 認証（Windows 統合認証 + AD グループ）。[閲覧 UI 認証（8514）を有効化する](authentication.md#閲覧-ui-認証8514を有効化する) |
| 手元の端末から管理画面を使いたい | 管理 UI のリモートアクセス（HTTPS 必須・認証必須。既定ポート 8516）。管理画面「管理 UI のリモートアクセス（HTTPS）」で設定し、[受信許可規則を足す](firewall.md) |

既に前置している場合は外す。特に、管理リスナ（8515）へ転送している構成は、上記のとおり管理操作が誰にでも開いた状態なので、直ちにやめる。

## 監査記録で「誰が操作したか」が分かる範囲

既定構成（認証なし）では、管理操作の監査記録の「誰が」欄に残るのは**接続元のアドレスだけ**である（設定の保存・再読み込みなど、画面からの操作では接続元のポートは記録されない）。管理操作はサーバ自身からしか行えないため、接続元はほぼ常に `127.0.0.1` か `::1` になる。イベントログ（アプリケーション、ソース `Yagura`）では次のように見える（`実行者=` の後ろはアドレスとコロンだけになる）。

```
[audit] 設定変更を適用: 実行者=127.0.0.1: 試行パス= …
```

**この記録だけでは、サーバにサインインしていた誰が操作したのかは分からない**（[ADR-0004](../adr/0004-security-model.md) 決定 7）。人を特定するには、Windows のログオン監査（セキュリティログ）と時刻で突き合わせる。

### 突き合わせの手順

サーバ上で「管理者として実行」した PowerShell で行う。

1. Yagura の監査記録から、操作の時刻を確かめる（監査はイベント ID 2000 番台）。

   ```powershell
   $From = Get-Date '2026-11-16 09:00'   # 調べたい時間帯に置き換える
   $To   = Get-Date '2026-11-16 18:00'
   Get-WinEvent -FilterHashtable @{ LogName = 'Application'; ProviderName = 'Yagura'; StartTime = $From; EndTime = $To } |
     Where-Object { $_.Id -ge 2000 -and $_.Id -lt 3000 } |
     Format-List TimeCreated, Id, Message
   ```

   `TimeCreated` はサーバのローカル時刻で表示される。監査記録のファイル（`%ProgramData%\Yagura\audit\audit-yyyyMMdd.jsonl`）を直接読む場合、`OccurredAtUtc` とファイル名の日付は **UTC** である。突き合わせの前に時刻の基準を揃える。

2. 同じ時間帯にサーバへサインインしていた人を、セキュリティログのログオン成功（イベント ID 4624）から調べる。ログオンの種類 2 はコンソール、7 はロック解除、10 はリモートデスクトップ、11 はキャッシュされた資格情報によるコンソールでのサインインである。

   ```powershell
   Get-WinEvent -FilterHashtable @{ LogName = 'Security'; Id = 4624; StartTime = $From; EndTime = $To } |
     ForEach-Object {
       $d = @{}
       foreach ($x in ([xml]$_.ToXml()).Event.EventData.Data) { $d[$x.Name] = $x.'#text' }
       if ($d['LogonType'] -in @('2', '7', '10', '11')) {
         [pscustomobject]@{
           Time      = $_.TimeCreated
           LogonType = $d['LogonType']
           Account   = '{0}\{1}' -f $d['TargetDomainName'], $d['TargetUserName']
           Source    = $d['IpAddress']
         }
       }
     } | Format-Table -AutoSize
   ```

### 限界

- **サインインしていた人が複数いれば、絞り込めない**。共有の管理者アカウント（1 つの Administrator を複数人で使う等）では、人までは特定できない。管理者ごとに個人のアカウントを使う
- **ログオン監査が記録されていなければ、突き合わせはできない**。監査ポリシーで「ログオン」の成功が記録される設定になっているかを `auditpol /get /category:*` で確かめる。記録されていなければ、グループポリシー（またはローカル セキュリティ ポリシー）で有効にする
- **セキュリティログは容量を超えると古いものから上書きされる**。突き合わせたい期間を保てる大きさにするか、ログを別の場所へ集めておく
- **設定ファイルを手で編集してサービスの再起動で反映した変更は、「どのキーが変わったか」しか残らない**（起動時に監査 2019 が 1 件記録される）。いつ・誰が編集したかは残らない。証跡を残したい場合は、手編集を再起動ではなく再読み込みで反映する（監査 2016 が残る。[手順](#手順)）
- **`sc.exe control Yagura 128` で実行した再読み込みは、実行者が `(SCM control)` と記録される**。誰が実行したかは残らないため、同じく突き合わせが要る
- Yagura の監査記録のファイルは、サーバの管理者であれば消せる。イベントログは、消去すると消去したこと自体が Windows の記録に残る

### 利用者名を記録に残したい場合

管理 UI の認証を有効にし、サーバ自身からの接続にも認証を課す（`Admin:Authentication:RequireForLoopback`。管理画面「管理 UI の認証」）。サインインして行った操作は、「誰が」欄に `windows:CONTOSO\taro` や `app:admin1` の形で利用者名が残る。この設定には締め出しの危険があるため、[ブレークグラス（非常口）の推奨](authentication.md#ブレークグラス非常口の推奨)と[管理画面に入れなくなる構成](degraded-operation.md#管理画面に入れなくなる構成)を先に読む。

## 機微なログを扱う環境での推奨

既定では、閲覧 UI（8514）に届く人は誰でもログを読める。認証の記録（ユーザー名・ログイン失敗）、VPN の接続記録、Windows のセキュリティログなど、個人や認証に関わる情報を集める環境では、次の順に検討することを推奨する。

1. **閲覧 UI 認証を有効にする**（[閲覧 UI 認証（8514）を有効化する](authentication.md#閲覧-ui-認証8514を有効化する)）。有効にしたら、閲覧を許可したい人で実際にサインインできることを確かめる
2. **閲覧 UI を HTTPS にする**（[閲覧 UI の HTTPS（8514）を有効化する](viewer-https.md)）。閲覧 UI 認証で `AdminGroups` を指定する場合は、管理役割の Cookie が平文で流れないよう特に併用を勧める
3. **LAN からの閲覧が要らなければ、公開範囲をサーバ自身だけに縮める**。管理画面「初期セットアップ」の「公開範囲」で「このサーバ自身のみ（localhost 限定）」を選ぶ（設定キーは `Viewer:PublicAccess = LocalhostOnly`）。ほかの手順の値（受信ポート・保持期間など）が現在の設定と同じかも確かめてから保存する（[管理画面と併用するとき](#管理画面と併用するとき)）。反映にはサービスの再起動が要る。縮めると、インストーラが作った規則「Yagura Viewer (TCP 8514)」がどの待ち受けにも対応しなくなり、起動時の突合で警告（イベント ID 1023）に列挙される。不要なら規則を無効にする（サーバ・管理者）

   ```powershell
   Disable-NetFirewallRule -DisplayName 'Yagura Viewer (TCP 8514)'
   ```

4. **サーバに管理者以外もサインインし得るなら、管理 UI の認証をサーバ自身からの接続にも課す**（[上記](#利用者名を記録に残したい場合)）

CSV エクスポートしたファイルは端末側に残り、Yagura の管理の外に出る。エクスポートできる人を閲覧 UI 認証で絞ることが、持ち出しの範囲を絞ることにもなる。24 時間無人で表示し続ける掲示用の画面と閲覧 UI 認証は両立しにくい（[セッションが切れたときの挙動](authentication.md#セッションが切れたときの挙動)）。

## 管理操作の想定頻度の目安

日々のログの閲覧・検索・CSV エクスポートは閲覧 UI（8514）で行い、管理画面は使わない。管理画面を使うのは次の契機に限られる。

| 管理操作（管理画面の名前） | 行う契機 | 頻度の目安 |
|---|---|---|
| 初期セットアップ（受信ポート・閲覧の公開範囲・保持期間） | 導入時。ポートや保持期間を変えるとき | 導入時に 1 回。以後は変えるときだけ |
| 保存先を SQL Server に切り替える | 本番昇格のとき | 通常 1 回 |
| フォワーダ配布キットの生成 | 導入時、宛先・収集するチャネルを変えるとき、Fluent Bit の版を更新するとき（転送元の端末を増やすだけなら、同じキットをそのまま配る） | 導入時に 1 回。以後はそれらを変えるときだけ |
| メール通知・送信元の途絶検知 | 通知を始めるとき、宛先や監視対象を変えるとき | 導入時と変更時 |
| TLS 受信・閲覧 UI の HTTPS・管理 UI のリモートアクセスの証明書設定 | 有効にするとき、証明書を更新するとき | 証明書の更新のたび（証明書の有効期間による） |
| 管理 UI の認証（緊急全失効を含む） | 認証を有効にするとき、退職者が出たとき、資格情報の漏洩が疑われるとき | 起きたときだけ |
| 画面とサーバの接続の管理 | 閲覧画面の接続を切りたいとき | 起きたときだけ |
| 設定の再読み込み | 設定ファイルを手で編集したとき | 手編集のたび |

既定構成では管理画面をサーバ自身からしか開けないが、上のとおり契機は限られるため、そのときだけサーバへサインイン（リモートデスクトップ等）すれば足りる。管理操作が多い環境や、サーバ上でのブラウザ操作を規程で禁じている環境では、管理 UI のリモートアクセス（HTTPS + 認証。opt-in）を使う。サーバ上でブラウザを使えないときのもう 1 つの手段は、[設定ファイルの手編集](#設定ファイルを手で編集する)である。

## インストール直後に最初のログを見るまで

手順は [README の「インストール」](../../README.md#インストール)の 3 ステップ（入れる・向ける・見る）のとおりである。ここでは、ログが見えないときに確かめる順番をまとめる。上から順に確かめると、原因の範囲を狭められる。

1. **サービスが動いているか**（サーバ・一般ユーザーで可）

   ```powershell
   Get-Service Yagura
   ```

   `Status` が `Running` でなければ、イベントログ（アプリケーション、ソース `Yagura`）のエラーを見る（[起動しなくなったとき](#起動しなくなったとき)も参照）。

2. **サーバ自身から送ったログが見えるか**（サーバ・一般ユーザーで可）。ファイアウォールを通らない経路で、受信と閲覧そのものを確かめる。

   ```powershell
   $msg = [Text.Encoding]::ASCII.GetBytes('<134>yagura-test hello-from-server')
   $udp = New-Object System.Net.Sockets.UdpClient
   [void]$udp.Send($msg, $msg.Length, '127.0.0.1', 514)
   $udp.Close()
   ```

   サーバのブラウザで `http://localhost:8514/search` を開く。条件を指定せずに開くと新しいログから並ぶので、`hello-from-server` を含む行があるかを見る。無ければ、次を確かめる。

   - **受信ポートを 514 から変えていないか**（管理画面「初期セットアップ」）。変えていれば、その番号へ送り直す
   - **イベント ID 1022（警告）が出ていないか**。他の syslog 製品などがポート 514 を使っていると、Yagura はその受信の待ち受けを開けないまま動き続け、1022 を記録する。サービスは `Running` のままなので、手順 1 では気づけない。ポートを使っているプログラムは、管理者として次で確かめる（Yagura 自身なら `Yagura.Host` と出る）

     ```powershell
     Get-NetUDPEndpoint -LocalPort 514 -ErrorAction SilentlyContinue |
       ForEach-Object { Get-Process -Id $_.OwningProcess } | Format-Table Id, ProcessName
     Get-NetTCPConnection -LocalPort 514 -State Listen -ErrorAction SilentlyContinue |
       ForEach-Object { Get-Process -Id $_.OwningProcess } | Format-Table Id, ProcessName
     ```

     他のプログラムが使っている場合は、そのプログラムを止めるか、Yagura の受信ポートを変える。Yagura は開けなかった待ち受けを定期的に開き直そうとするため、ポートが空けば受信を始める

3. **別の端末から送ったログが見えるか**（クライアント PC・一般ユーザーで可）。2 と同じものを、宛先をサーバにして手元の端末から送る。

   ```powershell
   $Server = 'yagura-srv'   # Yagura サーバの名前または IP アドレスに置き換える
   $msg = [Text.Encoding]::ASCII.GetBytes('<134>yagura-test hello-from-client')
   $udp = New-Object System.Net.Sockets.UdpClient
   [void]$udp.Send($msg, $msg.Length, $Server, 514)
   $udp.Close()
   Test-NetConnection -ComputerName $Server -Port 514    # TCP 514 に届くか
   Test-NetConnection -ComputerName $Server -Port 8514   # 閲覧 UI に届くか
   ```

   2 では見えて 3 では見えない場合、原因はサーバのファイアウォール・ネットワークか、Yagura の待ち受け範囲の設定である。サーバ上で、管理者として次を確かめる。

   - **待ち受け範囲の設定**: 受信の待ち受けアドレス（`Ingestion:Udp:BindAddress` / `Ingestion:Tcp:BindAddress`）を `127.0.0.1` などに縮めていないか。値が不正な場合も、Yagura は loopback（サーバ自身からしか届かない）で待ち受ける。閲覧 UI（8514）にだけ届かない場合は、公開範囲（`Viewer:PublicAccess`）が `LocalhostOnly` になっていないか。値が不正な場合も `LocalhostOnly` で動く。どちらも、不正な値なら起動時・再読み込み時にイベントログへ警告（キー名・書いた値・実際に使う値）が出る
   - **ネットワークの種類**: `Get-NetConnectionProfile` の `NetworkCategory` が `Public` だと、インストーラが作る規則（Domain + Private 限定）が効かない。その LAN が信頼できる社内ネットワークであれば、`Set-NetConnectionProfile -InterfaceIndex <番号> -NetworkCategory Private` で変える（ドメインに参加したサーバがドメインのネットワークにつながっていれば `DomainAuthenticated` と表示される）
   - **規則があるか**: `Get-NetFirewallRule -DisplayName 'Yagura*' | Format-Table DisplayName, Enabled, Profile`。インストール時に規則の作成を外した場合は無いので、ファイアウォールを集中管理している側で UDP 514・TCP 514・TCP 8514 の受信許可を配布する
   - **警告が出ていないか**: イベント ID 1023（[規則の突合と警告](firewall.md#規則の突合と警告イベント-id-1023)）

4. **機器から送ったログが見えるか**。機器の syslog 送信先に、サーバの IP アドレス・ポート 514・UDP（または TCP）を設定する。設定方法は機器のマニュアルによる。3 では見えて機器のログが見えない場合は、機器側の設定（送信先・ポート・送信する重大度の下限・送信元のインターフェース）と、機器からサーバまでの経路（途中のファイアウォールや ACL）を確かめる。

5. **状態画面で取りこぼしを確かめる**。`http://<サーバ名>:8514/status` を開き、保存済みのログ件数が増えているか、取りこぼしのカウンタが動いていないかを見る。

ログは届くが、詳細表示の「送信元が名乗った時刻（参考）」が受信時刻から数時間ずれる（「装置時刻はサーバ受信時刻より約 9 時間 進んでいます」のような注記が出る）場合、送信元がタイムゾーンを付けない形式（RFC 3164）で時刻を送っている可能性がある。タイムゾーンが付いていない時刻は、既定では UTC として解釈される。設定ファイルに `Ingestion:Rfc3164:DefaultTimeZone`（例: `Tokyo Standard Time`）を書き、[再読み込み](#手順)で反映する。効くのは反映したあとに受信したログだけで、保存済みのログの時刻は変わらない。送信元が時刻にタイムゾーンを付けている場合は、そちらが優先される。なお、検索結果の一覧に出る時刻はサーバの受信時刻であり、この設定の影響を受けない。

> **第三者製品の設定例について**: 本ガイドや利用者ガイドに載せるネットワーク機器・転送ツール（NXLog・rsyslog・syslog-ng など）の設定例は参考情報であり、Yagura はその製品の動作を保証しない。設定方法や既定値は製品の版で変わるため、各製品の公式文書を正とする。Yagura が「検証済み」と表明するのは、[フォワーダ配布キット](../guides/forward-windows-eventlog.md)が使う Fluent Bit の版だけである。

## 設定ファイルを手で編集する

設定は管理画面から変えるのが基本で、手編集は前提にしていない。ただし手編集は正式な手段であり（[configuration.md](../design/configuration.md) §1・§3）、次の場面で使う。

- 管理画面に設定欄がない項目を変えるとき（閲覧 UI 認証のグループ、`Ingestion:Rfc3164:DefaultTimeZone` など）
- 管理画面に入れないときの復旧（[ブレークグラス（非常口）の推奨](authentication.md#ブレークグラス非常口の推奨)・[管理画面に入れなくなる構成](degraded-operation.md#管理画面に入れなくなる構成)）
- サーバ上でブラウザを使えないとき

各項目のキー名・既定値・反映方式・不正な値のときの挙動の一覧は、[configuration.md](../design/configuration.md) §8 が正である。

### 置き場所と、編集できる人

- 場所はデータルート直下の `yagura.json`（既定 `%ProgramData%\Yagura\yagura.json`）
- インストール直後（管理画面で設定を一度も保存していない状態）には、ファイルが無い。無ければ新しく作ってよい。書きたいキーだけを書けばよく、書かなかった項目は既定値で動く
- データルートに書き込めるのは、サービスアカウントと Administrators だけである。**編集は「管理者として実行」したエディタ・PowerShell で行う**（昇格していないメモ帳では保存できない）
- 環境変数 `YAGURA_UDP_PORT` などが設定されている項目は、ファイルより環境変数が優先される

### 書き方の注意

- 本ガイドの `Ingestion:Rfc3164:DefaultTimeZone` のような表記は、JSON の入れ子を `:` でつないだものである。ファイルには次のように書く

  ```json
  {
    "Ingestion": {
      "Rfc3164": {
        "DefaultTimeZone": "Tokyo Standard Time"
      }
    }
  }
  ```

- 数値・真偽値は `514` と書いても `"514"` と書いてもよい。真偽値として受け付けるのは `true` / `false` だけで、`1`・`yes` などは不正な値として扱われる
- **項目を既定値に戻したいときは、値を空にせずキーごと消す**。値を空（`""`）にすると書かなかったのと同じに扱われ、**警告なしで製品既定が使われる**（例: `"PublicAccess": ""` は LAN 公開、`"Days": ""` は 30 日）。空にしても、狭める・止める意味にはならない。狭めたい項目は値を明示する（公開範囲なら `"LocalhostOnly"`）
- 同じキーを 2 回書かない。ファイル全体を読めないものとして扱われる
- `//` のコメントと末尾のカンマは読み込める。ただし、管理画面で保存するとコメントは消える（[管理画面と併用するとき](#管理画面と併用するとき)）
- 文字コードは UTF-8 にする（BOM の有無は問わない）。Windows PowerShell 5.1 でファイルに書き込むときは `-Encoding utf8` を付ける（既定は UTF-8 ではない）
- 知らないキー（綴りの誤りを含む）は無視され、起動時・再読み込み時にイベントログへ警告が出る

### 手順

サーバ上で「管理者として実行」した PowerShell で行う。

1. 編集前の控えを取る。

   ```powershell
   $Conf = "$env:ProgramData\Yagura\yagura.json"
   if (Test-Path $Conf) { Copy-Item $Conf "$Conf.before-edit" -Force }
   ```

2. 編集する。保存するときの文字コード（エンコード）は UTF-8 にする。

   ```powershell
   notepad $Conf
   ```

3. **再起動の前に、再読み込みで反映する**。管理画面「設定の再読み込み」（`http://localhost:8515/admin/reload`）で実行するか、PowerShell で次を実行する。`sc` ではなく `sc.exe` と書く（Windows PowerShell では `sc` が `Set-Content` の別名になっているため）。

   ```powershell
   sc.exe control Yagura 128
   ```

   再読み込みは、ファイルを読めない・値が検証を通らない場合は何も適用せず、編集前の設定のまま動き続ける（1021）。そのため、構文の誤りがあっても受信は止まらず、再起動の前に誤りに気づける。**再読み込みを通さずに再起動すると、構文の誤りがあった場合はサービスが起動しない**。

   ただし、**再読み込みは何も適用しない予行ではない**。検証を通った変更のうち、すぐ効く項目（受信ポート・受信の待ち受けアドレス・保持期間・流量制御・メール通知・送信元の途絶検知など）は、その場で適用される。次の項目を変えるときは、先に確かめる。

   - **受信ポート・待ち受けアドレス**: 受信の待ち受けがその場で張り替わる。書き間違い（例: 514 のつもりで 5140）でも、機器からの受信はその場で止まる。送信元の送信先の設定と、新しいポートの受信許可規則（無ければ警告 1023 が出る。[ファイアウォール規則を自分で足す](firewall.md)）を先に確かめる
   - **保持期間（`Retention:Days`）**: 短くすると、次の削除の実行から、新しい日数より古いログが消え始める。消えてよい範囲かを先に確かめる

   また、**再読み込みが通っても、再起動で問題が出ることがある**。新しい設定で受信の待ち受けを開けない場合（ポートが他のプログラムに使われている、IPv6 が無効なサーバで待ち受けアドレスに `::` を明示した等）、再読み込みでは編集前の待ち受けに戻して動き続ける（手順 4 の表にある警告が出る）。その設定のまま再起動すると、その待ち受けを開けないまま動く（1022）か、起動に失敗する（IPv6 の場合）。

4. 結果を確かめる。管理画面から実行した場合は画面に表示される。`sc.exe` は結果を返さないので、イベントログを見る。

   ```powershell
   Get-WinEvent -FilterHashtable @{ LogName = 'Application'; ProviderName = 'Yagura'; StartTime = (Get-Date).AddMinutes(-5) } -ErrorAction SilentlyContinue |
     Format-List TimeCreated, Id, LevelDisplayName, Message
   ```

   該当するイベントが 1 件も無ければ、何も表示されない（下の表の「どれも出ない」）。

   | 出ているイベント | 意味 | 次にすること |
   |---|---|---|
   | 1021（警告） | 再読み込みを拒否した。実行中の設定は編集前のまま | メッセージの理由（構文の誤り・不正な値）を直し、3 からやり直す |
   | 2016（情報） | 変更を読み込んだ。すぐ効く項目は反映済み | 1020 が無ければ完了 |
   | 1020（警告） | 再起動しないと効かない項目が残っている（キー名が列挙される） | 都合のよい時間に `Restart-Service Yagura` で再起動する（停止している間は受信できない） |
   | 未知のキー・不正な値の警告 | 綴りの誤り、または値が使えないため別の値で動いている（警告にキー名・書いた値・実際に使う値が出る） | キー名と値を直し、3 からやり直す |
   | 「新構成での bind に失敗したため、旧構成での復旧を試みます」（警告） | 新しい受信ポート・待ち受けアドレスで待ち受けを開けず、編集前の待ち受けに戻した | ポートを使っているプログラムや待ち受けアドレスを確かめて直し、3 からやり直す（直さずに再起動しない） |
   | どれも出ない | 変更が検出されなかった | ファイルを保存したか、キー名が正しいかを確かめる |

   再起動しないと効かない項目は、管理画面のホームにも「再起動待ちの設定変更」として表示される。

5. 控えを消す（資格情報を含むことがあるため、残さない）。

   ```powershell
   if (Test-Path "$Conf.before-edit") { Remove-Item "$Conf.before-edit" }
   ```

### 反映のされ方

- **ファイルを保存しただけでは何も反映されない**。Yagura はファイルの変更を自動では読み込まない。反映は再読み込み（管理画面または `sc.exe control Yagura 128`）か、サービスの再起動による
- 再読み込みでの反映方式は項目ごとに決まっている。すぐ効くもの（保持期間など）、受信ポートなど受信を開き直すもの（短い瞬断を伴い、その区間は受信断として記録される）、サービスの再起動が要るもの（認証・HTTPS・TLS 受信など）がある。どれに当たるかは、上の手順 4 の結果（再起動待ちとして列挙されたか）で確かめるのが確実である
- 手編集で反映していない変更は、管理画面で設定を保存したときにまとめて反映される（保存のあとに設定ファイル全体の再読み込みが走るため）。次の場合は例外である
  - メール通知・送信元の途絶検知の画面は、保存のあとに再読み込みをしない（その画面の項目だけをその場で反映する）
  - 初期セットアップで「保存後すぐ反映する」のチェックを外して保存した場合は、再読み込みをしない
- 保存のあとに再読み込みが走った場合、初期セットアップ以外の画面は、保存した項目以外に反映された項目を警告として列挙する。初期セットアップの完了画面は、反映された項目を（保存した項目かどうかを区別せずに）すべて並べる

### 管理画面と併用するとき

- **手編集の前後で管理画面を開いている場合は、必ず画面を開き直してから操作する**。管理画面は、画面を開いた時点の値をフォームに表示し、保存ボタンを押すとフォームの値を設定ファイルに書く。そのため、画面を開いたあとにその画面が扱う項目を手で書き換えると、画面で保存したときに、画面に残っていた古い値で**警告なしに上書きされる**。たとえば、メール通知の画面を開いたまま `Notification:Email:Smtp:Host` を手で書き換え、その後に画面で保存すると、手で書いた値は消える
- **初期セットアップの画面は、開き直しても設定ファイルの値を読み込まない**。サービスの起動後に初めて開いたときは、設定ファイルの値ではなく製品の初期値（受信ポート 514・閲覧ポート 8514・LAN に公開・管理ポート 8515・保持期間 30 日）を表示する。途中まで進めた場合は、そのとき入力した値を覚えている。そのまま確定すると、手編集した値や以前に保存した値がこれらの値で上書きされる。各手順で値が現在の設定と同じかを確かめ、変えない項目も現在の値を入力する。確認の手順に並ぶ値が、そのまま設定ファイルに書かれる（同じ画面で保存を完了したあとの「設定を変更する」は、設定ファイルの現在の値から始まる）
- 画面が扱わない項目の手編集は、画面で保存しても残る（保存の処理の中でファイルを読み直し、画面が扱う項目だけを差し替えて書くため）。ただし、コメントと製品が知らないキーは消える（次項）
- 保存の処理の中でファイルを読んでから書くまでの間（初期セットアップでは、確認の手順を確定してから保存するまでの間）にファイルが書き換えられた場合は、衝突として検出し、上書きせずに保存を中止する。画面を開いていた間の変更を検出する仕組みではない
- **管理画面で保存すると、ファイル全体が書き直される**。書き直しは製品が知っている項目だけで行うため、**手で書いたコメントと、製品が知らないキー（綴りを誤ったキーを含む）は消える**。値は文字列（`"514"` など）として、書かれていない項目は `null`（未設定と同じ扱い）として書かれる。コメントで残したい情報は、別の場所に控えておく

### 不正な値を書いたとき

| 書いた内容 | 起動時 | 稼働中の再読み込み |
|---|---|---|
| JSON として読めない（構文の誤り・文字化け・同じキーの重複） | 起動しない（イベント ID 1024。ファイルのパスと行番号が出る。同じキーの重複では行番号が出ず「位置不明」となる） | 適用せず、編集前の設定のまま動き続ける（1021） |
| 受信ポート（`Ingestion:Udp:Port` / `Ingestion:Tcp:Port`）の値が不正 | 起動しない（イベントログにエラー） | 同上（1021） |
| 危険な組み合わせ（例: `Admin:Authentication:RequireForLoopback` を有効にして、認証方式を 1 つも有効にしない） | 起動しない（イベント ID 1011・1012・1032 など） | 同上（1021） |
| 公開範囲・待ち受けアドレスの値が不正 | 狭い側（localhost・loopback）で動き続け、警告 | 同左 |
| opt-in の機能（認証・TLS 受信・メール通知など）を有効にする項目（`…:Enabled`）の値が不正 | **無効**として動き続け、警告（閲覧 UI の HTTPS は、証明書の拇印を設定済みなら閲覧 UI を開かずに止まる） | 同左 |
| 保持期間（`Retention:Days` / `Audit:RetentionDays`）の値が不正 | 既定の日数ではなく**削除しない**で動き続け、警告（意図しない削除を始めないため） | 同左 |
| メール通知を有効にして、差出人・宛先・SMTP サーバのいずれかが未設定、またはこれらとポート・暗号化の指定の値が不正（ユーザー名とパスワードの片方だけの指定を含む） | 既定値には戻さず、**メール通知そのものが無効**のまま動き続け、警告（`Notification:Email:Enabled` が `true` なら、管理画面のホームのメール通知カードにも「設定に不備があるため送信されていません」と出る） | 同左 |
| 送信元の途絶検知のウォッチリストのエントリが不正 | **そのエントリだけが無効**になり、ほかのエントリで動き続け、警告 | 同左 |
| 上記以外の項目の値が不正 | 既定値で動き続け、警告（キー名・書いた値・実際に使う値が出る） | 同左 |

**有効にするつもりの編集で値を誤ると、機能は無効のまま動く**。たとえば閲覧 UI 認証の `Viewer:Authentication:Windows:Enabled` の値を誤ると、認証なしで動き続ける（警告は出る）。認証や HTTPS を有効にする編集のあとは、警告が出ていないこと、実際に認証が求められる（HTTPS で開ける）ことを確かめる。

### 資格情報を書くとき

- SQL Server の接続文字列（`Storage:SqlServer:ConnectionString`）と SMTP のパスワード（`Notification:Email:Smtp:Password`）は、管理画面（「保存先を SQL Server に切り替える」「メール通知」）で入力すると、`dpapi:` で始まる暗号化した形で保存される
- **手で平文を書いても動くが、自動では暗号化されない**。起動・再読み込みのたびに警告が出続ける（警告に値そのものは出ない）。暗号化した形にしたいときは、管理画面で入力し直す
- 平文を書いていた間に取った控え・バックアップには、平文が残る。手順で作った控え（`yagura.json.before-edit`）は消す。製品が作る写しは次の 2 つで、どちらもデータルート直下にあり、設定全体（平文のパスワードを含む）をそのまま保存している。

  - `yagura.json.last-good`（起動できなかったときに戻すための写し。起動時と再読み込みの成功時に更新される）
  - `last-applied-configuration.json`（起動時に設定の変更点を調べるための基準。起動時・初期セットアップの保存時・再読み込みの成功時に更新される）

  どちらも、管理画面で入力し直したあとに再読み込み（またはサービスの再起動）をすると、暗号化した形に置き換わる。バックアップ製品などで取得済みの写しは、そちらの手順で扱う
- **`dpapi:` の値は、そのサーバでしか復号できない**。`yagura.json` を別のサーバへ写したり、`dpapi:` の値を貼り付けたりしても使えない。接続文字列の場合は組み込みデータベース（SQLite）に切り替わって強い警告が出たまま動き、ログは SQLite 側に保存されていく。SMTP パスワードの場合はメール通知が止まり、警告が出る。どちらも、そのサーバの管理画面で入力し直して直す。接続文字列の場合、SQLite に切り替わっていた間に受信したログは SQLite 側に残り、SQL Server に戻したあとの閲覧画面には出てこない。起動時・再読み込み時の警告に早く気づくほど、その範囲は小さくなる
- 構成管理ツールなどで `yagura.json` を複数のサーバへ配る場合は、`dpapi:` の値を含むキーを配る対象から外し、各サーバの管理画面で入力する

### 起動しなくなったとき

`yagura.json` を読めない（構文の誤りなど）と、サービスは起動に失敗し、閲覧 UI も開かない。イベントログ（アプリケーション、ソース `Yagura`）にイベント ID 1024（エラー）が記録される。メッセージには、ファイルのパスと行番号（1 始まり）、戻せる写し（`yagura.json.last-good`）の場所と日時が含まれる。行番号の代わりに「位置不明」と出る場合は、同じキーを 2 回書いていないかを疑う（同じキーの重複は、位置が分からない形で検出される）。

直し方は 2 通りある。

- **行番号を手がかりに直す**（「位置不明」のときは、同じキーが 2 回書かれていないかを探す）。直したら `Start-Service Yagura` で起動する
- **写しに戻す**。写しは、最後に起動できたとき（または再読み込みに成功したとき）の構成であり、それ以後の変更は含まれない。製品が写しを自動で適用することはない（編集前の、より開放側の設定に黙って戻ることを避けるため）。内容を確かめてから戻す

  ```powershell
  # サーバ上で「管理者として実行」した PowerShell で行う
  $Root = "$env:ProgramData\Yagura"
  Get-Item "$Root\yagura.json.last-good" | Format-List FullName, LastWriteTime   # いつ時点の写しか
  Get-Content "$Root\yagura.json.last-good" -Encoding UTF8                        # 内容を確かめる
  Copy-Item "$Root\yagura.json" "$Root\yagura.json.broken" -Force                 # 壊れたファイルを控える
  Copy-Item "$Root\yagura.json.last-good" "$Root\yagura.json" -Force
  Start-Service Yagura
  Get-Service Yagura
  ```

  起動を確かめたら、控えた `yagura.json.broken` は消す（資格情報を含むことがあるため）。写しが無い場合は、行番号を手がかりにファイルを直す。

設定の誤りは、サービスの失敗時の自動再起動では直らない。直したら手で起動する。また、この状態では閲覧 UI も止まるため、**Yagura 自身では起動失敗に気づけない**。Yagura 以外の手段で、サービスの停止やイベント ID 1024 を監視することを勧める。
