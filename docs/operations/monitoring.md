# 監視と警告への対処（イベント ID 一覧）

[運用ガイドの目次へ戻る](../operations.md)

Yagura が運用者に知らせる事象と、知らせを受けたときに何をするかをまとめる。イベント ID とレベルの定義の正は [security.md](../design/security.md) §4.3、カウンタと能動通知の仕組みの正は [architecture.md](../design/architecture.md) §4 である。本書はそれを運用者の行動の順に並べ直したもので、仕様を追加するものではない。

本書に出てくる判定のしきい値（使用率 80%、5 分、空き 1 GiB、証明書の期限の 30 日前、警告の再表示の抑制 15 分、メールの 60 分に 1 通・1 時間に 10 通など）は、現在の版の値であり、設定では変えられない。設定で変えられるのは、本文で変え方を示したもの（一時保管の上限、ログを保存しておく期間など）だけである。

## 通知が届く経路

| 経路 | 見る人 | 性質 |
|---|---|---|
| Windows イベントログ（「Windows ログ」>「アプリケーション」、ソース `Yagura`） | 既存の監視基盤・サーバにサインインした人 | **正本**。Web UI を開いていなくても記録が残る。監視はここを起点に組む |
| メール通知（opt-in。既定は無効） | 設定した宛先 | イベントログに書いた警告のうち、メール通知の対象と決めた ID だけを送る補助の経路。**届かないことがある**（[メール通知を使う場合](#メール通知を使う場合)） |
| Web UI の状態表示（全画面上部の状態帯・状態画面・管理ホームのカード） | 画面を開いている人 | 「今どうなっているか」の確認用。無人の時間帯の通知にはならない |

## 監視の組み方

### 最小構成: ソース Yagura の警告以上を通知する

イベントログのレベルは、ID の区画ごとに次のとおり割り当てている。**「ソース `Yagura` の警告とエラーを通知する」だけで、対応が必要な事象はほぼすべて拾える**。例外は 1034（情報）である。フォワーダ MSI の書き込み経路を使うときだけ開く運用では、1034 が閉じ忘れの知らせになるので、その運用では 1034 も監視の条件に加える（[1033・1034](#10331034-フォワーダ-msi-配置フォルダの書き込み権限)）。

| 区画 | 内容 | レベル |
|---|---|---|
| 1000 番台 | 運用警告（一時保管・保存先・容量・証明書・受信経路など） | 警告。機能の停止を伴うものはエラー。1029・1034・1040 の 3 つだけは情報（原則として対応を要しない記録。1034 は上記の例外） |
| 2000 番台 | 管理操作の監査（設定変更・サインインなど） | 情報 |
| 3000 番台 | 拒否・セキュリティ事象（認証の失敗・拒否した操作など） | 警告 |

- **ID の一覧だけで絞り込む監視にしない**。固有の ID を持たない警告・エラー（イベント ID 0）もある——たとえば TLS 受信の接続ごとのハンドシェイク失敗や、受信ポートの不正値による起動の中止である。レベルで拾えば漏れない
- **同じ原因の警告は繰り返し出ない**。周期的に判定する警告の多くは、同じ種類の警告を 15 分間は再表示しない。警告が止んだことは解消したことを意味しないので、状態は[状態画面](#状態画面とカウンタの読み方)で確かめる
- **自然に戻ったことを知らせない事象がある**。一時保管の消化完了（退避したログをすべて保存し終えたこと）はイベントログに出ない（状態帯が「稼働中」に戻るだけ）。保存先の回復（1040）と送信元の受信再開（1029）は情報レベルで記録される

サーバ上で直近 24 時間の警告・エラーを確かめる（管理者権限の PowerShell）:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName      = 'Application'
    ProviderName = 'Yagura'
    Level        = 1, 2, 3          # 1 = 重大 / 2 = エラー / 3 = 警告
    StartTime    = (Get-Date).AddDays(-1)
} -ErrorAction SilentlyContinue |
    Format-List TimeCreated, Id, LevelDisplayName, Message
```

該当がなければ何も表示されない。特定の ID だけを見たいときは、`Level` の行を `Id = 1003, 1005` のように置き換える。

組織でイベントログの転送や監視ツールを使っている場合は、その条件に「ソース `Yagura`・レベルが警告以上」を加える。

### サービスの死活は Yagura の外から監視する

**Yagura は自分自身の停止を知らせられない**。サービスが止まっている間、または起動に失敗している間は、Web UI も開かず、メールも送られない。残るのは停止の前にイベントログへ書いた記録と、Windows のサービス管理の記録だけである。とくに次の場合は、イベントログが唯一の手がかりになる。

- 設定ファイルを読み取れずに起動を中止した（1024）、または矛盾した設定の組み合わせで起動を中止した（1011・1012・1032）——[起動と設定の警告](#起動と設定の警告)
- gMSA で動かしていて、ドメインコントローラーに届かずに起動できない——[gMSA ガイド](../guides/gmsa-service-account.md#6-起動失敗エラー-1069-系の切り分け)

そのため、Yagura 以外の経路で次を監視することを勧める。

1. **サービスの状態**が「実行中（Running）」であること
2. **別の機器から**閲覧 UI のポート（既定 8514）に接続できること
3. イベントログに **1024・1011・1012・1032**（いずれもエラー。起動の中止）が出ていないこと

サーバ上でサービスの状態を確かめる（管理者権限の PowerShell）:

```powershell
Get-Service Yagura | Select-Object Name, Status, StartType
```

クライアント（閲覧に使う端末など）から閲覧 UI のポートに届くかを確かめる（PowerShell。`yagura01` はサーバ名に置き換える）:

```powershell
Test-NetConnection -ComputerName yagura01 -Port 8514
```

`TcpTestSucceeded : True` なら届いている。閲覧 UI の公開範囲をサーバ内だけ（`Viewer:PublicAccess = LocalhostOnly`）に絞っている構成では別の機器からは届かないので、この確認は使えない。閲覧 UI を HTTPS にしている場合は、ポートが開いているだけでは正常と判断できない（[閲覧 UI の HTTPS](viewer-https.md#外形監視をしている場合)）。

インストーラは、サービスが異常終了したときに 5 秒後に再起動するよう、サービスの回復動作を設定する。現在の設定はサーバ上で次のコマンドで確かめられる（Windows PowerShell では `sc` が `Set-Content` の別名なので、必ず `sc.exe` と書く）。

```powershell
sc.exe qfailure Yagura
```

原因が残っている限り（設定ファイルが壊れたまま、ドメインコントローラーに届かないままなど）、回復動作で再起動しても起動には失敗する。回復動作に頼らず、停止そのものを検知できるようにしておくこと。gMSA 構成での回復動作の見直しは [gMSA ガイド](../guides/gmsa-service-account.md#7-dc-到達性への依存と回復設定)を参照。

### メール通知を使う場合

メール通知は、サーバ上の管理画面（`http://localhost:8515/admin`）の「メール通知」で設定し、同じ画面からテスト送信できる。届き方には次の性質がある。

- **送るのはメール通知の対象の ID だけ**である（[運用警告の一覧](#運用警告1000-番台の一覧)の「メール」列）。2000 番台・3000 番台は送らない
- **同じ ID は 60 分に 1 通まで、全体では 1 時間に 10 通まで**（エラーレベルの事象は全体の上限の対象外）。上限で送らなかったことはイベントログに 1026 として記録される。この値は設定では変えられない
- **届かないことがある**。送信に失敗した通知は 5 分後に 1 回だけ送り直し、それでも失敗したら捨てる。送信待ちの通知が 64 件を超えてあふれた分も捨てる。送信の失敗は最初の失敗の時点で 1025 として記録されるが、15 分の抑制があるため、捨てたことまでは記録されないことが多い（[1025](#1025-メール通知の送信に失敗)）。起動時に 1 回しか出ない警告（1001 など）は、メールサーバの準備が整う前に出ると届かないまま失われる。**メールが来ないことは、正常であることを意味しない**——正本はイベントログである
- 送信の状態は、管理ホームのカード「メール通知チャネル」で確かめる（最終送信成功・直近の失敗・送信されず破棄した通知・抑制した通知の件数）。このカードはメール通知を有効にしている間だけ表示される
- メール送信自身の失敗（1025）と抑制（1026）はメールでは送らず、イベントログにだけ出る

## 状態画面とカウンタの読み方

**状態画面**は閲覧 UI の「システム状態」（`http://<サーバ名>:8514/status`。閲覧 UI を HTTPS にしている場合は `https://`）である。サーバ上では、管理画面の待ち受けからも同じ画面を開ける（`http://localhost:8515/status`）。

| 区画 | 内容 |
|---|---|
| 現在の状態 | 一時保管領域の使用量（使用率と「使用量 / 上限」）・保存済みログ件数・保存先（データベース）の使用量 |
| 各種カウンタ（累計） | 発生箇所別のカウンタ（[カウンタの一覧と意味](#カウンタの一覧と意味)） |
| 診断用の計器（再起動でリセットされます） | TLS の接続確立に失敗した回数・UDP の受信処理でエラーになった回数。原因の切り分けに使う値で、取りこぼしを表さない |
| 受信できなかった時間帯の履歴 | 停止・再起動、正常に終了しなかった場合（境界はおおよそ）、設定反映による瞬断、ポートを開けなかった間 |
| 通知・動作の記録 | 古いログの自動削除の実行、蓄積ログの移行など |

保存先（データベース）に接続できない間も、状態画面は開ける。カウンタと一時保管の状態は保存先に依存しないので表示され、保存済みログ件数・保存先の使用量・履歴だけが表示されなくなる（[データベースに接続できないとき（縮退運転）](degraded-operation.md)）。

### 状態帯の 3 状態

全画面の上部に「稼働中 / 警告あり / 異常あり」を常に表示する。判定は**直近 5 分間の増加と現在の状態**で行い、累計値では判定しない。

| 表示 | 主な理由 |
|---|---|
| 異常あり | 直近 5 分間に、項目名が「取りこぼし（」で始まるカウンタのどれかが増えた（「取りこぼしの疑い」は含まない） |
| 警告あり | 一時保管に未保存のログが残っている（退避が進行中）/ 一時保管の使用率が 80% 以上 / 一時保管なしの縮退運転中（1001） |
| 稼働中 | 上のいずれにも当たらない |

- 「異常あり」は、増加が止まって 5 分たつと消える。消えても、起きたことは累計カウンタと履歴に残る
- 「稼働中」はログが実際に届いていることまでは示さない。横に出る最終受信時刻と、ダッシュボードの「送信元別の受信状況」で確かめる

### カウンタの一覧と意味

「各種カウンタ（累計）」の各行は、画面の「項目」（平易な名前）と「識別子」（計器名）を併記している。

| 項目（画面の表示） | 識別子 | 取りこぼしか | 増えたときの意味 |
|---|---|---|---|
| 取りこぼし（サーバ内の処理待ちが満杯） | `yagura.ingestion.internal_buffer.dropped` | はい | 受信したが処理が追いつかず捨てた。受信量の急増を疑う |
| 同時接続の上限で受け付けなかった接続 | `yagura.ingestion.tcp_connection.rejected` | 不明 | TCP の同時接続数が上限に達して新しい接続を断った。断られた側が送り直すかどうかは送信側の実装次第で、サーバからは分からない |
| 取りこぼしの疑い（接続が想定外の理由で終了） | `yagura.ingestion.tcp_connection.faulted` | 疑い | 平常時は 0。下記参照 |
| 一時保管への退避（取りこぼしではありません） | `yagura.ingestion.spool.evacuated` | いいえ | 保存先への書き込みが追いつかない・失敗したので、一時保管へ逃がした。保存先が書けるようになれば自動で保存される |
| 取りこぼし（一時保管への保存失敗） | `yagura.ingestion.spool.write_failed` | はい | 一時保管へ書けず捨てた（1005） |
| 取りこぼし（一時保管が満杯） | `yagura.ingestion.spool.discarded` | はい | 一時保管が上限に達していて捨てた（1003） |
| 取りこぼし（保存の失敗） | `yagura.ingestion.persistence.failed` | はい | 再試行と一時保管でも救えなかった。一時保管なしの縮退運転中（1001）に保存先へ書けなかった分もここに入る |
| 取りこぼし（送信元ごとの受信量の制限） | `yagura.ingestion.flow_control.dropped` | はい | 1 つの送信元からの受信量が制限を超えた。どの装置かはダッシュボードの「流量制限の発火上位送信元」で見る |
| 取りこぼし（一時保管ファイルの末尾破損。単位はバイト） | `yagura.ingestion.spool.corrupt_tail_discarded_bytes` | はい | 正常に終了しなかったときなどに一時保管ファイルの末尾が壊れ、読めなかった分。**単位は件ではなくバイト** |
| 逆引きホスト名の取得（成功・名前の登録なし・失敗・見送り）の 4 行 | `yagura.web.reverse_dns.*` | いいえ | 閲覧画面のホスト名表示のための記録。ログの取りこぼしとは関係がない |

**「取りこぼしの疑い（接続が想定外の理由で終了）」が 0 でない場合**: TCP または TLS の接続が、想定していない理由で終わったことを示す。その接続で処理中だったログが失われた可能性がある。イベントログに「TCP 接続 <送信元>:<ポート> の処理が想定外の例外で終了しました。」（TLS 受信では「TLS 接続 …」。エラー。固有の ID なし）が記録されているので、その本文を添えて [Issues](https://github.com/Yanai-Taketo/Yagura/issues) へ報告してほしい。

### 再起動で値が戻るもの・戻らないもの

| 種類 | 再起動したとき | 対象 |
|---|---|---|
| 累計を保存するカウンタ | **続きから数える**（0 に戻らない） | 「各種カウンタ（累計）」のうち、逆引きの 4 行を除くすべて |
| プロセス内だけで数える計器 | **0 に戻る** | 「各種カウンタ（累計）」の逆引きの 4 行と、「診断用の計器」の 2 行 |

- 累計を保存するカウンタは、10 秒ごとと正常停止のときに、データルート直下のファイルへ書き込まれる。サービスが正常に終了しなかった場合は、最後の書き込み以降（最大でおよそ 10 秒分）の増加が失われることがある。その場合も、停止していた時間帯は「受信できなかった時間帯の履歴」に「正常に終了しなかったため境界はおおよそ」として残る
- 保存先のファイルが壊れていて読めなかった場合、カウンタは 0 から数え直し、イベントログに警告を残す
- ダッシュボードの「取りこぼし（累計）」は、「取りこぼし（…）」と「取りこぼしの疑い（…）」のカウンタの合計である。末尾破損（単位はバイト）もそのまま足し込んでいるので、内訳は状態画面で確かめる
- 「診断用の計器」で過去の発生を追いたいときは、イベントログを見る（再起動をまたいだ累計は保持していない）

### カウンタがすべて 0 のときに言えること

- 取りこぼし系がすべて 0 なのは「**サーバに届いた後の**取りこぼしが 0」という意味である。UDP では、ネットワークの途中で失われたログをサーバは観測できず、どのカウンタにも現れない
- OS が Yagura へ渡す前に捨てた受信データ（OS の受信バッファがあふれた分）の数は表示していない。Windows の UDP 統計にこの破棄を数える項目がないことを実機で確かめており、状態画面にも、この値を表示しない旨の注記がある。この種の取りこぼしは、受信バッファを広げておくこと（既定で 1 MiB）で抑え、ダッシュボードの「送信元別の受信状況」（最終受信時刻）と送信元の途絶検知（1027・1028）で「来るはずのログが来ていない」ことを検出する
- ファイアウォールで破棄された受信も、どのカウンタにも現れない（1023）
- TCP では、Yagura が止まっている間や接続を断られた間に、送信側が送り直すことがある（送信側の実装次第）。UDP にはこの仕組みがない

### Web UI が開けないときに状態を知る手段

| 状況 | 手段 |
|---|---|
| 閲覧 UI（8514）だけが開けない（閲覧 UI の HTTPS の証明書事故、ファイアウォール、公開範囲の設定など） | サーバ上で、管理画面の待ち受けにある状態画面 `http://localhost:8515/status` を開く。カウンタと一時保管の状態はここで見られる |
| サービスが止まっている・起動できない | Web UI 全体が開かない。イベントログ（停止の前に出ていた警告と、起動を中止した理由）とサービスの状態（`Get-Service Yagura`）で判断する |

**Web UI を通さずにカウンタの現在値を取り出す手段は、現在の版では提供していない**。累計を保存するカウンタは、サービスを起動し直せば状態画面で続きから確かめられる。

## 警告ごとの対処

各項目は「意味・まず確認すること・対処・関連」の順に書く。コマンドはすべて**サーバ上の管理者権限の PowerShell** で実行する。データルートを既定（`%ProgramData%\Yagura`）から変えている場合は、パスを読み替える。

### 一時保管（スプール）の警告

一時保管（スプール）は、保存先（データベース）へすぐに書けなかったログをディスクへ逃がしておく領域である。既定ではデータルート配下の `spool` フォルダに置き、既定の上限は 1 GiB である。保存先へ書けるようになると自動で保存され（消化）、消化が終わると状態帯は「稼働中」に戻る。**一時保管の上限が、保存先の障害に耐えられる時間の上限になる**。

状態画面とダッシュボードの「一時保管領域の使用量」には上限と使用率も出るが、**この表示はサービスを起動した時点の上限で計算している**。設定の再読み込みで上限を変えると、実際の上限（1002・1003 の判定と、満杯で捨てる動作）はすぐに変わるが、画面の上限・使用率と状態帯の「使用率 80% 以上」の判定は、再起動するまで起動時の上限のままである（[上限を広げる手順](#一時保管の上限を広げる手順)の手順 4）。

1000 番台の一時保管の警告を受けたら、最初に保存先の障害（1030・1031・1039）と容量の不足（1006・1007、および固有の ID を持たない `[capacity-exhausted]` の警告）が出ていないかを確かめる。出ていれば原因は保存先かディスクにある。

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'Application'; ProviderName = 'Yagura'; Id = 1006, 1007, 1030, 1031, 1039, 1040
} -MaxEvents 20 -ErrorAction SilentlyContinue |
    Format-List TimeCreated, Id, Message
# 固有の ID を持たない容量枯渇の警告（直近 24 時間）
Get-WinEvent -FilterHashtable @{
    LogName = 'Application'; ProviderName = 'Yagura'; Level = 3; StartTime = (Get-Date).AddDays(-1)
} -ErrorAction SilentlyContinue |
    Where-Object { $_.Message -match '\[capacity-exhausted\]' } |
    Format-List TimeCreated, Id, Message
```

`[capacity-exhausted]` の警告は、保存先の容量が尽きて書き込めなかったこと（SQL Server のデータファイル・トランザクションログの満杯、組み込みデータベースのディスクの満杯）を示す。Yagura は保持期間による削除を前倒しで実行して空きを作ろうとし、書けなかった分は一時保管へ退避する。対処は[ディスクと DB 容量の警告](#ディスクと-db-容量の警告)を参照。

#### 1004 スプールへの退避が継続（1010 を含む）

- **意味**: 一時保管への退避が 5 分以上続いている。保存先への書き込みが受信に追いついていないか、保存先に書けていない。1010 は、1 日 1 回の自己検証で投入した確認用のレコードが 10 分以内に戻らなかったが、消化そのものは進んでいる（滞留している）ことを示し、原因は 1004 と同じである
- **まず確認すること**:
  1. 保存先の障害（1030・1031・1039）が出ていないか。出ていれば[保存先の警告](#保存先データベースの警告)へ
  2. 容量の不足（1006・1007、本文に `[capacity-exhausted]` を含む警告）が出ていないか。出ていれば[ディスクと DB 容量の警告](#ディスクと-db-容量の警告)へ
  3. 固有の ID を持たない警告で、本文に「バッチ書き込みがタイムアウト時間」または「バッチ書き込みが一時的に失敗したため」を含むものが続いていないか。続いていれば、保存先の応答が遅れているか、一時的な失敗を繰り返している（保存先のサーバの負荷・ディスク・ネットワークを確かめる）
  4. 上のどれも出ておらず、状態画面の「一時保管への退避（取りこぼしではありません）」が増え続けているなら、保存先への書き込みの速さが受信の量に追いついていない
  5. ダッシュボードの「受信量上位の送信元」で、受信量が急に増えた装置がないか
- **対処**:
  - 保存先の障害・容量の不足なら、それぞれの節の対処を行う。保存先へ書けるようになれば、Yagura 側の操作なしに自動で消化される
  - 書き込みが追いつかないなら、受信の量を減らすことを主にする。特定の装置が大量に送っているなら、装置側の送信設定（送るログの重大度など）を見直す。あわせて、保存先のディスク（組み込みデータベースならデータルートのドライブ）がほかの処理で混み合っていないかを確かめる
  - **同じ機材のまま保存先を SQL Server に切り替えても、書き込みが速くなるとは限らない**。同じマシンでの実測では、組み込みデータベース（SQLite）の書き込みの上限は SQL Server 2022 Express のおよそ 3 倍だった（[architecture.md](../design/architecture.md) §9 の M-7）。SQL Server への切り替え（管理画面「保存先を SQL Server に切り替える」）は、保持期間・バックアップ・ほかのツールとの連携など、容量と運用の理由で選ぶものである
  - 一時保管の使用率が上がり続けるなら 1002 の対処へ進む
- **関連**: 消化が終わったことはイベントログに出ない。状態帯が「稼働中」に戻ったことで確かめる

#### 1002 スプール使用量が上限に接近

- **意味**: 一時保管の使用率が 80% に達した。上限に達すると、そこから先に退避するはずのログは捨てられる
- **まず確認すること**: 状態画面の「一時保管領域の使用量」を数分おいて 2 回見て、増える速さから上限までの残り時間を見積もる（再読み込みで上限を変えた後は、画面の上限ではなく設定した値で見積もる）。原因の切り分けは 1004 と同じ
- **対処**: 原因（保存先の障害・速度不足）の解消を最優先する。間に合わない場合は、大量に送っている装置の送信を一時的に絞るか、ディスクに空きがあれば次の手順で一時保管の上限を広げる

##### 一時保管の上限を広げる手順

1. 一時保管を置いているドライブの空きを確かめる。上限を広げても、ドライブの空きを超えては使えない

   ```powershell
   Get-Volume | Where-Object DriveLetter |
       Select-Object DriveLetter,
           @{ n = 'FreeGB'; e = { [math]::Round($_.SizeRemaining / 1GB, 1) } },
           @{ n = 'SizeGB'; e = { [math]::Round($_.Size / 1GB, 1) } }
   ```

   **空きのすべてを一時保管に充てない**。既定の一時保管はデータルート（`%ProgramData%\Yagura`。通常はシステムドライブの C:）の配下にあるので、一時保管がドライブを使い切ると、OS やほかのサービス、組み込みデータベース、監査記録まで書けなくなる。新しい上限は「現在の一時保管の使用量 ＋ ドライブの空き − 余裕」を超えないようにする。余裕には、組み込みデータベースと監査記録が増える分と、1006 の判定に使う空き 1 GiB を見込む

2. 設定ファイル `yagura.json` をメモ帳で開き、`Spool` の `QuotaBytes` に上限のバイト数を書く（例は 4 GiB）。文字コードは UTF-8 のまま上書き保存する。編集前に控えを取る手順と書き方の注意は[設定ファイルを手で編集する](prerequisites-and-hand-editing.md#設定ファイルを手で編集する)にある

   ```powershell
   notepad "$env:ProgramData\Yagura\yagura.json"
   ```

   **ファイル全体を下の例で置き換えない**。保存先・認証などの設定が消え、それらは再起動で反映される項目なので、再読み込みの時点では気づかないまま、次の再起動で組み込みデータベース・認証なしの構成に戻ってしまう。既存の最上位の `{ }` の中に、最後の項目の閉じかっこの後ろにカンマを付けてから足す。すでに `Spool` の項目があれば、その中に `QuotaBytes` を足す（あれば値を書き換える）。最後の項目が `Retention` の場合の例:

   追記前（ファイルの末尾の抜粋）:

   ```json
     "Retention": {
       "Days": "30"
     }
   }
   ```

   追記後（ファイルの末尾の抜粋）:

   ```json
     "Retention": {
       "Days": "30"
     },
     "Spool": {
       "QuotaBytes": "4294967296"
     }
   }
   ```

   ファイルがまだない（初期セットアップで一度も保存していない）場合だけは、次の内容で新しく作る

   ```json
   {
     "Spool": {
       "QuotaBytes": "4294967296"
     }
   }
   ```

3. 管理画面の「設定の再読み込み」（`http://localhost:8515/admin/reload`）で再読み込みを実行し、結果を画面で確かめる。ファイルの書式に誤りがあれば適用されず、元の設定のまま動き続ける。**結果の画面に `Spool:QuotaBytes` の警告（値が不正なため既定値を適用）が出たら、上限は既定の 1 GiB になっている**。以前に上限を広げていた環境では上限が下がり、現在の使用量が 1 GiB を超えていれば、新しく退避するログをその場で捨て始める（「取りこぼし（一時保管が満杯）」が増え、1003 が出る）。すぐに値を直して、再読み込みし直す
4. 結果の画面の「反映した項目」に `Spool:QuotaBytes` が出ていることを確かめる。これで新しい上限が使われている。**状態画面とダッシュボードの「一時保管領域の使用量」に出る上限と使用率は、再起動するまで起動時の値のまま変わらない**（状態帯の「使用率 80% 以上」の判定も起動時の上限で計算される）。表示が変わらないことを理由に再起動しない——再起動の間は受信が止まる

#### 1003 スプール使用量が上限に到達

- **意味**: 一時保管が満杯になり、**以降に退避するはずだったログを捨てている**（取りこぼしが起きている）。捨てた件数は「取りこぼし（一時保管が満杯）」に数えられる。すでに退避したログは捨てず、新しく来た分を捨てる
- **まず確認すること**: 1004・1002 と同じ。状態画面で「取りこぼし（一時保管が満杯）」が増え続けているか
- **対処**: 1002 の対処を急いで行う。保存先へ書けるようになれば消化が進み、空きができた時点で捨てる動作は止まる。復旧後、失われた期間の目安として、1003 が出た時刻と「取りこぼし（一時保管が満杯）」の件数を記録しておく
- **関連**: 警告の本文にある「保持期間の見直し」は、保存先の容量（SQL Server Express の上限など）が原因の場合の対処である（[ディスクと DB 容量の警告](#ディスクと-db-容量の警告)）

#### 1005 スプールへの書き込みに失敗

- **意味**: 一時保管へ書こうとしたが、再試行しても書けず、そのログを捨てた。ディスクの障害・空き不足・アクセス権の問題が考えられる。捨てた件数は「取りこぼし（一時保管への保存失敗）」に数えられる
- **まず確認すること**: 1006（空き容量）が出ていないか。ドライブの空き（1002 の手順 1 のコマンド）。システムログにディスク関連のエラーが出ていないか
- **対処**: 空きを作る、またはディスクを直す。データルートのアクセス権が壊れている場合は[アクセス権の戻し方](upgrade-recovery.md#再インストールしても-access-to-the-path--is-denied-で起動しない場合)を参照する。`Spool:Directory` で一時保管をデータルートの外に置いている場合は、そのフォルダにサービスアカウント（既定 `NT SERVICE\Yagura`）が書き込めるアクセス権が要る

#### 1001 スプールなし縮退運転で起動

- **意味**: 起動時に一時保管の領域を開けなかったため、一時保管なしで受信だけを続けている。**この間に保存先への書き込みが遅れたり失敗したりすると、そのログは逃がし先がなく失われる**（「取りこぼし（保存の失敗）」などに数えられる）。状態帯は「警告あり」になる
- **まず確認すること**: 警告の本文にある一時保管のフォルダと、開けなかった原因。`Spool:Directory` を設定している場合は、その場所が存在するか
- **対処**: 原因（ディスクの障害・アクセス権・存在しない場所の指定）を取り除いてから、**サービスを再起動する**（一時保管の領域を開くのは起動時だけである）。再起動の間は受信も止まる
- **関連**: 起動時に 1 回しか出ないので、メール通知では届かないことがある

#### 1009・1010 スプールの定期自己検証に失敗・タイムアウト

- **意味**: Yagura は 1 日 1 回、確認用のレコードを使って「一時保管 → 保存」の経路が働くかを自己検証する。1009（エラー）は、確認用のレコードを書き込めなかったか、10 分たっても戻らずその間に消化もまったく進まなかったことを示す——**障害のときに使う経路が壊れている疑い**がある。1010 は滞留であり、1004 と同じ扱いでよい
- **まず確認すること**（1009）: 1005・1006（ディスク）、1030・1031・1039（保存先）、1003（満杯）が出ていないか。状態画面の一時保管の使用量が減らずに止まっていないか
- **対処**（1009）: 上の原因があれば、それを解消する。どれにも当たらない場合は、前後のイベントログを添えて [Issues](https://github.com/Yanai-Taketo/Yagura/issues) へ報告してほしい

### 保存先（データベース）の警告

保存先へ書けない間も、受信は続き、書けなかった分は一時保管へ退避される。**放置すると一時保管が満ちる**ので、復旧作業は一時保管の残り（1002 の確認方法）を見ながら進める。保存先が復旧すれば、一時保管の内容は自動で保存される。

#### 1039・1040 保存先のスキーマ初期化に失敗（縮退運転中）／回復

- **意味**: 保存先に接続できない・初期化できないまま、起動を止めずに縮退して動いている（1039）。回復すると 1040（情報。縮退していた時間を含む）が記録される
- **対処**: 何が止まり何が動いているか、管理画面に入れなくなる構成とその復旧は[データベースに接続できないとき（縮退運転）](degraded-operation.md)を参照

#### 1030 恒久障害によりバッチ書き込みが失敗

- **意味**: 保存先へのログの書き込みが、再試行では解消しない種類の失敗をした。書けなかった分は一時保管へ退避している。Yagura は、一時的と分かっている少数の失敗（ロックの競合など）と容量の枯渇（`[capacity-exhausted]`）を除き、保存先の失敗をすべてこの種類に数える。そのため、次のどれでも 1030 が出る
  - SQL Server に到達できない（SQL Server のサービスの停止・ネットワークの断・名前解決の失敗など）
  - データベースがない、Yagura の接続に使うログインの権限が外された、スキーマが合わない
  - 組み込みデータベース（SQLite）のファイルを開けない・書き込めない（アクセス権・ファイルの破損・ディスクの入出力エラー）
- **まず確認すること**（SQL Server）:
  1. SQL Server のサービスが動いているか。Yagura のサーバから SQL Server に届くか（`sqlserver01` は SQL Server のサーバ名に置き換える）

     ```powershell
     Test-NetConnection -ComputerName sqlserver01 -Port 1433
     ```

     1433 は既定のインスタンスの既定のポートである。名前付きインスタンスは既定で動的ポートを使うので、接続文字列と SQL Server 構成マネージャーで実際のポートを確かめてから置き換える
  2. 警告の本文（例外の部分にある `SqlErrorNumber=` の番号）
  3. SQL Server 側で、データベースが存在するか、Yagura の接続に使うログインの権限が外されていないか
- **まず確認すること**（組み込みデータベース）: 警告の本文。1006（ディスクの空き）が出ていないか。システムログにディスク関連のエラーが出ていないか。データルートのアクセス権が壊れていないか（[アクセス権の戻し方](upgrade-recovery.md#再インストールしても-access-to-the-path--is-denied-で起動しない場合)）
- **対処**: 原因を直す。直れば Yagura 側の操作なしに書き込みが再開し、一時保管の内容も保存される

#### 1031 Windows 統合認証での DB 接続失敗

- **意味**: Windows 統合認証で SQL Server に接続できず、書けなかった分を一時保管へ退避している。本文に、サービスの実行アカウント名と失敗の種類（ドメインコントローラー側か SQL Server 側か）が入る
- **まず確認すること**: 本文の失敗の種類。ドメインコントローラー側なら、ドメインコントローラーに届くか。SQL Server 側なら、本文のアカウント名のログインが作られているか（SQL Server のエラー 18456）、データベースがありそのログインに接続の権限があるか（エラー 4060）
- **対処**: 原因を直す。gMSA 構成では [gMSA ガイド](../guides/gmsa-service-account.md#4-db-接続windows-統合認証)の DB 接続の節と、[DC 到達性への依存](../guides/gmsa-service-account.md#7-dc-到達性への依存と回復設定)の節を参照

### ディスクと DB 容量の警告

#### 1006 監視対象ボリュームの空き容量が減少

- **意味**: データルートのドライブ（一時保管を別のドライブに置いている場合は、そのドライブも）の空きが 1 GiB を下回った。本文にどのドライブか（例: `C:\`）が入る。空きが尽きると、一時保管・組み込みデータベース・監査記録に書けなくなる
- **まず確認すること**: データルートの中で何が大きいか

  ```powershell
  $Root = "$env:ProgramData\Yagura"
  Get-ChildItem $Root -File | Sort-Object Length -Descending |
      Select-Object -First 5 Name, @{ n = 'SizeGB'; e = { [math]::Round($_.Length / 1GB, 2) } }
  Get-ChildItem $Root -Directory | ForEach-Object {
      $bytes = (Get-ChildItem $_.FullName -Recurse -File -ErrorAction SilentlyContinue |
          Measure-Object Length -Sum).Sum
      [pscustomobject]@{ Name = $_.Name; SizeGB = [math]::Round($bytes / 1GB, 2) }
  }
  ```

  主な中身は、`yagura.db`（組み込みデータベース。`yagura.db-wal` が並ぶことがある）、`spool`（一時保管）、`audit`（監査記録。既定で 365 日分を保持する）である
- **対処**: Yagura 以外のファイルを整理して空きを作るか、ディスクを増やす。`spool` が大きいのは保存先へ書けていない・追いついていない状態なので、[一時保管の警告](#一時保管スプールの警告)へ進む。組み込みデータベースが大きくても、**保持期間を短くしてドライブの空きを戻すことはできない**:
  - Yagura は組み込みデータベースのファイルを縮める処理を行わない。SQLite は既定では、行を削除してもファイルを小さくせず、空いた領域をファイルの中に残して新しいログに再利用する（SQLite 公式ドキュメント「PRAGMA auto_vacuum」）。保持期間を短く（管理画面「初期セットアップ」の「ログを保存しておく期間」）すると `yagura.db` の増え方は止まるか緩やかになるが、ドライブの空きは増えない。空きを戻すには、ディスクを増やすか、Yagura 以外のファイルを整理する
  - 保持期間の変更はすぐに反映されるが、削除は変更した時点では始まらない。実際の削除は次の定期実行（既定は毎日 3:00。サーバの時刻。設定キー `Retention:ExecutionTimeOfDay`）で、対象がなくなるまで行われる
- **関連**: データルートの中のファイルを手で削除しない。`yagura.db` を消すと蓄積したログが、`spool` を消すと保存前のログが失われる

#### 1007 SQL Server Express の DB 容量が上限に接近

- **意味**: 保存先が SQL Server Express で、データベースのサイズが上限の 80% に達した。Yagura は接続先のバージョンに関係なく、Express の上限を 10 GB として判定する（SQL Server 2022 の Express の上限値）。Express には、ほかに使えるメモリ（バッファプール 1,410 MB）と CPU（1 ソケットまたは 4 コアの小さい方）の上限もあるが、こちらは障害ではなく処理速度の頭打ちとして現れる
- **まず確認すること**: 状態画面の「保存先（データベース）の使用量」、ダッシュボードの保持期間の表示（「○ 日より古いログは自動的に削除されます」）、受信量の推移
- **対処**: 保持期間を短くする（管理画面「初期セットアップ」の「ログを保存しておく期間」）か、容量の上限のない SQL Server のエディションへ移る。保持期間を短くしても、削除は次の定期実行（既定は毎日 3:00）で行われる
- **関連**:
  - 使用量は、データベースのすべてのファイル（トランザクションログファイルを含む）の割り当てサイズの合計で判定している。トランザクションログファイルが大きい環境では、使用率が高めに出る
  - 古いログを削除しても、ファイル内の空きが新しいログに再利用されるだけで割り当てサイズは小さくならないことがあり、その場合は保持期間を短くしても警告が出続ける
  - SQL Server 2025 の Express は、データベースの上限が 50 GB に引き上げられている（Microsoft Learn「Editions and supported features of SQL Server 2025」）。SQL Server 2025 は検証中であり、現在の版はこの上限を判定に反映していないので、2025 の Express では実際の上限よりずっと手前（10 GB の 80%）でこの警告が出る
  - ダッシュボードの保持期間の表示は、サービスを起動した時点の値である。管理画面で保持期間を変えても、再起動するまで表示は変わらない（実際の削除には変更後の値が使われる）
  - 上限に達して書き込めなくなると、Yagura は保持期間による削除を前倒しで実行して空きを作ろうとし、その間に受信した分は一時保管へ退避する。保持期間内のログだけで上限を超えている場合はこれでは解消しないので、上限に達する前に対処する

### 受信経路と送信元の警告

#### 1022 受信リスナの一部が開けず縮小継続

- **意味**: 起動時に、受信の待ち受け（UDP・TCP など）の一部または全部を開けず、開けたものだけで動いている。原因は、ほかのソフトが同じポートを使っている、ネットワークアダプターのアドレスがまだ確定していない、などである。開けなかった待ち受けは 30 秒ごとに開き直しを試み、開けた時点で受信を再開する。開けなかった間は、状態画面の「受信できなかった時間帯の履歴」に「ポートを開けなかった間（再試行で復旧）」として残る
- **まず確認すること**: 本文に書かれた、開けなかった待ち受け。そのポートを別のプロセスが使っていないか（例は既定の 514。変えている場合は読み替える）

  ```powershell
  Get-NetUDPEndpoint -LocalPort 514 -ErrorAction SilentlyContinue |
      Select-Object LocalAddress, LocalPort, OwningProcess
  Get-NetTCPConnection -LocalPort 514 -State Listen -ErrorAction SilentlyContinue |
      Select-Object LocalAddress, LocalPort, OwningProcess
  Get-Process -Id 1234   # 1234 は上で表示された OwningProcess の値に置き換える
  ```

  `Yagura.Host` 以外のプロセスが表示されたら、それが競合の相手である
- **対処**: 競合しているソフトを止めるか、Yagura の受信ポートを変える。ポートを変えた場合は、送信側の宛先とファイアウォール規則も合わせる（[ポートを変えたとき](firewall.md#ポートを変えたとき無効に戻したときアンインストールしたとき)）。競合が解消すれば、再起動しなくても受信は再開する

#### 1023 ファイアウォール規則の不一致

- **意味**: 待ち受けているポートと、名前が「Yagura」で始まるファイアウォール規則が合っていない。ファイアウォールで破棄された受信はどのカウンタにも現れないので、この警告が「届いていない」ことに気づく手がかりになる
- **対処**: [規則の突合と警告（イベント ID 1023）](firewall.md#規則の突合と警告イベント-id-1023)を参照

#### 1027・1028・1029 送信元の途絶（途絶検知を有効にしている場合）

- **意味**: 管理画面「送信元の途絶検知」のウォッチリストに登録した送信元からの受信が、設定したしきい値を超えて途絶えた（1027）。同じ判定の周期に 5 件以上が一斉に途絶えた場合は、1 件にまとめて出す（1028）。受信が再開すると 1029（情報）が記録され、1027 と対で「ログが欠けていた期間」が残る。全受信の待ち受けが受信できない間は、途絶の判定を保留する（サーバ側の問題を装置の途絶と取り違えないため）
- **まず確認すること**:
  - 1028（一斉）は、個々の装置より先に**サーバ側**を疑う。Yagura の待ち受け（1022 が出ていないか）、ファイアウォール（1023）、経路上のスイッチなど共通の機器。本文に「起動・受信断回復後の再アーム起点からの発火」とある場合は、Yagura の起動や受信断のあとに、同じしきい値の登録が揃って判定されたものであり、別々の障害の寄せ集めの可能性がある
  - 1027（個別）は、装置が動いているか、意図した設定変更や停止がないか、装置の IP アドレスが変わっていないか（DHCP・機器の入れ替え）
- **対処**: 装置側を直す。IP アドレスが変わった場合は、ウォッチリストを更新する（管理画面「送信元の途絶検知」）。どれにも当たらない場合は、ログの送信を意図的に止められた（証跡の遮断）可能性も検討する
- **関連**: ダッシュボードの「送信元別の受信状況」に、登録済みの送信元と途絶中のものが強調して表示される

### 証明書の警告

Yagura が使う証明書は 3 種類あり、用途ごとに警告の ID と、使えなくなったときの影響が異なる。「使用不能」は、証明書が証明書ストアから消えた・秘密鍵を読めなくなった・有効期限が切れた、のいずれかである。

| 用途 | 期限接近（30 日前から） | 稼働中に使用不能 | 起動時に使えない | 使えないときの影響 | 差し替える管理画面 |
|---|---|---|---|---|---|
| 閲覧 UI の HTTPS（8514） | 1036 | 1037 | 1035 | LAN からの閲覧が止まる（平文には戻らない）。受信・保存・管理画面は影響を受けない | 「閲覧 UI の HTTPS 設定」 |
| 管理画面のリモートアクセス（8516） | 1014 | 1015 | 1013 | リモートからの管理画面が使えない。サーバ上の管理画面と受信は影響を受けない | 「管理 UI のリモートアクセス（HTTPS）」 |
| TLS 受信（6514） | 1017 | 1018 | 1016 | 起動時に使えなければ TLS 受信だけが開かない（UDP・TCP の平文受信は影響を受けない）。稼働中に期限が切れても **TLS 受信は止めず**、期限切れの証明書を提示し続ける | 「TLS 受信の証明書設定」 |

- **対処の流れ**: 期限接近の段階で差し替える。新しい証明書をサーバの証明書ストア（ローカルコンピューターの「個人」）へ入れ、サーバ上の管理画面（`http://localhost:8515/admin`）の上表の画面で選び直し、サービスを再起動して反映する。再起動の間は受信も止まるので、複数の証明書を変えるときは保存をまとめて 1 回の再起動で反映する
- 証明書の秘密鍵の読み取り権限は、起動時に Yagura が自動で付与を試みる（成功した場合だけ監査 2028・2009・2010 が残る）が、秘密鍵の既定のアクセス権のままではこの付与は失敗する（[証明書を用意する](opt-in-features.md#証明書を用意するtls-受信閲覧-https管理画面のリモートアクセス)）。新しい証明書を選び直す前に、[閲覧 UI の HTTPS の手順 3](viewer-https.md#主経路-自己署名--gpo-ルート配布所要-半日を見込む)（`certlm.msc` の「秘密キーの管理」）の操作で、サービスアカウントに読み取り権限を付与しておく
- 閲覧 UI の HTTPS の詳しい手順と事故のときの復旧は [閲覧 UI の HTTPS（8514）を有効化する](viewer-https.md) を参照
- 管理画面のリモートアクセスが使えなくなったときは、RDP などでサーバにサインインして、サーバ上の管理画面から差し替える

**TLS 受信の証明書の期限が切れた場合**: 期限切れの証明書を受け入れるかどうかは送信側の検証設定次第で、拒否する送信側からは接続が確立しなくなる。どの送信元が脱落したかは次で確かめる。

- 状態画面の「診断用の計器」の「TLS の接続確立に失敗した回数」（再起動で 0 に戻る）
- イベントログの警告「TLS 接続 <送信元>:<ポート> のハンドシェイクに失敗しました。」（固有の ID なし。送信元ごとに出る）
- ダッシュボードの「送信元別の受信状況」の最終受信時刻

新しい証明書へ差し替える前に、その証明書の発行元を送信側が信頼していることを確かめておく。

### 起動と設定の警告

#### 1024 設定ファイルを読み取れず起動失敗

- **意味**: 設定ファイル `yagura.json` をファイル全体として解釈できなかった（書式の誤り・文字化け・同じキーの重複）ため、起動を中止した。閲覧 UI も開かない。本文に、ファイルのフルパス、解釈に失敗した行番号、**良好構成の写し**（最後に正常に読み取れた設定の写し。`yagura.json.last-good`）の場所と保存日時が入る
- **まず確認すること**: 本文の行番号のあたり（直前に手で編集した箇所か）。写しの日時（その時点より後の変更は写しに入っていない）
- **対処 A（直す）**: 本文の行番号の誤りを直して保存し、サービスを起動する（`Start-Service Yagura`）
- **対処 B（写しに戻す）**: 写しは自動では適用しない。写しの時点の設定は、壊れる直前に意図していた設定より公開範囲が広い・認証が緩い可能性があるので、内容を確かめてから戻す。戻すコマンドは[起動しなくなったとき](prerequisites-and-hand-editing.md#起動しなくなったとき)にある。控えた壊れたファイル（`yagura.json.broken`）には資格情報が含まれ得るので、必要な内容を戻し終えたら削除する。本文に「利用可能な良好構成の写しはありません」とある場合は、対処 A で直す。本文が案内する「ウィザードでの再生成」は、サービスが起動して管理画面を開ける状態で行う操作である
- **予防**: 手で編集したら、再起動の前に管理画面の「設定の再読み込み」で確かめる。壊れた設定は適用されず（1021）、元の設定のまま動き続けるので、再起動の前に誤りに気づける。ただし再読み込みは何も適用しない予行ではなく、検証を通った変更のうちすぐ効く項目はその場で適用される（[設定ファイルを手で編集する](prerequisites-and-hand-editing.md#手順)の手順 3）

#### 1011・1012・1032 矛盾した設定の組み合わせで起動を中止

- **意味**: 安全側に倒すため、次の組み合わせでは起動しない
  - 1011: `Admin:Authentication:RequireForLoopback` が有効なのに、管理 UI の認証方式（Windows 統合認証・アプリ独自認証）が 1 つも有効でない
  - 1012: 管理画面のリモートアクセス（`Admin:RemoteBinding:Enabled`）が有効なのに、認証か HTTPS が構成されていない
  - 1032: フォワーダ MSI のアップロード（`Admin:ForwarderKit:MsiUpload:Enabled`）が有効なのに、管理 UI の認証方式が 1 つも有効でない
- **まず確認すること**: 本文（何を直せばよいかが書かれている）
- **対処**: 本文の案内に従って `yagura.json` を直し、サービスを起動する。迷ったら、有効にした機能の側（`RequireForLoopback`・`RemoteBinding:Enabled`・`MsiUpload:Enabled`）を `false` に戻すのが最も早く確実である。1011 を認証方式の側（`Admin:Authentication:Windows:Enabled`・`Admin:Authentication:App:Enabled`）を有効にして直す場合は、その方式で管理者としてサインインできることが前提になる。アプリ独自認証なら管理者アカウントが作成済みであること、Windows 統合認証ならサインインするアカウントが管理者と判定されること（既定ではローカル Administrators の所属者。[管理 UI 認証と AD グループ](authentication.md#管理-ui-認証と-ad-グループsec-9)）。この前提が揃っていないと、起動はしても管理画面に入れない。揃っているか分からなければ、先に `RequireForLoopback` を `false` に戻して起動し、管理画面で認証を整えてサインインできることを確かめてから、`RequireForLoopback` を有効に戻す
- **関連**: 固有の ID を持たない起動の中止もある（受信ポートの不正値など）。本文は「設定ファイルの検証に失敗したため起動を中止します。」で始まり、続けて理由が記録される

#### 1020 設定の再読み込みで未反映の項目が残存

- **意味**: 再読み込みした変更のうち、反映にサービスの再起動が必要な項目が残っている。管理ホームのカード「再起動待ちの設定変更」にも、再起動するまで表示される
- **対処**: 受信が止まってもよい時間帯にサービスを再起動する（再起動の間は受信が止まる）

#### 1021 設定の再読み込みを拒否（旧設定で継続）

- **意味**: 再読み込みしようとした設定に、起動を中止させる種類の誤り（受信ポートの不正値・書式の誤りなど）があったため、適用しなかった。動作中の設定は変わっていない
- **対処**: **このまま再起動すると起動に失敗する**。本文の内容に従って設定ファイルを直し、再読み込みが通ることを確かめてから再起動する

### メール通知の警告

#### 1025 メール通知の送信に失敗

- **意味**: メール通知の送信に失敗した。最初の失敗の時点で記録され、その通知は 5 分後に 1 回だけ送り直される（本文に「1 回だけ再試行します」とある）。送り直しにも失敗した通知は捨てられるが、そのときの記録（本文に「再試行済みのため、この通知は破棄しました」とある）は 15 分の抑制にかかり、出ないことが多い。一部の宛先だけが受け付けられなかった場合も出る（このときは、送れた宛先への二重送信を避けるため送り直さない）。送信待ちの通知が 64 件を超えてあふれ、捨てた分は 1025 にならない。その件数はカード「メール通知チャネル」の「送信されず破棄した通知」で見る
- **まず確認すること**: 管理ホームのカード「メール通知チャネル」の「直近の失敗」。届かなかった通知の中身は、本文のイベント ID でイベントログを引けば分かる
- **対処**: 管理画面「メール通知」でテスト送信し、画面に表示される説明（接続できない・認証が拒否された・中継を拒否された、など）に従う。**認証の拒否を、同じパスワードで繰り返し試さない**（メールサーバ側でアカウントがロックされることがある）。一部の宛先だけが受け付けられなかった場合は、宛先の綴りと、メールサーバの中継の許可を確かめる

#### 1026 メール通知が流量制御により抑制された

- **意味**: 同じ ID の送信間隔（60 分）か全体の上限（1 時間に 10 通）にかかり、メールを送らなかった。抑制が続いている間は 1 回だけ記録される
- **対処**: 短時間に多くの警告が出ている状態なので、イベントログで実際に出ている警告を確かめる（メールで届かなかった分もイベントログには残っている）。抑制の内訳（イベント ID 別）は管理画面「メール通知」で見られる

### その他の警告

#### 1008 能動通知の周期評価に失敗

- **意味**: 1 分ごとの監視（一時保管・容量・証明書などの判定）の途中で想定外のエラーが起き、その回の判定ができなかった。監視は次の回から再開する
- **対処**: 単発なら様子を見る。繰り返し出る場合は、その間ほかの警告が出なくなっている可能性があるので、本文を添えて [Issues](https://github.com/Yanai-Taketo/Yagura/issues) へ報告してほしい

#### 1019 アプリ独自認証の三層防御が昇格閾値以上継続

- **意味**: ID/パスワードでのログインに対する待ち時間・回数の制限が、15 分以上続いて発動している。総当たりなどの試行が続いている兆候である
- **まず確認すること**: 3004（ログイン失敗）・3006・3007・3012（集約）で、送信元の IP アドレスと試されたユーザー名
- **対処**: 送信元に心当たりがなければ、ネットワーク側で管理画面への到達を絞る。**待ちを解消する目的でサービスを再起動しない**（受信が止まるだけである。正しいパスワードなら、待てばログインできる）

#### 1033・1034 フォワーダ MSI 配置フォルダの書き込み権限

- **1033**: 管理画面からの MSI のアップロードを無効にしているのに、配置フォルダ（本文にパスが入る）にサービスアカウントの書き込み権限が残っている（閉じ忘れ）。[転送ガイド](../guides/forward-windows-eventlog.md#書き込み経路の開放と撤去os-管理者の明示操作)の撤去のコマンドで、読み取りのみの既定に戻す
- **1034**（情報）: アップロードを有効にしていて、書き込み権限が 24 時間以上開いたままである。常に開けておく運用なら対応は要らない（7 日ごとに再表示される）。使うときだけ開く運用なら閉じ忘れなので、上と同じ手順で撤去する

#### 1038 「認証あり・平文・LAN」構成の起動時警告

- **意味**: 閲覧 UI の認証で管理グループ（`AdminGroups`）を指定しているのに、閲覧 UI が平文（HTTPS でない）で LAN に公開されている。管理の権限を持つ Cookie が暗号化されずに LAN を流れ得る
- **対処**: [閲覧 UI 認証（8514）を有効化する](authentication.md#閲覧-ui-認証8514を有効化する)の `AdminGroups` の注意を参照し、閲覧 UI の HTTPS を併用するか、閲覧 UI には `ViewerGroups` だけを指定する
