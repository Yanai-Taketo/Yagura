# アップグレードとアンインストール

[運用ガイドの目次へ戻る](../operations.md)

新しい版の MSI を、いまのインストールの上からそのまま実行するとアップグレードになる（設定とログは引き継がれる）。本書は通常のアップグレード手順、0.5.0 から 1.0 へ上げるときに確かめること、更新後の確認、アンインストールしたときに残るもの・消えるものをまとめる。アップグレードに失敗したときの復旧は[アップグレードに失敗した / 製品が消えた・起動しないとき](upgrade-recovery.md)を参照。

> **1.0 の公開をもって、0.5 系への修正の提供は終わる。** 修正は最新リリースにだけ提供し、過去の版へは遡って提供しない（[SECURITY.md](../../SECURITY.md#サポート対象バージョンと修正の届き方)）。0.5 系に留まると、脆弱性の修正も届かなくなる。

各手順には、**実行する場所**（サーバ / クライアント）と**必要な権限**を併記する。「管理者の PowerShell」は、PowerShell を「管理者として実行」で開いたものを指す。

## アップグレードで起きること・保たれること

- **いまの版を先にアンインストールする必要はない。** 新しい版の MSI をそのまま実行する（例外は 0.4.0 以前。[インストール済みの版が 0.4.0 以前の場合](#インストール済みの版が-040-以前の場合)）
- **更新中は受信が止まる。** インストーラは最初にサービス `Yagura` を止め、新しい版のファイルを置いてからサービスを起動する。その間に届いた UDP の syslog は受け取れず、どのカウンタにも計上されない（受け取っていないため、スプールでも救えない）。TCP で送る機器・エージェントが再送するかどうかは送信側の設定による。止まっている時間は環境によって異なるため、**送信の少ない時間帯に行う**。止まっていた時間帯は、更新後の「システム状態」画面の「受信できなかった時間帯の履歴」に「停止・再起動による」として残る
- **設定とログは引き継がれる。** データルート（既定は `%ProgramData%\Yagura`。設定ファイル `yagura.json`・組み込み DB・スプール・監査記録・カウンタの記録などを置く場所）はインストーラが管理するファイルではないため、更新しても消えない。保存先が SQL Server の場合、そのデータベースにもインストーラは触れない
- **インストール時の選択は引き継がれる。** ファイアウォール規則を作るかどうか・デスクトップのショートカットを作るかどうかは、前回の選択がサーバ（レジストリ `HKLM\SOFTWARE\Yagura`）に記録されており、更新でもそれに従う。サービスの実行アカウントも同じ仕組みで引き継ぐが、**0.5.0 は実行アカウントを記録していないため、0.5.0 からの更新では引き継がれない**（[gMSA で動かしている場合](#gmsa-で動かしている場合)）
- **保存先の形式の更新は自動で行われる。** 新しい版が保存先の表の形式を変える場合は、更新後の初回起動時にサービスが行う。0.5.0 から 1.0 への更新では、管理者アカウントの表に列が加わる。操作は要らない
- **失敗しても旧版が残る。** 1.0 の MSI は、旧版の削除を新しい版のインストールと同じ一連の処理の中で行う。途中で失敗すると全体が元に戻り、**旧版がそのまま残って動き続ける**（[ADR-0023](../adr/0023-upgrade-availability.md) 決定 2）。この仕組みは更新に使う新しい MSI の側にあるため、0.5.0 から 1.0 への更新でも働く
- **上書きで古い版へ戻すことはできない。** 新しい版が入っているサーバで古い版の MSI を実行すると、「より新しいバージョンの Yagura が既にインストールされています。」と表示されて止まる。戻す必要が生じた場合は[更新後に 0.5.0 へ戻す必要が生じたとき](#更新後に-050-へ戻す必要が生じたとき)を参照

## 更新の前に確かめること

**実行場所: サーバ / 権限: 管理者の PowerShell**

次を実行して、いまの状態を確かめる。出力は控えておく（更新後の確認で比べる）。

```powershell
# インストール済みの版（DisplayVersion）。Yagura が 1 件だけ表示されること
Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\*' |
  Where-Object DisplayName -eq 'Yagura' |
  Format-List DisplayName, DisplayVersion

# OS ビルド（インストーラが判定に使う値と同じもの）
(Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion').CurrentBuildNumber

# サービスの状態・実行アカウント（StartName）・実行ファイルの場所（PathName）
Get-CimInstance Win32_Service -Filter "Name='Yagura'" | Format-List State, StartName, PathName
```

結果に応じて、次の各項を確かめる。

### インストール済みの版が 0.4.0 以前の場合

**上書きで更新しない。先にアンインストールしてから、1.0 を新規インストールする。**

0.4.0 以前の版は、版番号の付け方を整える前のビルドであり、プログラムファイルに実際の版より大きい `1.0.0.0` という版番号が付いている（公開済みの 0.3.3・0.4.0 の MSI で確認）。Windows Installer は既存のファイルと新しいファイルの版番号を比べて置き換えるかどうかを決めるため、上書きで更新すると新しい版のファイルが正しく置き換わらないおそれがある。0.3.3 から上書きした場合には、`msiexec` が成功（終了コード 0）を返し「プログラムと機能」にも新しい版が表示されるのに、サービスが登録されず本体のファイルが欠けた状態になることが確認されている。

1. 念のため、[3. データを退避する](#3-データを退避する)の手順でデータを退避する（設定とログはアンインストールでは消えないが、作業の誤りに備える）
2. [アンインストールの手順](#アンインストールの手順)で旧版をアンインストールする
3. 1.0 の MSI を新規インストールする。残っている設定とログを引き継いで起動する
4. インストール時の選択の記録はアンインストールで消えるため、ファイアウォール規則・デスクトップのショートカットはセットアップ画面で選び直す

0.2.x 以前のデータを引き継ぐ場合は、初回起動時にログの表の形式の更新（本文検索の大文字・小文字の扱いを保存先によらず揃えるもの）が自動で走る。保存先が SQL Server のときは、更新が終わるまで新しいログの書き込みが待たされる（その間に届いたログはスプールが受ける）。所要時間の目安は開発機での実測で 10 万行で約 2 秒、100 万行で約 19 秒であり、本番機の性能とディスク構成によって変わる（[database.md](../design/database.md) §9 DB-D5）。既存の SQL Server では、大文字・小文字の扱いが揃うことで、更新後に本文検索の結果が以前と変わることがある。

### OS ビルドが 17763 未満の場合

**1.0 は導入できない。** 1.0 の MSI は、OS ビルドが 17763 未満の OS（Windows Server 2016 以前など）では、実行した直後に「この OS には Yagura をインストールできません」と表示して止まり、何も変更しない。**0.5.0 はそのまま動き続ける**が、0.5 系へのサポートは終わるため、対応 OS への移行を計画する（[対応外の OS で動かしている場合](supported-environments.md#対応外の-os-で動かしている場合)）。

この判定は OS のビルド番号だけを見る。ビルド番号では見分けられない対応外の環境（ビルド 17763 以上の Windows 10 Home・Pro、Server Core）では停止しないが、導入できても対応外であることに変わりはない（[README のシステム要件](../../README.md#システム要件)）。

### gMSA で動かしている場合

`StartName` が `DOMAIN\name$` 形式（gMSA）なら、この項を読む。

0.5.0 の MSI にはサービス実行アカウントを指定する仕組みがないため、0.5.0 を gMSA で動かしているなら、それは手作業で切り替えた構成である（[gMSA ガイド §5](../guides/gmsa-service-account.md#5-稼働中インストールからの切替手順書)）。0.5.0 はそのアカウントを記録していないので、**1.0 へ更新するときに gMSA を指定し直さないと、サービスは既定の仮想サービスアカウント `NT SERVICE\Yagura` で構成され、データルートのアクセス権も既定に戻る**。SQL Server へ Windows 統合認証で接続し、SQL Server 側のログインを gMSA に対して作っている場合は、保存先に接続できなくなる（[縮退運転](degraded-operation.md)になる）。

- **指定の方法**: [4. MSI を実行する](#4-msi-を実行する)で、コマンドラインに `YAGURA_SERVICE_ACCOUNT=<ドメイン>\<gMSA 名>$` を加える。セットアップ画面に「サービス実行アカウント」の入力欄が表示された場合は、そこに同じ値が入っていることを確かめてから進める
- 1.0 を一度この方法で入れれば、以後の更新では記録から引き継がれる（[gMSA ガイド「アップグレード時の継承」](../guides/gmsa-service-account.md#アップグレード時の継承)）
- **指定し忘れた場合**は、更新後に [gMSA ガイド §5](../guides/gmsa-service-account.md#5-稼働中インストールからの切替手順書) の手順で gMSA へ切り替え直す
- **サービスの失敗時の回復設定**: インストーラは回復設定を既定値（5 秒後に再起動・3 回まで）で書き込む。[gMSA ガイド §7](../guides/gmsa-service-account.md#7-dc-到達性への依存と回復設定)に従って回復設定を変えている場合は、更新後に確かめて設定し直す（[5. 更新後に確かめる](#5-更新後に確かめる)）

### インストール先を既定から変えている場合

`PathName` のフォルダが `C:\Program Files\Yagura` 以外なら、この項を読む。

インストーラは前回のインストール先を記録していない。**セットアップ画面のインストール先で、いまのインストール先（`PathName` のフォルダ）を指定する**。コマンドラインで実行する場合は `INSTALLFOLDER="<いまのインストール先>"` を加える。自分で追加したファイアウォール規則（TLS 受信・管理画面のリモートアクセス）は実行ファイルのパスで限定しているため、インストール先が変わると規則が効かなくなる（[ファイアウォール規則を自分で足す](firewall.md)）。

## アップグレードの手順

### 1. MSI を入手して確かめる

**実行場所: インターネットに出られる PC（サーバでもクライアントでもよい） / 権限: 一般ユーザーでよい**

[Releases](https://github.com/Yanai-Taketo/Yagura/releases) から、新しい版の MSI（x64 なら `Yagura-1.0.0-x64.msi`、ARM64 なら `Yagura-1.0.0-arm64.msi`）と、同じ名前に `.sha256` が付いたファイルを入手する。ダウンロードしたフォルダで PowerShell を開き、次を実行する。

```powershell
$msi = '.\Yagura-1.0.0-x64.msi'
$expected = (Get-Content "$msi.sha256" -Raw).Split(' ')[0]
$actual   = (Get-FileHash $msi -Algorithm SHA256).Hash
if ($actual -eq $expected) { 'SHA256 は一致' } else { 'SHA256 が一致しない（この MSI は使わない）' }
Get-AuthenticodeSignature $msi | Format-List Status, SignerCertificate
```

SHA256 が一致し、`Status` が `Valid` で、署名者が[コード署名ポリシーの期待値](../code-signing-policy.md#署名者の期待値)と一致することを確かめる。確かめた MSI をサーバへ移す。

### 2. 更新前の状態を控える

**実行場所: サーバ（ブラウザでの確認はクライアントからでもよい） / 権限: コマンドは管理者の PowerShell**

- [更新の前に確かめること](#更新の前に確かめること)のコマンドの出力（版・実行アカウント・実行ファイルの場所）を控える
- ブラウザで `http://<サーバ名>:8514/status`（「システム状態」画面。サーバ上なら `http://localhost:8514/status`、閲覧 UI を HTTPS にしている場合は `https://`）を開き、「各種カウンタ（累計）」の値を画面の写しなどで控える
- 「ダッシュボード」の「送信元別の受信状況」で、普段ログを送ってくる機器を確かめておく

### 3. データを退避する

**実行場所: サーバ / 権限: 管理者の PowerShell**

```powershell
$Root = "$env:ProgramData\Yagura"        # データルート（環境変数 YAGURA_DATAROOT で移している場合はその場所）
$Dest = 'D:\Backup\Yagura-before-1.0'    # 退避先（管理者だけが読める場所。データルートと別のディスクを勧める）

Stop-Service Yagura
robocopy $Root $Dest /E /R:1 /W:1
"robocopy の終了コード: $LASTEXITCODE（8 未満なら成功）"
```

- **サービスを止めてから複製する。** 組み込み DB（SQLite）は本体ファイル `yagura.db` の脇に書き込み途中の内容（`yagura.db-wal`）を持つことがあり、動いたままでは全体を揃えて写せない
- **サービスは止めたまま手順 4 へ進んでよい**（インストーラが最後にサービスを起動する）。すぐに更新しない場合は `Start-Service Yagura` で起動しておく
- `yagura.json` の `Spool:Directory` でスプールを別の場所に置いている場合は、そのフォルダも同じように複製する
- **保存先が SQL Server の場合**、ログ本体と管理者アカウントの台帳は SQL Server のデータベースにある。SQL Server 側の通常の手順で、更新の直前にデータベースのバックアップを取る。既存のバックアップ計画がある場合は、計画の差分バックアップの基点を変えない「コピーのみ」のバックアップ（`BACKUP DATABASE ... WITH COPY_ONLY`）にする
- 退避したデータは**このサーバへ戻すためのもの**である。設定ファイル内の暗号化された値（SQL Server の接続文字列・SMTP のパスワード）は、このサーバでしか復号できない
- 退避先には設定ファイル（暗号化した資格情報を含むことがある）と監査記録が含まれる。**管理者以外が読めない場所に置く**（`robocopy` は上のコマンドではアクセス権を写さず、退避先のフォルダのアクセス権を引き継ぐ）

### 4. MSI を実行する

**実行場所: サーバ / 権限: 管理者**

ログを残せるため、コマンドでの実行を勧める。管理者の PowerShell で次を実行する。

```powershell
$msi = 'C:\Work\Yagura-1.0.0-x64.msi'    # 手順 1 で確かめた MSI
$log = "$env:TEMP\yagura-upgrade.log"
$msiArgs = @('/i', "`"$msi`"", '/l*v', "`"$log`"")
# gMSA で動かしている場合だけ、次の行の先頭の # を外して gMSA 名に書き換える
# $msiArgs += 'YAGURA_SERVICE_ACCOUNT=EXAMPLE\gmsaYagura$'
# インストール先を既定から変えている場合だけ、次の行の先頭の # を外して書き換える
# $msiArgs += 'INSTALLFOLDER="D:\Apps\Yagura"'
$p = Start-Process msiexec.exe -Wait -PassThru -ArgumentList $msiArgs
"msiexec の終了コード: $($p.ExitCode)"
```

- 終了コード `0` は成功、`3010` は成功（OS の再起動が必要）。それ以外は[更新に失敗したとき](#更新に失敗したとき)へ
- 画面を出さずに実行する場合は、`$msiArgs` に `'/qn'` を加える
- **画面で実行する場合**は、MSI をダブルクリックし、UAC に表示される発行元を確かめて進める。セットアップ画面が表示された場合、ファイアウォール規則・デスクトップのショートカットの選択には前回の選択が入っているので、変えずに進める。インストール先とサービス実行アカウントは[更新の前に確かめること](#更新の前に確かめること)の注意に従う

### 5. 更新後に確かめる

**実行場所: サーバ / 権限: 管理者の PowerShell**

```powershell
Get-Service Yagura | Format-List Name, Status

Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\*' |
  Where-Object DisplayName -eq 'Yagura' |
  Format-List DisplayName, DisplayVersion

$svc = Get-CimInstance Win32_Service -Filter "Name='Yagura'"
$svc | Format-List State, StartName, PathName
(Get-Item $svc.PathName.Trim('"')).VersionInfo.FileVersion

# 直近 1 時間の Yagura の警告・エラー
Get-WinEvent -ErrorAction SilentlyContinue -FilterHashtable @{
  LogName = 'Application'; ProviderName = 'Yagura'; Level = 1, 2, 3
  StartTime = (Get-Date).AddHours(-1)
} | Format-Table TimeCreated, Id, LevelDisplayName, Message -Wrap
```

| 確かめること | 期待する結果 | 違ったとき |
|---|---|---|
| サービス | `Status` が `Running` | [まず確認する](upgrade-recovery.md#まず確認する)へ |
| 製品の版 | Yagura が **1 件だけ**表示され、`DisplayVersion` が `1.0.0` | 2 件表示される場合は、**どちらもアンインストールせず**、[まず確認する](upgrade-recovery.md#まず確認する)を確かめたうえで [Issues](https://github.com/Yanai-Taketo/Yagura/issues) へ報告する |
| 実行ファイルの版 | `FileVersion` が `1.0.0.0` | 本体のファイルが置き換わっていない。手順 4 のログを添えて [Issues](https://github.com/Yanai-Taketo/Yagura/issues) へ報告する |
| 実行アカウント | `StartName` が更新前と同じ（既定は `NT SERVICE\Yagura`、gMSA ならその名前） | gMSA が仮想サービスアカウントに戻っていたら、[gMSA ガイド §5](../guides/gmsa-service-account.md#5-稼働中インストールからの切替手順書)の手順で切り替え直す |
| イベントログ | 更新後の時刻に Yagura のエラーが無い | 内容に応じて各節（[縮退運転](degraded-operation.md)・[ファイアウォール規則の突合](firewall.md#規則の突合と警告イベント-id-1023)など）を参照する |

**受信を確かめる**（実行場所: サーバ / 権限: 一般ユーザーでよい）。テスト用の 1 件を送り、ログ検索で探す。

```powershell
$token = 'yagura-upgrade-check-' + (Get-Date -Format 'yyyyMMddHHmmss')
$udp = New-Object System.Net.Sockets.UdpClient
$bytes = [System.Text.Encoding]::ASCII.GetBytes("<134>1 - - - - - - $token")
[void]$udp.Send($bytes, $bytes.Length, '127.0.0.1', 514)   # 受信ポートを変えている場合はその番号
$udp.Close()
$token
```

表示された文字列を、「ログ検索」画面の「本文の検索語（部分一致）」に入れて検索し、1 件見つかることを確かめる。サーバ自身からの送信はファイアウォールの規則が無くても届くため、**ネットワーク越しに届くことは別に確かめる**: 同じコマンドをクライアント（同じネットワークの Windows PC。一般ユーザーでよい）で、`'127.0.0.1'` をサーバ名に替えて実行するか、「ダッシュボード」の「送信元別の受信状況」で、普段の機器の最終受信が更新後の時刻になっていることを確かめる。

**カウンタを確かめる**（「システム状態」画面）。

- 「各種カウンタ（累計）」の値は、再起動をまたいで累計を引き継ぐ。**手順 2 で控えた値以上**であること
- 「取りこぼし」で始まる項目が手順 2 の値から増えていれば、その項目の内容を確かめる。「一時保管への退避（取りこぼしではありません）」は、サービスが止まるときにメモリ上のログを一時保管（スプール）へ逃がすため、更新で増えることがある。逃がしたログは起動後にデータベースへ保存される
- 1.0 で加わった項目（例: 「取りこぼしの疑い（接続が想定外の理由で終了）」）は 0 から数え始める。項目の並びが更新前と違うことがあるので、「識別子」の列で同じ項目どうしを比べる
- 「受信できなかった時間帯の履歴」に、更新の時間帯が「停止・再起動による」として載っているのは正常である

**このほかに確かめること**

- 管理画面に ID とパスワード（アプリ独自のアカウント）でサインインしている場合は、サインインできること
- gMSA の手順で回復設定を変えている場合は、`sc.exe qfailure Yagura` で回復設定を表示し、変わっていれば [gMSA ガイド §7](../guides/gmsa-service-account.md#7-dc-到達性への依存と回復設定) のコマンドを実行し直す（PowerShell では `sc` が別のコマンドの別名になっているため、`sc.exe` と書く）

## 更新に失敗したとき

- 1.0 の MSI は、失敗すると全体を元に戻す。**旧版が残っているはずなので、慌てて再インストールせず**、まず[まず確認する](upgrade-recovery.md#まず確認する)を行う
- 手順 3 でサービスを止めたまま実行した場合は、元に戻った後もサービスが止まったままのことがある。`Get-Service Yagura` が `Stopped` なら `Start-Service Yagura` で起動する
- `1920`（サービスを開始できませんでした）・`1603`（インストール中に致命的なエラー）・`Access to the path ... is denied` が出た場合は、[アップグレードに失敗した / 製品が消えた・起動しないとき](upgrade-recovery.md)の手順に従う
- 原因の手がかりは手順 4 のログ（`$env:TEMP\yagura-upgrade.log`）にある。ログの中で `Return value 3` を検索すると、失敗した処理の近くが見つかる。[Issues](https://github.com/Yanai-Taketo/Yagura/issues) へ報告するときはこのログを添える（ログにはサーバ名やアカウント名が含まれるため、公開の場に貼る前に内容を確かめる）

## 更新後に 0.5.0 へ戻す必要が生じたとき

0.5 系はサポートが終わっているため、戻すのは 1.0 での問題を解決するまでの一時的な措置に限る。

- 0.5.0 の MSI は、1.0 が入っているサーバには上書きで入らない（[アップグレードで起きること・保たれること](#アップグレードで起きること保たれること)）
- 1.0 は初回起動時に保存先の形式を更新する。1.0 で起動した後のデータを 0.5.0 でそのまま使えるかは確かめていないため、**手順 3 で退避したデータへ戻す**。更新後に受信したログは、戻したデータには含まれない

**実行場所: サーバ / 権限: 管理者の PowerShell**

1. 1.0 をアンインストールする（[アンインストールの手順](#アンインストールの手順)）
2. 退避したデータをデータルートへ戻す。`/MIR` はデータルートを退避時の内容に揃える指定で、退避した後に増えたファイルは消える

   ```powershell
   $Root = "$env:ProgramData\Yagura"
   $Dest = 'D:\Backup\Yagura-before-1.0'    # 手順 3 の退避先
   robocopy $Dest $Root /MIR /R:1 /W:1
   "robocopy の終了コード: $LASTEXITCODE（8 未満なら成功）"
   ```

3. 保存先が SQL Server の場合は、手順 3 で取ったバックアップからデータベースを復元する
4. 0.5.0 の MSI をインストールする（戻したデータを引き継いで起動する）

## アンインストール

### アンインストールの手順

**実行場所: サーバ / 権限: 管理者**

コントロールパネルの「プログラムと機能」（または「設定」のアプリの一覧）で Yagura を選び、アンインストールする。PowerShell で行う場合は、管理者の PowerShell で次を実行する。

```powershell
$p = Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\*' |
  Where-Object DisplayName -eq 'Yagura'
$log = "$env:TEMP\yagura-uninstall.log"
$r = Start-Process msiexec.exe -Wait -PassThru -ArgumentList "/x $($p.PSChildName) /l*v `"$log`""
"msiexec の終了コード: $($r.ExitCode)"
```

- アンインストールを始めた時点でサービスが止まり、以後は受信しない
- 対応外の OS 上でもアンインストールはできる（インストーラは削除のときには OS を判定しない）

### 消えるもの

| 対象 | 補足 |
|---|---|
| サービス `Yagura` | |
| インストール先のプログラム（既定は `C:\Program Files\Yagura`） | |
| インストーラが作ったファイアウォール規則 3 本（`Yagura Syslog (UDP 514)`・`Yagura Syslog (TCP 514)`・`Yagura Viewer (TCP 8514)`） | 自分で追加した規則は消えない（下の「残るもの」） |
| スタートメニューの「Yagura」フォルダと、デスクトップの閲覧ショートカット | |
| レジストリ `HKLM\SOFTWARE\Yagura`（インストール時の選択の記録） | 入れ直すときは、ファイアウォール規則・ショートカット・サービス実行アカウントを選び直す |
| イベントログのソース `Yagura` の登録 | 既にアプリケーションログへ記録されたイベントは消えない |

### 残るもの

| 対象 | 場所 | 補足 |
|---|---|---|
| **データルート一式**（設定ファイル・組み込み DB・スプール・監査記録・カウンタの記録など） | `%ProgramData%\Yagura`（環境変数 `YAGURA_DATAROOT` で移している場合はその場所） | インストーラはデータルートの中身を管理しないため消えない（中身が空のときだけフォルダが消える）。フォルダのアクセス権（SYSTEM・Administrators・サービスアカウント）もそのまま残る。gMSA で動かしていた場合は gMSA のアクセス権も残る。本番昇格した後の旧データベースファイルもここに含まれる（[昇格後に旧データベースファイルを処分する](promotion-old-db.md)） |
| フォワーダ配布フォルダ | `%ProgramData%\Yagura\forwarder` | Fluent Bit の MSI を置いていれば、そのファイルとフォルダのアクセス権ごと残る（空なら消える） |
| データルートの外に置いたスプール | `yagura.json` の `Spool:Directory` の場所 | |
| 自分で追加したファイアウォール規則（TLS 受信・管理画面のリモートアクセスなど） | Windows ファイアウォール | [ポートを変えたとき・無効に戻したとき・アンインストールしたとき](firewall.md#ポートを変えたとき無効に戻したときアンインストールしたとき)の手順で確認・削除する |
| 証明書と、その秘密鍵へのサービスアカウントの読み取り権限 | コンピューターの証明書ストア（個人） | 閲覧 UI の HTTPS・管理画面のリモートアクセス・TLS 受信に使った証明書。Yagura は起動時にサービスアカウントへ秘密鍵の読み取り権限の付与を試みる（手作業で付与した場合もある）が、アンインストールではどちらも取り消さない。不要なら `certlm.msc` → 個人 > 証明書 → 対象を右クリック →「すべてのタスク」→「秘密キーの管理」でサービスアカウントの項目を削除するか、証明書ごと削除する。GPO で配ったルート証明書は[撤去・棚卸し（配布の対）](viewer-https.md#撤去棚卸し配布の対)に従う |
| 保存先の SQL Server のデータベースとログイン | SQL Server | インストーラは SQL Server に触れない |
| gMSA 本体・HTTP の SPN・「サービスとしてログオン」の権利 | Active Directory・ローカルポリシー / GPO | gMSA で動かしていた場合。不要なら AD 管理者が整理する（[gMSA ガイド](../guides/gmsa-service-account.md)） |

### データも残さず取り除く場合

サーバを廃棄・転用する場合など、データを残さないときは、アンインストールの後に次を行う。**元に戻せない**——必要なら先に[3. データを退避する](#3-データを退避する)の手順で退避する。データルートには、ログ・監査記録に加えて、暗号化した資格情報を含む設定ファイルがある。

**実行場所: サーバ / 権限: 管理者の PowerShell**

```powershell
Remove-Item "$env:ProgramData\Yagura" -Recurse -Force
```

あわせて、上の「残るもの」の表のうち不要なもの（データルートの外のスプール、自分で追加したファイアウォール規則、証明書とその権限、SQL Server のデータベースとログイン、gMSA まわりの設定）を整理する。環境変数 `YAGURA_DATAROOT` を設定していた場合は、その場所と環境変数も削除する。

### 後で入れ直す場合

- データルートを残しておけば、MSI を新規インストールするだけで、設定とログを引き継いで起動する
- インストール時の選択の記録はアンインストールで消えているため、ファイアウォール規則・デスクトップのショートカット・サービス実行アカウントはセットアップ画面（またはコマンドラインのプロパティ）で選び直す。gMSA で動かす場合は `YAGURA_SERVICE_ACCOUNT` を指定する（[gMSA ガイド §3](../guides/gmsa-service-account.md#3-インストール時の指定)）
