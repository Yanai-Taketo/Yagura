## 1. provider 抽象

### 1.1 構成

- 永続化層は**初日から provider 抽象**とし、SQL 方言・機能差は provider 層に封じ込める（ADR-0002 決定 3）。上位（受信・UI・ホスト）は抽象インターフェースのみを参照し、特定 DB の SQL・接続 API を直接書かない
- v0.1 の必須 provider は **SQLite**（組み込み既定。§4）と **SQL Server**（本番第一推奨。§5）の 2 つ。PostgreSQL / MySQL は追加を意図する（約束ではない。ADR-0002 決定 3）
- 抽象の縫い目は 2 実装で検証するが、2 実装での検証が第 3 の provider への適合を保証するわけではない——十分性は適合テストスイート（§1.3）の設計で担保する（ADR-0002 の同趣旨を本文書が引き受ける）

### 1.2 provider 契約

provider が実装すべき操作と性質。インターフェースの C# シグネチャは実装設計で確定するが、**契約の意味論はここで固定する**:

| 契約 | 内容 | architecture.md §7 対応 | 主な利用者 |
|---|---|---|---|
| スキーマ管理 | スキーマの新規作成と版間移行（冪等——既に適用済みなら何もしない）。実行に必要な権限が不足する場合、**不足内容と、管理者がそのまま実行できる SQL を区別可能に報告する**（§5.2。**提示 SQL は秘密情報を含まない**） | —（本文書独自） | ホスト（起動時・昇格時） |
| バッチ挿入 | ログレコードのバッチ書き込み（architecture.md §2.1）。部分成功の扱い（全再試行で重複になっても at-least-once の範囲内）を含む | ① | 永続化段 |
| 失敗の分類報告 | 書き込み失敗を**一時障害（再試行に意味がある）・恒久障害（設定・スキーマ・権限の問題）・容量枯渇（保存領域の上限。削除で回復し得る）の 3 区分で報告する**。応答しないハングは呼び出し側のタイムアウトが打ち切る（architecture.md §3.2.1） | ② | 永続化段・ホスト |
| 対話的検索 | 条件（時間範囲・送信元・**重大度の閾値（以下。Issue #148）**・**facility**・**解析状態（ParseStatus）**・自由文等）+ **射影（一覧用の軽量列）+ 結果上限 + タイムアウト**を必須引数とする読み取り（architecture.md §6 の防御を契約レベルで強制する。**防御対象は UI の対話的検索であり、下記「契約拡張の予約」の管理経路には適用しない**）。並びは `ReceivedAt` 降順、同一 `ReceivedAt` は `Id` 降順でタイブレークする（Issue #144。UDP バースト等の同一時刻多発でも結果順序を決定的にする）。任意で**カーソル（キーセット）ページング**（`(ReceivedAt, Id)` 基準。[DB-11](#8-確定待ち一覧)）を受け付け、指定時は先頭ページと同じ条件のまま「カーソルより過去」の行だけを返す——OFFSET は使わない | —（本文書独自。architecture.md §6 の契約化） | UI |
| 保持期間の削除 | 基準時刻より古いレコードの削除。**受信の書き込みを長時間妨げない方式**（分割実行等）であること（§3） | ④ | ホスト（定期実行） |
| 統計 | 保存件数・DB サイズ（またはサイズ取得不能の明示。**SQL Server provider には適用しない**——§5.3 の必須要件）。Express の上限接近警告（§5.3）と昇格案内の入力 | —（本文書独自） | ホスト・UI |
| 読み書き分離の性質 | 「検索が書き込みをブロックし得るか」と付随する運用特性（§4 の WAL 肥大等）を provider ごとに明示する。**これは文書化義務であり、機械検証の対象ではない**（§1.3） | ③ | 設計・レビュー |

- **重大度・facility・解析状態の絞り込み（Issue #148。M8-3 追補）**: severity は完全一致ではなく**閾値方式**（`SeverityAtMost` 以下）で絞り込む——syslog は数値が小さいほど深刻なため、「N 以上の重大度」という運用語彙は「Severity ≤ N」に対応する（完全一致では「エラー以上」のつもりで選んでも、より深刻な緊急・警報・重大が結果から消える実害があった）。severity が未設定（PRI 自体を解析できなかった行）は閾値比較の対象外——それらを明示的に拾う手段は `ParseStatus` 条件（完全一致）。facility も完全一致。いずれも既存列のみを対象としスキーマ変更は不要。**自由文検索の対象列拡張（Hostname/AppName/StructuredData 等への拡張）は本 PR のスコープ外**——DB-6（下記）が確定した対象は Message のみであり、他列への拡張自体は別途の提案を要する
- **結果順序の決定性（Issue #144）**: `ORDER BY ReceivedAt DESC, Id DESC` に統一——`Id` は挿入順（採番順）と一致するため、同一 `ReceivedAt` 内は「新しく挿入された行が先」という決定的な順序になる
- **カーソル（キーセット）ページング（[DB-11](#8-確定待ち一覧)。✅ 実装・実行計画実測済み。2026-07-10）**: `LogQuery.Cursor`（`LogQueryCursor(ReceivedAt, Id)`）を任意引数として追加した。指定時、両 provider の `QueryAsync` は `ORDER BY ReceivedAt DESC, Id DESC` と同じ複合キーに対する「カーソルより真に過去」のシーク条件を他の WHERE 条件と AND で組み合わせ、複合索引 `IX_LogRecords_ReceivedAt_Id`（§2.1 DDL。既に #189 で追加済み）の索引シークとして実行される。**OFFSET は使わない**——OFFSET はスキップ件数分を毎回スキャンする方式でありページが深くなるほど劣化するのに対し、シーク法（keyset pagination）はページ番号に依存しない一定の性能特性を持つ。`Cursor` 省略時（既定 `null`）は従来どおり先頭ページ（最新から）を返し後方互換性を保つ。適合テストスイート（§1.3）に境界ケース（同一 `ReceivedAt` 内でカーソルが割れる場合の重複/欠落なし・`ReceivedAt` をまたぐ継続・カーソルなし=先頭ページ・多ページ走査での網羅性・**フィルタ条件（重大度閾値）との併用での重複/欠落なし**）を追加済み。**索引設計は新規追加が不要**（#189 で確定済みの `(ReceivedAt DESC, Id DESC)` 複合索引がカーソル条件のシークにもそのまま適用できる）。**「索引シークとして実行される」は両 provider とも実行計画の実測で裏付け済み**（PR #221 レビュー起点。2026-07-10。いずれも 200 万行・同一 `ReceivedAt` に平均 10 行のクラスタ = UDP バースト相当の分布）。述語の形は provider ごとに異なる（意味論は同一——各 provider の最適化器が確実にシークする形を実測で選ぶ。§1.1 の方言封じ込めの範囲）:
  - **SQLite**: OR 分解形 `(ReceivedAt < @c OR (ReceivedAt = @c AND Id < @i))` をそのまま使う。`EXPLAIN QUERY PLAN` が `SEARCH LogRecords USING INDEX IX_LogRecords_ReceivedAt_Id (ReceivedAt<?)`（SCAN ではなく SEARCH = 索引シーク）を返し、0.021ms/クエリで安定することを確認済み（PR #221 レビューでの実測）
  - **SQL Server**: 等価な書き換え形 `(ReceivedAt <= @c AND (ReceivedAt < @c OR Id < @i))` に **`FORCESEEK` テーブルヒント（カーソル指定時のみ付与）**を併用する。理由: OR 分解形は SqlLocalDB での実測で**計画選択が不安定**——同一スキーマ・同一データに対し、Clustered Index Scan + Top N Sort（全該当行を読んでからソート。中間カーソルで実際に約 100 万行走査・約 1 秒/クエリ・**浅いカーソルほど遅い** = シーク法の狙いと真逆の特性）に落ちる場合と Index Seek になる場合の両方を観測した（統計サンプリングの揺れによるコスト境界と推定）。書き換え形は先頭 conjunct（`ReceivedAt <= @c`）が常に索引のシーク述語になれる形であり、FORCESEEK（Microsoft Learn "Table hints (Transact-SQL)" が用途として明記する「カーディナリティ推定の問題でシークではなくスキャンが選ばれる場合」そのもの。確認日 2026-07-10）で計画を決定論的に固定する。実測: シーク計画は**カーソル深度（先頭直後・100 万行目・198.5 万行目）によらず約 19ms/クエリ（limit=10,000・全 15 列射影・キールックアップ 10,000 回込み・各深度 100 回実行）で平坦**。フィルタ併用（Severity 閾値・自由文 LIKE）でもコンパイル可能・シーク計画になることを実行計画で確認済み。カーソルなし（先頭ページ = 従来経路）にはヒントを付与せず、従来の計画選択を変えない。却下した代替: キー先行 deferred join（内側サブクエリで索引内列のみの TOP を確定 → 本体列を join で取得）は実測で Merge Join + 全表 Clustered Index Scan に落ち、深度比例で劣化（浅 22ms→深 131ms）したため却下
- **契約拡張の予約**: 次の 2 操作は現契約に含めないが、必要になる時点が既に見えているため、**§7 の互換性規則に従う optional 操作（capability 検出）として追加する**ことを予約する: (a) **一括読み出し**——移行（§6.2）・エクスポート用のストリーミング読み出し。上限・タイムアウトの必須化は適用せず、呼び出し経路を管理操作に限定する。(b) **集計**——ダッシュボード用の件数集計等（要否と形は ui.md 起筆時に確定）。対話的検索の防御を契約全体の禁止事項に一般化しない
- **M8-3（Issue #70）で追加した読み取り専用 3 操作**: 閲覧 3 画面の実装が要求する最小の読み取り口として、`ILogStore` へ次を追加した——①**詳細表示の個別取得** `FindByIdAsync`（全項目——Message 全文・StructuredData・Raw——を 1 件返す。architecture.md §6「全文は詳細表示で個別取得する」の契約化）、②**システムイベントの読み出し** `QuerySystemEventsAsync`（§2.3 の可視化面。区間の重なり判定 + 上限 + タイムアウト必須。Issue #150——保持期間削除の起動時キャッチアップ——で **Kind の完全一致フィルタ（省略可・既定は全種別）を最小の契約拡張として追加**した。理由は §3「起動時キャッチアップ」参照）、③**送信元別の集計** `QuerySourceActivityAsync`（予約 (b) の初の実体化。送信元ごとの最終受信時刻・件数を**最終受信時刻の古い順**で返す——ui.md UI-4 の無音化検出の要件「量の上位 N 抽出は不可」を集計の並び・打ち切り方向のレベルで満たす）。いずれもタイムアウトを必須引数とし、書き込みを行わない。v0.x のため通常のインターフェースメソッドとして追加した（optional 操作——capability 検出——へ移すかは §7 の v1.0 凍結判断で確定する）。適合テストスイート（§1.3）に 3 操作の検証を追加済み。(a) 一括読み出しは引き続き予約のまま
- **M8-5（Issue #159）で追加した読み取り専用 2 操作**: ダッシュボードに欠けていた「平常時からの逸脱検知」と「フラッディング検知」の 2 視点を満たすため、`ILogStore` へ予約 (b) 集計の追加実体化として次を追加した——④**重大度分布** `QuerySeverityDistributionAsync`（観測窓内の重大度別件数。PRI が解析できず Severity 未設定のレコードも 1 バケットとして返す——解析失敗の事実を隠さない）、⑤**受信量上位の送信元（Top talkers）** `QueryTopTalkersAsync`（観測窓内の件数降順。`QuerySourceActivityAsync` とは逆方向の集計であり、UI-4「量の上位 N 抽出は不可」の対象を無音化検出の一覧に限定するため、既存操作を書き換えずに別メソッドとして追加した）。**両操作は観測窓（`from`/`to`）を必須引数とする**——無条件の集計は大規模時にフルスキャンへ劣化し得るため、索引済みの `ReceivedAt` 範囲へ先に絞り込んでから集計する設計とした（Severity・SourceAddress の複合索引は Issue #145 のスキーマ v1→v2 移行で追加済みだが、窓の必須化はそれとは独立の防御として維持する）。ダッシュボード実装（M8-5）は受信量推移と同じ窓（直近 1 時間）を用いる。適合テストスイート（§1.3）に 2 操作の検証を追加済み
- **Issue #383 で追加した読み取り専用 1 操作**: 途絶検知のウォッチリスト候補選択（ADR-0018 決定 4——実受信のある送信元から選ばせる）向けに `QueryMostRecentlyActiveSourcesAsync`（**最終受信時刻の新しい順**）を追加した。`QuerySourceActivityAsync`（無音化検出用の古い順）を後から並べ替えるだけでは、送信元数が上限を超える環境で**現役の送信元が DB 側の打ち切りで既に落ちている**（打ち切りの向きが逆）。両者は同じ集計の並び順違いのため、`ILogStore` に**既定実装（`QuerySourceActivityAsync` へ委譲——送信元数が上限以下・偽実装では正しい）を持つ 1 メソッドとして追加**し、実ストア（SQLite / SQL Server）が `ORDER BY … DESC LIMIT` で打ち切りの向きを正すオーバーライドを提供する。適合テストスイート（§1.3）に降順の並び・打ち切り方向の検証を追加済み
- **Issue #502 で追加した optional 操作**: 予約 (b) 集計の optional 実体化として `IHourlyLogCountReader.CountByHourAsync`（ReceivedAt の UTC の正時ごとの件数。件数 0 の時間帯は返さない）を追加した。`ILogStore` 本体には載せず、`store is IHourlyLogCountReader` で検出する（`IBulkLogReader` と同じ）。呼び出し経路は管理操作（§6.3 の処分の前の時間帯ごとの照合）に限り、上限・タイムアウトの必須化は適用しない。両 provider が実装する（SQLite = ReceivedAt の文字列の先頭 13 文字〔`yyyy-MM-ddTHH`〕で集約、SQL Server = 固定の基準時刻からの経過時間数〔`DATEDIFF(hour, …)`〕で集約）。対応しない provider では §6.3 の照合ができず、処分の前にすべてのログを未移行とみなす（安全側）
- **自由文検索の一致規則（[DB-6](#8-確定待ち一覧)。規則・実装とも確定。SQL Server は v1→v2 スキーマ移行で列 COLLATE を適用済み・SQLite は DB-9 の性能実測（2026-07-10）を経てアプリ定義比較関数で実装・検証済み——§4。2026-07-09 オーナー決定「大文字小文字非区別で provider 間統一」）**: 対象列は `LogRecord.Message` のみ（[LogQuery.cs](../../src/Yagura.Storage/LogQuery.cs) の暫定規則を確定として採用。送信元等の他条件は完全一致のまま §1.2 表のとおり）。一致方式は部分一致（前後を問わない中間一致）。**大文字小文字は区別しない。そして折り畳むのは大文字小文字のみ**——アクセント記号の同一視（café ≒ cafe）・かな種の同一視（ひらがな ≒ カタカナ）・全角/半角の同一視は、いずれもこの規則の対象に**含めない**（同一視しない。したがって大文字小文字を持たない日本語文字——ひらがな・カタカナ・漢字——の一致判定はこの規則で変わらない）。検証の強度は二段階に分ける:
  - **ASCII 範囲（A–Z/a–z）の非区別は両 provider が確実に満たす最小要件**とする（適合テストで blocking——不合格は provider 受け入れを止める）
  - **非 ASCII の大文字小文字非区別は provider 間で揃えることを目標**とし、適合テストスイート（§1.3）の非 ASCII 大小ケースで検証する。合否の「正」は特定 provider の挙動ではなく **Unicode の simple case folding が一意に定まる文字の集合（保証集合）**に置く——保証集合の具体的な文字一覧は実装バッチで確定するが、**Issue #146 の再現例（CAFÉ/café）を含むラテン基本の大小ペアを必ず含める**。**保証集合は正例と負例の双方を blocking として含める**——正例（同一視されるべき大小ペア）に加え、負例（同一視されて**はならない**ペア: ひらがな「あ」/カタカナ「ア」・全角「Ａ」/半角「A」・café/cafe）を明記する（「規則を超えた過剰な同一視」——本改訂の初稿が SQL Server 照合順序の KS/WS 省略で作り込みかけた欠陥と同種——の回帰を機械検出するため）。保証集合外の既知の難例（トルコ語 İ/ı・ドイツ語 ß・ギリシャ語の語末シグマ等、言語依存・多対一の折り畳みを持つ文字）は非 blocking（情報表示）とし、provider 間の差異は各 provider 節に性質として文書化する（CI 回帰ベンチの `enforceRatio` と同じ「blocking / 情報表示を明示的に区別する」運用）
  - この二段階の置き方は「特定 provider の挙動を暗黙の基準にしない」（§1.3）の実行形である。**規則の確定と実現手段の適用（SQLite = §4 のアプリ定義比較関数、SQL Server = §5.4 の列 COLLATE。Issue #145・#147 と同一のスキーマ移行バッチ + DB-9 実装バッチで実装・検証）の両方が揃い、Issue #146 の不具合は解消済み**
- 契約に**含めない**もの: カウンタ等のメタデータ領域（ホスト管轄のローカルファイル。architecture.md §4.3）、スプール（永続化モジュール内だが provider の外側）

### 1.3 適合テストスイート — 外部貢献の入口

- **すべての provider が合格すべき単一の適合テストスイート**を v0.1 の開発範囲に含める（SQLite・SQL Server 自身もこのスイートで検証する——「2 実装があって初めて抽象が検証される」の実行形）
- 検証対象を 2 種に区別する: **機械検証する契約**（§1.2 の操作——スキーマ管理・バッチ挿入・失敗の分類・対話的検索・保持期間削除・統計——と境界ケース: 最大長メッセージ・不正 UTF-8・タイムスタンプ境界・空バッチ・保持期間削除と挿入の並行）と、**文書化義務**（読み書き分離の性質——テストではなくレビューで検証する）
- 対話的検索の一致規則（自由文の対象列・大文字小文字・部分一致の意味論）は §1.2 で確定済み（[DB-6](#8-確定待ち一覧)。2026-07-09。ASCII = blocking・非 ASCII = 保証集合 blocking / 保証集合外は情報表示、の二段階）。適合テストスイートへの反映（ASCII・非 ASCII 双方の大文字小文字ケース——**同一視すべき正例と、かな種・全角/半角・アクセントを同一視してはならない負例の双方**（§1.2 の保証集合）——の追加。**性能側——タイムアウト予算内に収まるか——は適合テストではなく `tools/Yagura.Bench` の実測 [DB-9](#8-確定待ち一覧) が受け持つ**）は、SQL Server の列 COLLATE 付与・SQLite の比較関数導入（§4・§5.4）と同じスキーマ移行バッチ（Issue #145・#147 と合流）で行う。**特定 provider の挙動を暗黙の基準にしない**——規則を先に固め、全 provider を同じ規則で検証する。**反映状況**: ASCII の正例（error/ERROR 等）は両 provider の適合スイートで blocking として検証済み。非 ASCII の正例（CAFÉ/café）と負例（あ/ア・全角Ａ/半角A・café/cafe）も両 provider で blocking として検証済み——SQL Server 側は `SqlServerSchemaMigrationTests`、SQLite 側は DB-9 の実現手段確定（2026-07-10。§4）を受けて追加した `SqliteFreeTextSearchNonAsciiTests`（両者は同一のテストデータを使い、provider 間の対称性を保つ）
- **新 provider の追加提案は「適合テストスイートが通ること」を受け入れの技術条件とする**。提案は本文書に provider 節（§4・§5 と同格。読み書き分離の性質の明示を含む）を追加する PR として行う——性質明示の置き場は本文書である。提案手順（Issue → 設計対話 → PR）は CONTRIBUTING の管轄。実証完了前（SQLite + SQL Server が本番品質で動く前）に外部から provider 追加 PR が届いた場合、適合テストの整備を優先課題に繰り上げる（ADR-0002 再評価トリガの受け皿）
- 適合テストの CI 実行構成と、追加 DB の実行環境（コンテナ等）の提供責任の所在（貢献者側か受け入れ側か）は実装設計で確定する（[DB-3](#8-確定待ち一覧)）

## 2. 論理スキーマ

物理設計（DDL・索引・データ型の方言）は各 provider に委ねる。ここでは**全 provider が同じ意味で保存すべき論理形**を固定する。

### 2.1 ログレコード

| 項目 | 内容 | 備考 |
|---|---|---|
| Id | レコード識別子 | provider 内で一意。採番方式は provider 実装に委ねる |
| ReceivedAt | **サーバが受信した時刻（UTC）** | 検索・並び・保持期間の基準軸。刻印点は §2.2 |
| SourceAddress / SourcePort | 送信元 | ソケット層で取得 |
| Protocol | UDP / TCP（将来: TLS） | 受信リスナ由来 |
| DeviceTimestamp | 送信元が名乗った時刻（あれば） | **参考情報。基準軸にしない**（§2.2）。解析失敗時も、TIMESTAMP がその前段で解析済みなら保持する（後述「解析失敗時のフィールド保持」） |
| Facility / Severity | syslog PRI の分解値 | PRI 自体が解析できなかった場合は未設定。**PRI は解析済みで、より後段（本文等）の解析失敗で ParseStatus が解析失敗になった場合は保持する**（後述） |
| Hostname / AppName / ProcId / MsgId | RFC 5424 ヘッダ（RFC 3164 は対応部分をマップ） | 解析できた範囲で設定。**この「解析できた範囲」は ParseStatus が解析失敗のレコードにも及ぶ**（後述）。**長さの上限は設けない**（Issue #147。RFC 5424 の各上限を超える非準拠に長い値を送る機器が現実に存在し、黙った切り詰めは調査の手掛かりを消す。全 provider が全長を保存する——SQLite = TEXT・SQL Server = NVARCHAR(MAX)。適合テストの最大長超過ヘッダケースで検証する） |
| StructuredData | RFC 5424 構造化データ | 原文のまま保存（要素分解はしない——加工しない方針。ADR-0001 スコープ外の「加工パイプライン」に踏み込まない）。**一覧射影（`LogRecordSummary`）にも原文のまま含める**（切り詰めはしない——ui.md §4 の一覧で本文の前に接頭表示するための入力。2026-07-07 オーナー承認）。自身が非 UTF-8 で解析失敗した場合は未設定（後述） |
| Message | メッセージ本文 | 一覧は先頭 N 文字の射影で返す（architecture.md §6）。非 UTF-8 で解析失敗した場合は未設定（Raw に生バイト列が残る） |
| Raw | **受信したバイト列そのもの**（不正 UTF-8 を含み得るため、文字列変換を経ない） | **ParseStatus が解析失敗・不完全のときのみ保存する**（このとき Raw が一次保存物）。解析済みレコードには保存しない——却下案「常時保存」はストレージをほぼ倍化させる一方、StructuredData・Message を原文のまま保持する本スキーマでは追加で守れる情報がヘッダの整形差程度に留まるため採らない |
| ParseStatus | 解析済み / 解析失敗 / 不完全 | **排他の 3 値。不完全（TCP 切断による途中終端）は解析失敗に優先する**。解析失敗もログとして検索・閲覧できる |

**解析失敗時のフィールド保持**（Issue #139。2026-07-09）: PRI・HEADER・STRUCTURED-DATA・Message は
それぞれ独立に確定するタイミングを持つ（PRI → TIMESTAMP/HOSTNAME/AppName/ProcId/MsgId →
STRUCTURED-DATA → Message の順）。**ParseStatus が解析失敗になった時点より手前で既に確定した
項目は破棄せず保存する**。対象は原因を問わない——典型は Message/STRUCTURED-DATA の非 UTF-8
（CP932/Shift-JIS 等でログを送る国産機器を含む）だが、TIMESTAMP の値だけが RFC 3339 として
不正な場合（時計設定が壊れた機器等。確定済みの HOSTNAME 等は保持し DeviceTimestamp のみ未設定）や、
STRUCTURED-DATA 直後の構造違反（確定済みの HEADER・StructuredData は保持）も同じ規則に従う。
従来は解析失敗の原因がどこにあっても Raw のみを保持し確定済みヘッダごと捨てていたため、
「本文だけ非 UTF-8 の機器」のログがホスト名でさえ検索できなくなっていた（旧実装の欠陥。修正は
[src/Yagura.Ingestion/Parsing/SyslogParser.cs](../../src/Yagura.Ingestion/Parsing/SyslogParser.cs)）。
一方、フィールドのトークン化そのものが失敗した場合（PRI 不正、HEADER が ABNF 途中で途切れる等）は、
値が確定していないため該当フィールド以降を設定しない。**非 UTF-8 本文をフォールバックエンコーディング
（CP932 自動判定等）で読み替えて Message に格納することは本対応の範囲外**（Raw の生バイト列から
利用者が事後的に判読する運用を継続する。フォールバックエンコーディング対応は将来課題として追跡する）。

**RFC 3164 の寛容な TIMESTAMP 読み取り**（Issue #135。2026-07-09）: RFC 3164 は「べき」規定が多く実装依存の逸脱が現実に多い（§2.1 の best-effort 方針と同じ思想）。TIMESTAMP は厳密な `Mmm dd hh:mm:ss` に加え、次のベンダ拡張（主に Cisco IOS）を取りこぼさない: 秒の小数部（msec。例: `.345`）、TIMESTAMP 直後の TZ 付記（前述の優先順位①）、先頭シーケンス番号（`service sequence-numbers`。例: `45: Mar  1 ...`）、`Mmm dd yyyy hh:mm:ss` の 4 桁年変種。これらの形式に一致しない・後続の解析（HOSTNAME 等）が破綻する場合は、従来どおり TIMESTAMP 解析全体を諦めて CONTENT 側（Message）へ委ねる best-effort にフォールバックする（ログを失わない。値そのものは失われず本文に残る）。

### 2.2 時刻の契約

- **保存はすべて UTC**。表示層（UI・通知）でローカル時刻へ変換する。この契約は ui.md の画面設計より先に固定し、画面はこれに従う
- **基準軸は ReceivedAt（サーバ受信時刻）**とする。送信元の時計は信頼できない（進み・遅れ・未設定が現実に起こる）ため、DeviceTimestamp は保存するが、検索の並び・保持期間・受信断区間との突合には使わない。両者のずれが大きいことはそれ自体が運用上の発見であり、UI での見せ方は ui.md に委ねる
- **ReceivedAt は受信段で刻印し、以後変更しない**。スプール退避・drain・停止時退避・移行（§6.2）のどこを経ても再刻印しない——スプールのセグメント形式（architecture.md §3.2.1。凍結対象）は ReceivedAt を運ぶ。drain が数時間遅れてもログの時刻・保持期間の起算・受信断区間との突合は揺れない
- **RFC 3164 TIMESTAMP のタイムゾーン解釈**（Issue #134・#135。2026-07-09）: RFC 3164 の TIMESTAMP（`Mmm dd hh:mm:ss`）は年もタイムゾーンも持たず、値は送信機器のローカル時刻（RFC 3164 §4.1.2）。DeviceTimestamp への変換時、タイムゾーンは次の優先順位で解決する:
  1. **TIMESTAMP に送信元付記の TZ が取れた場合はそれを最優先で使う**（Cisco IOS の `service timestamps log datetime show-timezone` 等。数値オフセット `+HH:MM`/`+HHMM`、または曖昧でない略号 `UTC`/`GMT`/`JST` に限る——米国 4 系統の略号 `CST`/`EST`/`PST`/`MST` 等は Cisco の `clock timezone <name> <offset>` が任意の名称を任意のオフセットに割り当てられるため、略号だけからオフセットを断定できず意図的に解決対象へ含めない。未知の略号は TZ として消費せず、従来どおり HOSTNAME 側の解析に委ねる）
  2. **①が取れない場合、設定項目 `Ingestion:Rfc3164:DefaultTimeZone`（configuration.md）の既定タイムゾーンを適用する**。値は Windows タイムゾーン ID・IANA タイムゾーン ID のいずれも受理し、TIMESTAMP の年月日時刻に対する UTC オフセットを都度計算する（DST を持つゾーンでも季節に応じた正しいオフセットになる）
  3. **未設定時は UTC**（2026-07-09 以前の現状互換）
  年についても、`Mmm dd yyyy hh:mm:ss` の 4 桁年変種が取れた場合はそれを使い、取れない場合は ReceivedAt から最も近い年を補完する（既存の年またぎ補完。実装は [SyslogParser.TryReadRfc3164Timestamp](../../src/Yagura.Ingestion/Parsing/SyslogParser.cs)）。本節はいずれも DeviceTimestamp（参考情報。基準軸にしない）の精度改善であり、ReceivedAt ベースの検索・保持期間・受信断突合には影響しない。

### 2.3 システムイベント

受信断区間（architecture.md §4.4）等、製品自身が生成する記録はログレコードとは**別の論理テーブル**に保存する（利用者のログと製品の自己記録を混ぜない——検索結果に「本物のログではない行」が混入しない）:

| 項目 | 内容 |
|---|---|
| Kind | 受信断（正常停止 / クラッシュ近似）・保持期間削除の実行記録（§3）等 |
| StartAt / EndAt | 区間（UTC） |
| Approximate | 近似断点か（architecture.md §4.4 の印） |
| Details | 付帯情報（削除実行なら削除件数等） |

- システムイベントも保持期間管理の対象とするが、**保持期間はログ本体と同じ以上とする**（ログより先に「その期間の説明」が消える逆転を防ぐ。既定 30 日（2026-07-05 オーナー決定。実測根拠 = [tools/Yagura.Bench/results/2026-07-05-dev-machine/](../../tools/Yagura.Bench/results/2026-07-05-dev-machine/)）——システムイベントはログ本体と同じ既定日数を採用し、「ログ本体と同じ以上」の制約を満たす。システムイベント専用の別既定値は設けない）
- ログの保持期間を越えた過去では、ログの不在は保持期間削除でも説明される——その期間の受信断区間だけを見せると「受信断以外はログがあったはず」という誤読を招くため、**表示上の前提（保持地平より古い期間の扱い）を ui.md へ申し送る**（homework.md に登録）

## 3. 保持期間管理

「ログを失わない」の裏面——溜まり続けたログをいつ・どう消すか——を初版から定義する（architecture.md §7 要求④）:

- **保持期間（日数）を設定項目とし、既定値を持つ**。既定値は「無期限」にしない——ゼロ設定ファーストランの環境こそ設定を触らないまま運用され、無期限の既定はディスク枯渇として現れるため。**既定は 30 日**（2026-07-05 オーナー決定。[DB-1](#8-確定待ち一覧) 確定値。実測根拠 = [tools/Yagura.Bench/results/2026-07-05-dev-machine/](../../tools/Yagura.Bench/results/2026-07-05-dev-machine/)——レコード単価 ≈ メッセージ長 + 約 95 B、10 msg/s × 30 日 ≈ 7.8 GB は SQL Server Express の 10 GB 上限に収まる）。**設定ファイルで不正値（0 以下・数値以外）が指定された場合のフォールバック先は「削除しない」とし、既定 30 日へは自動フォールバックしない**（意図しない自動削除の開始を避ける安全側の判断。configuration.md §8 参照）。容量超過そのものへの対策ではなく、**ディスク空き容量・DB 容量上限への接近は保持期間とは独立に監視・警告する**（後述・§5.3）
- **却下案 — 容量連動の保持（サイズ上限で古い順に削除）**: ディスク枯渇への直接対策ではあるが、「何日分のログが残っているか」が流量次第で変動し利用者に予測できない。監査・調査の要求は「○日分」という日数で来るため、日数を正とする。ただし日数既定は高流量環境での枯渇を防がない（保持期間内に容量へ先に当たる）ことを認め、**ディスク空き容量・DB 容量上限への接近は保持期間とは独立に監視・警告する**（§5.3、architecture.md §4.6 の経路）
- **設定を触らない利用者にも削除の存在が届くようにする**: 保持期間の現在値（「○日より古いログは自動的に削除されます」）をファーストラン完了時とダッシュボード上で常時明示する。表示設計は ui.md（homework.md に登録）
- 期限超過分の削除は**定期実行**とし、受信の書き込みを長時間妨げない方式（分割実行等）を provider 契約（§1.2）の条件とする。さらに**実行判断側も譲歩する**: スプール退避が進行中・Q2 が高水位・drain が進行中の間は削除を開始せず、実行中でも次のバッチ境界で中断できる（メンテナンスが自ら飽和を作らない）。**ただし容量枯渇（§1.2・§5.3）を契機とする前倒し削除は譲歩条件の例外とする**——このとき退避が進行しているのは削除でしか解けない状態であり、譲歩を適用すると復旧が永久に開始されない。**保持期間削除の実行中に発生したスプール退避は昇格案内の「速度不足」に数えない**（architecture.md §5.3 に反映済み）
- **定期実行は起動時キャッチアップを持つ**: 定期実行の実行時刻（既定は深夜帯）に稼働していないホスト——日中のみ稼働する設置・再起動が実行時刻付近に偏る環境——では、定刻待ちだけの実装は削除を恒常的にスキップし、「保持期間を設定した＝消える」という利用者の前提を静かに裏切る（無期限の既定を排した本節の安全網に穴が開く）。これを防ぐため、スケジューラは**起動時に直近の削除実行記録（下記のシステムイベント）を検索し、前回実行から 1 日以上経過している（または記録が存在しない）場合は定刻を待たず即座に削除を実行する**。キャッチアップ判定の情報源は削除実行のシステムイベント（§2.3。既存の記録）であり、**専用のメタデータ領域は設けない**——実行の事実の記録と判定の情報源を一本化する。**判定の検索は Kind（`retention.delete`）でサーバ側フィルタする**——削除実行記録の StartAt は意図的な過去日付（cutoff）である一方、受信断イベントの StartAt は実時刻という非対称があり、種別を問わない直近 N 件の走査では受信断の蓄積が削除記録をウィンドウから恒常的に押し出すため（このために §1.2 の `QuerySystemEventsAsync` へ Kind フィルタを最小の契約拡張として追加した）。**判定の検索は保存先のスキーマ初期化の完了を待ってから行う**——初期化は起動シーケンスの外で進む（architecture.md §1.2 手順 3）ため、待たずに検索すると新しい保存先へ切り替えた直後の初回起動ではスキーマ作成前の検索となり確定的に失敗する。待つ上限は 2 分とし、上限に達したら初期化を待たずに検索を試みる（失敗すれば警告に留め、定期実行の待機に委ねる——保存先の長期障害中に保持期間削除を止め続けないため）。停止要求で待機を打ち切った場合は検索せずに終了する。キャッチアップ直後に定刻がわずかな遅延で到来した場合の二重実行は、直前の実行からの経過時間による抑止（プロセス内メモリで足りる——抑止に失敗しても削除は冪等であり、防いでいるのは無駄な再実行のみ）で防ぐ。実装 = `Yagura.Host.Retention.RetentionScheduler`
- **保持期間を大幅に短縮した直後の一括削除は、複数回の定期実行に分けて漸進する**（数百万行規模の削除が一撃で走ることを防ぐ）
- 保持期間による削除は「損失」ではなく意図した仕様動作であり、architecture.md §4.1 のドロップカウンタには計上しない。**実行の事実（実行時刻・削除件数）はシステムイベント（§2.3）として保存する**——保持期間はシステムイベント側（ログ本体と同じ以上）に従うため、削除記録が削除対象のログより先に消えることはない。実行の失敗は architecture.md §4.6 の能動通知の対象とする
- 保持期間の変更は管理操作であり、監査記録の対象（ADR-0004 決定 7）

## 4. 組み込み provider: SQLite

- ゼロ設定ファーストランの既定 DB。**組み込みのまま使い続ける運用も正式サポート**（ADR-0002 決定 3）
- **WAL モードを用いる**。WAL では読み取りは書き込みをブロックせず、書き込みも読み取りをブロックしない（読み書きは並行できる）。一方 **writer は同時に 1 つ**である（いずれも SQLite 公式ドキュメント "Write-Ahead Logging" の記載。確認日 2026-07-04）
- 読み書き分離の性質（§1.2 の明示義務）:
  - 検索（読み取り）が受信の書き込みをブロックしない条件は WAL により成立する。**書き込みが単一 writer である制約は、書き込み呼び出しをホストの単一の書き込みゲートで直列化する本設計と整合する**——ライブ書き込み（永続化段）・スプール drain・保持期間削除（+ 実行記録のシステムイベント）の 3 経路は、ホストが構築する共有ゲート（実装 = `Yagura.Storage.LogStoreWriteGate`。結線 = `Yagura.Host.Program`）を通ることで provider 契約（§1.2「呼び出し側が直列化する」）を実配線で満たす。ゲート待ちの時間予算は DB 操作自体のタイムアウトとは独立させる（保持期間削除がゲートを保持する間のゲート待ちを「速度不足」と誤認してスプール退避が連発することを防ぐ——§3・architecture.md §5.3 の誤発火防止と同じ趣旨。設計判断の詳細は `LogStoreWriteGate` の doc コメント）。なお、ホスト起動処理の受信断記録（architecture.md §4.4。起動時 1 回の `WriteSystemEventAsync` 直接呼び出し）はゲートを通らない第 4 の書き込み経路だが、上記 3 経路のいずれもまだ開始されていない時点で実行されるため、非同時実行は起動順序により保証される（`ILogStore` の doc コメントに明記）
  - **付随する運用特性 — WAL ファイルの肥大**: 読み取りが常に重なり続けると checkpoint が完了できず、WAL ファイルが際限なく成長し得る（checkpoint starvation。SQLite 公式ドキュメント "Write-Ahead Logging" §6 の記載。確認日 2026-07-04）。本設計では対話的検索のタイムアウト（architecture.md §6・M-10）が個々の読者の上限時間を画す。checkpoint の実行方式（読者の切れ目での実行等）は実装設計で確定し、WAL ファイルサイズを観測対象（architecture.md §4.6 のゲージ）に含める
- 飽和特性: 書き込み上限は実測で確定し（architecture.md §9 M-7）、昇格案内（同 §5.3）の入力とする
- **容量枯渇の扱い**: ディスク満杯による書き込み失敗は §1.2 の「容量枯渇」として報告し、§5.3 と同じ復旧連鎖（保持期間削除の前倒し実行。§3 の譲歩条件の例外）を適用する。ただし**「削除で回復し得る」が SQLite で実際に成立するか**（行削除後のページ再利用の挙動、満杯状態での削除自体がディスク追記を要さないか）は自明ではないため、推測で確定せず実機検証で確認する（[DB-8](#8-確定待ち一覧)）
- **自由文検索の大文字小文字（[DB-6](#8-確定待ち一覧)。§1.2 の規則を SQLite でどう実現するか）**: SQLite の `LIKE` は既定で ASCII 範囲のみ大文字小文字を区別しない（SQLite 公式ドキュメント "The LIKE operator" — https://www.sqlite.org/lang_expr.html。確認日 2026-07-05）。組み込みの `NOCASE` 照合順序も同じ制限を持つ（SQLite 公式ドキュメント "Datatypes In SQLite" §7 Collating Sequences — https://www.sqlite.org/datatype3.html: 「the 26 upper case characters of ASCII are folded to their lower case equivalents... Note that only ASCII characters are case folded. SQLite does not attempt to do full UTF case folding due to the size of the tables required」。確認日 2026-07-09）——**SQLite に非 ASCII を含む大文字小文字非区別を標準機能だけで実現する手段はない**。
  - **ICU 拡張は採用しない**: SQLite 本体は ICU 拡張のソースを同梱するが、既定ビルドには含まれず `SQLITE_ENABLE_ICU` コンパイルオプションを指定した独自ビルドが要る（SQLite 公式ドキュメント "Compile-Time Options" — https://www.sqlite.org/compile.html: 「This option causes the International Components for Unicode ("ICU") extension to SQLite to be added to the build」——既定では追加されないことの裏返し。確認日 2026-07-09）。Yagura が利用するネイティブ SQLite バイナリ（SQLitePCLRaw 経由の配布物）はこのオプションを有効化した配布形態を持たず、独自コンパイルはプラットフォームごとの再ビルド・差し替えという継続的な運用コストを生む——本節冒頭の「組み込みのまま使い続ける運用も正式サポートする」という設計方針に反するため却下する
  - **✅ 採用確定: 自由文検索専用にアプリケーション定義の比較関数を導入する**（[DB-9](#8-確定待ち一覧)。実測 2026-07-10。実装 = `SqliteLogStore.RegisterFreeTextComparisonFunction`）。Microsoft.Data.Sqlite は `SqliteConnection.CreateFunction` により .NET 側で実装したスカラー関数を SQL から呼び出し可能にする機構を公式に提供する（Microsoft Learn "User-defined functions - Microsoft.Data.Sqlite" — https://learn.microsoft.com/dotnet/standard/data/sqlite/user-defined-functions。確認日 2026-07-09）。**組み込み `LIKE` 演算子自体のグローバルな上書き**（同文書は `X LIKE Y` が内部で `like(Y, X)` 関数へ解決され、同名関数の再定義で演算子の挙動そのものを上書きできるとも説明する）は採らない——現時点で `LIKE` の利用箇所は自由文検索のみだが、演算子の意味を接続全体で差し替えると将来の利用箇所が暗黙に影響を受けるため、呼び出し経路を限定した専用関数（SQL 側の関数名 `yagura_ci_contains`）とする。**比較の実体は `string.Contains(needle, StringComparison.OrdinalIgnoreCase)`**——.NET の `OrdinalIgnoreCase` は不変カルチャの大小変換テーブルに基づく比較であり ASCII に限らない大小変換を行う一方（Microsoft Learn "Globalization invariant mode"。確認日 2026-07-09: Invariant Mode 下でのみ非 ASCII 変換が縮退する——通常モードでは働く）、アクセント記号・かな種・全角/半角は同一視しない（コードポイントが異なり大小関係を持たないため）——DB-6「折り畳むのは大文字小文字のみ」を過不足なく満たす
  - **DB-9 実測結果（`tools/Yagura.Bench QueryLatency`。2026-07-10・開発機 1 台・単独実行——同時実行はディスク I/O 競合で数値が歪むため避けた。実行コマンド例: `Yagura.Bench QueryLatency --rows 100000,1000000,10000000`）**: 行数規模別に、ASCII 中選択性語（`error`。約 1% 一致）・非 ASCII 疎一致語（`café`＝DB-6 保証集合正例。7 件固定）・該当なし語（全表走査の最悪系）の 3 パターンで、ネイティブ `LIKE`（ASCII 限定）と比較関数候補案を比較した（結果上限 10,000 件・タイムアウト 30 秒——いずれも M-10 仮値——を前提。クエリ自体は診断のため 90 秒まで打ち切らずに実測した）:
    | 行数 | LIKE worst-case（該当なし語 p95） | UDF worst-case（該当なし語 p95） | UDF/LIKE 比（p95・3 パターン中最大） | 対タイムアウト予算比（UDF worst-case ÷ 30 秒） |
    |---|---|---|---|---|
    | 10 万 | 37.4 ms | 52.5 ms | 約 1.7 倍 | 0.2% |
    | 100 万 | 429.1 ms | 606.6 ms | 約 1.6 倍 | 2.0% |
    | 1000 万 | 4,402.5 ms（非 ASCII 疎一致語は後述） | 10,086.7 ms（非 ASCII 疎一致語） | 約 1.4 倍（該当なし語） | 34% |

    **判定**: 全行数規模で UDF 方式の worst-case が対話的検索のタイムアウト予算（30 秒）の 34% 以内に収まり、ネイティブ `LIKE` 比は最大でも約 1.7 倍（上表の「UDF/LIKE 比」列 = 安定して計測できた「該当なし語」パターンの p95 比の代表値。1.3〜1.7 倍はこの代表値の範囲であり、**全パターンの比の範囲ではない**——中選択性語では UDF が LIKE と同等かむしろ速いケース（1000 万行 ASCII で 0.86x）、LIKE 側の I/O 外れ値で比が 0.23x になったケースも含まれる。生データ参照）だった——**予算内に収まることを確認し、比較関数方式を採用に確定した**。行数規模が増えるほど比が縮む傾向も観測した（両者とも「行ごとに全表を評価してから `LIMIT` で打ち切る」という支配的コストは同一であるため、関数呼び出し自体のオーバーヘッドが相対的に薄まると考えられる）。
    **1000 万行の非 ASCII 疎一致語（`café`）で観測した外れ値**: ネイティブ `LIKE`（該当 0 件——ASCII 限定のため元々ヒットしない）の 3 試行が 6.8 秒・6.8 秒・47.3 秒と大きくばらつき、最後の 1 試行が予算（30 秒）を超過した。同じ全表走査に分類される「該当なしパターン」（`LIKE` 4.2〜4.4 秒で安定）と比べて異常な値であり、開発機の一時的な I/O ノイズ（他プロセスのディスクアクセス等。単独実行に切り替えた後も完全排除はできていない）による外れ値と判断する——**比較関数（UDF）側は同条件で 7.4〜10.1 秒とばらつきが小さく、予算超過は 1 度も発生しなかった**。この非対称自体は比較関数方式を否定する材料ではない（外れ値はネイティブ LIKE 側で発生した）が、**1000 万行規模の SQLite 単一ファイルでは開発機相当のディスク性能だと個々のクエリが数秒〜十数秒かかり得る**という事実は Issue #145 の FTS5 検討（索引による全表走査の回避）の動機として記録に残す。生データは `tools/Yagura.Bench/results/2026-07-10-db9-db10/`（PR 添付）を参照
  - **却下しなかった代替（フォールバック。不採用のまま記録）**: 上記実測が予算超過だった場合のフォールバックとして「ASCII 限定のネイティブ `LIKE`（旧実装）を維持し、非 ASCII の大文字小文字非区別は Issue #145 の全文検索索引（FTS5）検討に委ねる」を用意していたが、実測が予算内に収まったため採用しなかった
  - **Issue #145（FTS5 検討）との関係**: FTS5 はトークナイザベースの索引でありスカラー比較関数とは実現機構が別系統（大文字小文字の折り畳みはトークナイザ側の設定で扱う）。**凍結対象は §1.2 の一致規則であって実現機構ではない**——#145 で FTS5 を採用する場合、本比較関数は FTS5 側の実装に置き換わってよい（同じ規則を満たすことを適合テストで再検証する）。比較関数方式はその意味で「FTS5 の要否が確定するまでの規則充足手段」であり、#145 の選択肢を拘束しない
  - **.NET グローバリゼーションへの依存を前提として明記する**: 比較関数の非 ASCII 折り畳みは .NET のカルチャ非依存の大小変換（ICU ベース）に依存する。.NET には ICU を切り離す **Globalization Invariant Mode**（MSBuild プロパティ `InvariantGlobalization`。有効化すると「culture-specific data and behavior へのアクセスなし」で動作する——Microsoft Learn "Globalization config settings" — https://learn.microsoft.com/dotnet/core/runtime-config/globalization。確認日 2026-07-09）があり、これが有効な発行構成では非 ASCII の折り畳みが成立しない。**Yagura の発行設定は Invariant Mode を有効化しない（ICU を利用可能に保つ）ことを本方式の前提とし、実装バッチでビルド設定の固定とテストによる検知を含める**
  - **折り畳み範囲の非対称の申し送り**: SQL Server 側（§5.4）は `_SC` により補助文字（U+10000 以降）まで比較対象に含むが、SQLite 比較関数がサロゲートペアをどこまで折り畳むかは実装設計で確定する。差が残る場合は §1.2 の二段階検証（保証集合外の性質文書化）で扱う
- ファイルの配置・ACL は ADR-0004 決定 5 に従う（既定の置き場所は configuration.md と合同で確定 [DB-2](#8-確定待ち一覧)）

## 5. 本番 provider: SQL Server

### 5.1 接続と認証

- **Windows 統合認証を第一推奨**とする。パスワード認証（SQL 認証）を使う場合、資格情報は DPAPI machine スコープで暗号化保存する（ADR-0004 決定 5。設定スキーマは configuration.md）

### 5.2 権限の分離 — 実行時最小・管理時都度

ADR-0004 決定 4 の具体化。実行時権限を最小化すると初回セットアップの手数が増えるという既知の緊張があり、次の 3 点で解消する:

- **実行時**: サービスの接続はログテーブルへの読み書き（+ 保持期間削除）に必要な最小権限のみ。スキーマ作成・変更権限を常時保持しない
- **セットアップ・昇格・版間移行時**: 必要な管理権限は管理者資格情報の都度入力で得て、使用後破棄する（保持しない。長時間処理での再入力方針は configuration.md の管轄——ADR-0004 委任の引き受け先を明記）
- **権限不足時の自走可能な失敗**: スキーマ管理（§1.2）が権限不足で失敗する場合、「何が足りないか」と**環境の実値が入った実行可能な SQL**（ログイン作成・権限付与・DB 作成）を提示する。DBA が別部署にいる環境では、この SQL がそのまま依頼文になる。スキーマ管理は冪等とし、途中失敗からの再実行を安全にする
- **提示 SQL は秘密情報を含まない**: ログイン作成は Windows 統合認証を既定とし、SQL 認証を選んだ場合もパスワード部は明示のプレースホルダとして**生成時点で実値を埋めない**（依頼文がメール・チケットを経由して流通する前提で設計する）。監査記録（ADR-0004 決定 7）には提示 SQL の原文を保存せず、要約のみ残す

### 5.3 SQL Server Express の適用限界

無償の Express を動作対象に含める（ADR-0002 決定 3）ため、その限界を仕様として記録する（Microsoft Learn「Editions and supported features of SQL Server 2022」の値。確認日 2026-07-04）:

- **データベース最大サイズ: 10 GB**（Express / Express with Advanced Services とも）
- バッファプール最大メモリ: インスタンスあたり 1,410 MB
- 計算能力: 1 ソケットまたは 4 コアの小さい方

含意と対応:

- 10 GB は中小環境のログ保存として実用になり得る規模だが、**保持期間と流量によっては到達する**。メモリ・コア制限は障害ではなく性能の頭打ちとして現れる（性能公称値の基準環境の定義——architecture.md M-6——とは別に扱う。利用者向け文書 DB-D2 では 10 GB を主とし、他 2 点は性能上の注記として平易に述べる）
- **SQL Server provider は DB サイズの取得とエディション判別（容量上限が適用されるか否か）を必須とする**（§1.2 統計の「取得不能の明示」の逃げ道はこの provider には適用しない——Express 接近警告の成立条件であるため）。**上限への接近を警告する**（architecture.md §4.6 の能動通知の経路。**Issue #149（M4-6）で配線済み**——`Yagura.Host.Observability.ActiveNotification.ActiveNotificationMonitor` が周期監視し、使用率が閾値（仮値 0.8。architecture.md §9 M-16）以上でイベントログへ警告する。判定は `SqlServerLogStore.IsExpressEditionAsync` + `GetStatisticsAsync`（割当ファイルサイズ）を用いる）。何を「サイズ」として測るか（割当ファイルサイズか使用ページ量か——**現状は割当ファイルサイズのみ**）・削除後の空き解放の挙動・警告閾値の最終確定は、実機検証を含めて [DB-4](#8-確定待ち一覧) で行う（割当サイズを測ると削除しても警告が消えない、という運用者の混乱を設計段階で潰す）
- **到達後の復旧連鎖**: 容量上限由来の書き込み失敗は provider が「容量枯渇」として報告し（§1.2 の 3 区分。一時障害のリトライでも恒久障害の停止でもない第 3 の経路）、ホストは**保持期間削除の前倒し実行を試みて自走復旧を図る**（この前倒し削除は §3 の譲歩条件の例外である——同節参照）。回復までの受信分はスプールが受ける（architecture.md §3.2）。前倒し削除でも回復しない場合（保持期間内でも満杯）は能動通知で保持期間の短縮かエディション移行を促す。上限到達時の SQL Server の実挙動の確認は DB-4 の実機検証に含める

### 5.4 自由文検索の照合順序（COLLATE）

- **列単位で COLLATE を明示する**（[DB-6](#8-確定待ち一覧) 確定）: サーバの既定照合順序に委ねない。既定はインストール時の OS ロケールに依存し、大文字小文字を区別する照合順序（CS）が入ったサーバでは「自由文検索は大文字小文字を区別しない」という §1.2 の契約が配備先ごとに静かに反転する——Issue #146 で確認された不具合そのものであり、DDL に COLLATE 指定がなかったこと（本節改訂前の実装。SqlServerLogStore.cs の DDL・自由文検索コメントが自認していた暫定状態）が原因だった
- **採用する照合順序: `Latin1_General_100_CI_AS_KS_WS_SC`**（Windows 照合順序・version 100・大文字小文字非区別 `CI`・アクセント区別 `AS`・かな種区別 `KS`・全角/半角区別 `WS`・補助文字対応 `SC`）
  - **`CI` 以外の感度をすべて「区別する」側に明示するのは、§1.2 の規則「折り畳むのは大文字小文字のみ」を照合順序レベルで正確に実装するため**である。Windows 照合順序は `KS` を省略すると**かな種非区別**（ひらがな ≒ カタカナ）、`WS` を省略すると**全角/半角非区別**になる（Microsoft Learn "Windows collation name (Transact-SQL)" — https://learn.microsoft.com/sql/t-sql/statements/windows-collation-name-transact-sql: 「Omitting this option specifies kanatype-insensitive」「Omitting this option specifies width-insensitive」。確認日 2026-07-09）。つまり一般に推奨される `Latin1_General_100_CI_AS_SC`（KS/WS なし）をそのまま使うと、SQL Server だけが大文字小文字**以外**（かな種・全角/半角）まで同一視し、SQLite（かな種・全角/半角を区別する）との新たな provider 差を作り込む。`KS`・`WS` の明示でこの過剰な折り畳みを止める
  - `CI_AS_KS_WS` の組合せは Windows 照合順序の正規の構文（同文書の Syntax: `<CaseSensitivity>_<AccentSensitivity> [_<KanatypeSensitive>] [_<WidthSensitive>]`）であり、`_KS_WS_SC` を併記した照合順序の実例も公式ドキュメントに載る（Microsoft Learn "Collation and Unicode Support" — https://learn.microsoft.com/sql/relational-databases/collations/collation-and-unicode-support の例 `Japanese_Bushu_Kakusu_100_CS_AS_KS_WS_SC_UTF8`。確認日 2026-07-09）。**`Latin1_General_100_CI_AS_KS_WS_SC` が配備先インスタンスの `sys.fn_helpcollations()` に実在することの確認を、実装バッチのスキーマ管理（接続検証）に含める**
  - Windows 照合順序の大小比較は Windows システムロケールの規則に基づき、Unicode データにも同じアルゴリズムを適用する（同 "Collation and Unicode Support": 「Windows collations define rules for storing character data that are based on an associated Windows system locale... you can implement a comparison of non-Unicode data by using the same algorithm as that for Unicode data」。確認日 2026-07-09）——`CI` の折り畳みは ASCII に限られない
  - `SC`（補助文字対応）により `nvarchar` 列で全 Unicode 範囲（U+000000–U+10FFFF）を比較対象にできる（同文書: 「SQL Server 2012 (11.x) introduced a new family of supplementary character (_SC) collations that can be used with the nchar, nvarchar, and sql_variant data types to represent the full Unicode character range」。確認日 2026-07-09）。`_UTF8` 系照合順序は付与しない——UTF-8 エンコーディングは `char`/`varchar` 列向けの機能であり、本スキーマの文字列列はすべて `nvarchar`（UCS-2/UTF-16）のため効果がない（同文書のデータ型節）
  - **サーバ既定からの意図的な乖離**: Microsoft Learn は互換性照合順序（`SQL_Latin1_General_CP1_CI_AS` 等）から Windows 照合順序への切り替えを推奨している（「To take full advantage of SQL Server features, change the default installation settings to use Windows collations」。確認日 2026-07-09）。Yagura はこの推奨に従いつつ KS/WS を追加し、**サーバの既定照合順序が何であっても列単位指定で上書きする**——Issue #146 の症状（配備先次第で挙動が変わる）を構造的に解消する
- **適用列**: `dbo.LogRecords` の全 `NVARCHAR` 列（SourceAddress・Hostname・AppName・ProcId・MsgId・StructuredData・Message）と `dbo.SystemEvents` の Kind・Details。**自由文検索の対象は Message のみ（§1.2）だが、同一テーブル内で列ごとに照合順序が食い違うと、比較・結合を伴うクエリで「照合順序の競合」エラーを誘発しうるため、列を個別に選別せずテーブル単位で統一する**
- **スキーマ移行への申し送り**（Issue #145（絞り込み列の複合索引追加）・#147（列長の provider 間統一）と**同一のスキーマ移行バッチ**で実装する。3 件とも `ALTER TABLE` を伴う変更であり、メンテナンスの機会を 1 回にまとめる。**実装状況: スキーマ v1→v2 移行として実装済み**——新規 DDL は v2 形状で直接作成し、既存 v1 デプロイは `InitializeAsync`（スキーマ管理契約）が起動時に移行する。**所要時間・ロック挙動・受信継続性は DB-10 で 100 万行規模まで実機検証済み**（下記表）。1000 万行規模超は実測未完遂——詳細は下記参照）:
  - **DDL**: 新規作成の `CREATE TABLE` は列定義へ `COLLATE Latin1_General_100_CI_AS_KS_WS_SC` を追加する。既存デプロイへは `ALTER TABLE ... ALTER COLUMN ... COLLATE ...` で適用し、当該列に索引がある場合は再構築を伴う
  - **受信継続性**: 移行中に到着したログはスプール（architecture.md §3.2——書き込みが確定できない状態そのものの受け皿）が受け、**ログを損失させないことを移行の要件とする**。書き込み可用性が中断する幅（`NVARCHAR(MAX)` の Message 列を含む size-of-data 変更のロック・所要時間）は実機検証（[DB-10](#8-確定待ち一覧)）で見積もり、長時間の中断が不可避なら実行タイミングの利用者告知（[§9](#9-利用者向けドキュメントへの申し送り) DB-D5）を要件に含める
  - **✅ DB-10 実測結果（`tools/Yagura.Bench SchemaMigrationDdl --sqlserver`。2026-07-10・開発機の SqlLocalDB（ci.yml と同じ公式 MSI 導入パターン）。実行コマンド例: `Yagura.Bench SchemaMigrationDdl --rows 100000,1000000,10000000 --sqlserver "Server=(localdb)\MSSQLLocalDB;Integrated Security=true;TrustServerCertificate=true;"`）**:

    **受信継続性への示唆**: 移行（テーブル/索引作成 → 列 COLLATE 付与の `ALTER COLUMN` 9 本 → 索引再構築）は単一トランザクションで実行される（実装済み。§5.2「途中失敗からの安全な再実行」の要件）。probe write（移行開始 0.3 秒後に発行した 1 行 INSERT）の所要時間は移行所要時間とほぼ一致した——**移行中の書き込みは移行完了（トランザクションコミット）までブロックされ、部分的にも進行しない**（読み取りも同じスキーマロックの対象となり得る。§5.2 相当の排他は `sp_getapplock` によるアプリケーションロックとは別に、`ALTER COLUMN` 自体が取得するスキーマ変更ロック（Sch-M）に由来する——Microsoft Learn の一般的な DDL ロック挙動どおり）。したがって**「受信継続性」は「移行の全所要時間にわたりスプールが吸収する」という前提で設計する必要がある**（無瞬断ではない）。10 万→100 万行で所要時間が約 11 倍（行数比の 10 倍を上回る）に伸びており、**単純な行数比例より重い**傾向が見える——`NVARCHAR(255)`→`NVARCHAR(MAX)` を伴う 4 列（Hostname/AppName/ProcId/MsgId）の size-of-data 変更が全ページ書き換えを要すること（§5.4 DDL 節）が主因と推定する。

    **1000 万行での制約（未完遂の記録）**: 1000 万行規模での実測を試みたが、**移行の単一トランザクションが進むにつれてトランザクションログが大きく肥大し、開発機のディスク空き容量（実測開始時点で約 30 GB）を数分で圧迫した**ため、ディスク枯渇による機材破損を避けるべく実測を中断した（実行コマンドは上記と同じ。中断時点で `ALTER COLUMN` 群の実行中と推定——ログ上は投入完了から 2 分以上経過して継続中だった）。**この事象自体が DB-10 の重要な実測結果である**: 単一トランザクションでの移行は、行数が数百万〜一千万規模に達すると、データ本体の増分だけでなくトランザクションログの一時増分（ロールバック可能性を保つため、変更前イメージを保持する）が無視できない容量を要する。**本番昇格・大規模環境への申し送り**: (1) 移行前にトランザクションログ用の空き容量を実データサイズの数倍単位で確保することを利用者向け案内（[§9](#9-利用者向けドキュメントへの申し送り) DB-D5）に含める、(2) 数百万行を超える既存データに対する移行は、単一トランザクションではなく分割実行（列単位・またはバッチ単位のコミット）を将来検討する価値がある——ただし分割コミットは「移行の冪等性」（§5.2）の再設計を要するため、本 PR のスコープ外とし、Issue 化して追跡する（DB-10 は「単一トランザクション実行のまま採用」を 100 万行規模の実測に基づき確定したが、**それを大きく超える既存データ規模（1000 万行超）への一般化はこの制約により保留**とする）。
    **バグ発見と修正**: 当初の実装（`SqlServerLogStore.EnsureColumnCollationAsync` 等）は `SqlCommand.CommandTimeout` を明示しておらず ADO.NET 既定の 30 秒のままだった。1000 万行規模の実測で `ALTER COLUMN` が 30 秒を超え、移行そのものが「実行タイムアウトの期限が切れました」で失敗することを発見した——**スキーマ管理は対話的検索のようなタイムアウト予算（M-10）を持たない管理経路**（§1.2「対話的検索の防御は…下記『契約拡張の予約』の管理経路には適用しない」）であるにも関わらず、実装が誤って対話的検索と同程度の暗黙の時間制約を持っていた欠陥。`InitializeAsync` 内の全 DDL コマンドの `CommandTimeout` を無制限（`0`）にし、打ち切りは呼び出し側の `CancellationToken` にのみ委ねるよう修正した（本 PR に含む）。
  - **「損失させない」をスプール容量計画に接続する**: 上記要件が成立する条件は、移行中の流入をスプール容量が吸収し切ることである（容量上限到達時の新規破棄——architecture.md §3.2.3——と正面から緊張する）。architecture.md M-12（スプール容量上限の既定値）が本番昇格切替について「切替中に受ける流入 × 想定切替時間」を容量算定の入力に含めるのと同じ扱いで、**DB-10 で実測した移行所要時間 × 想定流量を M-12 の容量算定の入力に含める**——具体化: DB-1 の実測単価（レコード単価 ≈ メッセージ長 + 約 95 B）と 10 msg/s の代表流量を当てはめると、100 万行規模の移行（約 19 秒のブロック）で吸収すべき流入は約 10 msg/s × 19 秒 × 約 200 B/msg ≈ 38 KB——architecture.md M-12 の既定容量候補（既存の本番昇格切替入力と同様、MB〜GB オーダーで検討中）に対して無視できる規模。**ただし高流量環境（数百 msg/s 以上）や、1000 万行規模の既存データに対する移行（申し送り欄）では同じ計算式で数百 KB〜数 MB のオーダーへ増える**ため、M-12 の容量算定は「本番昇格切替中の流入」に加えて「スキーマ移行中の流入」も入力に含めること。吸収し切れない見積りになる場合の代替手段（移行前の一時的なスプール容量拡張、または §3 の分割削除に相当する移行の分割実行）を実装バッチで用意する——実行タイミングの選択（低トラフィック帯の指定）が効かない 24 時間運用の環境を想定条件に含める
  - **冪等性**: §1.2 スキーマ管理の冪等性要件をこの移行にも適用する——現在の列照合順序を（`sys.columns` 等で）確認し、適用済みなら何もしない。途中失敗からの再実行を安全にする
  - **失敗の扱い**: §5.2 の「自走可能な失敗」の枠組みを適用するが、**原因種別で提示内容を書き分ける**（実装バッチへの申し送り）——権限不足には「不足内容 + 実行可能な SQL の提示」がそのまま当てはまる。一方、**容量不足は「実行可能な SQL」では解決しない物理的対処**（空き領域の確保・増設・保持期間の短縮）であるため、「不足内容の明示 + 対処の案内」の形に書き分ける（§5.2 の原型は権限不足向けの設計であり、そのままの転用は成立しない）
  - **観測性**: 移行の実行中・進捗・所要時間をゲージ・能動通知（architecture.md §4.6）へ露出し、**適用したスキーマ版と適用日時を事後に問い合わせ可能な形で保持する**（検索の意味論が変わる変更が「いつ効き始めたか」に監査上答えるため。**適用版・適用日時の保持は両 provider の `SchemaMigrationHistory` 表として実装済み**——版ごとに 1 行を追記し、再実行では上書きしない）。移行の進捗のゲージ露出と、**スキーマ移行の実行を ADR-0004 決定 7 の監査記録対象に含めるか**は、DB-10（移行の実行方式とタイミングの確定）と合わせて確定する
  - **コード整合**: [LogQuery.cs](../../src/Yagura.Storage/LogQuery.cs)・[SqlServerLogStore.cs](../../src/Yagura.Storage/SqlServer/SqlServerLogStore.cs)・[SqliteLogStore.cs](../../src/Yagura.Storage/Sqlite/SqliteLogStore.cs) に残る「DB-6 確定までの暫定規則」コメントの更新（規則確定済みの旨への書き換え）を同バッチに含める（反映済み）
- **却下した代替案**:
  - **既定（COLLATE 未指定）のまま**: Issue #146 の不具合そのもの。配備先の OS ロケールに挙動が依存し、provider 契約（§1.2）の「特定 provider の挙動を暗黙の基準にしない」に反する。却下
  - **`SQL_Latin1_General_CP1_CI_AS`（互換性照合順序）を明示指定**: 配備依存は解消するが、レガシーな SQL Server 照合順序であり Unicode 比較の挙動保証が弱い（Microsoft Learn が Windows 照合順序への切り替えを推奨する理由——上記引用）。却下
  - **`Latin1_General_100_CI_AS_SC`（KS/WS なし。Microsoft の一般推奨そのまま）**: 本改訂の初稿が採っていた案。かな種・全角/半角まで同一視するため「折り畳むのは大文字小文字のみ」という §1.2 の規則を超過し、SQLite との差を大文字小文字以外の次元で新設する。ペルソナレビュー（PR #168）の指摘を受けて KS/WS 明示へ改めた。却下
  - **日本語照合順序（`Japanese_XJIS_140_CI_AS_KS_WS` 等）**: 照合順序指定子（`Latin1_General` / `Japanese_XJIS` 等）が定めるのは辞書順ソートの規則と `varchar` 用コードページである（Microsoft Learn "Windows collation name": 「The base collation rules cover: The sorting and comparison rules that are applied when dictionary sorting is specified... The code page used to store varchar data」。確認日 2026-07-09）。Yagura は文字列列で `ORDER BY` しない（並びは常に ReceivedAt——§2.2）ため辞書順の言語差は使われず、列はすべて `nvarchar` のためコードページ差も効かない。DB-6 の要件（大文字小文字のみの折り畳み）は `CI_AS_KS_WS` の感度指定で決まり、これは両系列で同一に指定できる——したがって日本語系列を選ぶ積極的理由が現時点でない一方、ロケール固有の系列を選ぶと「なぜこのロケールか」の説明責任を全配備先に対して負う。汎用系列（Latin1_General_100）を既定とし、**日本語ロケール固有の大小折り畳み差が適合テスト（非 ASCII 大小ケース）で実際に検出された場合に限り、実測を根拠に再評価する**。却下（条件付き——実測での再開扉を残す）
  - **大文字小文字を区別する方向へ統一（両 provider を CS 化）**: 現行の暫定規則・実務要求（Issue #146 の根拠——「error」で ERROR/Error を拾えることが自由文検索の根幹）に反する。却下
  - **ASCII 限定の折り畳みで統一する（SQLite の現状挙動に両者を揃える）**: この案の利点は SQLite 側を一切変更せずに済み、provider 間一致が「目標」でなく構造的に成立することにある。しかし Windows 照合順序の比較スタイルで大文字小文字の扱いは `CI` / `CS` の二値であり、折り畳みの適用範囲を ASCII に限定する修飾子は構文上存在しない（Microsoft Learn "Windows collation name (Transact-SQL)" — https://learn.microsoft.com/sql/t-sql/statements/windows-collation-name-transact-sql の Syntax: `<CaseSensitivity>` は `CI` | `CS` のみ。確認日 2026-07-09）——ASCII 限定の折り畳みを実現するには SQL Server 側にこそ独自機構（CS/BIN2 照合 + アプリ層での折り畳み等）が要る。**つまり「新規機構ゼロ」という見かけの利点は成立せず、独自機構の置き場所が SQLite から SQL Server へ移るだけ**である。さらに Issue #146 の再現例（CAFÉ/café）を「両者ともヒットしない」側で恒久化し、利用者の期待（大文字小文字を区別しない検索）を非 ASCII で裏切り続ける。機構コストが対称である以上、期待に沿う意味論を選ぶ。却下

## 6. 本番昇格（SQLite → SQL Server）

ADR-0002 決定 3 の昇格支援 3 点 (i)〜(iii) のうち、(i) 案内は architecture.md §5.3、(ii) 接続切替を §6.1、(iii) 蓄積ログの移行を §6.2 で定め、昇格の最終段である旧・組み込み DB ファイルの処分（ADR-0004 決定 5）を §6.3 で定める。

### 6.1 接続切替（v0.1。昇格 (ii)）

- **昇格の全体の流れ**: 本番昇格は管理画面の昇格ウィザード（ui.md §4 の `/admin/promotion`。契約 `IPromotionWizardService` / 実体 `Yagura.Host.Administration.PromotionWizardService`）で次の順に進む——**1.** 準備フェーズ（接続検証。`ISqlServerConnectionValidator` 抽象により SQL Server 不在の開発機でも経路をテストできる）→ **2.** 切替確定前の予告 → **3.** 切替実行（冪等トークンつき。監査対象 = security.md §4.3 の 2002/2003）→ **4.** サービス再起動による反映 → **5.** 蓄積ログの移行（§6.2。任意）→ **6.** 旧・組み込み DB ファイルの処分（§6.3。必須）。**段階 6 が完了するまで昇格は未完了である**。段階 1〜3 は再起動前のウィザード、段階 5・6 は再起動後に同じ画面へ現れるセクションで行う
- **実装参照（Issue #502）**: 段階 1〜5 と、段階 6 のサービス側は実装済み。切替の実行（段階 3）は処分の方法を選ばせず、切替の境界をデータルートに記録する（§6.3・[DB-14](#8-確定待ち一覧)）。段階 6 の処分は契約 `IOldDatabaseDisposalService` / 実体 `Yagura.Host.Administration.OldDatabaseDisposal.OldDatabaseDisposalService` が担い、昇格ウィザードの処分セクション（`Yagura.Web.Administration.OldDatabaseDisposalSection`）と `/admin` の常設カード（`AdminHome`）がこの契約を使う（ui.md §4・§5.4）
- **切替実行の実効は「検証済み接続の設定保存 → サービス再起動での反映」である**: 下記の切替本番手順①〜④は、再起動を要しない切替（無瞬断切替）の設計として保持する（未実装）。§6.3 の処分は再起動による切替を前提に設計している——無瞬断切替を実装する場合は、§6.3 の前提条件 3（プロセス内に旧ファイルを開いた接続が残っていないこと）を改めて設計する（起動時の provider に従って SQLite の実体に束縛される部品——管理者アカウントストア等——は、`ILogStore` の差し替えだけでは旧ファイルを手放さない）。切替の保存が成立すると、画面は直後に設定の再読み込みを自動で実行し、保存先の切替キー（`Storage:Provider`・`Storage:SqlServer:ConnectionString`）を管理ホームの「再起動待ちの設定変更」に計上する（configuration.md §3）——切替後に再起動を忘れ、旧保存先のまま動き続けている状態を見えるようにするため
- **準備フェーズの入力と検証失敗の扱い（骨格の UX 完成。2026-07-06 オーナー合意のモックアップの実装）**:
  - **接続は項目で入力し、接続文字列はサーバ側で組み立てる**: サーバ名・データベース名・認証方式（**Windows 統合認証を既定** = §5.1 の第一推奨。選択時は**接続に使うアカウント = サービスの実行アカウント名を画面に表示する**——SQL Server 側にどの名前で見えるかを推測させない。**実行主体は実行アカウントであり、SQL Server 側から見える名前は構成で変わる**——既定の仮想サービスアカウントはネットワーク上マシンアカウント `DOMAIN\HOST$` に畳まれ、gMSA 実行（[ADR-0015](../adr/0015-gmsa-service-account.md)。configuration.md §4.4）では `DOMAIN\name$`。**§5.2 の `CREATE LOGIN` すべきアカウント名としてこの実効名を提示する**——固定名でなく実行アカウントから導出し、gMSA 構成では gMSA 名でログインを作らせる〔ADR-0015 決定 5〕）・SQL Server 認証時のユーザー名とパスワード・サーバ証明書の信頼（`TrustServerCertificate`。既定は信頼しない。チェックボックス自体に「暗号化は維持・証明書の検証のみ省略・なりすまし検知は行われない」の説明を常設する——自己署名証明書の閉域環境向けの選択であることを失敗前から読める形にする）。上級者向けに**接続文字列の直接入力を併存**する（項目が網羅しない接続オプションの逃げ道。既定は項目入力）
  - **パスワードは入力方式によらずマスク付きの専用欄からのみ入力する**: 直接入力欄のパスワード系キーは検証エラーとして拒否する。**拒否判定は文字列走査ではなく `SqlConnectionStringBuilder` で正規化パースした上で行う**（`Pwd` 別名・大文字小文字・空白ゆれを素通りさせない。単体テストで固定する）——画面・snapshot・設定画面の確認表示のいずれにもパスワードが平文で現れる経路を作らない（configuration.md §5。適用時の保存は従来どおり DPAPI 暗号化表現のみ）
  - **検証失敗は原因で分類し、原因別の次の一手を画面に示す**（分類の根拠 = Microsoft Learn 公式ドキュメント確認 2026-07-07）: ①**サーバ証明書が信頼されない**（SChannel `SEC_E_UNTRUSTED_ROOT` 0x80090325）→「サーバ証明書を信頼する」の有効化を案内、②**サーバへ到達できない**（タイムアウト・名前解決不能・ポート閉塞）→ サーバ名・ポート・ファイアウォールの確認を案内（修復 SQL なし）、③**ログイン失敗**（SQL Server エラー 18456）→ **18456 は誤パスワードでも DB 不在（state 38/46——クライアントへ返る情報は意図的に詳細を隠す）でも返るため、案内は「まずユーザー名・パスワードを再確認 → ログインが未作成の場合は次の SQL」の条件付き提示とする**、④**データベース不在**（同 4060）→ DB 作成を含む SQL を提示。③④は §5.2 の「実行可能な SQL」（ログイン作成・DB 作成・権限付与。環境の実値入り・SQL 認証のパスワードはプレースホルダ）をコピー可能に提示する。**分類できない失敗は生のエラーメッセージ + 汎用案内に留め、修復 SQL を断定提示しない**（誤分類の被害を画面内で閉じる安全側）。**提示のみでありサーバは実行しない**（§5.2 の統治——DBA 依頼文としての流通を前提とする）。監査記録（2002）には SQL 原文を残さず、失敗の分類値（分類不能を含む）と証明書信頼の選択値を付す
  - **v0.1 の提示 SQL は対象データベースの `db_owner` を付与する**（昇格・スキーマ作成を含む導入時権限として。実行時最小権限への分離——§5.2 の完全形——は後続 Issue の課題のまま変えない）。**提示 SQL 内のコメントで「導入時権限であり、実行時最小権限への分離で縮小予定」の暫定性を明記する**（依頼文として流通した先の DBA にも伝わる形にする）
  - **gMSA を推奨する主語を限定する（[ADR-0015](../adr/0015-gmsa-service-account.md) 決定 5）**: Windows 統合認証で **gMSA を推奨するのは「リモート SQL Server + DB 側の最小権限付与を要する AD 環境」**——仮想サービスアカウントの識別がマシンアカウント（`DOMAIN\HOST$`）に畳まれ同一ホストの他サービスと権限を共有してしまうため、DB 側で Yagura に限定した権限を付けたい場合に gMSA の専用ドメイン識別が効く。**SQLite のまま・SQL Server 同居・マシンアカウント許可で足りる環境では仮想 SA のままでよい**（全 AD 環境への無条件推奨にしない）。この判断フローは configuration.md CF-D9・security.md SEC-D8 のガイドに含める
  - **統合認証の接続失敗の観測性（ADR-0015 決定 5）**: Windows 統合認証での接続失敗時、イベントログ警告に**実行主体（アカウント名）・失敗種別**を含め、DC 起因（gMSA のパスワード取得不能・DC 到達不能）か SQL Server 起因（ログイン未作成・権限不足）かの一次切り分けがサーバ単体でつくようにする。準備フェーズの検証失敗は上記の原因分類（①〜④）で画面に示すが、**稼働中の統合認証接続失敗**は運用者が画面を見ていない時間帯に起こり得るため、イベントログ側にも実行主体と失敗種別を残す。**専用のイベント ID は 1031 として採番済み**（security.md §4.3。Issue #418。1000 番台運用警告・エラーレベル）。発火点は `PersistenceWriter`——Storage 層はロガーを持たないため、`SqlServerLogStore` が書き込み失敗時に分類（`SqlServerFailureClassifier.ClassifyIntegratedAuthConnectionFailure`）を `LogStoreWriteException` に載せて運び、1030（恒久障害）と同一の発火点・抑制窓で、統合認証の接続失敗と分類できた恒久障害では 1030 の**代わりに** 1031 を出す（同一例外で二重警告にしない。分類できない失敗は従来どおり 1030 の安全側）。分類根拠は SEC-14 (a)/(c) の AD lab 実測（2026-07-24。[ADR-0015](../adr/0015-gmsa-service-account.md) 改訂履歴 3——推測の分類表を作らない）。**メール通知は対象（エラー）**——gMSA 構成の夜間 DC 断は「書き込みが止まる」導火線であり、1030 の代替として発火する以上、同じ重大度で allowlist に載せないと夜間到達が退行する
  - **gMSA のパスワードローテーション跨ぎの接続継続（ADR-0015 決定 7 (b)。継続を担保する設計方針）**: gMSA のパスワードは AD が自動ローテーションし、**LSA が新パスワードを透過的に取得・キャッシュする**ため、Windows 統合認証（SSPI/Kerberos）の DB 接続は接続確立のたびに現在の gMSA 資格情報で再認証され、ローテーション自体はアプリの追加処理なしに跨げる（これが gMSA の主眼）。**設計として担保すべきは、ローテーション直後にプール内の既存接続が一時的に認証エラーになった場合の扱い**——恒久障害ではなく再試行で解消する一過性として扱い、接続プールのリセット + 再接続で回復する（database.md §1.2 の再試行契約に合流。恒久障害〔1030・スプール退避〕へ即座に落とさない）。この「一過性として扱う」判定は決定 7 (b) の E2E（`Reset-ADServiceAccountPassword` を跨ぐ受信・DB 書き込みの継続。security.md SEC-14 (b)）で実機確認する
  - **gMSA の DB 最小権限は v0.1 では未達（田中レビュー指摘。正直に記す）**: gMSA 採用の一次動機の一つは「DB 側で Yagura に限定した最小権限を付与できる」ことだが、**v0.1 の提示 SQL は導入時権限として引き続き `db_owner` を付与する**（上記「v0.1 の提示 SQL は…」の項）。したがって v0.1 時点では gMSA を使っても DB 側権限は最小化されておらず、**実行時最小権限への分離（§5.2 の完全形）が後続 Issue で実装されて初めて、gMSA の専用ドメイン識別に対する最小権限付与が実効化する**。この段階差は SEC-D8 のガイドにも明記し、「gMSA にすれば即座に DB が最小権限になる」という誤解を避ける
- **準備と本番を分離する**: 切替は「準備フェーズ」（接続・権限・スキーマの事前検証。§5.2 の SQL 提示 → DBA 依頼待ちのような長時間の停滞はここで吸収する）と「切替本番」（事前検証済みの接続への差し替え。短時間で完了する）に分ける。準備フェーズは何度でも中断・再開でき、本番はすべての事前検証が通ってから実行する
- **切替本番の手順**: ①旧 provider の書き込み停止 → ②システムイベントの複写（下記）→ ③新 provider へ差し替え（**この時点をもって切替の確定とする**）→ ④スプール分の drain（新 DB へ）。この間に到着したログは Q2 とスプール（architecture.md §3.2.1——書き込みが確定できない状態そのもの）が受ける。**切替以降の新規ログは新 DB へ**保存される
- **切替中の可視化と打ち切り**: 切替中であることと経過時間をゲージ・能動通知（architecture.md §4.6）に露出する。**打ち切り監視（[DB-7](#8-確定待ち一覧)）の区間は手順①〜③、すなわち差し替えの確定まで**とする——確定までに既定時間を超えた場合は**自動で旧 provider へ戻す**（戻った場合、スプール退避分の drain 先は旧 DB である——差し替え前なので通常経路のまま）。手順④の drain の長時間化は巻き戻しの対象ではなく、通常の drain 規則（architecture.md §3.2.2）で扱う
- **差し替え確定後の障害は昇格の失敗として扱わない**: 差し替え（手順③）以降に新 DB への書き込みが失敗し始めた場合は、巻き戻さず通常の障害経路（リトライ・スプール退避）で扱う——新 DB が正であり、旧へ戻すと新 DB 側のコミット済みログが管理外の複製になる（ADR-0004 決定 5 が嫌う状態）。事前検証の分離が、この局面に至るリスク自体を縮める
- **システムイベントは切替処理が新 DB へ複写する**: 受信断区間等（§2.3）はログ本体より件数が桁違いに少なく、蓄積ログ移行 (iii) を待たずに複写できる。「ログ本体と同じ以上の保持」（§2.3）を昇格が破らないようにするため、複写は手順②——**書き込み停止後・差し替え前**——に行う（停止後なので取り残しは生じない）。**複写の失敗は巻き戻しの対象**（まだ確定前であり安全に戻せる）。巻き戻し後の新 DB に複写済みイベントが残留し、再切替で重複し得ることは、システムイベントにも適用される at-least-once の範囲として許容する（切替自体の監査記録はホストの管理操作経路であり、この複写とは独立）。**現行の再起動による切替ではこの複写は行われない**——切替前のシステムイベントの引き継ぎ（移行に含めるか）は [DB-13](#8-確定待ち一覧)
- **切替前に保存したログは、切替が反映された時点（段階 4）から、移行（§6.2）を実行するまで Web UI から参照できない**。移行せずに処分すると、削除なら参照できないまま失われ、退避なら退避ファイル（SQLite ファイル）には残るが Web UI からは参照できない（§6.3）。ウィザードは**切替の確定前に**この帰結と、切替後に要る段階（再起動 → 移行 → 処分）を予告する（文言は ui.md §5.4）
- **旧・組み込み DB ファイルは残置しない**（ADR-0004 決定 5）。処分（退避 / 削除）は**切替の確定前ではなく、再起動と移行の後に管理画面から実行する**（§6.3）。切替実行の時点では処分の方法を選ばせない——その時点の旧ファイルは使用中で処分できず、移行の要否・結果も未確定であり、先取りした選択は実行時に再確認を要する（選択と実行が離れると、利用者は選んだ時点で処分が済んだと受け取りやすい）
- 切替は管理操作であり監査記録の対象（ADR-0004 決定 7）

### 6.2 蓄積ログの移行（昇格 (iii)。Issue #266 で実装済み）

- 蓄積済みログの移行機能は**それ単体で提案書 1 本分の規模**があり、時期と方式は個別に確定する（ADR-0002 決定 3 のとおり。着手判断の入力は [DB-5](#8-確定待ち一覧)）
- ただし**満たすべき要件は先に固定する**（提案書はこの要件を出発点にする）:
  1. 移行中も受信を止めない（新規ログの保存を移行処理が妨げない）
  2. **完全性の検証を移行機能自体が持つ**: 移行元・移行先の件数突合を実行し、結果を記録する。突合の軸は ReceivedAt の範囲とし、**合格条件は at-least-once と整合させる**——「移行先件数 ≥ 移行元件数、かつ差分のレコードを抽出して重複として説明できること」（件数の完全一致を合格条件にしない——重複と損失の相殺を隠すため）
  3. 中断・再開が安全（冪等または再開点の記録。at-least-once の意味論と整合）
  4. **ReceivedAt を再刻印しない**（§2.2 の契約。移行後も時刻・保持期間の起算は変わらない）
  5. **移行由来のレコードは投入経路を事後に識別できる**（監査で「このレコードはいつ・どの経路で入ったか」に答える。重複調査にも使う。識別の持たせ方は移行設計時に確定）
  6. 移行完了後の旧データは残置しない（§6.3 の処分による）
- 移行の読み出しは §1.2「契約拡張の予約」の一括読み出し操作として追加する（契約外の裏口 SQL で実装しない）
- **実装参照（Issue #266。DB-5）**: 一括読み出しは `IBulkLogReader`（optional 契約——`store is IBulkLogReader` の capability 検出。両 provider が実装。昇順キーセット反復・上限/タイムアウト非適用・呼び出しは管理操作限定 = 予約 (a) の条件どおり）として実体化した。移行の実体は `LogMigrationService`（Host）——固定要件との対応: ①受信継続 = 書き込みゲートをバッチ（仮値 500 件）単位で取得・解放し、ライブ永続化をバッチの合間に通す ②検証内蔵 = 完了時に「移行先の移行範囲（最終 ReceivedAt 以前）件数 ≥ 移行元総件数」を突合（差分は at-least-once 再開の重複として説明）。**総数の比較だけであり、要件 2 後半の「差分のレコードを抽出して重複として説明する」処理は持たない**——移行先の同じ範囲にライブ受信が含まれる場合（切替 → 縮退運転 → 復帰の後に移行した場合等）は欠落を隠し得るため、処分の判定（§6.3）では静止した旧ファイルを時間帯ごとに照合し直す ③中断・再開 = チェックポイント（データルート直下 `log-migration-checkpoint.json`。バッチごと原子的置換）から再開。破損時は先頭からやり直し（欠落側に倒さない） ④ReceivedAt 不変 = 読んだレコードをそのまま `WriteBatchAsync` へ（Id のみ再採番） ⑤事後識別 = 移行範囲 + 件数をシステムイベント `migration.import` として移行先に記録 ⑥残置しない = 完了状態を昇格ウィザードに提示し、旧ファイルの処分（§6.3）へ引き継ぐ。状態表示の完了判定は §6.3 の規則 1・2 による（完了記録が移行済み位置を持ち、その位置より後のレコードが旧ファイルに無いこと。位置を持たない完了記録は、旧ファイルにレコードが 1 件でもあれば未完了）。完了の後に追加されたレコード（縮退運転で旧ファイルへ書き込まれたログ）や移行先に無いシステムイベントがあれば、再実行（追補）できる状態を返す ⑦**システムイベントの引き継ぎ**（[DB-13](#8-確定待ち一覧) ①）= ログ本体の移行と完了時の検証の後、旧ファイルのシステムイベントのうち移行先に無いもの（種別・区間〔UTC の tick 精度〕・近似の印で照合する。Id は採番し直し、付帯情報は照合に使わない）を `WriteSystemEventAsync` で複写し、複写後の照合で揃わなければ検証不合格とする（`SystemEventReconciler`。§6.3 の完了判定も同じ照合を使う）。旧ファイルを開く操作（状態取得の件数読み取り・移行）は処分と同じ排他（§6.3 前提条件 2）の下で、ファイルを作成しない開き方で行う。移行はサービスの停止要求でも中断する（画面の取り消しトークンの有無によらない。中断はチェックポイントから再開できる）。実行は昇格ウィザードの移行セクション（昇格 + 再起動後に表示）から。管理操作として監査 2018 に記録
- 移行機能（上記）を提供したため、**手動移行手順**（[§9](#9-利用者向けドキュメントへの申し送り) DB-D1）は移行機能を使えない場合の非常手段と位置づける。手順を文書で提供する場合は要件 2 と同じ判定基準の件数突合を含め、**移行実施の事実（日時・移行元/先件数・実施者）を製品の監査記録に残すステップを置く**（手動移行が製品の証跡から断絶しないようにする。記録手段はセキュリティ設計文書の監査記録仕様と合同で確定する）

### 6.3 旧・組み込み DB ファイルの処分（昇格の最終段）

ADR-0004 決定 5 の「本番昇格後の旧・組み込み DB ファイルは残置しない」を、昇格手順の最終段（§6.1 の段階 6）として製品が実行する。処分は切替が反映された（段階 4）後、蓄積ログの移行（段階 5。§6.2）を済ませてから——移行しない場合は下記の明示確認を経て——管理画面から実行する。

- **実装参照（Issue #502）**: 契約 `IOldDatabaseDisposalService`（Abstractions）/ 実体 `OldDatabaseDisposalService`（`Yagura.Host.Administration.OldDatabaseDisposal`）。対象の導出と安全検査 = `OldDatabaseTargetPaths`・`OldDatabaseTargetInspector`、移行の完了判定 = `MigrationCompletionJudge`（時間帯ごとの件数は optional 契約 `IHourlyLogCountReader`——§1.2）、移行と共有する排他 = `OldDatabaseAccessGate`、退避先の条件 = `ArchiveDestinationValidator`、書き出しと検証 = `SqliteArchiveExporter`、ファイルシステム・ACL の判定と操作 = 差し替え口 `IArchivePlatform`（Windows の実体 `WindowsArchivePlatform`）、切替の境界の記録 = `PromotionSwitchBoundaryStore`、1041 と製品外での消失の記録（2031）= `OldDatabaseDisposalNotifier`。切替の前の処分方式の選択は撤去した（2003 の Detail にも含めない）。画面は昇格ページの処分セクション `OldDatabaseDisposalSection`（`Yagura.Web.Administration`）と `/admin` の常設カード（`AdminHome`）——ui.md §4・§5.4。[DB-13](#8-確定待ち一覧)・[DB-14](#8-確定待ち一覧) はオーナー判断待ちのまま推奨案（いずれも ①）で実装している（判断が推奨案と異なれば実装を改める）
- **処分が必須である理由**: 旧ファイルには切替前のログ・システムイベント（§2.3）と、組み込み DB の時期にアプリ独自認証（[ADR-0010](../adr/0010-admin-ui-authentication.md)）を使っていた場合は管理者アカウント台帳（パスワードハッシュ）が残る。**保持期間による削除（§3）は現行 provider にしか効かない**ため、放置すると旧ファイルの中身は期限を過ぎても消えず、保持期間の約束が旧ファイルについてだけ破れる。データルートの ACL（security.md §5）で保護されてはいるが、製品が管理しない複製が製品の管理領域に残り続ける状態である
- **ADR-0004 決定 5 との関係**: 決定 5 は「削除または明示の退避を昇格手順に含める。管理外の複製を作らない」とする。本節の退避は決定 5 が挙げる「明示の退避」にあたる。「管理外の複製を作らない」は、**製品の管理領域（データルート）に、製品が管理しない複製を残さない**ことと読む——退避ファイルは管理領域の外に置かれ、その管理（保管場所の統制・バックアップ・不要になった時点の削除）の責任は、確認ダイアログでの明示を経て利用者へ移る（下記「退避ファイルの保護」）。誰も管理しない複製を作るのではない。この読み方は、ADR-0004 が具体的な実装方式を全体設計書に委ねた範囲での解釈である
- **処分の対象（削除してよいファイルの限定）**:
  - 対象は**データルート直下の組み込み DB ファイル（既定 `yagura.db`）と、同名の `-wal`・`-shm` のうち、存在するもの**に限る。`Storage:SqliteFileName`（configuration.md §8。区切り文字を含まないファイル名に検証済み）で名前を変えた構成ではその名前を使う——処分の対象・§6.2 の移行元・SQLite provider の書き込み先は同一の導出で決め、互いに食い違わせない
  - **画面で利用者が入力したパスは削除に使わない**。利用者が入力するのは退避先の親フォルダだけであり、書き込み先としてのみ使う（クラッシュ後の掃除で削除するのは、製品が作り、製品の作業中の ACL を持つことを確かめた作業用サブフォルダに限る——下記「失敗時の振る舞い」）
  - 実行時に次の安全検査を行い、満たさなければ処分を拒否する: ①対象が正規化後のパスでデータルート直下にあること、②通常のファイルであること（ディレクトリ・再解析ポイント——シンボリックリンク・ジャンクション——ではない）、③**本体が存在する場合は**、SQLite のデータベースファイルであること（ファイル先頭の識別子で判定する。開いてスキーマを読める場合は、組み込み DB のスキーマ——ログ本体のテーブル——を持つことも確かめる）。設定の誤記で別のファイルを指していても消さないための検査である
  - **③を満たさない場合・本体が無い場合の扱い**（処分できないまま未完了を鳴らし続けないため）:
    - 0 バイトの本体は内容を持たないため、製品がデータルート直下に置く他のファイル（設定ファイル・移行チェックポイント等）の名前でないことを確かめて、削除の対象にする（退避の対象にはしない）
    - 先頭の識別子が無い・壊れている本体（0 バイトを除く）は、製品が置く他のファイルの名前でないことを確かめたうえで、ファイル名・サイズを示す明示確認を取って**削除でのみ**処分できる（内容を検証できないため退避はできない）
    - 本体が無く `-wal`・`-shm` だけが残る場合は、それらを（①②の検査を経て）削除の対象にする（退避の対象にはしない）
  - **昇格後に旧ファイルを開く経路（状態取得・移行・処分）は、ファイルを作成しない開き方にする**（ファイルが無ければ作らずに失敗する。現行の `SqliteLogStore` は作成を伴う開き方——`SqliteOpenMode.ReadWriteCreate`）。排他による順序の保証をすり抜けた場合にも、空のファイルを作り直して未完了を鳴らし続ける事故を構造的に防ぐ
- **前提条件（すべてを満たすときだけ処分を実行できる）**:
  1. **実効 provider が SQL Server であること**（= 旧ファイルが使用中でない）。判定は設定ファイルの記載値ではなく、起動時に解決された実効値で行う——切替を実行したが再起動していない場合も、接続文字列の不備・復号失敗で SQLite へ縮小して起動した場合（configuration.md §2。旧ファイルが現に書き込み先になっている）も、旧ファイルは使用中であり処分できない
  2. **移行（§6.2）が実行中でないこと**。処分と移行は同じ排他（旧ファイルの利用権）を取り合う——処分の実行中は移行を開始できず、移行の実行中は処分を開始できない。移行画面の状態取得（旧ファイルの件数読み取り）も同じ排他の下で行う
  3. **プロセス内に旧ファイルを開いた接続が残っていないこと**。移行・状態取得が使った SQLite 接続は、破棄時に接続プールごと解放する（`SqliteLogStore.DisposeAsync` の既存の振る舞い）。プロセス外のツールが開いている場合は下記「失敗時の振る舞い」に従う
  4. **移行が未完了なら、「移行せずに処分する」の明示確認があること**（次項）
  5. **ライブ受信が逼迫していないこと**: スプール退避の継続中・Q2 の高水位の間は開始しない（下記「処分中の受信への影響と停止」）。判定は、スプールに未消化のデータがあること、または Q2 の使用率が drain の高水位（architecture.md §3.2.2 と同じ尺度）を超えていることとする
- **移行の完了判定と明示確認**:
  - 移行済みとみなすのは、**次のすべてを満たす場合に限る**。§6.2 の移行の状態表示も 1・2 の規則で完了を判定する（3・4 は旧ファイル全体を読む照合であり、処分の直前に排他の下で行う。状態表示では「処分の前に照合する」と示す）
    1. 移行のチェックポイントに完了記録（§6.2 の完了時の検証の合格）があり、移行済み位置（最終 `(ReceivedAt, Id)`）を持つこと。**位置を持たない完了記録（移行元 0 件で完了した場合）は、旧ファイルにレコードが 1 件でもあれば未完了とみなす**
    2. 処分の直前に旧ファイルを調べて、移行済み位置より後のレコードが無いこと——移行の完了後に縮退運転（前提条件 1 の SQLite への縮小）で旧ファイルへ書き込まれたログを「移行済み」と誤認しない
    3. **静止した旧ファイルを時間帯ごとに照合して合格すること**: 旧ファイルの ReceivedAt を時間帯（仮値 1 時間）ごとに数え、すべての時間帯で「移行先の同じ時間帯の件数 ≥ 旧ファイルの件数」であること。§6.2 の完了時の検証は総数の ≥ であり、移行先のライブ受信が同じ ReceivedAt の範囲にあると欠落を隠し得る（例: 切替 → 縮退運転 → 復帰の後に移行すると、移行先の移行範囲には切替後のライブ受信が丸ごと含まれる）。処分は製品がログを消す操作であり、その許可条件を総数の比較に頼らない。旧ファイルは前提条件 1〜3 により静止しているため、処分の時点で照合し直せる。時間帯は UTC の正時で区切る。**保存期間の境界より前に始まる時間帯（境界を跨ぐ時間帯を含む）は照合しない**——移行先では保存期間による削除が進み、その時間帯の件数は削除の進み具合で変わる（これらのログは製品の約束の上では既に消えているはずのものであり、未移行と呼んで明示確認を求めない）。移行先が時間帯ごとの件数に対応しない provider なら、照合できないものとしてすべてを未移行とみなす
    4. **移行先のライブ受信と重なる区間（切替の反映より後の ReceivedAt）に、旧ファイルのレコードが無いこと**——その区間は件数では照合できない（移行先にライブ受信が混ざる）ため、旧ファイルにレコードがあれば移行済みとはみなさない。区間の境界（切替の反映の時刻）は、切替の実行時にデータルートへ記録した切替の境界（[DB-14](#8-確定待ち一覧) ①。下記「切替の境界の記録」）から得る。記録が無い・読めない場合は、境界が分からないものとして全区間を照合できない区間とみなす（安全側——明示確認に回す）
  - 未完了（未実行・中断・検証不合格・完了後の追加あり・照合の不合格・照合できない区間のレコードあり）で旧ファイルにログが 1 件以上あるときは、確認ダイアログに**未移行の件数と、その ReceivedAt の範囲（最古〜最新）**を示し、**「移行せずに処分する」の明示確認（既定は未確認。利用者の能動操作で確認する）を取ったうえで許可する**。削除なら Web UI から参照できないまま失われること、退避なら退避ファイルには残るが Web UI からは参照できないことを、文言で区別する（ui.md §5.4）
  - **旧ファイルの中身を一律に「切り替え前のログ」と呼ばない**: 移行の完了後に追加されたログがあると分かる場合（上記 2）は、処分セクションと確認ダイアログでその旨を区別して示す（「SQL Server に保存できなかった間に組み込みデータベースへ保存したログ」。ui.md §5.4）。/admin の常設カードと 1041 は旧ファイルを開かずに判定する（旧ファイルを開くのは排他の下の状態取得と処分に限る）ため、件数による区別はせず、中身を決めつけない呼び方（「以前の保存先〔組み込みデータベース〕のファイル」）に留める。縮退運転を経た旧ファイルの一般的な区別は DB-14 に従う
  - 明示確認の有無は監査記録に残す
  - **切替前のシステムイベント（受信断区間等。§2.3）は移行が引き継ぐ**（[DB-13](#8-確定待ち一覧) ①。§6.2 実装参照 ⑦。再起動による切替は §6.1 の複写を行わないため）。移行済みとみなすには、上記 1〜4 に加えて、**旧ファイルのシステムイベントがすべて移行先にあること**（§6.2 と同じ照合）を要する。無いものがあれば、確認ダイアログは削除すると失われる受信できなかった時間帯の記録の**件数と期間**を示し、明示確認の対象に含める
  - **切替の境界の記録**（[DB-14](#8-確定待ち一覧) ①）: 切替の実行（§6.1 段階 3）で設定の保存が成立したら、その時点の事実——切替の時刻・組み込み DB ファイルのフルパス・最新の `(ReceivedAt, Id)` と件数——をデータルート直下の `promotion-switch-boundary.json` に記録する（監査記録とは別の状態。原子的置換で書く）。実効 provider が SQL Server になった最初の起動で、その時刻（切替の反映の時刻）を書き足す——受信の開始より前に書くため、これより後の ReceivedAt だけが移行先のライブ受信と重なる。反映の時刻が無ければ切替の時刻を境界とする（照合できない区間が広がる安全側）。実効 provider が SQL Server の間にウィザードをやり直しても記録は書き換えない（本物の切替の境界を上書きしない）。記録の失敗は切替・起動を失敗させない（判定が安全側へ倒れる）。**判定の引き金は旧ファイルの存在という事実のままであり**、記録は「どこからが照合できない区間か」と「設定の名前を変えて見失った旧ファイル」（下記「未完了の判定」）を知るための補助に限る。処分の完了時に、記録が処分したファイルを指していれば撤去する
- **処分の方式**: 利用者は「退避」か「削除」を選ぶ。**既定の選択は置かない**（どちらかを利用者に能動的に選ばせる）。
  - **退避** = 旧ファイルの内容を、退避先に製品が作る作業用サブフォルダの中へ単一ファイルとして書き出し、**検証に合格してから**元のファイルを削除する。**移動ではなく、書き出し + 削除とする**——①`-wal` 上の確定済み変更を含む一貫した内容を単一ファイルにまとめられる、②検証の合格を元の削除の条件にできる、③管理者アカウント台帳と空き領域の残留を退避ファイルから除ける（移動では元のバイト列がそのまま出る）。**保存期間を過ぎたログ（旧ファイルに行として残っているもの）も退避ファイルに含める**——退避の目的は元のファイルそのものの保管であり、保護責任は明示を経て利用者へ移る。その件数を確認ダイアログに示し、2030 の開始の記録に残す（行として残っていない削除済みのデータは手順 6 で除く）
  - **削除** = 元のファイルを削除する
  - **選択の目安**（画面に添える。ui.md §5.4）: 移行が完了していれば、通常は削除で足りる（ログは SQL Server に移っている。削除の前に、移行先の SQL Server のバックアップが取られていることを確かめるよう案内する——削除の後は移行先が唯一のコピーになる）。元のファイルそのものの保管を組織の規程等で求められる場合に退避を選ぶ。この目安は、切替前のシステムイベントが移行で引き継がれること（DB-13 の①）を前提にする
  - **呼び名と識別子**: 画面と利用者向けドキュメントでは、旧ファイルの退避を「書き出して保管」と呼び、「退避」の語を使わない（スプールの「一時保管への退避」と取り違えないため。ui.md §7.2）。コード上の識別子は `Archive` 系とする（例: `OldDatabaseDisposalMethod.Archive`・`ArchiveParentDirectory`）——スプールの `Evacuate*` と検索で分かれるようにする。本書と監査記録の内部用語は「退避」のままとする
- **退避先の条件**（実行前に検証し、満たさなければ何も変更せずに拒否する。条件は入力の前に画面へ示す——ui.md §5.4）:
  - **利用者が指定するのは退避先の親フォルダであり、既存のフォルダに限る**。製品は親フォルダを作らない（実行アカウントが作ったフォルダは実行アカウントが所有者になり、処分の後も実行アカウントがデータルートの外に書ける範囲を残すため）。製品はその中に処分ごとの作業用サブフォルダだけを作る（下記の手順 4）
  - **ドライブ文字から始まるローカルの絶対パスに限る**。UNC パス（`\\server\share`）・デバイスパス（`\\?\`・`\\.\` で始まる形）・ネットワークドライブは受け付けない——退避ファイルの保護（下記の ACL）を製品が確定できるのはローカルのファイルシステムに限られる（ネットワーク上の共有には共有側の権限が別に掛かり、実行アカウントのネットワーク上の識別も構成で変わる——§6.1 の gMSA の項）。拒否したときは、ローカルに書き出した後で管理者としてファイルサーバへ複写する手順を次の一手として示す
  - **リムーバブル媒体・光学ドライブは受け付けない**——媒体ごと別のマシンへ持ち出されると、持ち出し先の管理者は ACL を越えて読める。種別の判定方法とその限界は [DB-12](#8-確定待ち一覧) で確認する。退避先のドライブ種別は監査記録に残す
  - **ACL を保持するファイルシステムであること**（ACL を付けられない場所へは退避しない。判定方法は DB-12）
  - **データルート・スプールの置き場所・プログラムのインストール先のいずれの配下でもないこと**（再解析ポイントを解決した実体のパスで判定する）。データルート配下は実行アカウントが変更権を持つ製品の管理領域であり、そこへ置くと処分の意味——製品の管理外へ出す——が成り立たない
  - **実行アカウントが親フォルダにサブフォルダを作れること**: 書き込むのはサービスの実行アカウントである。作れるかどうかは、作業用サブフォルダを実際に作ること（手順 4）で確かめる。作れない場合は、実効実行アカウント名（§6.1 の gMSA の項と同じ導出）を入れた付与コマンド（親フォルダにフォルダの作成に要る権限だけを与える `icacls`）と、処分の後にそれを外すコマンドを画面に示す（security.md §5.1.1 の MSI 配置フォルダと同じ形——実書き込みのプローブ + 付与コマンドの表示）
  - **空き容量**:
    - 書き出しの開始前に、旧ファイル（本体 + `-wal`）の合計サイズを書き出しても、退避先ボリュームの空き容量が下限を下回らない見込みであること。下限は空き容量監視の警告閾値（1006 と同じ値。architecture.md §9 M-16）とし、**退避先がデータルート・スプールの置き場所と同じボリュームなら、警告閾値とスプールの使用量上限の残り枠の大きい方**とする——退避ファイルがスプールの使える領域を食い、後の DB 障害でスプールが上限より先にディスク満杯で書き込みに失敗するのを防ぐ（警告閾値 1 GiB の根拠——スプール上限の既定値と同値——は上限を変更した構成では成り立たない）
    - WAL の反映（手順 3）で本体が伸びる分（データルートのボリューム）と、DB-12 ② の方式が要る一時領域（その置き場所のボリューム）も、それぞれのボリュームについて見積もって同じ下限で判定する
    - **書き出し・検証の途中も周期的に再検査し**、下限を下回ったら取り消す（退避の失敗として扱い、元は変えない）
  - 作業用サブフォルダ名と退避ファイル名は製品が決める（`yagura-archive-<UTC 日時>` の形）。**作成は排他で行い、既存のファイル・フォルダは上書きしない**
- **退避の手順**:
  1. 前提条件・対象の安全検査・退避先の条件を検証する。退避先の条件の最後の段として**作業用サブフォルダを排他作成する**（作れるかどうかの確認を兼ねる。作成の時点から手順 4 の保護 ACL を持つ）。ここまでで拒否した場合は何も残さない
  2. **開始を記録する**（2030。結果 = 開始）。**記録が監査記録の正本に載ったことを確かめ、載らなければ作業用サブフォルダを削除して拒否する**（下記「監査記録」）。続いて、同じ親フォルダに残るクラッシュ後の作業用サブフォルダを掃除する（下記「失敗時の振る舞い」）
  3. **旧ファイルの WAL を本体へ反映する**（チェックポイント）。**反映が完了しない場合は、プロセス外の誰かが旧ファイルを使用中の可能性があるため、処分を開始しない**。ただし反映の完了は、使用中でないことの証明にはならない（読み取りトランザクションを持たずに開いているだけの接続は反映を妨げないと考えられる——DB-12 ⑤で確認する）。使用中であることの最終的な検出は、削除の失敗（本体を最後に消す順序）が担う。反映の後は本体だけで内容が完全になるため、後段の削除が途中で失敗しても、残った本体から同じ内容を再び退避できる
  4. **作業用サブフォルダの保護**: 手順 1 で排他作成した作業用サブフォルダは、**作成の時点から、親からの継承を切った保護 ACL**（`SYSTEM`・`Administrators`、作業中に限り実行アカウント。いずれも配下へ継承する）を持つ（security.md §5.3）。以後の書き出しはこのサブフォルダの中だけで行う——SQLite が書き出しの過程で自ら作る付随ファイル（製品がハンドルを先に持って ACL を付ける機会が無い）も、作成の時点からサブフォルダの ACL を継承し、親フォルダの ACE（`Users` の読み取り等）を受けない
  5. **SQLite を経由して、作業中のファイルへ一貫した内容を書き出す**（方式は下記「実現方式の記録（DB-12）」）。旧ファイルを OS のファイル複写で写さない（SQLite を経由しない複写は一貫性を保証しない）。作業中のファイルは排他で作成し、再解析ポイントを辿らない
  6. **空き領域に由来する残留を除く**: 退避ファイルには、**管理者アカウント台帳**（アプリ独自認証のパスワードハッシュ）も、**旧ファイルの空き領域に残る削除済みのデータ**（保持期間で削除したログ・削除された行）も含めない——退避の目的は切替前のログの保管であり、資格情報の検証材料や、保持期間の約束で消えているはずのデータを製品の管理外へ持ち出す理由がない。件数照合も整合性検査も空き領域の中身は検知しないため、方式の選択で担保する: ページを空き領域ごと複写する方式（online backup API の単独使用）は採らず、段階的に書き出す方式を採る場合も最後に空き領域を除く処理（`VACUUM` 等）を通す（判定基準と方式は DB-12 ①②。退避ファイルのバイト列に削除済みの行・台帳の目印が現れないことを自動テストで固定する——下記）
  7. **検証**（すべて合格したときだけ次へ進む）: ①退避ファイルの整合性検査（`PRAGMA integrity_check` が `ok`）、②**ログ本体・システムイベントの件数が旧ファイルと一致すること**——旧ファイルは前提条件 1〜3 により書き手のいない静止状態にあるため、§6.2 の移行（受信と並行するため「移行先 ≥ 移行元」で判定する）と異なり**完全一致を合格条件にできる**、③スキーマ版が旧ファイルと一致すること、④退避ファイルが単一ファイルで完結していること（`-wal`・`-shm` を伴わない）。あわせて退避ファイルの SHA-256 と、ログ本体の ReceivedAt の最古・最新を求める（監査記録に残す。保護責任の移転後に、提出されたファイルが製品の書き出したものかを確かめる手段とする）
  8. **確定**: 作業中の名前から退避ファイル名へ改名する（上書きしない）。続いて作業用サブフォルダと退避ファイルから実行アカウントの ACE を外し、所有者の暗黙の権限を抑止して、最終の ACL（下記）にする。確定の後、**削除の段階に入る前に**、退避ファイルのパスと SHA-256 を含む記録を書く（2030。結果 = 削除の開始）。**この記録が監査記録の正本に載らなければ削除の段階に入らない**（中断として終える。元のファイルは変更していない。確定済みの退避ファイルは残り、画面と終了の記録から辿れる）
  9. 元のファイルを削除する（下記「削除の手順」）
- **退避ファイルの保護（ACL。security.md §5.3）**:
  - **最終の ACL は、作業用サブフォルダ・退避ファイルとも `SYSTEM` と `Administrators` のフルコントロールのみとし、親フォルダからの継承を切る**（親フォルダの ACE——`Users` の読み取り等——を受けない）。**サービスの実行アカウントには確定後のアクセスを残さない**——退避ファイルは製品がもはや読まないデータであり、外部入力を扱うサービスプロセスから到達できる必要がない（データルートの ACL〔security.md §5〕より一段絞る）
  - **書き出しの途中も、退避データ（作業中のファイルと、SQLite が書き出しの過程で作る付随ファイルを含む）は作成の時点から保護する**——作業用サブフォルダの保護 ACL の継承による（手順 4）。作成後に ACL を付け替える方式は、付け替えまでの間に親フォルダの継承 ACL で読める窓を作るため採らない
  - **所有者の暗黙の権限も残さない**: 作業用サブフォルダと退避ファイルを作成した実行アカウントは、それらの所有者になり得る。所有者が DACL の内容によらず持つ暗黙の権限（ACL の読み書き——フォルダについては、自らに子の削除権を与え直す経路を含む）を確定時に両方について抑止し、確定後に実行アカウントが退避ファイルへ到達できる経路を残さない（方式と確定後の `icacls` 出力は DB-12 ④で一次情報と実機により確認し、security.md §5.3 に記録する）
  - **最終の ACL を適用できない場合は退避の失敗として扱う**（警告して続行しない——保護できない複製を作らないことを優先する）
  - **退避の完了をもって、退避ファイルの保護責任（保管場所の統制・バックアップ・不要になった時点の削除）は利用者へ移る**。製品は退避ファイルを以後追跡しない（保持期間削除・未完了判定・起動時 ACL 検証のいずれの対象でもない）。**製品は退避ファイルを読み戻す機能を持たない**（Web UI で参照する・データルートへ戻して移行にかける、のいずれも提供しない。開くには管理者として sqlite3 等を使う）。この移転と読み戻せないことは、確認ダイアログと利用者向けドキュメントに明記する（[§9](#9-利用者向けドキュメントへの申し送り) DB-D4）
- **削除の手順**:
  - **`-wal`・`-shm` を先に、本体を最後に削除する。1 つでも失敗したらその時点で止める**——本体が残る側に倒し、未完了の判定（下記）が外れない状態を保つ
  - **共有違反は短く再試行する**: 削除が共有違反（ウイルス対策・バックアップソフトが一瞬開いた場合等）で失敗したときは、短い間隔で数回（合計の仮値 30 秒以内）再試行してから部分失敗とする。再試行はサービスの停止要求で打ち切る
  - 削除を選んだ場合も、削除の前に退避の手順 3 の反映を試みる（完了しなければ使用中の可能性があるため開始しない）。ただし反映の失敗が使用中以外の理由（ファイルの破損等）によるときは、反映を省いて削除へ進む——破損した旧ファイルは残置の理由にならない（二つの理由を区別できることは DB-12 ⑤で確認する）。削除を選んだ場合は、開始の記録（2030）が削除の前の記録を兼ねる——正本に載らなければ開始しない（下記「監査記録」）
  - 削除は通常のファイル削除であり、**上書き消去は行わない**（architecture.md §3.2.4 のスプールの削除保証と同じ扱い。ストレージ上の残留痕への対抗は ACL とディスク全体の暗号化が担う。利用者向けに明記する——DB-D4）
- **処分中の受信への影響と停止**:
  - 処分は旧ファイルと退避ファイルを全量読み書きする（書き出し・整合性検査・件数照合・ハッシュ）。データルート・退避先が SQL Server やスプールと同じディスクにある構成では、書き込みの遅延 → Q2 の溢れ → スプール退避（上限到達で新規の破棄——architecture.md §3.2.3）の連鎖を起こし得る。**ライブ受信を優先する**: スプール退避の継続中・Q2 の高水位の間は処分を開始せず（前提条件 5）、書き出し・検証の途中でそうなった場合は取り消す（退避の失敗として扱い、元は変えない。段階的に書き出せる方式なら一時停止でもよい）——architecture.md §3.2.2 の drain の「ライブ優先」と同じ原則
  - 画面と利用者向けドキュメントで**低トラフィック帯での実行を推奨**し、所要時間の目安（DB-12 ⑥の実測による）を示す（§5.4 のスキーマ移行と同じ扱い）。実測までは、所要時間がファイルの大きさにほぼ比例することだけを示す
  - **サービスの停止要求で処分は取り消される**: 処分の処理はホストの停止要求に結び付け（画面の circuit とは独立）、書き出し・整合性検査・検証は停止要求に速やかに応じる。architecture.md §1.3 の停止手順（メモリ上のログのスプールへの退避）を待たせない——応じるまでの時間は M-9 の停止時間目標の内側に収める（単一の文の途中で取り消しに応じられるかを含め、DB-12 ⑥で確認する）。削除の段階（ファイルの削除のみ）は最後まで行い、共有違反の再試行だけを打ち切る。実装は、実行中の文（`VACUUM INTO`・`PRAGMA integrity_check`・件数の集計・チェックポイント）を取り消しで `sqlite3_interrupt` によって止め、停止要求から取り消しの完了を待つ上限を仮値 5 秒とする（`OldDatabaseDisposalOptions.StopResponseTimeout`。M-9 の内側に収まることの実測は DB-12 ⑥）。蓄積ログの移行（§6.2）もサービスの停止要求で中断する
- **失敗時の振る舞い**:
  - **検証の段階（前提条件・安全検査・退避先の条件）での拒否**: 何も変更しない。理由と次の一手を画面に示す。**対象側の安全検査（上記 ①〜③）による拒否は監査記録に残す**（2030。結果 = 拒否と理由）——入力ミスではなく、改竄か構成の異常を示す信号であるため。前提条件・退避先の条件による拒否は記録しない
  - **退避の失敗（反映・書き出し・残留の除去・検証・確定のいずれか）**: **旧ファイルは削除しない**。作業用サブフォルダを中身ごと削除し、昇格は未完了のまま残る。作業用サブフォルダを削除できなかった場合は、そのパスを画面と監査記録に示す（作成時点からの保護 ACL のまま残る）。旧ファイルが破損していて検証に合格しない場合、退避は完了できない——削除を選ぶか、利用者向けドキュメントの手順で扱う
  - **削除の部分失敗**: 退避を選んだ場合、退避ファイルは確定済み（検証合格）である。残ったファイルを画面と監査記録に列挙し、昇格は未完了のまま残る。典型の原因（プロセス外のツール——バックアップソフト・ウイルス対策・データベース閲覧ツール等——が開いている）と次の一手（閉じてから再実行）を画面に示す
  - **再実行**: 処分は何度でも実行できる。**再実行は常に前提条件の判定からやり直す**——処分の進み具合を記録するファイルを持たないため、どこまで済んだかは残っているファイル（事実）だけから決まる。退避の再実行は新しい作業用サブフォルダに新しい退避ファイルを作る（手順 3 により残った本体だけで内容が完全なため、内容は前回と同じになる）。前回の部分失敗で確定済みの退避ファイルは残り、監査記録（パス・SHA-256）から辿れる
  - **中断（取り消し・サービス停止・クラッシュ）**: 書き出しから確定までの間は取り消せる（取り消しは退避の失敗と同じ扱い）。削除の段階に入った後は取り消せない（中断は部分失敗と同じ扱いになる）。旧ファイルは削除の段階に入るまで論理的な内容を変えない（手順 3 の反映は内容を変えない）ため、中断しても元は失われない
  - **クラッシュ後の作業用サブフォルダの掃除**: 同じ親フォルダでの次回の処分の開始時（開始の記録の後。今回の作業用サブフォルダは除く）に、製品の命名規則に一致し、**かつ ACL が製品の作業中の構成（親からの継承なし・`SYSTEM`・`Administrators`・実行アカウント）と一致する**サブフォルダだけを中身ごと削除する。これは確定の前に止まったもの——元のファイルは変更されていない——であり、名前の一致だけを根拠に削除しない。確定済みのサブフォルダ（実行アカウントの ACE を外したもの）には製品はもう到達できず、触れない。別の親フォルダを選んだ場合は残るため、確認・削除の方法を利用者向けドキュメントで案内する（DB-D4）
  - **クラッシュの記録**: 開始の記録（2030。結果 = 開始）に終了の記録が対応しないことが、中断（クラッシュ等）を示す。次回の起動時に監査記録を読み戻して補記することはしない（監査記録を製品の状態判定の入力にしない）

- **未完了の判定と可視化・通知**:
  - **未完了 = 実効 provider が SQL Server であり、かつ処分の対象（本体・`-wal`・`-shm` のいずれか）が存在する**。判定の引き金はファイルの存在という事実であり、処分待ちを記録するマーカーファイルは持たない——判定の根拠と実体が一致し、利用者が手作業で処分した場合も追加の操作なしに解消される。ただしこの事実は「今の設定名の組み込み DB ファイルが残っている」ことであり、「切替前のファイルが残っている」ことと一致するのは通常の流れのときだけである——縮退運転で書き込まれたファイルは、切替の境界の記録（上記）を使って確認ダイアログで区別する（照合できない区間の件数と期間）。**切替後に `Storage:SqliteFileName` を変えた場合**（設定の削除・不正値による既定値へのフォールバックを含む）は、切替の境界の記録が指す旧ファイルが今の設定から導いた対象と別の名前で残っていることを検出し、**未完了として扱い**、1041 の本文にそのパスと「管理画面の操作では解消できない」旨・手作業の手順への誘導を含める。製品はそのファイルを処分しない——処分の対象は今の設定から導いたものに限る（削除に使うパスを、記録や設定の変更前の名前から取らない）
  - 未完了の間も新 DB への保存は継続する（受信・保存・閲覧には影響しない）
  - **管理画面の入口（`/admin`）に常設カードで表示し、昇格ウィザードの処分セクションへの導線を置く**（ui.md §4・§5.4）。カードの冒頭で受信と保存が正常に続いていることを示す。閲覧面には出さない（管理系の情報を閲覧面に露出しない——ui.md §4 の再起動待ちカードと同じ判断）。処分セクションは対象ファイル（パス・サイズ）・移行の状態・処分の操作を示す
  - **Windows イベントログへ警告 1041 を出す**（security.md §4.3 で採番済み。メール通知の対象〔警告〕とする）。**未完了が継続判定期間（仮値 24 時間）連続して観測されたときに発火し**、以後は専用の抑制窓（仮値 24 時間）で繰り返す（いずれも architecture.md §9 M-16）——昇格を正しく進めている最中（再起動の直後・移行の途中）には鳴らさない。継続はプロセス内の観測で判定し、サービスの再起動で起算し直す（1034 の継続判定と同じ形。常設カードは再起動によらず出る）。移行・処分の実行中は発火しない。処分が退避の失敗・削除の部分失敗・中断で終わったときは、その確定時に継続判定期間・抑制窓によらず 1 回発火し、本文に結果と理由を含める（画面を離れても完走する処分の失敗に、夜間でも気づけるようにする）。本文は画面と同じ言葉（後始末・管理画面の昇格ページ）で書き、冒頭で受信と保存が正常に続いていることを示し、対象ファイルのパスと合計サイズを含める
  - **製品の処分によらず旧ファイルが無くなったことを記録する**: 周期評価で「未完了 → 解消」を観測したとき、このプロセスで処分の完了（2030）を記録していなければ、その旨を監査記録に残す（2031。security.md §4.3）——切替前のログ（証跡）が製品の外で消えた事実を、監査記録から辿れるようにする。サービスの停止中に消えた場合は観測できない（OS のファイル監査〔SACL〕の領分——DB-D4）
- **画面と操作の統治**:
  - 処分の実行は**破壊的操作**であり、確認ダイアログ（ui.md §3.1）と冪等トークン（configuration.md §7）を伴う。**確認ダイアログの最上段には、元に戻せないことと、（未移行なら）未移行の件数・期間と明示確認を置く**。方式・対象ファイル・（退避なら）退避先と退避ファイル名と保護責任の移転はその下に置く（同じ重みで並べると読まれない）
  - 書き込み系の管理操作として、昇格の他の段階と同じ統治（管理リスナ・管理の役割。ADR-0004 決定 2・security.md §3）に従う
  - **旧ファイルを開く照合は利用者の操作でだけ行う**: 処分セクションは、画面を開いた時点では旧ファイルを開かない状態の取得（対象ファイル・移行の状態）だけを示し、照合（上記の完了判定 1〜4 と対象の安全検査。排他の下で旧ファイル全体を読む）は利用者の操作で行ってから、その結果・方式の選択・保管先・実行の操作を示す——照合の間は移行を開始できず、画面を開いただけで移行を妨げないため。照合の結果は確認ダイアログの材料であり、処分の開始時にサービスが照合し直す。結果が変わっていれば（未移行が見つかった等）開始を拒否し、画面は照合のやり直しを求める
  - 処分の所要時間は旧ファイルの大きさに比例する（書き出しと整合性検査はファイル全体を読む）。進捗を示し、**画面を離れても・circuit が失われても処分を途中で放棄しない**（サービス側の処理として完走し、再入時に進行状況と結果を示す——結果の保持は上記の状態表のとおり）
- **監査記録**:
  - **処分を 2030（security.md §4.3 で採番済み）に記録する**。記録の時点は、**開始**（検証の通過後・最初の変更の前）・**削除の開始**（退避のみ。確定の後・削除の前）・**終了**（完了 / 退避の失敗〔元は変更なし〕/ 削除の部分失敗〔残ったファイル〕/ 中断）と、**対象側の安全検査による拒否**である。記録内容は、方式（退避 / 削除）・対象ファイル（パス・サイズ）・退避先の親フォルダと作業用サブフォルダ・退避ファイル名・退避先のドライブ種別・検証の結果（整合性検査・件数照合の値）・退避ファイルの SHA-256 とログ本体の ReceivedAt の最古・最新・移行の状態と「移行せずに処分する」の明示確認の有無・結果・撤去した移行チェックポイントの要約（下記）・操作者（security.md §2.4 の「誰が」欄）。ログの内容・資格情報は記録しない
  - **成功・失敗のいずれも記録する**（失敗・部分適用こそ証跡の価値が高い——§6.2 の移行の監査と同じ考え方）。前提条件・退避先の条件の検証で拒否され、何も変更しなかった試行は記録しない
  - **削除の前の記録は必須とする（ADR-0004 決定 7 の限定）**: 開始の記録と（退避のみ）削除の開始の記録は、監査記録の正本（アプリ記録ファイル。security.md §4.2）に載ったことを確かめてから先へ進み、**載らなければ処分を開始しない・削除の段階に入らない**（開始の拒否は何も変更しない。削除の開始の記録が載らない場合は中断として終える）。決定 7（監査記録の書き込み不能は要求処理を妨げない）の根拠は障害中の復旧操作を止めないことであり、処分は急ぐ理由のない不可逆な後始末であるため、この限定を置く。正本に載らなかった記録は、障害中の保持・復旧後の書き戻しの対象にもイベントログへの併記にもしない（行われなかった操作の記録を残さない）。終了・安全検査による拒否の記録の失敗は処分を妨げない
  - 既定構成（loopback は認証なし）では操作者は loopback の送信元としてだけ記録される。操作者の特定が要る組織は、処分の前に loopback の認証（`Admin:Authentication:RequireForLoopback`。security.md §2.4）を有効にする（DB-D4）
- **移行チェックポイントの撤去**: 処分の完了時に §6.2 の移行チェックポイント（`log-migration-checkpoint.json`）を撤去し、その要約（完了の有無・移行件数）を同じ監査記録に含める——チェックポイントは旧ファイルに対する再開点であり、旧ファイルの消滅後に残すと、将来あらためて組み込み DB から昇格した際に移行を「完了済み」と誤判定するため
- **実現方式の記録（DB-12。実装時点）**——要件を満たす方式として実装したものであり、Windows・同梱の e_sqlite3 での実機記録（DB-12 ①〜⑥）は未実施:
  - **書き出し（①②）**: `VACUUM INTO` を 2 段で使う——①旧ファイル → 作業ファイル 1、②作業ファイル 1 から管理者アカウント台帳の表（`AdminAccounts`・`AdminAccountsSchemaVersion`）を削除して作業ファイル 2 へ `VACUUM INTO`。作業ファイル 2 を `journal_mode=DELETE` にして単一ファイルで完結させ、検証に合格したら退避ファイル名へ改名する。**選定理由**: `VACUUM INTO` は論理的な内容からファイルを組み立て直すため、旧ファイルの空き領域（保存期間で削除したログ・削除された行）も、②で落とした台帳のページも出力に現れない。online backup API はページを空き領域ごと複写する（単独使用は不可という判定基準）。必要な表だけの選択的な複写はスキーマ（索引・スキーマ版の表）の再現を製品が持つことになり、スキーマの追加のたびに書き出しが追随を要する。2 段にしたのは、台帳を書き出しの前に旧ファイルから消すと元のファイルを変更することになり（手順 3 は内容を変えない、の前提が崩れる）、1 段目の出力から消すだけでは消した台帳のページが空き領域として残るため。一時領域は作業用サブフォルダの中の作業ファイル 2 つ（同時に存在する）であり、空き容量の見積もりは旧ファイル（本体 + `-wal`）の 2 倍とする
  - **参考確認（Linux・同梱の e_sqlite3 3.53.3。2026-11-16）**: `PRAGMA compile_options` に `SECURE_DELETE` は無く、`PRAGMA secure_delete` は 0。WAL の旧ファイルからの `VACUUM INTO` の出力は rollback ジャーナル（`journal_mode=delete`）で、完了後に付随ファイルは残らなかった。退避ファイルのバイト列に削除済みの行・台帳の目印が現れないことは自動テスト（下記）で固定している
  - **取り消し（⑥）**: 各文は取り消しで `sqlite3_interrupt` により文の途中で止まる（単一の長い文の中断は自動テストで固定。旧ファイルの規模別の所要時間・停止要求への応答時間の実測は未実施）
  - **使用中と破損の区別（⑤）**: チェックポイント（`PRAGMA wal_checkpoint(TRUNCATE)`）の結果の busy 列が非 0、または `SQLITE_BUSY`・`SQLITE_LOCKED` を「使用中の可能性」、`SQLITE_CORRUPT`・`SQLITE_NOTADB` を「破損」とする
  - **ACL（③④）**: security.md §5.3 の実装の項。ACL を保持するファイルシステムの判定はファイルシステム名（NTFS・ReFS）、ドライブ種別は `DriveInfo.DriveType`（固定ディスク以外——取り外せる媒体・光学ドライブ・ネットワーク・RAM ディスク・不明——を拒否）
  - **未確認**: SQLite が `VACUUM INTO` で一時ファイル（`temp_store`）を使う場合の置き場所（実行アカウントの一時フォルダ）とその容量、上記の参考確認の Windows・同梱版での再確認、仮想サービスアカウントでの確定後の `icacls` 出力と実行アカウントからのアクセス試行の拒否、規模別の所要時間と受信への影響
- **自動テストで固定する不変条件**（CI で固定する。lab でしか確かめられない項目は DB-12 に置く）:
  - 削除に利用者の入力したパスを使わない（入力は退避先の親フォルダとしてのみ使われる）
  - 削除の順序（`-wal`・`-shm` → 本体）と、1 つの失敗でその時点で止まること
  - 対象の安全検査 ①〜③ と、③を満たさない本体・本体が無い場合の扱い
  - 移行の完了判定（完了後の追加がある場合・位置を持たない完了記録・時間帯の照合の不合格・照合できない区間のレコードがある場合）
  - 移行と処分の排他、冪等トークン、状態表の各状態での常設カード・1041 の振る舞い
  - クラッシュ後の掃除が、命名規則と作業中の ACL の両方に一致するサブフォルダだけを対象にすること
  - 退避ファイルのバイト列に、削除済みの行と台帳の目印が現れないこと（Windows ランナー・同梱の e_sqlite3 で実行する。依存の更新で SQLite の挙動が変わったときに検知する）
  - ファイルシステムの種別判定・ドライブ種別の判定・ACL の適用と検査・再解析ポイントの判定は**差し替え可能な口の後ろに置く**（§6.1 の `ISqlServerConnectionValidator` と同じ考え方）——Windows 以外の開発機でも、前提条件・完了判定・削除順序といった判定ロジックのテストを回せるようにする

## 7. v1.0 で凍結する対象（ADR-0006 基準 4 の一覧）

v1.0 以降、後方互換を破る変更を MAJOR でのみ行う対象の一覧。**本節が ADR-0006 基準 4 の「凍結対象の一覧」の置き場である**:

| 凍結対象 | 定義場所 |
|---|---|
| DB 論理スキーマ（§2。ログレコード・システムイベントの項目と意味） | 本文書 |
| provider 契約（§1.2 の操作と意味論） | 本文書 |
| スプールのセグメント形式（未消化セグメントを残した版間更新が成立すること） | architecture.md §3.2.1 |
| メタデータ領域の形式（カウンタ・稼働記録の継続性） | architecture.md §4.3 |
| 設定スキーマ | [configuration.md](configuration.md) §8 |
| Windows イベントログのイベント ID の意味（additive-only。ID の追加は MINOR 可・意味の変更/転用は不可） | [security.md](security.md) §4.3 |

- **provider 契約の「凍結」の意味を精密化する**（契約の消費者は実装者であり、利用者向け互換とは破壊の意味が異なる）: 凍結されるのは**既存操作の意味論とスキーマ項目の意味**である。**契約への操作追加は optional 操作（capability 検出——provider が実装有無を宣言し、ホストが検出する機構）として MINOR で行える**。既存操作の意味論変更・必須操作の追加は MAJOR とする。§1.2 の「契約拡張の予約」（一括読み出し・集計）はこの optional 機構で追加する
- v0.x の間はこれらの互換を破る変更を許容するが、conventions.md の deprecation 階段（1 バージョン警告 → 次バージョン削除）は v0.x でも守る
- v0.x → v1.0 の更新で蓄積データと設定が保全されることの実地実証は ADR-0006 基準 4 が要求する（本表がその検証範囲の定義になる）
