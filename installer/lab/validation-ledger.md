# lab 検証記録の台帳

作者の lab で行った実機検証を、1 回を 1 行として並べた台帳である。結果の詳細は「記録」列の一次記録（Issue・PR のコメント、installer/lab/ の手順書、tools/Yagura.Bench/results/ のベンチ結果）にあり、本台帳はその索引にあたる。**回の番号づけと、記録どうしの食い違いの整理は本台帳を正とする。**

## 1. 目的

- **v1.0 公開基準の証拠の本体**である。ADR-0025（[PR #532](https://github.com/Yanai-Taketo/Yagura/pull/532) で審議中）の基準 2'（作者 lab の検証記録）は、この台帳を証拠とする。基準 3' (ii)（手順書・利用者向け文書に沿って実施した回）の対応づけも、本台帳の「手順書」「沿った利用者向け文書の節」「実施者」「実施者の判別根拠」の列から行う。
- 基準 1 が求める「実環境での動作確認記録」の索引としても使う。
- 本台帳は**新しい検証を加えない**。並んでいるのは既存の記録だけである。独立した環境での運用実績と長期の連続稼働は、本台帳では示せない（§10・§11）。

## 2. 対象と範囲

- 2026-07-05 以降の回のうち、Issue・PR・手順書・ベンチ結果・利用者向け文書のいずれかに記録が残っているもの。
- 実施されたことは分かるが、結果の記録が残っていない回（結果がチャットにしか無いものを含む）も「**記録なし**」として載せる。この回は証拠に数えない。
- **載せる回**: 機械の区別は記録の書き方に従う。
  - 記録が lab・lab 機・試用機・検証環境での実施と書く回と、記録が lab 機として扱う機械（YAGURA-STG、試用機 WINSV2025、`yagura.test` の DC とメンバー機、Proxmox・QEMU 上の検証用 VM）での回
  - 開発機での実施でも、記録自身が lab 検証と呼ぶ回（L-09。PR #225 は開発機での実プロセスの確認を「手動 lab 検証」と書く）と、利用者向け文書が「検証済み環境」に挙げる回（L-08）
  - 製品そのものではなく、製品のコードを載せた検証用プログラムや計測スクリプトを lab 機で動かした回（L-02・L-04）。製品の判断に使った記録だからである。製品そのものを動かしたかは「版と SHA」列に書く
- **載せないもの**:
  - CI での検証（installer-e2e・暗号スイート採取など）
  - 開発機と CI ランナーでのベンチ計測（`tools/Yagura.Bench/results/` のうち `2026-07-05-dev-machine`・`2026-07-05-dev-machine-rcvbuf`・`2026-07-06-dev-machine-ci-baseline`・`2026-07-06-ci-windows-latest-m5`・`2026-07-10-db9-db10`）
  - 開発機での実施のうち、記録が lab 検証と呼ばないもの: PR #214（「本 worktree 上で実施」「lab 検証: 未実施」と自ら書く）、PR #245（自動テストを手元の Windows Server 2025 で走らせた記録）
  - 実施した機械も、lab で行ったことも記録に無い実機確認: PR #232（「実機で確認済み」とだけ書く）、#248 と PR #249（「v0.3.1 実機で再現」）、PR #333（「実機での通し確認」）。どこで行ったかを記録から判別できないため載せない。lab で行ったことがほかの記録で分かれば、行として足す
- **走査の方法**（2026-11-16）: 2026-07-05〜08-17 に作成された Issue・PR のうち、本文かコメントに「lab」または「実機」を含むもの（GitHub の検索で 335 件）と、「試用機」「WINSV2025」「YAGURA-STG」を含むものについて、本文とコメントを読み、実機での実施を書いた箇所を拾った。Discussion は対象にしていない。
- 日付と時刻は日本時間（UTC+09:00）で書く。Issue・PR の投稿時刻も日本時間に直して書く。

## 3. 列の定義

| 列 | 内容 |
|---|---|
| 回 | 台帳の通し番号 `L-NN`（日付順）。対応環境の検証で使ってきた「第 1〜4 回」の呼び方は括弧で併記する（番号は §8.1 の整理に従う） |
| 日付 | 実施日 |
| 環境 | OS とビルド、SQL Server の版（使った場合）、AD・gMSA の有無。ホスト名は記録にあるものだけ書く |
| 版と SHA | 検証した Yagura の版と、ビルド元のコミット SHA。記録に無いものは「記録なし」 |
| 実施者 | 人間の作者 / AI エージェント / 記録上不明（ADR-0025 の草案の「不明」にあたる）。判定の基準は §4 |
| 実施者の判別根拠 | 実施者の区分の根拠にした記録の箇所。人間の作者・AI エージェントとした行は、記録中の該当箇所へのリンクと、その文言を書く。リンクは、Issue・PR のコメントはコメントの URL、PR の本文は PR の URL、リポジトリ内のファイルはコミット SHA つきの URL とする。記録上不明の行は「明記なし」と書き、許可や承認を示す文言など紛らわしいものがあれば、それが実施者の明記にあたらない理由を書く |
| 手順書 | 使った lab 手順書（installer/lab/）と、分かればその版。手順書を使わずに依頼や Issue の項目で行った回はそう書く |
| 沿った利用者向け文書の節 | README・operations.md・docs/guides/ のうち、手順として沿った節。記録に明記が無いものは「明記なし」、利用者向け文書が関係しない回は「—」。本回の後に書かれた文書や、本回の結果を受けて追加された節は、沿ったことにしない |
| 結果 | 要約。無効だった項目には **無効** と書き、理由を §7 に書く |
| 欠陥 | その回で見つかり、Issue（または修正 PR）になった欠陥。lab の後に入った修正を lab で確かめていないものは「lab 未確認」と添える |
| 記録 | 一次記録へのリンク |

## 4. 実施者の判定基準

| 区分 | 基準 |
|---|---|
| **人間の作者** | 記録が、作者本人が操作したことを明記している（例: 「実行者: オーナー」「オーナーにより…検証が完了」） |
| **AI エージェント** | 記録が、AI エージェント（Claude Code など）による実施を明記している |
| **AI エージェント + 人間の作者** | 記録が両方を明記している。人が操作した範囲を括弧で書く |
| **記録上不明** | 上のどの明記も無い。**人間の作者の実施には数えない** |

判定に使わないもの:

- 投稿したアカウント。記録はすべて作者のアカウントから投稿されており、AI エージェントの報告も同じアカウントで投稿される
- コメント末尾の「Generated by Claude Code」。記録の文章を AI が書いたことを示すだけで、lab を操作した主体を示さない
- 「オーナー lab」という表現。lab の持ち主を示すだけで、操作した主体を示さない
- 「オーナー明示許可」「オーナー承認」「オーナー GO を受けて」など、許可や承認を示す表現。許可した人を示すだけで、操作した主体を示さない
- 文体や文脈からの推測。推測が付く回は「記録上不明」としたうえで、判別根拠の列か §7 に事実だけを書く

## 7. 無効だった検証と、後に覆った結論

### 7.1 アップグレード確認の無効（#514）

- **仕組み**: `-p:YaguraVersion=` で版を振ってビルドすると、MSI の版だけが上がり、収録アセンブリの FileVersion は `Directory.Build.props` の版のまま残っていた（子の `dotnet publish` へ値が渡っていなかった。修正は PR #513。#514 の 08-16 のコメントは「#504 で main に入っていた」と書くが、`installer/Yagura.Installer.wixproj` の該当の変更は PR #513 のマージコミット `db3d76e` にある。値の伝播は installer-e2e の版伝播ガードが検査する。L-35 は `-p:YaguraVersion=` を使わず、`Directory.Build.props` の書き換えで版を変えた）。MajorUpgrade が `afterInstallExecute` になって以降（PR #473。07-26 22:08 にマージ）は、同じ版のファイルは置換されない。このため、更新が成功と表示されても新しいコードは 1 つも入らない。
- **無効と判明した回**:
  - L-34（第 3 回）の 0.5.0 → 0.5.2 の更新。#514 の発見元である
  - L-33（第 2 回）のアップグレード確認。#514 の 08-16 のコメントが「第 1 回・第 2 回とも `-p:YaguraVersion=` でビルドしており無効」と書く。ビルド元 `41be3fd` は PR #473 より後なので、上の仕組みに当てはまる。ただし本回の記録（ADR-0024 改訂 10）には、更新の実施も、何を確かめた更新だったかも書かれていない
  - L-31 の 0.6.4 → 0.6.5 の更新で観測した「バイナリが 1 つも置換されない」事象（#479）。製品の欠陥ではなく、上の方式の産物だった（#514・#479 の 08-16 のコメント）
- **無効か確定できない回**: L-32（第 1 回）。根拠は #514 の 08-16 のコメントの主張だけで、本回の記録（#494 のコメント、PR #499）には更新の実施も、更新側の MSI のビルド元も書かれていない。本回が検証した v0.5.0（`7f638da`）は PR #473 より前のビルドであり、下の「PR #473 より前の回の扱い」に従えば、更新側の MSI をどのコミットから作ったかで結論が変わる。#514 のコメントにある「前回 lab の 2 本（0.5.0・0.5.1）のサイズが一致」「ARP の版が 0.5.1 なのに実バイナリが 0.5.0.0」も、更新側が #473 の前後どちらのビルドでも同じ状態になるため、区別の根拠にならない
- **有効な更新確認**: L-35（第 4 回）が初めてである（版と中身が一致する 2 本を使った）。
- **PR #473 より前の回の扱い**（L-17 の 0.4.0 → 0.4.1、L-23 の (d)、L-27〜L-29）: 当時の MajorUpgrade は旧製品を先に削除する方式だったため、版だけ上がった MSI でも新しいファイルが入る。台帳ではこれらを無効と数えない。ただし、この判断は Windows Installer の既定の動作からの推定であり、各回で収録ファイルの版を確かめた記録は無い。L-28 では修正（#457）の挙動が更新後に現れており、新しいファイルが入っていた傍証になる。
- **L-30 は有効性を確定できない**: 記録上のビルド元 `f39b396` は PR #473 のマージより前である。一方で同じ記録は、更新の失敗で製品が消える現象（#467 の現象 A）の解消を観測したと書いている。この現象を解消したのは PR #473 の変更であり、実際に使ったビルドの中身を記録から確定できない。

### 7.2 測定の誤りで無効になった観測

- L-02 のクロスマシン UDP 統計の「受信総数の増分 0」と「自己宛の送信はカウント経路を通らない」: `stats-check.ps1` が存在しないプロパティ名を読んでおり、値が常に 0 だった（L-15 で判明。PR #340）。破棄側の観測は実在するプロパティを読んでいたため有効で、それに基づく決定は変わらない。

### 7.3 後に覆った結論

- **L-10**: Kerberos で認証した管理者が 403 になる原因を「ネットワーク Kerberos ログオンのトークンに `BUILTIN\Administrators` が載らない」と見立てたが、誤りだった。L-11 の診断で、トークンは `S-1-5-32-544` を保持しており、真の原因は認証種別の判定の誤りだったと分かった（#235）。
- **L-15**: gMSA に `SeServiceLogonRight` の明示付与が必須とした結論は、L-22 で 10.0.26100 では不要と実測されて覆った（#422、ADR-0015 改訂履歴 2）。L-30 でも、権利を外したまま切替が成功している。
- **L-23**: (d)③ の「実在しないアカウントを指定すると、元のアカウント・元の ACL へクリーンに着地する」は、ACL については正しいが、製品そのものが残らないことを見落としていた（L-29 で判明。#467）。
- **L-29**: 切替失敗（1920）の原因を一度 `SeServiceLogonRight` の欠如と見立てたが、誤りだった（同じ記録の中で訂正）。

## 10. 連続稼働の最長記録

- **連続稼働の時間を測った記録は無い。24 時間以上の連続稼働の記録も無い。**
- 24 時間の計測を試みた記録は 1 件だけである。L-29 でフォワーダ手順書の ③-3（1034）の計測を 07-26 16:11:05 に始めたが、L-30 の作業（同日 21:47 の記録）までに再インストールで起点が戻り、成立しなかった。この区間は 5 時間 36 分未満である。以後、③-3 の計測の記録は無い。
- 同じ環境を続けて観察した時間の幅で最も長いのは、07-26 の DC 環境（L-25〜L-31）の約 12 時間である（最初の記録 11:28 から最後の記録 23:27 まで）。この間も再インストールと再起動を何度も挟んでおり、連続稼働ではない。最後の記録の時点で、この環境の保存先にあったログは 521 件だった。
- 試用機 WINSV2025 は、07-06〜07-07 の記録で「試用機は稼働中」「稼働継続」と書かれているが、稼働時間の値は無い。
- ほかの回の記録にも、稼働時間の値は書かれていない。
- **開示に使う値**: 連続稼働を測った記録は無い。記録から上限として言えるのは、1 つの環境を続けて観察した幅が最長で約 12 時間（その間に再起動を含む）であることだけである。24 時間の計測は 1 回試みて、成立していない。

## 11. lab で確かめていないこと

### 11.1 開示の根拠になる 4 点
